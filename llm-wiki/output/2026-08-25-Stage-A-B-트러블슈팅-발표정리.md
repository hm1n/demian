# Stage A·B 트러블슈팅과 트레이드오프 (발표용 정리)

정리일 2026-08-25. 대상은 경험 후보 생성 파이프라인(이슈 #12)의 Stage A(경량 1차 선별)와
Stage B(diff·PR 기반 최종 판단)입니다. 근거 문서는 다음과 같습니다.

- `wiki/2026-08-21-stage-a-선별-계약.md`
- `wiki/2026-08-21-stage-b-diff-pr-판단-계약.md`
- `wiki/2026-08-24-실데이터-검증-배치-상한-확정.md` (이슈 #19)
- `wiki/2026-08-24-경험-판단단위-PR-묶음-전환-검토.md` (이슈 #49·#58)
- `wiki/2026-08-24-stage-a-청크-분할-실데이터-검증.md` (이슈 #44)
- `wiki/2026-08-25-Stage-A-청크-폐기와-점수-선별-전환.md` (이슈 #58)

## 0. 파이프라인 한 장 요약

| | Stage A | Stage B |
| --- | --- | --- |
| 입력 | 커밋 메시지·stat 같은 경량 정보 (patch 금지) | Stage A 후보 + 서버가 조회한 diff·PR |
| 모델 | Groq `openai/gpt-oss-120b` | Google `gemini-3.7-flash` |
| 출력 | 후보 목록 + 미분류 SHA | 최종 후보 3개 + 근거·인용 파일 |
| 실질 제약 | **분당 토큰 한도 8,000 (무료 등급)** | **일일 요청 20회 (무료 등급) + 55초 예산** |

두 단계의 문제는 성격이 다릅니다. Stage A는 **입력을 어떻게 줄이고 무엇을 판단 단위로 삼을
것인가**의 문제였고, Stage B는 **한정된 근거 예산을 어떻게 배분하고 실패를 어떻게 분류할
것인가**의 문제였습니다.

## 1. Stage A

### 1-1. 병목을 처음부터 잘못 짚고 있었습니다

초기 상한은 Vercel 본문 4.5MB와 55초 시한을 기준으로 설계했습니다. 실측은 둘 다 병목이
아니라고 말했습니다.

- Stage A 입력 63커밋 = 47,086B로 **4.5MB의 1.00%**입니다.
- 성공 호출은 3.1~11.1초, 계약 위반으로 끝난 호출도 29.0초입니다.
- 실제로 먼저 걸리는 것은 Groq 무료 등급의 **분당 토큰 한도(TPM) 8,000**입니다. 63커밋은
  14,555토큰 요청으로 413 `rate_limit_exceeded`를 받습니다.

게다가 코드 주석은 청크 상한의 근거를 "모델 컨텍스트 한도"라고 적고 있었는데 이것도 사실이
아니었습니다. `gpt-oss` 계열 컨텍스트는 131,072토큰이고 `andbread` 66묶음 전체가 약
17,000토큰, 즉 컨텍스트의 13퍼센트입니다. **한도라고 믿고 있던 값이 세 개였고 셋 다 틀린
한도였습니다.**

> 발표 포인트: 상한을 정할 때 "무엇이 먼저 걸리는가"를 실측하지 않으면 걸리지도 않는 제약에
> 맞춰 설계를 비틀게 됩니다. 미검증 상수 11개를 이슈 #19에서 한 번에 실측 확정한 이유입니다.

### 1-2. "입력 SHA 전수 응답" 계약이 입력 수에 비례해 깨졌습니다

Stage A는 입력 SHA를 정확히 한 번씩 돌려받는 것을 계약으로 잡았습니다. 누락을 미분류로
간주하면 "모델이 아니라고 판단한 것"과 "모델이 답을 안 준 것"을 구분할 수 없기 때문입니다.

| 모델 | 입력 커밋 | 결과 |
| --- | --- | --- |
| `gpt-oss-120b` | 18 | 계약 위반 (9/18, 4/18) |
| `gpt-oss-120b` | 12 | 성공 (12/12) |
| `gpt-oss-120b` | 8 | 성공 (8/8) |
| `gpt-oss-20b` | 18 | 계약 위반 (16/18) |
| `gpt-oss-20b` | 8 | 계약 위반 (1/8) |

**트레이드오프**: 계약을 유지하려면 입력을 작게 유지해야 하고, 입력을 크게 하려면 계약을
포기해야 합니다. 계약을 포기하면 "설명할 가치가 없다고 판단된 커밋"과 "모델이 빠뜨린 커밋"이
같은 통에 담기고, 그것은 사용자에게 **조용한 배제**가 됩니다. 계약을 유지하는 쪽을
선택했습니다.

### 1-3. 청크 분할: 도입했다가 폐기했습니다

입력을 작게 유지하려고 커밋 8개·6,000바이트·파일 32개 경계로 청크를 나누고, 누락 SHA만 최대
두 번 재호출하는 정책을 이슈 #44에서 확정했습니다. 실측에서 무너졌습니다.

`andbread` 66묶음을 7청크로 나눈 실행 기록입니다.

| 청크 | 입력 묶음 | 첫 시도 | 결과 |
| --- | --- | --- | --- |
| 1 | 14 | 통과 | 후보 2 |
| 2 | 13 | 11개 누락 | 복구 1회로 회복 |
| 3 | 9 | 7개 누락 | 복구 1회로 회복 |
| 4 | 12 | 통과 | 후보 2 |
| 5 | 7 | 5개 누락 | 복구 1회로 회복 |
| 6 | 7 | 복구 2회 후에도 3개 미해결 | **전체 실패** |
| 7 | - | 도달하지 못함 | - |

세 가지가 드러났습니다.

1. 첫 시도 전수 응답 준수가 **6청크 중 2회**입니다.
2. **청크 하나의 복구 소진이 Stage A 전체를 죽입니다.** 청크 1~5에서 묶음 63개가 정상
   처리됐는데 청크 6의 묶음 3개 때문에 전부 버려졌습니다.
3. **"작은 청크가 더 안전하다"는 가정에 근거가 없습니다.** 14개·12개짜리는 첫 시도에 통과했고
   7개짜리 둘은 모두 복구를 불렀습니다.

여기에 더해 청크별로 후보 쿼터를 나눠 주는 방식 자체가 **"어느 묶음이 어느 청크에 담겼는가"라는
우연이 선정 결과를 좌우**하게 만듭니다. 선별 품질의 근거가 될 수 없는 구조입니다.

**트레이드오프**: 청크 분할은 "한도 안에 들어간다"는 문제를 풀지만 "판단 품질"과 "부분 실패
내성"을 대가로 냅니다. 부분 실패 내성은 방어 코드로 보완할 수 있어도(1-7 참조) 쿼터 배분의
우연성은 구조적으로 남습니다. 폐기했습니다. 단 **청크 분할 코드 자체는 남겨** 선별이 예상보다
큰 입력을 넘길 때의 안전장치로 씁니다.

### 1-4. 진짜 해법은 판단 단위 전환이었습니다 (커밋 → PR 묶음)

이슈 #49는 "입력 범위(기간) 축소"를 해결책으로 전제하고 시작했습니다. 실측 결과 **범위를 줄이지
않고도** 목표를 달성할 수 있었습니다.

| 저장소 | 방식 | 판단 단위 | 페이로드 | 감소율 |
| --- | --- | --- | --- | --- |
| `demian` | 커밋 | 83 | 73,034B | - |
| `demian` | PR 묶음 | 21 | 12,474B | **83%** |
| `andbread` | 커밋 | 319 | 188,334B | - |
| `andbread` | PR 묶음 | 66 | 36,292B | **81%** |

핵심은 비용 절감이 아니라 **경험이 커밋 단위에 존재하지 않는다**는 사실입니다.

- `andbread` PR#113 `PWA + Supabase 알림 기능 구현`: 커밋 18개, 69일, 파일 56개. iOS PWA 대응,
  `next-pwa` 제거와 커스텀 서비스워커 작성, Supabase edge function 알림이 한 덩어리입니다.
- `andbread` PR#66 `vercel 배포 오류 수정`: 커밋 18개 중 8개가 파일명 대소문자 변경입니다.

둘 다 인터뷰에서 설명할 가치가 큰 경험인데 **개별 커밋으로 보면** `chore: console.log 제거`,
`fix: 타입 오류 수정`, `Rename Modal.tsx to Modal.tsx`처럼 전부 잡무입니다. 비교 기준을 아무리
잘 줘도 잡무 커밋은 잡무입니다. 판단 단위가 틀렸던 것입니다.

부수 효과로 **추가 API 비용이 0**입니다. `fetchCommitDetail`이 커밋마다 `pullRequests`를 이미
조회하고 있었고 Stage B는 그 데이터를 이미 쓰고 있었습니다. **이미 값을 치른 데이터를 쓰지 않고
있던 상태**였습니다.

**트레이드오프**: PR에 묶이지 않은 커밋은 후보에서 제외됩니다(`demian` 83개 중 2개,
`andbread` 319개 중 0개). 폴백 묶음 규칙(경로·시간 기반 클러스터링)을 측정했지만 채택하지
않았습니다.

| 폴백 규칙 | 묶음 | 순도 | 최대 묶음 |
| --- | --- | --- | --- |
| 정확 경로 겹침 | 31 | 16% | 282 |
| 경로 겹침 + 72시간 | 143 | 69% | 37 |
| 디렉터리 겹침 | 7 | 9% | 311 |
| 디렉터리 겹침 + 24시간 | 130 | **77%** | 29 |

경로 겹침만 쓰면 전이 관계로 연쇄 병합이 일어나 319개 중 282개가 한 묶음이 됩니다. 최선인
77퍼센트도 정답 66개 대비 130묶음으로 과분할입니다. **정확도가 충분하지 않아 도입 비용 대비
얻는 것이 적다**고 판단했고, 대신 제외 건수와 사유를 사용자에게 표시합니다(조용한 배제 금지).

### 1-5. 상위 N이 아니라 점수 경계로 자릅니다

청크를 폐기한 자리에 휴리스틱 점수 상위 묶음 선별을 넣었습니다. 여기서도 직관적인 "상위 20개"를
쓰지 않았습니다.

```
andbread 상위 20 컷: 20위=2점  21위=2점  → 경계 점수(2점) 묶음이 15개
demian   상위 20 컷: 20위=0점  21위=0점
```

`andbread`는 2점짜리가 15개 뭉쳐 있어 상위 20으로 자르면 그중 10개만 남고 **5개가 입력 순서로**
잘립니다. "상위 20개를 골랐습니다"가 설명이 되지 않습니다. 그래서 **점수 내림차순으로 내려가되
동점 무리는 쪼개지 않고, 바이트 예산에 들어가는 마지막 경계에서 끊습니다.**

| 컷 | demian 묶음/바이트 | andbread 묶음/바이트 |
| --- | --- | --- |
| 4점 이상 | 1 / 904 | 5 / 5,446 |
| 3점 이상 | 5 / 3,415 | **10 / 10,263** |
| 2점 이상 | 9 / 5,707 | 25 / 20,185 |
| 1점 이상 | **15 / 9,070** | 41 / 27,771 |
| 전체 | 21 / 11,659 | 66 / 35,550 |

결과적으로 두 저장소 모두 **청크 1개, LLM 호출 1~2회**로 끝납니다. 함께 재산정한 상한은
`STAGE_A_CHUNK_MAX_BYTES` 6,000 → 10,500(관측 최대 바이트당 0.676토큰 기준 약 7,100토큰으로
한도 8,000 대비 11퍼센트 여유), 요청 본문 16,000 → 20,000, 청크 쿼터 2 → 5입니다. 여유를 남긴
이유는 출력 변동입니다. `gpt-oss` 계열은 추론 토큰이 출력에 실려 프롬프트 바이트가 거의 같아도
총 토큰이 2,954~3,949로 34퍼센트 흔들립니다.

**정직하게 남길 것 두 가지.**

- 이 점수는 **사실상 규모 점수**입니다. 신호 9개 중 `revert_or_hotfix`는 두 저장소 모두 0퍼센트,
  `demian`은 `infrastructure_added`·`large_refactor`·`long_span`도 0이라 실질적으로
  `file_rewritten_repeatedly`(52%)와 `many_commits`(43%)가 점수를 지배합니다. "일곱 가지 경험
  유형을 탐지한다"고 설명하면 과장입니다.
- **직전 결정을 뒤집은 것입니다.** 2026-08-25 정정에서 "휴리스틱 점수는 입력 축소에 쓰지 않고
  정렬·접기 표시에만 쓴다"고 적었습니다(0점 묶음을 빼도 청크가 7 → 6으로만 줄어 이득이 작았기
  때문입니다). 청크 방식 자체를 폐기하면서 점수의 역할이 다시 "선별"로 돌아왔습니다. 커밋 2개로
  미묘한 경쟁 조건을 고친 PR은 어떤 신호도 발화시키지 않지만 인터뷰 주제로는 훌륭하다는 위험은
  **그대로 남아 있고**, 이것이 선별 방식의 실제 비용입니다.

### 1-6. 프롬프트가 전수 응답 계약을 스스로 깨고 있었습니다

측정 지표를 묶음 기준으로 고치고 나서야 보인 문제입니다. 모델이 계약을 어길 때 돌려주는 개수가
**매번 정확히 `candidateLimit`**이었습니다.

| 실행 | 입력 묶음 | 후보 상한 | 모델이 답한 수 |
| --- | --- | --- | --- |
| 청크 방식 1 | 10 | 2 | 2 |
| 청크 방식 2 | 11 | 2 | 2 |
| 선별 방식 1 | 15 | 5 | 5 |
| 선별 방식 2 | 10 | 5 | 5 |
| 단일 호출 | 15 | 5 | 5 |

6건 중 5건이 상한과 정확히 일치합니다. 원인은 시스템 프롬프트가 **"각 PR 번호를 정확히 한 번
반환하세요"와 "합쳐서 최대 N개입니다"를 한 문단에 이어 붙인 것**이었습니다. 모델이 상한을
**반환 배열 길이 제한**으로 읽었습니다.

문단을 가르고 `decisions` 배열 길이는 입력 묶음 수와 반드시 같으며 상한은 "고르는 개수"에만
걸린다고 명시했습니다. `gpt-oss-20b`, 묶음 15개, 상한 5의 A/B 실측입니다.

```
현행: 5개(누락10)  5개(누락10)  오류  5개(누락10)
개정: 15개(누락0)  5개(누락10)  15개(누락0)  15개(누락0)
```

전체 경로에서 복구 호출과 병합 트림이 사라지고 `andbread` 소요가 **29.5초 → 17.9초**로
줄었습니다. 선별을 통과하고도 뽑히지 않던 PR#66이 후보로 올라왔습니다.

> 발표 포인트: 모델이 계약을 못 지킨 것이 아니라 **우리가 상충하는 지시를 줬고**, 그 사실은
> 측정 지표가 틀려 있는 동안에는 보이지 않았습니다. 지표 수정 → 패턴 발견 → 프롬프트 수정
> 순서였습니다.

### 1-7. 그래도 모델은 계약을 어깁니다: 방어 세 가지

프롬프트를 고친 뒤에도 출력 실패가 한 번 발생했습니다. 방어는 유지합니다.

| 방어 | 문제 | 해결 | 트레이드오프 |
| --- | --- | --- | --- |
| `unjudgedShas` 분리 | 복구 소진이 Stage A 전체를 죽임 | 판단받지 못한 묶음만 내리고 나머지를 살림 | "후보가 아님"과 "판단 못 함"을 화면에서 구분해 표시해야 함. 합치면 조용한 배제 |
| 병합 지점 트림 | 부분 응답 + 복구 응답 합류 지점을 아무도 세지 않아 상한 5에 후보 6개 | 병합 결과에서 자르되 기여 항목 일치 후보를 먼저 남기고 동률은 입력 순서 | 복구 요구 상한의 `Math.max(1, ...)` 바닥은 유지. 0으로 내리면 모델이 하나만 줘도 422로 전체 사망 |
| `json_validate_failed` 재분류 | Groq가 모델 출력 실패에 400 `invalid_request_error`를 반환해 재시도 없이 502 | 스키마 검증 실패로 분류해 같은 입력을 재시도 | 요청은 멀쩡한데 `type`만 보고 분류하면 회복 가능한 실패를 버림. Stage B에도 동일 적용 |

`gpt-oss-20b`에 묶음 15개를 4회 보냈을 때 전수 응답 위반, 400, 전수 응답 위반, 400 순으로 한
번도 성공하지 못했고 같은 입력이 시도마다 다른 결과를 냈습니다. 복구 호출이 어떤 이유로
실패하든 이미 받은 부분 응답은 살립니다.

### 1-8. 근거가 틀린 결정을 철회했습니다 (블랙리스트 순서)

"PR 묶음에서는 블랙리스트를 상세 조회 앞이 아니라 묶음 요약 정리에만 적용해야 한다"고
확정했다가 다음 날 철회했습니다. 근거 네 가지 모두 실측입니다.

1. 근거로 쓴 예시가 틀렸습니다. PR#66의 파일명 변경 커밋 8개는 `classifyBlacklistedCommit`을
   직접 돌리면 **8개 모두 통과**합니다. 캐시 전체를 재분류해도 걸러지는 커밋은 두 저장소 모두
   **0건**입니다.
2. 블랙리스트가 실제로 제거하는 것은 두 가지뿐입니다. `demian` develop 작성자 커밋 173건 분류
   결과는 통과 90 / documentation 53 / merge 30이고 typo·dependency·formatting은 각 0건입니다.
3. **순서를 뒤집으면 블랙리스트의 존재 이유가 사라집니다.** 묶기는 PR 소속 정보를 필요로 하고,
   PR 소속은 상세 조회에서 나오며, 블랙리스트는 바로 그 상세 조회를 줄이려고 있습니다. 뒤집으면
   상세 조회 대상이 90건 → 173건, 약 1.9배입니다.
4. 병합 커밋은 묶음 안에서 정보가 없습니다. PR 번호·제목은 이미 묶음 머리줄에 있습니다.

## 2. Stage B

### 2-1. diff 예산이 후보의 절반을 굶겼고, 모델은 그래도 답을 만들었습니다

`buildStageBPayload`가 커밋 순서대로 patch 예산 60,000자를 소비하고 있었습니다.

```
수정 전: 0:3618 1:2281 2:836 3:16936 4:8722 5:4895 6:2112 7:8000 8:12600
        9:0 10:0 11:0 12:0 13:0 14:0 15:0 16:0 17:0 18:0 19:0
```

후보 20개 중 앞 9개가 예산을 다 쓰고 **나머지 11개(55%)가 patch를 한 글자도 못 받았습니다.**

예상은 "모델이 diff 있는 앞쪽에서만 고를 것"이었습니다. **실측이 그 가설을 반박했습니다.**
성공한 실행이 고른 최종 후보 3개는 payload 인덱스 3·9·17이었고 **9번과 17번은 patch가 0자인
후보**입니다. 즉 "실제 diff와 PR 소속만 근거로 고르라"고 지시받은 모델이 **근거가 전혀 없는
후보를 근거 있다고 선정**하고 있었습니다.

수정은 총량과 후보 수를 그대로 두고 **배분 방식만** 바꿨습니다. 후보별 몫 = 60,000 ÷ 후보 수,
파일별 4,000자 상한은 몫 안에서 적용, 남은 잔액은 뒤 후보로 이월합니다.

```
수정 후: 0:3000 1:2281 2:836 3:5883 4:3000 5:3000 6:2112 7:3888 8:3000 9:3000
        10:3000 11:3000 ... 19:3000
```

후보 20개 전원이 patch를 받고 총량은 여전히 정확히 60,000자입니다. 절단 파일 90 → 77개, patch
생략 파일 78 → 59개로 줄었습니다. 균등 배분 후 선정은 인덱스 0·6·10이었고 **모든 선정이 실제
diff를 근거로 삼았습니다.**

**트레이드오프**: 이월을 앞 → 뒤 한 방향으로만 흘립니다. 뒤 → 앞 재분배는 두 번 순회가 필요한데
얻는 이득이 작아 채택하지 않았습니다. 예산 때문에 빠진 파일도 `patchTruncated: true`를 받습니다.
모델이 그 후보의 diff를 전부 본 것으로 오해하지 않게 하려는 것입니다.

> 발표 포인트: **근거 부재는 입력 단계에서 막아야 합니다.** 프롬프트로 "근거만 보고 고르라"고
> 지시하면서 근거를 주지 않으면 모델은 지시를 지키는 대신 답을 만듭니다.

### 2-2. 시간 예산의 시작점이 틀려 있었습니다

최초 구현은 55초 타이머를 **GitHub 조회 루프 뒤에** 시작했습니다. 후보 20개면 순차 요청 40회,
약 16.9초가 예산 밖에 있었습니다. `maxDuration = 60`보다 먼저 오류를 반환한다는 계약이 이미
깨져 있었습니다. 원인은 Stage A의 시한 상수 의미를 그대로 복사한 것입니다. **Stage A는 LLM 호출
전에 하는 일이 없지만 Stage B는 GitHub을 먼저 훑습니다.**

같은 맥락에서 `STAGE_B_MIN_LLM_BUDGET_MS`를 10초 → **20초**로 올렸습니다. 성공한 LLM 호출이 최대
19.9초 걸렸으므로 잔여 10초로 시작하면 완주하지 못합니다.

**트레이드오프**: 55초 예산은 줄일 수 없습니다. 실패 시 AI SDK 기본 재시도 3회가 20~46초를
소비하기 때문입니다. 또한 Vercel Hobby의 실제 실행 상한은 60초가 아니라 **300초**임을 공식
문서로 확인했습니다. 즉 `maxDuration = 60`과 55초는 **플랫폼 제약이 아니라 우리가 스스로 건 UX
제약**입니다. 이 사실을 문서에 명시했습니다.

### 2-3. 실패 분류가 통째로 도달 불가였습니다

가장 비싼 착각이었습니다. 세 겹으로 쌓여 있었습니다.

1. **Groq는 분당 토큰 한도 초과를 429가 아니라 413 `rate_limit_exceeded`로 반환합니다.**
   `mapLlmError`에 413이 없어 한도 초과가 일반 실패(502)로 분류됐습니다.
2. **413을 상태 코드만으로 한도로 볼 수도 없습니다.** 한도 초과 413은 기다리면 풀리지만,
   요청·컨텍스트가 모델 한도보다 큰 413은 같은 페이로드로는 영원히 풀리지 않습니다. Stage B는
   diff를 싣기 때문에 후자가 실제로 발생합니다. 응답 **본문**의 `rate_limit_exceeded` 유무로
   갈라 한도일 때만 `llm_rate_limit`(503), 나머지는 `llm_request`(502)로 분류했습니다. 판별은
   `errors.ts`의 `isRateLimitResponseBody` 한 곳에 두고 두 단계가 공유합니다.
3. **그런데 그것을 고쳐도 프로덕션에서는 동작하지 않았을 것입니다.** AI SDK는 재시도한 실패를
   `RetryError`로 감싸고 `RetryError`는 `APICallError`가 아닙니다. 따라서 `mapLlmError`의
   `APICallError` 분기 **전체가 실제 provider 오류에 도달하지 않았고** 429·413·503이 전부
   `llm_failure`로 뭉개졌습니다. `generateObject`가 기본으로 재시도하므로 이 경로가 예외가 아니라
   일반입니다. `RetryError.lastError`를 벗겨 분류하도록 고쳤습니다.

이 오분류가 **원인 진단 자체를 오염시켰습니다.** Stage B 성공률이 낮았을 때(후보 8개 기준 14회
중 3회 성공) provider의 "This model is currently experiencing high demand" 메시지를 보고 모델
과부하로 해석했습니다. **틀렸습니다.** 실제 원인은 `gemini-3.7-flash`의
`GenerateRequestsPerDayPerProjectPerModel-FreeTier` = **하루 20요청** 소진이었고, 그 429가 위의
`RetryError` 문제로 한도로 보이지 않았을 뿐입니다.

**결론이 바뀝니다.** 필요한 것은 "과부하 재시도 정책"이 아니라 **재시도해도 풀리지 않는 한도를
정확히 알리는 것**입니다. 하루 20요청에서는 재시도가 쿼터만 더 태웁니다. 한도는 모델별로 따로
걸려서 `gemini-3.7-flash`가 막힌 뒤에도 `gemini-3.6-flash`·`gemini-3.5-flash`는 동작했지만,
모델을 바꿔 측정을 이어가면 **실행 간 비교가 모델 간 비교로 바뀝니다.**

### 2-4. 검증 실패 등급: 거부와 교정을 가르는 기준

`source` 불일치를 처음에는 응답 전체 거부로 처리했습니다. 서버 교정으로 바꿨습니다.

기준은 이렇습니다. **서버가 정답을 확정적으로 아는 필드는 교정하고, 환각 SHA처럼 모델의 의도를
알 수 없는 필드는 전체 거부합니다.** `source`는 Stage A가 SHA별로 확정한 값이라 서버에 권위가
있습니다. `evidence`·`citedFilePaths`·PR 관계는 계속 실제 Repository 사실과 대조하므로 교정이
근거 안전성을 낮추지 않습니다.

**트레이드오프**: `source` 불일치는 "모델이 입력을 잘못 읽었다"는 신호일 수 있습니다. 그러나
다른 필드를 Repository 사실로 직접 검증하고 있고, 최대 55초짜리 호출을 재시도해도 같은 오류가
반복될 수 있으며, **Gemini 무료 등급 하루 20요청**을 전체 거부로 태울 이유가 없습니다. 이 신호가
필요해지면 거부가 아니라 로깅으로 다룹니다.

같은 이유로 `relatedShas`·`citedFilePaths`의 중복과 대표 SHA 자기 참조도 응답 전체를 거부하지
않고 소비자인 화면 뷰 모델에서 정규화합니다. 원본 응답은 감사 목적으로 보존합니다.

### 2-5. 판단 단위 전환이 Stage B로 번졌습니다

`buildStageBPayload`는 커밋 키 기반입니다. Stage A가 PR 묶음을 넘기면 묶음 하나가 커밋 여러 개로
펼쳐집니다. 묶음 8개 × 평균 4.8커밋 = 38커밋이면 커밋당 patch 예산이 1,578자로, 실측된 후보당
3,750자보다 크게 떨어집니다. 묶음당 대표 커밋을 `changes` 기준 상위 3개로 제한해 커밋당 2,500자를
확보했습니다. `STAGE_B_MAX_CANDIDATES`의 의미도 "커밋 20개"에서 바뀌므로 상수 이름과 주석을
함께 정리해야 합니다.

`INITIAL_STAGE_A_CANDIDATE_LIMIT`과 `STAGE_B_MAX_CANDIDATES`가 같은 값(20)이라 개수 초과 422는
**정상 흐름에서 도달 불가**입니다. 이 422는 형식 위반 방어용으로만 의미가 있고, **두 상수는 함께
바꿔야 이 성질이 유지됩니다.**

### 2-6. 채택하지 않은 대안도 기록해 둡니다

- **요청 2개 분할**: "한 번의 판단" 확정과 충돌해 기각했습니다.
- **서버 내부 후보 축소 재시도**: 첫 시도가 이미 예산을 소진한 상태라 같은 함수 실행 안에서는
  성립하지 않습니다. 축소 재시도가 성립하는 형태는 클라이언트가 더 적은 후보로 다시 요청하는
  것이며 이는 상태 머신(이슈 #18) 계층입니다. 실제로는 **스테이지 단위 재시도**(Stage A 결과를
  재사용해 Stage B부터)로 정리했습니다.
- **`fileTree` 입력**: 모델이 프롬프트에서 보지 못한 경로는 인용할 수 없어 검증만 느슨해지고
  본문만 커집니다. 서버가 직접 조회하면 가장 지연에 민감한 엔드포인트에 API 호출이 2회 늡니다.
- **후보 생성 파이프라인 스트리밍**: 총 실행 시간 상한을 늘려주지 않아 기각했습니다. 채팅
  기능의 스트리밍은 별개이며 그대로 유지합니다.

## 3. 측정 도구 자체가 결함을 가리고 있었습니다

발표에서 따로 떼어 말할 가치가 있는 부분입니다. **틀린 지표는 결함을 못 잡는 데 그치지 않고,
결함이 없다고 적극적으로 말합니다.**

| 결함 | 증상 | 영향 |
| --- | --- | --- |
| 누락 계산이 커밋 기준 | 판단 단위가 묶음이 됐는데 커밋 90 − 묶음 21 = **69가 항상 누락으로 찍힘** | 실제 누락이 69에 묻혀 보이지 않음 |
| 계약 충족 기대값이 커밋 수 | 계약 충족 판정이 **구조적으로 항상 거짓** | 개선 효과 측정 불가 |
| 토큰 집계 누락 | 계약 위반으로 던지는 호출의 토큰이 반환값에 안 실림 | 같은 입력에서 총토큰 5,935 → 7,404 (실제 소비를 크게 밑돎) |
| `x-ratelimit-used` probe | `githubFetch`가 상태 코드를 안 보고 Response를 반환해 403·429에서도 probe가 진행되고, 없는 헤더가 `Number(null)` = 0 | **위조된 소비량**이 측정에 섞일 수 있었음 |
| `/rate_limit` 엔드포인트 | 캐시된 값 반환. 응답 헤더가 4,762일 때 4,996을 반환 | 소비량은 각 응답의 `x-ratelimit-used`로만 판단해야 함 |

첫 두 항목을 고친 직후에 1-6의 프롬프트 결함이 드러났습니다. **지표를 고치지 않았으면 프롬프트
문제는 계속 안 보였을 것입니다.**

부수로 확인한 GitHub 경계 한 가지: 상세 응답의 파일 목록은 페이지당 300개 × 최대 10페이지라
`changedFiles`가 **정확히 3000에서 포화**하는데, 같은 응답의 `additions`는 6,718,755로 포화하지
않습니다. 즉 "파일 3000개인데 추가 670만 줄"이라는 **내부적으로 모순된 신호**가 Stage A 입력으로
들어갑니다. 측정 대상 저장소에는 이런 커밋이 없어(중앙 4, 최대 17) 별도 이슈 후보로 남겼습니다.

| Stage B patch 예산 | 총량·후보 수 조정 | 배분 방식만 선착순 → 균등 + 앞→뒤 이월 | 뒤→앞 재분배 포기 (순회 2회 대비 이득 작음) |

## 5. 남아 있는 한계 (발표에서 숨기지 말 것)

- **프로덕션 모델 `openai/gpt-oss-120b`로 현재 설계를 한 번도 돌리지 못했습니다.** 일일 토큰
  한도가 소진돼 대기가 616초 → 794초로 늘어 재시도가 손해임을 확인하고 중단했습니다. 검증은 전부
  `gpt-oss-20b` 기준입니다. `gpt-oss` 계열은 분당 버킷을 공유하지만 일일 버킷은 모델별로
  따로입니다.
- **한 번의 실행으로 모델의 계약 준수를 판단할 수 없습니다.** 같은 입력에서 21묶음 중 17개를
  빠뜨린 실행과 하나도 빠뜨리지 않은 실행이 모두 있었습니다. 같은 커밋이 실행에 따라
  `contribution_match`와 `automatic_recommendation`으로 갈리기도 합니다.
- **기여 항목 의미 매칭이 느슨합니다.** "GitHub API 오류 처리와 부분 실패 복구 구현"에 UI 상태
  연결 커밋과 클라이언트 요청 계층 커밋을 매칭했습니다. `+2/-2` 커밋과 줄 길이 정리 리팩터를
  후보로 올린 적도 있습니다.
- **점수 컷이 좋은 경험을 남기는지 검증되지 않았습니다.** PR#113과 PR#66이 통과한다는 사실
  하나뿐입니다. `demian`이 1점 경계까지 내려가 15묶음을 남기는 것이 적절한지도 미확인입니다.
- **분당 토큰 여유가 빠듯합니다.** 두 실행 모두 잔여 토큰이 111과 30까지 떨어졌습니다. 리셋이
  60초라 치명적이지는 않습니다.
- **종단 측정 경로가 프로덕션과 다릅니다.** `stage-b` 종단 측정이 복구 없는 `stage-a` 단계를
  앞단으로 씁니다.
- **PR을 쓰지 않는 저장소**(`hm1n/Algorithm`, PR 0개)에서 묶음과 점수가 모두 비었을 때 "후보를
  찾지 못했다"고 응답하는 경로가 아직 없습니다.
