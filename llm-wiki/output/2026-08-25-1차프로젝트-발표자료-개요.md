# 1차 프로젝트 발표 자료 개요 (프론트엔드 / demian)

정리일 2026-08-25. 심사 기준은 1차 프로젝트 안내문의 제작 원칙 5개와 프론트엔드 플래그십
기준입니다. 이 문서는 슬라이드 개요 + 데모 시나리오 + 발표 전 마감 과제 + 예상 질문으로
구성했습니다.

## 0. 한 줄 주제

> **"AI가 이력서를 대신 써 주는 서비스가 아니라, 실제 커밋을 근거로 사용자가 자기 경험을
> 설명하게 만드는 서비스. 그 근거를 어떻게 고르고, 스트리밍 화면을 어떻게 끊기지 않게
> 만들었는가."**

발표 축은 두 개입니다. 화면 나열을 하지 않습니다.

- **축 1 (프론트엔드 플래그십)**: AI 스트리밍 화면의 렌더링 비용을 측정하고, 측정이 가리킨
  것만 최적화했습니다. 추측 최적화를 하지 않았다는 것이 이야기의 핵심입니다.
- **축 2 (문제 정의 깊이)**: LLM 판단 단위를 커밋에서 PR 묶음으로 바꿔 입력을 81퍼센트 줄이고,
  근거 없는 선정(patch 0자 후보 선정)을 입력 단계에서 막았습니다.

## 2. 슬라이드 개요 (기본 12분 기준 · 괄호는 시간)

### S1. 표지 + 한 줄 정의 (0:20)
- 서비스 한 줄: "GitHub 커밋을 근거로 설명할 가치가 있는 경험을 골라, 코드 기반 AI 인터뷰로
  사용자가 스스로 설명하게 만드는 서비스."
- 하지 않는 것 한 줄: "AI가 이력서나 코드 설명을 대신 쓰지 않습니다."

### S2. 문제 정의 (1:00)
- 사전 인터뷰 4건에서 나온 문제: 자기 경험을 설명할 근거를 못 찾는다.
- **화면 문제로 번역**: (1) 무엇이 설명할 가치가 있는 경험인지 자동으로 골라야 한다.
  (2) AI가 근거를 지어내면 서비스 전체가 무의미하다. (3) 긴 코드·마크다운 답변이 스트리밍으로
  흐르는 동안 화면이 끊기면 안 된다.
- 이 세 문장이 뒤 슬라이드 세 덩어리와 1:1 대응한다고 미리 예고합니다.

### S3. 전체 구조 한 장 (0:50)
- Repository 입력 → 커밋 조회(블랙리스트) → **PR 묶음 구성 → 점수 선별 → Stage A(경량 선별)**
  → **Stage B(diff·PR 근거로 최종 3개)** → 근거 확인 → **인터뷰 스트리밍**.
- 화면 상태 머신 6단계(`repository-analysis.ts`)와 API route 경계를 같이 표시합니다.
- 여기서 "Loading·Empty·Error를 모든 핵심 흐름에 함께 구현" 원칙을 한 번 못 박습니다.

### S4. [축 1] 스트리밍 화면 — 측정 먼저 (1:30) ★핵심
- 슬라이드 제목: **"최적화하기 전에 뭐가 비싼지부터 쟀습니다."**
- 표 그대로 노출:

| 방식 | 청크 1개당 | 청크 31개 누적 |
| --- | --- | --- |
| 대화 전체 리렌더 | 6.75 ms | 209 ms |
| 스트리밍 중인 메시지만 리렌더 | 0.13 ms | 4 ms |

- **51.7배**. 메시지 80개면 전체 리렌더 1회가 32.62ms = 60fps 한 프레임(16.7ms)의 두 배.
- 측정 방법 한 줄: Node에서 CPU(파싱·렌더 트리·highlight), Playwright Chromium에서 layout.
  warmup 5회 + 표본 21회 중앙값, 난수 없음.

### S5. [축 1] 측정이 가리킨 최적화 3개 (1:30) ★핵심
1. **완료 메시지 `React.memo` 고정, 스트리밍 중 메시지만 갱신** ← 51.7배 근거.
2. **청크를 `requestAnimationFrame` 단위로 모아 반영** ← 재파싱 비용이 길이에 비례
   (4,919자에서 청크당 2.94ms, 한 프레임에 5개 도착하면 14.7ms를 같은 파싱에 소모).
3. **Syntax Highlighting은 코드 펜스가 닫힌 뒤 1회** ← 청크마다 highlight하면 **10.2배**.
   `createHighlighter` 53.67ms는 최초 1회라 단일 인스턴스로 지연 생성.

### S6. [축 1] 도입하지 않은 최적화 (1:00) ★차별점
- **가상 스크롤을 넣지 않았습니다.** `@tanstack/react-virtual`이 의존성에 있는데도 안 씁니다.
- 근거: Chromium 실측에서 DOM 노드 82 → 13,120개(**160배**) 동안 메시지 append는
  0.30ms → 0.50ms, 스트리밍 청크 layout은 0.1ms 미만, 자동 스크롤은 측정 한계 아래.
- **병목은 누적 DOM이 아니라 JS의 Markdown 재파싱**이었습니다.
- 재검토 기준을 문서에 박아 뒀습니다: 메시지 160개 초과 또는 append 8ms 초과 시 재측정.
- 발표 문장: "안 한 최적화도 근거가 있어야 한다고 봤습니다."

### S7. [축 1] 접근성 — 틀렸다가 고친 사례 (1:00) ★차별점
- 처음: 메시지 영역에 `role="log"` + `aria-live="polite"`.
- 문제: 이 화면은 메시지 하나의 텍스트가 프레임마다 자랍니다. live region으로 두면 스크린리더가
  **커지는 질문 전체를 프레임마다 다시 읽습니다.**
- 수정: 메시지 영역은 `aria-live="off"`. 대신 **상태 문단**("연결이 끊겨 다시 연결하고
  있습니다")과 **새 메시지 도착 안내**를 live region으로. 자동 스크롤이 멈춘 걸 볼 수 없는
  사용자에게 필요한 건 본문이 아니라 이 두 가지입니다.
- 디테일: 안내 문단을 조건부 렌더하지 않고 항상 두고 내용만 비웁니다(붙어 있는 동안의 변경만
  알리는 스크린리더 대응). 빈 상태에서 `:empty`일 때 grid 항목에서 제외해 간격이 안 생기게.

### S8. [축 2] 판단 단위를 바꾼 것이 진짜 해법 (1:30) ★핵심
- 처음 전제: "입력이 크니 기간을 줄이자."
- 실측 결과 범위를 안 줄이고 해결: **판단 단위를 커밋 → PR 묶음**.

| 저장소 | 커밋 단위 | PR 묶음 | 감소 |
| --- | --- | --- | --- |
| `demian` | 83단위 / 73,034B | 21단위 / 12,474B | **83%** |
| `andbread` | 319단위 / 188,334B | 66단위 / 36,292B | **81%** |

- 진짜 이유는 비용이 아니라 **경험이 커밋 단위에 없다**는 것: PR#113(커밋 18개, 69일, 파일
  56개)은 훌륭한 인터뷰 주제인데, 개별 커밋으로 보면 `chore: console.log 제거`,
  `Rename Modal.tsx to Modal.tsx` 같은 잡무뿐입니다.
- 추가 API 비용 0 — `pullRequests`를 이미 조회해 놓고 안 쓰고 있었습니다.

### S9. [축 2] 근거 없는 선정을 입력에서 막았다 (1:20) ★핵심
- 증상: patch 예산 60,000자를 커밋 순서대로 쓰다 보니 후보 20개 중 **앞 9개가 다 쓰고 11개(55%)가
  0자**.
- 예상은 "모델이 앞쪽에서만 고르겠지"였는데 **실측이 반박**: 최종 선정 3개가 인덱스 3·9·17이고
  **9·17은 patch 0자**. 즉 "diff와 PR 소속만 근거로 고르라"는 지시를 받은 모델이 **근거 없이
  답을 만들고** 있었습니다.
- 수정: 총량·후보 수 그대로, **배분만 선착순 → 균등 + 앞→뒤 이월**. 결과 굶는 후보 11개 → **0개**,
  총량은 여전히 정확히 60,000자, 절단 파일 90 → 77, 생략 78 → 59.
- 발표 문장: **"프롬프트로 지시하고 근거를 안 주면, 모델은 지시를 지키는 대신 답을 만듭니다.
  근거 부재는 입력 단계에서 막아야 합니다."**

### S10. 안정성 — 실패를 어떻게 다뤘나 (1:20)
세 장면만 고릅니다. 전부 실데이터에서 관측한 것입니다.

1. **오류 분류가 통째로 도달 불가였던 것**: AI SDK가 재시도 실패를 `RetryError`로 감싸는데
   `RetryError`는 `APICallError`가 아니라, `mapLlmError`의 분기 전체가 실제로는 안 타고
   429·413·503이 전부 `llm_failure`로 뭉개졌습니다. → `lastError` 언랩.
2. **413 두 갈래**: Groq는 분당 토큰 한도 초과를 429가 아니라 413으로 줍니다. 그런데 "요청이
   모델 한도보다 큰 413"은 기다려도 안 풀립니다. **본문의 `rate_limit_exceeded`로 갈라**
   한도만 503(재시도 안내), 나머지는 502.
3. **오진 정정**: 낮은 성공률을 provider의 "high demand" 메시지 보고 과부하로 해석했는데,
   실제로는 **Gemini 무료 등급 하루 20요청 소진**이었습니다. 결론이 뒤집힙니다 — 필요한 건
   재시도 정책이 아니라 한도를 정확히 알리는 것.
- 스트리밍 쪽 한 줄: `done` 이벤트 도착을 완료로 보지 않고 **`seq` 일치를 검증**합니다. 도착은
  완결의 대리 지표일 뿐이라 청크가 빠진 채 완료 처리되면 잘린 질문이 완성된 것처럼 남습니다.

### S11. 재현성 (0:40)
- 파이프라인: `scripts/measure-pipeline.ts` (`npx tsx`), 상세 조회 캐시로 GitHub 요청 0회 재실행,
  토큰은 env로만 주입.
- 렌더링: `streaming-render-cost.measure.mts` (`node <파일>`), 합성 코퍼스 733자 고정, 난수 없음,
  warmup 5 + 21표본 중앙값, Chromium 0.1ms 분해능 보정을 위해 20회 묶어 측정.
- 테스트: 유닛·컴포넌트 테스트 파일 27개, `lint`·`typecheck`·`test` 통과 기준으로 머지.

### S12. 한계와 다음 (0:50) ★신뢰 포인트
- 프로덕션 모델 `gpt-oss-120b`로 현재 설계를 **한 번도 못 돌렸습니다**(일일 토큰 한도 소진,
  대기 616초 → 794초). 검증은 `20b` 기준.
- 모델 계약 준수가 실행마다 갈립니다(같은 입력에서 17개 누락 실행과 0개 누락 실행이 모두 존재).
  **한 번의 실행으로 판단할 수 없습니다.**
- 휴리스틱 점수는 사실상 **규모 점수**입니다(발화 신호가 `file_rewritten_repeatedly` 52%,
  `many_commits` 43%에 쏠림). "7가지 경험 유형 탐지"라고 말하면 과장입니다.
- 스트리밍 측정은 합성 코퍼스 기준이고 실제 질문 생성 경로 배선 후 재측정이 필요합니다.
- PR을 안 쓰는 저장소(`hm1n/Algorithm`, PR 0개) 빈 결과 경로가 아직 없습니다.
