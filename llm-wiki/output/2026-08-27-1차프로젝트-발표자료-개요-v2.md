# 1차 프로젝트 발표 자료 개요 (프론트엔드 · demian)

## 이 문서에서 정한 것

이 문서에서는 1차 프로젝트 발표에서 무엇을 이야기할지, 어떤 순서로 보여줄지, 그리고 발표 전에 무엇을 끝내야 하는지를 정했습니다. 발표 시간은 12분을 기본으로 잡았고, 7분으로 줄여야 하는 상황에서 어느 슬라이드를 빼는지도 함께 적어 두었습니다. 심사 기준은 1차 프로젝트 안내문의 제작 원칙 5개와 프론트엔드 플래그십 기준을 그대로 따랐습니다.

이렇게 정한 이유는 이 프로젝트의 강점이 화면의 개수가 아니라 판단의 근거에 있기 때문입니다. 스트리밍 화면의 렌더링 비용을 먼저 측정한 다음 측정이 가리킨 곳만 고쳤고, LLM에 넘기는 입력의 판단 단위를 커밋에서 PR 묶음으로 바꿔 입력 크기를 81퍼센트 줄였습니다. 화면을 순서대로 훑는 발표로는 이 두 가지가 전혀 드러나지 않습니다.

반대로 하지 않기로 한 것도 분명히 정했습니다. 화면 스크린샷을 나열하지 않고, 슬라이드 한 장마다 수치 하나 또는 결정 하나를 담습니다. 또한 실시간 LLM 호출에 발표 전체를 걸지 않고 녹화 영상과 캐시 실행을 백업으로 준비합니다. 프로덕션 모델을 아직 한 번도 완주하지 못했으므로 "안정적으로 동작한다"는 표현도 쓰지 않습니다.

## 먼저 정리하는 용어

뒤에서 계속 나오는 용어를 먼저 풀어 둡니다. 발표를 듣는 사람이 이 프로젝트를 처음 본다고 가정했습니다.

- **Stage A (경량 선별)**: 커밋과 PR 정보를 가볍게 훑어 인터뷰 주제가 될 만한 후보를 좁히는 첫 번째 LLM 호출입니다.
- **Stage B (최종 선별)**: Stage A가 좁힌 후보에 실제 코드 변경 내용을 붙여, 최종 경험 후보 3개를 고르는 두 번째 LLM 호출입니다.
- **patch**: 커밋이 코드를 어떻게 바꿨는지 보여 주는 변경 본문입니다. Stage B가 근거로 삼는 자료이며, 이것이 비어 있으면 모델은 근거 없이 판단하게 됩니다.
- **PR 묶음**: 하나의 Pull Request에 속한 커밋 여러 개를 한 덩어리로 묶은 판단 단위입니다. 커밋 단위를 대신해 도입한 개념입니다.
- **청크**: LLM이 답변을 조금씩 흘려보낼 때 한 번에 도착하는 글자 묶음입니다. 스트리밍 화면은 이 청크가 도착할 때마다 화면을 다시 그립니다.
- **live region**: 화면 내용이 바뀌었을 때 스크린리더가 그 변화를 소리로 읽어 주도록 표시해 둔 영역입니다.

## 발표의 한 줄 주제와 두 축

발표의 한 줄 주제는 이렇게 잡았습니다.

> AI가 이력서를 대신 써 주는 서비스가 아니라, 실제 커밋을 근거로 사용자가 자기 경험을 설명하게 만드는 서비스입니다. 그 근거를 어떻게 골랐고, 스트리밍 화면을 어떻게 끊기지 않게 만들었는지를 이야기합니다.

발표는 두 개의 축으로만 진행합니다. 첫 번째 축은 프론트엔드 플래그십에 해당하는 스트리밍 렌더링입니다. AI 스트리밍 화면의 렌더링 비용을 측정한 다음 측정이 가리킨 것만 최적화했으며, 추측으로 최적화하지 않았다는 점이 이 축의 핵심입니다. 두 번째 축은 문제 정의의 깊이에 해당하는 근거 품질입니다. LLM의 판단 단위를 커밋에서 PR 묶음으로 바꿔 입력을 **81퍼센트** 줄였고, 근거가 없는 후보가 선정되는 일을 입력 단계에서 막았습니다.

## 2. 슬라이드 구성 (12분 기준)

괄호 안의 숫자는 해당 슬라이드에 배정한 시간입니다. 본문은 읽고 이해하기 위한 설명이고, 발표에서 실제로 입으로 말할 문구는 인용 블록으로 따로 표시했습니다. 슬라이드를 만들 때는 인용 블록과 표를 가져다 쓰면 됩니다.

### S1. 표지와 한 줄 정의 (0:20)

서비스를 한 줄로 소개한 다음, 하지 않는 것을 바로 한 줄 붙입니다. 무엇을 하지 않는지를 첫 장에서 못 박아야 뒤의 근거 이야기가 이해됩니다.

> GitHub 커밋을 근거로 설명할 가치가 있는 경험을 골라, 코드 기반 AI 인터뷰로 사용자가 스스로 설명하게 만드는 서비스입니다.
>
> AI가 이력서나 코드 설명을 대신 쓰지 않습니다.

### S2. 문제 정의 (1:00)

사전 인터뷰 4건에서 나온 문제는 자기 경험을 설명할 근거를 찾지 못한다는 것이었습니다. 이 문제를 화면이 풀어야 하는 세 가지 문제로 번역했습니다. 첫째로 무엇이 설명할 가치가 있는 경험인지 자동으로 골라야 하고, 둘째로 AI가 근거를 지어내면 서비스 전체가 무의미해지며, 셋째로 긴 코드나 마크다운 답변이 스트리밍으로 흐르는 동안 화면이 끊겨서는 안 됩니다. 이 세 문장이 뒤에 나오는 슬라이드 세 덩어리와 하나씩 짝을 이룬다는 점을 여기서 미리 예고합니다.

### S3. 전체 구조 한 장 (0:50)

데이터가 흐르는 순서를 한 장으로 보여 줍니다. Repository 입력에서 시작해 커밋 조회와 블랙리스트 필터를 지나고, PR 묶음 구성과 점수 선별을 거쳐 Stage A와 Stage B로 이어지며, 근거 확인을 지나 인터뷰 스트리밍에서 끝납니다. 여기에 화면 상태 머신 6단계(`repository-analysis.ts`)와 API route 경계를 함께 표시합니다. 그리고 Loading, Empty, Error 상태를 모든 핵심 흐름에 함께 구현했다는 원칙을 이 자리에서 한 번 못 박습니다.

### S4. 스트리밍 화면, 측정을 먼저 했습니다 (1:30, 핵심)

슬라이드 제목은 이렇게 잡았습니다.

> 최적화하기 전에 뭐가 비싼지부터 쟀습니다.

그리고 아래 표를 그대로 노출합니다.

| 방식 | 청크 1개당 | 청크 31개 누적 |
| --- | --- | --- |
| 대화 전체 리렌더 | 6.75 ms | 209 ms |
| 스트리밍 중인 메시지만 리렌더 | 0.13 ms | 4 ms |

차이는 **51.7배**입니다. 메시지가 80개 쌓인 상태에서는 전체 리렌더 한 번이 **32.62밀리초**를 쓰는데, 이는 60프레임 기준 한 프레임(16.7밀리초)의 두 배에 해당합니다. 측정 방법도 한 줄로 밝힙니다. CPU 비용인 파싱, 렌더 트리 구성, syntax highlighting은 Node에서 재고, layout 비용은 Playwright Chromium에서 쟀으며, warmup 5회 뒤 표본 21회의 중앙값을 사용하고 난수는 쓰지 않았습니다.

### S5. 측정이 가리킨 최적화 세 가지 (1:30, 핵심)

실제로 적용한 최적화는 세 개이며, 세 개 모두 앞 슬라이드의 측정값이 직접 가리킨 것입니다.

첫째로 완료된 메시지는 `React.memo`로 고정하고 스트리밍 중인 메시지만 갱신하도록 바꿨습니다. 근거는 앞의 **51.7배**입니다. 둘째로 도착한 청크를 `requestAnimationFrame` 단위로 모아 한 번에 반영했습니다. 재파싱 비용이 글의 길이에 비례해서 커지기 때문인데, 4,919자 시점에서는 청크 하나당 **2.94밀리초**가 들고 한 프레임에 청크 5개가 도착하면 **14.7밀리초**를 같은 파싱에 소모합니다. 셋째로 syntax highlighting은 코드 펜스가 닫힌 뒤에 한 번만 수행하도록 바꿨습니다. 청크마다 highlighting을 하면 **10.2배** 비싸기 때문입니다. 다만 `createHighlighter` 자체의 **53.67밀리초**는 최초 1회만 발생하므로, 단일 인스턴스를 지연 생성하는 방식으로 처리했습니다.

### S6. 도입하지 않은 최적화 (1:00, 차별점)

가상 스크롤은 넣지 않았습니다. `@tanstack/react-virtual`이 이미 의존성에 들어 있는데도 쓰지 않았습니다.

근거는 Chromium 실측입니다. DOM 노드가 82개에서 13,120개로 **160배** 늘어나는 동안 메시지를 덧붙이는 비용은 **0.30밀리초에서 0.50밀리초로만** 올랐고, 스트리밍 청크의 layout 비용은 0.1밀리초 미만이었으며, 자동 스크롤 비용은 측정 한계 아래였습니다. 즉 병목은 누적된 DOM이 아니라 JavaScript의 Markdown 재파싱이었습니다.

그렇다고 이 판단을 영구적인 결론으로 두지는 않았습니다. 메시지가 160개를 넘거나 메시지 덧붙이기가 8밀리초를 넘으면 다시 측정한다는 재검토 기준을 문서에 박아 뒀습니다. 이 슬라이드는 이 문장으로 마무리합니다.

> 안 한 최적화도 근거가 있어야 한다고 봤습니다.

### S7. 접근성, 틀렸다가 고친 사례 (1:00, 차별점)

처음에는 메시지 영역에 `role="log"`과 `aria-live="polite"`를 붙였습니다. 화면이 계속 갱신되는 영역이므로 변화를 읽어 주는 것이 맞다고 판단했기 때문입니다.

그러나 이 화면은 메시지 하나의 텍스트가 프레임마다 자라나는 구조였습니다. 그래서 이 영역을 live region으로 두면 스크린리더가 길어지는 질문 전체를 프레임마다 처음부터 다시 읽게 됩니다.

수정은 이렇게 했습니다. 메시지 영역은 `aria-live="off"`로 돌리고, 대신 상태 문단("연결이 끊겨 다시 연결하고 있습니다")과 새 메시지 도착 안내만 live region으로 두었습니다. 자동 스크롤이 멈춘 것을 눈으로 확인할 수 없는 사용자에게 필요한 정보는 본문 전체가 아니라 이 두 가지이기 때문입니다.

여기에 두 가지 세부 처리를 덧붙였습니다. 안내 문단은 조건에 따라 렌더링을 켜고 끄지 않고 항상 두되 내용만 비웁니다. 스크린리더가 처음부터 붙어 있던 영역의 변경만 알려 주는 경우에 대응하기 위해서입니다. 그리고 내용이 비어 있을 때는 `:empty` 상태에서 grid 항목에서 제외해, 빈 문단 때문에 간격이 벌어지지 않게 했습니다.

### S8. 판단 단위를 바꾼 것이 진짜 해법이었습니다 (1:30, 핵심)

처음 세운 전제는 "입력이 크니 조회 기간을 줄이자"였습니다. 그러나 실측 결과 조회 범위를 줄이지 않고 문제를 해결했습니다. 판단 단위를 커밋에서 PR 묶음으로 바꾼 것이 해법이었습니다.

| 저장소 | 커밋 단위 | PR 묶음 | 감소 |
| --- | --- | --- | --- |
| `demian` | 83단위 / 73,034B | 21단위 / 12,474B | **83%** |
| `andbread` | 319단위 / 188,334B | 66단위 / 36,292B | **81%** |

다만 이 변경의 진짜 이유는 비용 절감이 아니라, 경험이라는 것이 커밋 단위에 존재하지 않는다는 사실이었습니다. `andbread`의 PR 113번은 커밋 18개, 기간 69일, 파일 56개로 인터뷰 주제로 훌륭한 덩어리입니다. 그런데 이를 개별 커밋으로 쪼개서 보면 `chore: console.log 제거`나 `Rename Modal.tsx to Modal.tsx` 같은 잡무만 남습니다.

추가로 든 API 비용은 없습니다. `pullRequests` 데이터를 이미 조회해 놓고 쓰지 않고 있었기 때문입니다.

### S9. 근거 없는 선정을 입력 단계에서 막았습니다 (1:20, 핵심)

증상은 이렇게 나타났습니다. Stage B의 patch 예산 60,000자를 커밋 순서대로 소진하다 보니, 후보 20개 중 앞의 9개가 예산을 모두 쓰고 나머지 **11개(55퍼센트)에는 0자**가 배정되었습니다.

우리는 "모델이 결국 앞쪽 후보에서만 고를 것"이라고 예상했습니다. 그러나 실측이 이 예상을 반박했습니다. 최종 선정된 3개의 인덱스가 3번, 9번, 17번이었고 그중 9번과 17번은 patch가 0자였습니다. 즉 "diff와 PR 소속만 근거로 고르라"는 지시를 받은 모델이 근거 없이 답을 만들고 있었던 것입니다.

수정은 총량과 후보 수를 건드리지 않고 배분 방식만 바꾸는 것이었습니다. 선착순 배분을 균등 배분으로 바꾸고, 남은 몫을 앞에서 뒤로 이월하도록 했습니다. 그 결과 patch를 한 자도 받지 못하는 후보가 **11개에서 0개로** 줄었고, 총량은 여전히 정확히 60,000자였으며, 절단된 파일은 90개에서 77개로, 생략된 파일은 78개에서 59개로 줄었습니다.

이 슬라이드는 이 문장으로 마무리합니다.

> 프롬프트로 지시하고 근거를 주지 않으면, 모델은 지시를 지키는 대신 답을 만듭니다. 근거의 부재는 입력 단계에서 막아야 합니다.

### S10. 안정성, 실패를 어떻게 다뤘는지 (1:20)

장면 세 개만 고릅니다. 세 개 모두 실제 데이터에서 관측한 것입니다.

첫 번째는 오류 분류 코드가 통째로 도달 불가였던 문제입니다. AI SDK는 재시도 실패를 `RetryError`로 감싸는데, `RetryError`는 `APICallError`가 아닙니다. 그래서 `mapLlmError`의 분기 전체가 실제로는 실행되지 않았고, 429와 413과 503이 전부 `llm_failure` 하나로 뭉개지고 있었습니다. `lastError`를 언랩하도록 고쳐서 해결했습니다.

두 번째는 413이 두 갈래라는 문제입니다. Groq는 분당 토큰 한도 초과를 429가 아니라 413으로 돌려줍니다. 그런데 "요청 자체가 모델 한도보다 커서 발생한 413"은 기다려도 풀리지 않습니다. 따라서 응답 본문의 `rate_limit_exceeded` 값으로 두 경우를 갈라, 한도 초과만 503으로 내려 재시도를 안내하고 나머지는 502로 처리했습니다.

세 번째는 우리가 원인을 잘못 짚었다가 정정한 사례입니다. 낮은 성공률을 보고 provider의 "high demand" 메시지를 근거로 서버 과부하라고 해석했는데, 실제 원인은 Gemini 무료 등급의 하루 20요청 소진이었습니다. 원인이 바뀌면 결론도 뒤집힙니다. 필요한 것은 재시도 정책이 아니라 한도를 정확히 알려 주는 안내였습니다.

스트리밍 쪽에서는 한 가지를 덧붙입니다. `done` 이벤트의 도착을 완료로 보지 않고 `seq` 값의 일치를 검증합니다. 도착은 완결의 대리 지표일 뿐이어서, 청크가 빠진 채로 완료 처리되면 잘린 질문이 완성된 질문처럼 화면에 남기 때문입니다.

### S11. 재현성 (0:40)

파이프라인 측정은 `scripts/measure-pipeline.ts`를 `npx tsx`로 실행합니다. 상세 조회 결과를 캐시해 두었기 때문에 GitHub 요청을 0회로 두고 다시 돌릴 수 있으며, 토큰은 환경 변수로만 주입합니다.

렌더링 측정은 `streaming-render-cost.measure.mts`를 `node` 명령으로 실행합니다. 합성 코퍼스 733자를 고정해서 쓰고 난수는 쓰지 않으며, warmup 5회 뒤 표본 21회의 중앙값을 사용합니다. Chromium의 분해능이 0.1밀리초여서 이를 보정하기 위해 20회를 묶어 측정했습니다.

테스트는 유닛 테스트와 컴포넌트 테스트 파일 27개를 두고, `lint`와 `typecheck`와 `test`를 모두 통과하는 것을 머지 조건으로 삼았습니다.

### S12. 한계와 다음 단계 (0:50, 신뢰 포인트)

프로덕션 모델인 `gpt-oss-120b`로는 현재 설계를 한 번도 끝까지 돌리지 못했습니다. 일일 토큰 한도가 소진되어 대기 시간이 616초에서 794초까지 늘어났기 때문입니다. 따라서 지금까지의 검증은 모두 `20b` 기준입니다.

모델이 출력 계약을 지키는지도 실행마다 갈립니다. 같은 입력에서 17개가 누락된 실행과 하나도 누락되지 않은 실행이 모두 존재했습니다. 따라서 한 번의 실행으로는 판단할 수 없습니다.

휴리스틱 점수는 사실상 규모 점수입니다. 발화한 신호가 `file_rewritten_repeatedly`에 52퍼센트, `many_commits`에 43퍼센트로 쏠려 있기 때문입니다. 그래서 "7가지 경험 유형을 탐지한다"고 말하면 과장이 됩니다.

스트리밍 측정은 합성 코퍼스 기준이므로, 실제 질문 생성 경로를 배선한 뒤에 다시 측정해야 합니다. 그리고 PR을 쓰지 않는 저장소(`hm1n/Algorithm`은 PR이 0개입니다)를 위한 빈 결과 경로가 아직 없습니다.

## 5. 발표에서 쓸 수치

발표 중에 근사치로 말하지 않기 위해 측정값을 그대로 모아 두었습니다.

- 리렌더 범위: 51.7배 (6.75밀리초에서 0.13밀리초). 메시지 80개 전체 리렌더는 32.62밀리초로 한 프레임의 두 배
- Highlighting: 청크마다 수행하는 방식과 완료 후 1회 수행하는 방식의 차이가 10.2배. `createHighlighter`는 최초 1회에 53.67밀리초
- 재파싱: 733자에서 0.53밀리초, 4,919자에서 2.94밀리초로 길이에 비례
- DOM: 노드가 82개에서 13,120개로 160배 늘어도 덧붙이기는 0.30밀리초에서 0.50밀리초. 가상 스크롤을 넣지 않은 근거
- Stage A 입력: `andbread`가 188,334B에서 36,292B로 81퍼센트 감소, `demian`은 83퍼센트 감소
- Stage A 종단 시간: `andbread`가 29.5초에서 17.9초로 단축, LLM 호출은 2회에서 1회로 감소
- 전수 응답 계약: 프롬프트 개정 전에는 3회 모두 5/15였고, 개정 후에는 4회 중 3회가 15/15
- Stage B patch: patch를 받지 못하는 후보가 11/20에서 0/20으로 감소, 총량은 60,000자로 동일
- 실제 데이터 규모: `demian` 116커밋, `andbread` 431커밋(319 통과), `Algorithm` 435커밋
- 병렬 조회: 순차 15.6초에서 병렬 16으로 1.5초, 10.3배 단축. 403과 429는 관측되지 않았으나 도입은 후속 과제로 보류

## 7. 발표에서 하지 말 것

"7가지 경험 유형을 탐지합니다"라고 말하지 않습니다. 사실상 규모 점수이므로 과장입니다.

"안정적으로 동작합니다"라고 말하지 않습니다. 프로덕션 모델을 검증하지 못했고 실행 간 편차가 존재하므로, 반드시 조건을 붙여 말합니다.

화면 스크린샷을 나열하지 않습니다. 슬라이드 한 장에는 수치 하나 또는 결정 하나를 담습니다.

실시간 LLM 데모에 발표 전체를 걸지 않습니다. 녹화 영상과 캐시 실행을 백업으로 준비합니다.

수치를 근사로 말하지 않습니다. 51.7배, 10.2배, 81퍼센트, 11/20에서 0/20처럼 측정값을 그대로 말합니다.

## 8. 백업 슬라이드

질의응답에서만 쓰고 발표 본편에는 넣지 않습니다.

- 오류 kind 13종과 HTTP status의 매핑 표
- 청크 분할을 폐기한 실측 (7청크 중 첫 시도에서 계약을 지킨 것이 2회, 청크 6의 실패로 정상 63묶음을 폐기)
- 점수 경계 컷을 상위 N개 대신 쓴 이유 (`andbread`에서 2점 동점이 15개)
- 폴백 클러스터링의 순도 표 (디렉터리와 24시간 기준으로 77퍼센트, 과분할 130묶음)
- 블랙리스트 순서 변경을 철회한 근거 4가지
- 측정 지표 자체의 결함 5건 (누락 69 고정, 토큰 집계 누락, probe 위조 등)
- `changedFiles`가 3000에서 포화하는데 `additions`는 670만으로 나오는 모순 신호
