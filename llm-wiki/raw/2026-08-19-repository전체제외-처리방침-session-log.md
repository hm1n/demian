# 전체 커밋 제외 대상일 때 처리 방침 세션 로그

## 문서 목적

"Repository 데이터 조회 및 기본 분석" 기능 정의서의 확인 필요 항목 중 "모든 커밋이 제외 대상일 때 다음 단계로 전달할 데이터와 사용자 안내 방식을 확정해야 합니다" 항목을 논의하고 결정한 내용을 보존한다.

## 논의 내용

로컬에서 개발하다가 GitHub에는 나중에 한 번에 올리는 경우, 실제로 의미 있는 커밋 이력이 거의 없거나 스쿼시 커밋 한두 개뿐인 저장소가 있을 수 있다는 문제 제기가 있었다. 이런 경우 블랙리스트 필터를 통과하고도 상세 조회할 커밋이 하나도 남지 않을 수 있다.

해결책으로 "커밋 이력이 부족하면 저장소 전체 파일 트리를 탐색해서 경험 후보를 만드는" 대안을 검토했다. 이 대안의 장단점을 비교했다.

장점으로는 실제 존재하는 코드를 근거로 쓸 수 있어 "Repository 근거 기반" 원칙을 어기지 않는다는 점, 커밋 이력이 부실한 유저도 서비스를 계속 이용하게 할 수 있다는 점이 있었다.

단점은 다음과 같다.

- 지금 설계된 6개 기능 전부 diff 기반으로 짜여 있다. 대표 커밋, diff, 근거 표시, 질문 생성, 꼬리 질문 모두 커밋 변경 내역을 전제로 한다. 파일 트리 스냅샷은 diff가 아니므로 근거 표시부터 질문 생성까지 로직을 별도로 다시 설계해야 하는, 사실상 두 번째 파이프라인이다.
- diff는 변경 전후를 비교할 수 있어 "왜 이렇게 바꿨는지" 질문을 만들 근거가 되지만, 파일 트리 스냅샷 하나는 결과물만 보여줘서 인터뷰 설계 원칙(기술 선택 이유를 설명하도록 꼬리 질문 생성)에 필요한 변화의 근거가 약하다.
- 5일 작업 범위 결정에서 토큰 비용을 최우선 과제로 확정했는데, 저장소 전체 파일을 LLM으로 분석하는 것은 diff 조회보다 비용이 커질 수 있어 이 결정과 충돌한다.
- 로컬 작업 후 한 번에 push하는 패턴이 실제로 얼마나 흔한지 검증된 자료가 없다. 드문 경우를 위해 파이프라인을 통째로 하나 더 만드는 것은 과할 수 있다.

이미 5일 작업 범위 결정에서 의도 없는 유저와 최소 숙련도 이하 유저를 범위 밖으로 뒀는데, 커밋 이력이 사실상 없는 유저도 같은 성격의 문제로 볼 수 있다는 데 의견이 모였다. 서비스 핵심 가치인 "실제 코드 근거 기반 인터뷰" 자체가 성립하지 않는 입력이기 때문이다.

## 결정 사항 요약

- 커밋 이력 부족을 이유로 한 파일 트리 전체 탐색 fallback은 도입하지 않는다.
- 블랙리스트 필터를 통과한 뒤 상세 조회할 커밋이 하나도 남지 않으면, 안내 문구로 처리한다. 이 저장소는 분석하기 어렵다는 사실을 안내하고 커밋 이력이 있는 다른 저장소를 선택하도록 유도한다.
- 이 처리는 GitHub Repository 입력 기능의 저장소 선택 단계와 연결된다. 저장소 선택 직후 또는 데이터 조회 직후 커밋 수를 확인해 안내할 수 있다.

## 확인 필요

- 안내 문구를 정확히 언제 보여줄지 확정해야 한다. 저장소 목록 선택 시점에 미리 걸러줄지, 아니면 데이터 조회를 마친 뒤 결과가 0개일 때 보여줄지 정해야 한다.
- 커밋 수가 매우 적지만 0은 아닌 경계 상황(예: 유의미한 커밋이 1~2개뿐)의 처리 방식은 이번 논의에서 다루지 않았다.
