# Repository 데이터 조회 및 기본 분석 기능 경계 세션 로그

## 문서 목적

raw/2026-08-19-github-repository-입력-기능-설계-session-log.md에서 "GitHub Repository 입력" 기능 동작에 2단계 커밋 조회 로직을 전부 넣었는데, MVP 목록에는 "Repository 데이터 조회 및 기본 분석"이 별도 항목으로 있어 두 기능이 겹치는 문제를 논의하고 경계를 다시 정한 내용을 보존한다.

## 논의 내용

### 기능 분리 여부

두 기능을 하나로 합치는 안과, 분리를 유지하되 "GitHub Repository 입력"을 인증과 저장소 선택으로만 좁히는 안을 비교했다. 분리를 유지하는 것으로 결정했다. "GitHub Repository 입력"은 OAuth 인증과 저장소 선택까지만 담당하고, 2단계 커밋 조회 로직은 "Repository 데이터 조회 및 기본 분석"으로 옮긴다.

### 조회와 분석과 후보 생성의 경계

"Repository 데이터 조회 및 기본 분석"과 "개발 경험 후보 생성"의 역할 경계도 함께 정했다.

"Repository 데이터 조회 및 기본 분석"은 원본 데이터를 수집하고, 커밋별로 diff 줄 수나 변경 파일 수 같은 파생 지표를 계산하는 데까지 담당한다. 즉 재료를 준비하는 역할이다.

"개발 경험 후보 생성"은 이렇게 계산된 지표를 바탕으로 실제 점수를 매기고 순위를 매겨 최종 후보 3개를 뽑는 판단 역할을 담당한다.

## 결정 사항 요약

- "GitHub Repository 입력"은 OAuth 인증과 저장소 선택까지만 담당하도록 범위를 좁힌다. 기존 노션 페이지의 기능 동작에서 2단계 커밋 조회 관련 내용을 제거해야 한다.
- "Repository 데이터 조회 및 기본 분석"이 2단계 커밋 조회 로직과 파생 지표 계산을 담당한다. raw/2026-08-19-github-repository-입력-기능-설계-session-log.md에서 논의했던 2단계 구조, 커밋 개수 상한 없음, 조회 데이터 범위(커밋, diff, 파일 트리, 언어 통계) 결정은 그대로 이 기능으로 옮겨온다.
- "개발 경험 후보 생성"은 파생 지표를 바탕으로 점수를 매기고 순위를 매겨 최종 후보를 뽑는 역할만 담당한다.

## 확인 필요

- 1단계 필터링에 쓸 커밋 메시지 키워드 목록
- 2단계로 넘어가는 후보 커밋의 상한 개수
- 1차 필터링을 통과한 후보가 하나도 없을 때 처리 방침
