# Repository 기여 항목 상세 조회 구현

## 범위

- GitHub Issue #3과 Notion 기능 정의서 `Repository 데이터 조회 및 분석`을 기준으로 구현했다.
- 블랙리스트 통과 여부는 앞 단계의 책임으로 두고, 전달받은 커밋만 상세 조회한다.
- 후보 평가, 점수 계산, 순위 결정, 시간 근접성·파일 겹침 기반 관련성 추론은 추가하지 않았다.

## 데이터 계약

- 커밋 상세: 전체 메시지, 파일별 patch와 변경 통계, 추가·삭제 줄 수, 변경 파일 수
- PR 소속: 번호, 제목, 상태, URL, base/head 브랜치를 API 응답 의미 그대로 전달
- Repository 메타데이터: 재귀 파일 트리, 트리 잘림 여부, 언어별 바이트 통계
- PR이 없는 커밋은 빈 배열로 표현한다.

## 상태와 오류

- 진행 상태는 `commit_details`, `repository_metadata`로 구분한다. 파생 지표는 커밋 상세 응답을 변환할 때 함께 계산하므로 별도 진행 단계로 두지 않는다.
- 기존 GitHub 오류 분류(rate limit, 인증 취소, 미존재, 네트워크, 서버 오류)를 재사용한다.
- 일부 커밋 상세를 수집한 뒤 실패하면 `partial_failure`와 수집 완료된 커밋을 함께 전달한다.

## 성능 판단

- 실제 호출량과 응답 시간을 아직 측정하지 않았으므로 동시 요청, 캐시, 상세 조회 상한을 도입하지 않았다.
- API 호출량은 필터 통과 커밋당 상세 1회와 PR 1회, Repository 단위 정보 2회다.
- 실제 Repository 측정 후 병렬화나 호출 제한이 필요한지 판단한다.
