# 점수 정규화 방식과 가중치 세션 로그

## 문서 목적

"개발 경험 후보 생성" 기능 정의서의 확인 필요 항목 "점수 정규화 방식과 각 지표의 가중치를 구현 단계에서 확정해야 합니다"를 논의하고 결정한 내용을 보존한다.

## 논의 내용

### 초기 제안과 반론

처음에는 스펙에 있는 두 축, "코드 변경 규모와 복잡도" 점수와 "기술적 의사결정의 흔적" 점수를 각각 min-max 정규화하고 0.5 대 0.5로 가중합하는 안을 제안했다.

- 축 1(규모·복잡도): 변경 줄 수, 변경 파일 수, 서로 다른 최상위 디렉토리에 걸친 변경 개수를 min-max 정규화 후 평균.
- 축 2(기술적 의사결정 흔적): 새 의존성 추가 여부, 여러 레이어 동시 변경 여부를 min-max 정규화 후 평균.

이에 대해 "이 방식은 결국 크고 복잡한 작업을 가려내는 것이지, 실제로 의미 있는 작업인지 판별하기는 어렵다"는 문제 제기가 있었고, 대안으로 채용 공고에서 필요 키워드를 뽑아 그 키워드 기반으로 경험을 골라내는 방식을 제안했다.

### 대안에 대한 초기 반대와 정정

채용 공고 기반 키워드 매칭에 대해 처음에는 다음 이유로 반대했다.

- 채용 공고를 실시간으로 수집·분석하는 파이프라인은 GitHub 데이터만 다루던 기존 설계 범위를 크게 벗어난다.
- 키워드 언급 여부는 실제 작업 깊이를 보장하지 않아, 지적된 문제(규모만으로는 의미를 못 가린다)를 해결하지 못하고 같은 종류의 문제를 다른 형태로 옮긴 것에 가깝다.
- 서비스는 이력서나 코드 설명을 대신 작성하지 않는다는 원칙이 있어 채용 시장 관련성을 선별 기준에 반영하는 것이 서비스 정체성과 맞지 않는다고 판단했다.

이 판단에 대해 정정이 있었다. 서비스의 일차 목표는 구현한 내용을 스스로 설명할 수 있게 돕는 것이 맞지만, 이차 목표는 이력서와 포트폴리오, 면접에 쓸 수 있는 경험 블록을 만들고 그것을 면접에서 설명할 수 있는 수준까지 이해하게 만드는 것이다. 이 맥락에서는 채용 시장 관련성을 선별 기준에 반영하는 것이 서비스 목적에 부합한다.

이 정정을 받아들이면서 두 가지 우려는 분리해서 남겨두었다.

- 실현 가능성 우려는 "실시간 크롤링" 방식의 문제이지 "채용 시장 키워드를 반영한다"는 목표 자체의 문제가 아니다. 정적으로 정리한 고정 키워드 목록을 쓰면 크롤링 파이프라인 없이도 목표를 달성할 수 있다.
- 신호 품질 우려, 즉 키워드 언급만으로는 실제 작업 깊이를 보장하지 못한다는 우려에 대해서는, 언급된 커밋도 포함하는 것이 오히려 낫다는 답변이 있었다. 기술 사용 목적과 트레이드오프를 캐묻는 꼬리 질문 기능이 별도로 있으므로, 실제로 깊이 이해했는지는 점수 계산이 아니라 인터뷰 과정에서 드러난다. 점수 계산은 캐물을 만한 후보를 잘 뽑는 역할까지만 하면 된다.

## 결정 사항 요약

- 채용 공고 기반 키워드는 고정 키워드 목록으로 반영한다. 실시간 수집·크롤링 파이프라인은 만들지 않는다.
- 키워드 매칭은 언급 여부만 본다. 실제 사용 깊이는 따지지 않는다. 깊이 검증은 실제 코드 기반 AI 질문 생성과 꼬리 질문 기능이 담당한다.
- 최종 점수는 세 개 축의 가중합으로 계산한다.
  - 축 1(규모·복잡도): 변경 줄 수, 변경 파일 수, 서로 다른 최상위 디렉토리에 걸친 변경 개수를 min-max 정규화 후 평균.
  - 축 2(기술적 의사결정 흔적): 새 의존성 추가 여부, 여러 레이어 동시 변경 여부를 min-max 정규화 후 평균.
  - 축 3(채용 시장 관련성): 고정 키워드 목록과의 매칭 개수를 min-max 정규화.
- 기본 가중치는 `w1=0.4, w2=0.4, w3=0.2`로 시작한다. 축 3은 보조적인 성격으로 비중을 낮게 잡았다. 세 값 모두 검증되지 않은 초기값이며 실데이터로 조정한다.
- 정규화 방식은 min-max를 사용한다. 후보군 규모가 레포 하나당 수십에서 수백 개 수준이라 단순한 방식으로 충분하다고 판단했다.

## 확인 필요

- 채용 공고 기반 고정 키워드 목록의 실제 내용은 이번 논의에서 다루지 않았다. 블랙리스트 키워드와 마찬가지로 별도로 정리하고 실데이터로 검증해야 한다.
- 세 축의 가중치(0.4, 0.4, 0.2)는 실제 본인 Repository로 돌려본 뒤 대표 커밋 3개가 실제로 타당한지 확인하고 조정한다.
- min-max 정규화가 극단값(예외적으로 아주 큰 커밋 하나)에 민감하다는 점은 실측 후 문제가 되면 다시 검토한다.
