# 실시간 AI Streaming 응답 기능 설계 세션 로그

## 문서 목적

"실시간 AI Streaming 응답" 기능을 설계하면서 논의하고 결정한 내용을 보존한다. 이 기능은 "실제 코드 기반 AI 질문"과 "꼬리 질문"이 생성한 질문 내용을 화면에 실시간으로 출력하는 역할을 담당한다.

## 논의 내용

### 전송 방식

AI 응답을 서버에서 클라이언트로 스트리밍할 때 SSE와 WebSocket을 비교했다. 이 서비스의 스트리밍은 서버에서 클라이언트로만 흘러가는 단방향 구조이므로 SSE로 결정했다. 양방향 통신이 필요 없는데 WebSocket을 쓰면 구현과 인프라 부담만 늘어난다고 판단했다.

### 자동 스크롤과 수동 스크롤 충돌

새 토큰이 계속 도착하는 중에 사용자가 과거 대화를 보려고 위로 스크롤하는 경우를 논의했다. 사용자가 위로 스크롤하면 자동 스크롤을 멈추고, 새 메시지가 도착했다는 안내만 보여주는 것으로 결정했다. 사용자가 읽고 있는 도중에 화면이 강제로 내려가면 불편하기 때문이다. 사용자가 다시 하단으로 내려오면 자동 스크롤을 재개한다.

### 스트리밍 이탈 처리

스트리밍 도중 사용자가 다른 경험으로 전환하거나 페이지를 떠나는 경우를 논의했다. 클라이언트 연결이 끊어져도 서버는 응답 생성을 계속하고 완성된 응답을 저장하는 것으로 결정했다. 사용자가 다시 돌아오면 완성된 응답을 그대로 보여준다. 이 결정은 "경험 선택" 기능 설계에서 남겨두었던 확인 필요 항목인 "스트리밍 응답이 진행되는 도중 다른 경험으로 전환할 때 처리 방식"을 해소한다. 경험별 대화 세션이 서버에 저장되어 재방문해도 유지된다는 기존 원칙과도 맞닿아 있다.

### 렌더링 성능과 관련한 프로젝트 원칙 반영

CLAUDE.md에 정의된 이 서비스의 프론트엔드 핵심 챌린지를 그대로 이 기능의 요구사항으로 가져왔다. 스트리밍 중 리렌더링 범위를 최소화해야 하고, 메시지가 누적될 때 DOM 증가와 렌더링 비용을 관리해야 하고, Syntax Highlighting과 Markdown Parsing 비용을 관리해야 하고, 수동 스크롤과 자동 스크롤이 충돌하지 않아야 한다. 다만 구체적인 구현 기법은 프로젝트 원칙에 따라 실제 성능 측정 없이 먼저 정하지 않기로 했다. 추측성 최적화를 먼저 적용하지 않는다는 원칙에 따른 것이다.

## 결정 사항 요약

- 스트리밍 전송 방식은 SSE로 한다.
- 사용자가 위로 스크롤하면 자동 스크롤을 멈추고 새 메시지 도착 안내만 보여준다. 사용자가 하단으로 돌아오면 자동 스크롤을 재개한다.
- 클라이언트 연결이 끊어져도 서버는 응답 생성을 계속하고 완성된 응답을 저장한다. 사용자가 돌아오면 완성된 응답을 바로 보여준다.
- 이 기능은 질문 내용을 화면에 출력하는 것까지 담당한다. 질문 내용을 생성하는 일은 "실제 코드 기반 AI 질문"과 "꼬리 질문" 기능이 담당한다.
- 리렌더링 최소화, DOM 관리, Syntax Highlighting과 Markdown Parsing 비용 관리는 이 기능이 지켜야 할 원칙으로 남기되, 구체적인 구현 기법은 실제 성능 측정 이후에 정한다.

## 확인 필요

- 리렌더링 범위를 최소화하는 구체적인 구현 방식
- 메시지 누적에 따른 DOM 증가를 관리하는 구체적인 방식
- Syntax Highlighting과 Markdown Parsing 비용을 관리하는 구체적인 방식
- 스트리밍 연결이 끊겼을 때 재연결하는 구체적인 방식
