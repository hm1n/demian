# Stage A 후보 선정 개수의 분산을 측정한다

## 물음

배선 뒤 후보 0개가 나온 원인이 **로컬 전환 때 붙던 프롬프트 문구의 부재**인지 확인한다.
`localInputScopeHint()`를 프로덕션 프롬프트로 승격하고 네이티브 경로 그대로 반복 측정했다.

## 결과

입력은 모두 같다. 커밋 141건, 점수 선별 후 12묶음, 후보 상한 5개, 기여 항목 0개다.

| 모델 | 문구 | 실행 | 선정 개수 | 후보 0개 비율 |
| --- | --- | --- | --- | --- |
| `gemini-3.1-flash-lite` | 없음 | 6회 | 0, 5, 5, 5, 5, 0 | **2/6** |
| `gemini-3.1-flash-lite` | 있음 | 10회 | 5, 5, 5, 5, 2, 4, 5, 0, 5, 1 | **1/10** |
| `gemini-3.5-flash-lite` | 없음 | 4회 | 0, 0, 0, 0 | **4/4** |
| `gemini-3.5-flash-lite` | 있음 | 4회 | 0, 0, 0, 0 | **4/4** |

## 판정 1. 문구는 원인이 아니다

`gemini-3.5-flash-lite`는 문구를 넣어도 네 번 모두 0개다. **문구가 이 현상을 설명하지 못한다.**

`gemini-3.1-flash-lite`는 0개 비율이 2/6에서 1/10으로 줄었으나 표본이 작아 분산과 구별되지 않는다.
문구를 넣어도 0개가 여전히 나온다.

따라서 문구를 프로덕션으로 승격하지 않고 되돌렸다. **효과를 귀속시킬 수 없는 변경을 남기지 않는다.**

## 판정 2. 진짜 문제는 선정 개수의 분산이다

`gemini-3.1-flash-lite`가 같은 입력에서 0개부터 5개까지 낸다. 문구를 넣은 10회에서 5개가 6회, 4개가
1회, 2개가 1회, 1개가 1회, 0개가 1회다. **후보 개수가 안정적이지 않다.**

`raw/2026-08-28-Stage-A-실데이터-판단품질-비교.md`가 이것을 잡지 못한 이유는 각 경로를 **1회만** 실행했기
때문이다. 같은 문서의 한계 절에 적어 둔 항목이다.

## 판정 3. 프롬프트의 선정 지시에 하한이 없다

현재 지시다.

```
recommended가 true이거나 기여 항목에 맞는 묶음은 합쳐서 최대 N개까지만 고르세요. 이 상한은 고르는
개수에만 걸립니다. (...) 규모가 크다는 이유만으로 고르지 말고 설명할 거리가 있는 묶음을 고르세요.
```

상한만 있고 하한이 없다. 마지막 문장은 선정을 **억제하는** 방향이다. 입력이 이미 점수 선별을 통과한
상위 12묶음이라는 사실도 프롬프트에 없다. 모델이 "고를 것이 없다"고 답하면 형식상 정상이다.

`gpt-oss-120b`는 같은 지시에서 5개를 골랐고 Gemini Lite 두 모델은 0개를 고른다. **같은 프롬프트가 모델에
따라 다르게 읽힌다.**

## 다음에 할 것

1. **하한을 주는 프롬프트 변형을 만들어 같은 입력으로 비교한다.** 점수 선별을 통과한 입력이라는 사실과
   최소 개수를 명시하는 변형이다. 프롬프트 변형 두 개를 측정으로 가르는 방식은 이 저장소에 선례가 있다
   (`wiki/2026-08-25-Stage-A-청크-폐기와-점수-선별-전환.md`).
2. **엔드포인트 가설도 열려 있다.** 2026-08-28에 `gemini-3.5-flash-lite`가 5개를 골랐던 실행은 OpenAI
   호환 경로였다. 문구가 원인이 아니므로 남은 차이는 경로다. 하한 변형이 실패하면 이쪽을 잰다.
3. **반복 횟수를 정해야 한다.** 1회 측정으로는 이 분산을 볼 수 없다. 선정 관련 판단은 최소 5회를 쓴다.
