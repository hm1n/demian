# 기능 정의서 템플릿 설계 세션 로그

## 문서 목적

노션 "기능 정의서" 데이터베이스에 재사용할 템플릿 페이지의 항목 구성을 논의하고 확정한 내용을 보존한다.

## 논의 내용

### 사용자 흐름과 기능 동작 분리

처음에는 "사용자 흐름" 항목만 넣으려 했으나, 사용자가 화면에서 인지 불가능한 내부 처리 로직(판단 조건, 데이터 조회/가공 방식, 알고리즘)이 빠질 위험을 지적했다. 실제로 raw/2026-08-19-github-repository-입력-기능-설계-session-log.md에서 논의한 2단계 커밋 조회 구조가 이 사각지대에 해당했다.

이에 따라 "사용자 흐름"(화면/인터랙션 순서)과 "기능 동작"(내부 처리 로직)을 별도 항목으로 분리하기로 결정했다. 구분 기준은 "사용자가 화면에서 인지 가능한가"이다.

### Loading / Empty / Error 상태 처리

기능 정의서에 상태 처리 방식(UI 컴포넌트, 문구 등)까지 전부 적기에는 너무 구체적이라는 문제 제기가 있었다. 같이 적을 때와 별도 문서로 뺄 때의 장단점을 비교했다.

같이 적을 때는 예외 상태를 빠뜨릴 위험이 낮고 CLAUDE.md의 "모든 핵심 흐름에서 항상 함께 구현" 원칙과 맞지만, 문서가 길어지고 기능마다 공통 UI 패턴이 중복 서술되는 단점이 있다. 별도 문서로 빼면 서비스 전체 차원의 상태 UX 일관성을 잡기 쉽지만, 기능 문서만 보고 구현할 때 예외 케이스를 놓칠 위험이 있고 두 문서 동기화 부담이 생긴다.

절충안으로, 기능 정의서에는 "이 기능에서 발생 가능한 Loading/Empty/Error 케이스 목록"만 나열하고, 실제 처리 방식(공통 컴포넌트, 문구 패턴)은 별도 상태 처리 가이드 문서에서 통합 정의하기로 결정했다.

## 확정한 템플릿 항목

1. 기능명
2. 목적
3. 사용자 흐름
4. 기능 동작
5. 입력/출력 데이터
6. 주요 결정 사항
7. Loading / Empty / Error 케이스 (케이스 목록만, 처리 방식은 별도 문서)
8. 확인 필요

각 항목은 노션 페이지에서 h2로 작성한다. 노션 "기능 정의서" 데이터베이스의 템플릿 페이지(https://app.notion.com/p/3c1e7e8fdd1280a8840dcc32e14df409)에 위 형식으로 적용했다.

## 확인 필요

- 별도 "상태 처리 가이드" 문서는 아직 작성하지 않음
