# Stage A 판단 온도를 0으로 고정한 실측

## 확정

**프로덕션 온도를 제공자 기본값에서 0으로 고정했다.** Stage A는 같은 입력 8회에서 후보 개수와 고른
내용이 모두 같아졌다. 고정 전에는 7회에 서로 다른 후보 집합 4개가 나왔다.

Stage B에도 같은 온도가 걸린다. **Stage B는 온도 0에서도 회차마다 결과가 다르다.** 3회 중 2회만
같은 Pull Request 집합을 골랐고 대표 커밋과 evidence 문장은 매회 달랐다. 즉 온도 고정은 결정론을
보장하지 않는다.

## 왜 쟀는가

온도를 정하는 경로가 로컬 전환 안에만 있었다. `localSamplingOptions()`가 `isLocalLlm()` 게이트
뒤에 있어서 프로덕션은 제공자 기본값을 그대로 썼다. Groq 시절에는 그 편이 맞았다. 이슈 #19 실측이
기본 샘플링에서 나왔고 기본값을 바꿀 이유가 없었다.

제공자를 Gemini로 옮기면서 조건이 달라졌다. Gemini의 기본 온도는 1.0이고 두 단계가 하는 일은
창작이 아니라 판단이다. wiki 8절 10번에 "Stage A의 선정 개수는 여전히 회차마다 다르다"가 열린
채로 남아 있었고, 선택 내용이 같은지는 아예 재지 않았다.

## 측정 조건

| 항목 | 값 |
| --- | --- |
| 저장소 | `hm1n/demian` (본인 저장소) |
| 입력 커밋 | 141개 (작성자 커밋 257개 중 블랙리스트 통과) |
| 선별 묶음 | 12개 (선별 예산 10,500바이트, 재산정 전) |
| 후보 상한 | 5 |
| 모델 | `gemini-3.1-flash-lite` |
| 반복 | 온도 기본값 7회, 온도 0 8회 |

상세 조회 결과를 저장소 밖 임시 경로에 캐시해 회차마다 같은 입력을 보냈다. 즉 회차 사이에 달라진
것은 모델 응답뿐이다.

전수 응답 계약은 7회 모두 `12/12`였고 누락과 중복이 0이었다. 소요는 1,863~2,300밀리초다.

**서로 다른 후보 집합이 4개 나왔다.** 묶음별 출현 횟수는 35b70b5와 dac4c70이 7회, 9737f3f가 6회,
feca70b가 5회, f6794c8이 4회, d353626이 2회, f101a8d가 1회다. 사용자가 같은 저장소를 두 번
분석하면 후보 목록이 달라진다는 뜻이다.

## 결과 2. 온도 0

8회 전부 같았다.

| 항목 | 값 |
| --- | --- |
| 후보 개수 | 8회 모두 5 |
| 고른 묶음 | 8회 모두 35b70b5, dac4c70, feca70b, 9737f3f, f6794c8 |
| 전수 응답 계약 | 8회 모두 `12/12`, 누락·중복 0 |
| 소요 | 1,832~2,070밀리초 |

기본 온도에서 가장 자주 뽑힌 다섯 개와 같은 집합이다. 즉 온도를 낮춰 다른 것을 고르게 된 것이
아니라, 흔들리던 것이 가장 자주 나오던 답으로 모였다.

## 결과 3. Stage B는 온도 0에서도 흔들린다

같은 Stage A 출력(후보 묶음 5개, 커밋 30개)으로 3회 돌렸다.

| 회차 | 소요 | 최종 후보 PR | 대표 커밋 |
| --- | --- | --- | --- |
| 1 | 5,003밀리초 | #73, #62, #40 | feca70b, 35b70b5, 9737f3f |
| 2 | 4,733밀리초 | #73, #62, #61 | feca70b, 5c26a0c, dac4c70 |
| 3 | 4,932밀리초 | #73, #62, #61 | feca70b, 5c26a0c, dac4c70 |

3회 모두 완주했고 최종 후보 3개, 인용 파일 4~9개, 같은 Pull Request 중복 0이었다. 그러나 회차 1이
다른 PR을 골랐고, 회차 2와 3은 같은 PR을 골랐으나 관련 커밋 수(7 대 4)와 evidence 문장이 달랐다.

**온도 0이 결정론을 뜻하지 않는다.** Stage B의 입력이 Stage A보다 훨씬 크고(직렬화 158.7KB) 출력도
자유 문장을 포함하므로 흔들릴 여지가 더 크다. 그래도 온도를 고정할 이유는 남는다. 관측된 손해가
없고 Stage A에서 얻은 것이 뚜렷하다.

## 반영

- `llm-provider.ts`에 `STAGE_JUDGMENT_TEMPERATURE = 0`을 두고 `localSamplingOptions()`를
  `judgmentSamplingOptions()`로 바꿨다. 프로덕션은 항상 이 고정값을 보낸다.
- 로컬 전환에서만 `LLM_TEMPERATURE`로 갈아탈 수 있다. 프로덕션에서 환경변수로 온도를 흔들 수 있게
  두면 실측 조건과 실행 조건이 갈리고 그 차이가 로그에 남지 않는다.
- 첫 질문 생성에는 주지 않았다. 그 경로의 확정 근거가 기본 샘플링에서 나왔고, 판단이 아니라 문장을
  만드는 일이라 온도를 낮출 근거가 아직 없다.

## 재지 못한 것

- **Stage B의 온도 기본값 비교군이 없다.** 온도를 고정한 뒤에 쟀으므로 기본값에서 3회를 돌린 기록이
  없다. 온도 0의 흔들림이 기본값보다 작은지는 확인되지 않았다.
- **판단 품질은 여전히 사람이 봐야 한다.** 이 측정이 말하는 것은 재현성이고, 고른 다섯 개가 사용자에게
  유용한지는 다루지 않는다.
- **기여 항목이 있는 입력을 재지 않았다.** `contribution_match` 경로가 열리면 온도의 영향이 다를 수
  있다.
