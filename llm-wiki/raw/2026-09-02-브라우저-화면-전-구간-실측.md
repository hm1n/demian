# 브라우저 화면에서 전 구간을 통과시킨 실측

## 확정

**저장소 입력부터 첫 질문 스트리밍 완료까지 두 저장소 모두 브라우저에서 완주했다.** 콘솔 오류 0건,
페이지 오류 0건, API 응답 전부 200·204다. 그 과정에서 Stage A 진행 표시가 사실과 다르다는 것을
발견해 문구와 진행 바를 함께 고쳤다.

## 왜 했는가

직전 기록의 "재지 못한 것"이 **브라우저 클라이언트의 단일 요청 경로는 단위 테스트로만 확인했다**였다.
측정 스크립트는 `selectStageACandidates`를 직접 부르므로 `candidate-client.ts`의 요청 경로와 화면
상태 전이를 밟지 않는다. 청크 구조를 걷어낸 변경이 실제로 화면에서 무엇을 바꿨는지도 확인되지 않은
상태였다.

## 측정 조건

Playwright chromium 헤드리스, 뷰포트 1280×1400. `next dev`는 포트 3000이 다른 프로세스에 잡혀 있어
3003에서 떴다. 토큰은 폼의 GitHub token 입력에 넣어 `/api/auth/session`이 만드는 암호화 쿠키로 갔고,
스크립트는 화면의 `role="status"`·`role="alert"`·`data-empty-kind`를 폴링해 상태 전이를 기록했다.

## 결과 1. 단계별 소요

| 단계 | `hm1n/demian` | `andbread/Andbread_Frontend` |
| --- | --- | --- |
| 전체 커밋 | 257개 / 5.7초 | 444개 / 4.3초 |
| 커밋 상세 | 141개 / 123.6초 | 327개 / 290.5초 |
| 저장소 메타 | 1.6초 | 0.6초 |
| Stage A | 27묶음 / **6.3초** | 67묶음 / **5.4초** |
| Stage B | 28.3초 / 최종 후보 3개 | 29.2초 / 최종 후보 3개 |
| 첫 질문 스트리밍 | 2.5초 | 1.6초 |
| 전 구간 | **187초** | **332초** |

**시간의 대부분은 LLM이 아니라 GitHub다.** 커밋 상세 조회가 20커밋씩 한 요청으로 약 17.5초이고,
두 저장소 모두 전체의 66퍼센트와 87퍼센트를 차지한다. Stage A와 Stage B를 합쳐도 35초다.

두 저장소 다 묶음 수가 상한 200 아래라 요청은 각각 한 번이었다. 청크 구조를 걷어낸 뒤 단일 요청
경로가 화면에서 도는 것을 이것으로 확인했다.

## 결과 2. 화면에서 확인한 것

- 후보 목록의 제외 요약이 그려진다. `demian`에서 "Pull Request에 속하지 않아 제외한 커밋 2건"이
  나왔다.
- 후보 상세의 근거 절단 안내, 인용 파일 목록, "Repository로 확인할 수 없는 항목"이 모두 나온다.
- 첫 질문이 근거 안의 코드 심볼을 인용한다. `andbread`는 `e2e/fixtures/seed.ts`의 `insertUserRow`와
  재시도 10회를, `demian`은 `resolveChunkQuota`를 짚었다.

## 결과 3. 찾은 결함 — Stage A 진행 표시가 0에 멈춰 있었다

4단계 화면이 응답이 올 때까지 **"27개 중 0개를 판단했고 27개가 남았습니다"와 0퍼센트 진행 바를**
붙들고 있었다. `andbread`에서는 같은 문구가 5.4초, `demian`에서는 6.3초 동안 그대로였다.

원인은 청크 구조를 걷어낸 자리에 있다. 진행률은 청크가 끝날 때마다 보고하던 값이고, 요청이 하나가
되면서 중간에 보고할 지점이 사라졌다. `fetchStageACandidatesFromApi`의 `onProgress`는 응답을 받은
뒤 한 번만 불렸고(`completed`가 곧바로 `total`이 되어 다음 단계로 넘어간다), 그전까지 화면이 쥐고
있는 값은 호출 직전에 넣은 0이었다.

**세지 못하는 것을 세는 척했다.** 문구는 판단이 진행 중이라고 말하는데 숫자는 아무것도 진행되지
않았다고 말하고, 멈춘 진행 바는 요청이 죽은 것처럼 보인다.

고친 방향은 진행률을 흉내 내지 않는 것이다.

| 항목 | 이전 | 이후 |
| --- | --- | --- |
| 문구 | `27개 중 0개를 판단했고 27개가 남았습니다.` | `27개 묶음을 한 번의 요청으로 판단하고 있습니다. 중간 진행률은 알 수 없습니다.` |
| 진행 바 | `completed / total` (항상 0퍼센트) | 불확정 막대 |

몇 묶음을 보냈는지는 여전히 알린다. 그 수는 클라이언트가 `toStageAUnits`로 다시 구할 수 있고 선별을
통과한 실제 요청 크기라 사실이다. 알 수 없는 것은 그 안의 진행률뿐이다.

값이 죽었으므로 `StageAProgress` 타입, `fetchStageACandidatesFromApi`의 `onProgress` 인자,
`LoadingPhase`의 `stage_a` 갈래에 있던 `completed` 필드를 함께 지웠다. 2단계 커밋 상세 조회의
진행률은 요청이 여러 번이라 그대로 둔다.

## 검증

고친 뒤 같은 경로를 브라우저로 다시 통과시켰다. 4단계 화면이 `27개 묶음을 한 번의 요청으로 판단하고
있습니다`를 띄우고 Stage A 2.9초, Stage B 26.2초로 전 구간 148초에 완주했다. 단위 테스트 783건,
`tsc --noEmit`, `eslint` 모두 통과다. 회귀 테스트는 문구에 "판단했고"가 없다는 것까지 고정한다.

## 재지 못한 것

- **점수 기반 제외 문구를 화면에서 보지 못했다.** 두 저장소가 27묶음과 67묶음이라 상한 200에 닿지
  않아 "저장소가 커서 전체 N묶음 중 점수 상위 M묶음만 판단했습니다"가 뜨지 않는다. 여전히 단위
  테스트로만 확인된 문구다.
- **오류 화면을 밟지 않았다.** 두 회차 모두 실패 없이 통과해 `role="alert"` 경로가 그려지는 것을
  보지 못했다.
- **꼬리 질문이 없다.** 첫 질문이 도착한 뒤 사용자가 답하는 경로는 구현되지 않았다.
- **커밋 상세 조회 시간을 줄이려는 시도는 하지 않았다.** 전 구간의 대부분이지만 이 작업의 범위가
  아니다.
