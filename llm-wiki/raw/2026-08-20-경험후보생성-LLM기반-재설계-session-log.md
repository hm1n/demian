# 경험 후보 생성 LLM 기반 재설계 세션 로그

## 문서 목적

직전 세션에서 확정한 3축 점수 정규화·가중치(raw/2026-08-20-점수정규화-가중치-session-log.md)를 출근길 재고 끝에 뒤집은 논의를 보존한다. 이 문서는 그 결정을 대체한다.

## 논의 내용

### 문제 제기

모든 diff·commit을 규칙 기반으로 분류하는 로직 자체가 애초에 무리한 시도일 수 있다는 문제 제기가 있었다. 대안으로 사용자에게 저장소 소개와 본인이 한 기여(예: "푸시 알림 구현", "게시판 기능 구현")를 입력받고, 그 입력을 기준으로 LLM이 커밋을 분류하는 방식을 검토했다.

### 적용 범위 논의

기존 블랙리스트 필터(raw/2026-08-20-repository데이터조회-블랙리스트기준-session-log.md)와 3축 점수 스코어링을 완전히 대체할지, 블랙리스트는 두고 그 위에 LLM 분류만 얹을지 논의했다. 블랙리스트는 노이즈 커밋 제거용으로 여전히 유효해 유지하기로 했다(하이브리드).

### 기여 항목 입력 생략 가능 여부

사용자가 본인 기여를 기억 못 하거나, 아예 입력 없이 추천만 받고 싶은 경우를 위해 입력을 선택 사항으로 두기로 했다. 처음에는 입력 없을 때 기존 3축 점수 스코어링으로 폴백하는 안을 제안했다.

### 3축 점수 스코어링 자체에 대한 재검토

이 폴백안에 대해,애초에 3축 점수 스코어링 자체가 "LLM이 판단할 일을 숫자로 어설프게 흉내"낸 것 아니냐는 문제 제기가 있었다.

- 축 1(규모·복잡도)·축 2(의사결정 흔적)는 변경 줄 수·파일 수 같은 대리 지표일 뿐, LLM에 원본 데이터(메시지, stat, diff)를 그대로 주고 판단시키는 것보다 나을 이유가 없다.
- 축 3(채용 시장 관련성)은 애초에 고정 키워드 목록 내용도 정해지지 않은 상태였고, LLM이 자체 지식으로 "이력서·면접에 설명할 만한 경험"을 판단하면 별도 키워드 목록 없이도 같은 목적을 달성할 수 있다.
- 입력이 있는 경우(사용자 기여 항목 기준 LLM 분류)와 입력이 없는 경우(LLM이 스스로 판단) 모두 "LLM에 근거 데이터를 주고 직접 고르게 한다"는 같은 메커니즘으로 통일할 수 있어, 두 경로를 다르게 설계할 이유가 없다는 결론에 도달했다.

이로써 3축 가중합 점수 공식(raw/2026-08-20-점수정규화-가중치-session-log.md에서 확정했던 내용)은 폐기한다.

### 비용 구조 재확인

공식을 없애도 비용 구조 자체는 유지해야 한다는 점을 확인했다. 생존 커밋 수가 많은 저장소는 diff까지 포함해 한 번에 LLM에 전부 넣을 수 없다.

- 1차: 블랙리스트 통과 생존 커밋의 메시지 + stat(변경 줄 수·파일 수)만으로 LLM이 저렴하게 후보를 좁힌다.
- 2차: 좁혀진 후보만 diff를 조회해 LLM이 최종 대표 커밋과 근거를 정리한다.

이 2단계 구조(저렴한 1차 필터 → 비싼 2차 정밀 판단)는 공식 폐기와 무관하게 유지한다.

### 설계를 너무 타이트하게 잡지 않기

구현·실험 과정에서 바뀔 수 있는 세부값과, 구조적으로 확정해도 되는 부분을 분리해서 기록하기로 했다. 세부값(1차 필터링 후 후보 개수, 미분류 커밋 처리, 부분 입력 시 UX)은 확정하지 않고 "확인 필요"로 남긴다.

## 결정 사항 요약

- 기존 3축 가중합 점수 공식(축1·축2·축3, 가중치 0.4/0.4/0.2, min-max 정규화)은 폐기한다. raw/2026-08-20-점수정규화-가중치-session-log.md의 "결정 사항"은 이 문서로 대체된 것으로 본다.
- 블랙리스트 필터(Stage 1, 노이즈 커밋 제거)는 그대로 유지한다.
- 사용자가 저장소 입력 시 본인 기여 항목을 텍스트로 입력할 수 있게 한다. 입력은 선택 사항이며 생략 가능하다.
  - 입력 있음: 생존 커밋 메시지를 기여 항목 목록 기준으로 LLM이 분류. 매칭된 그룹 안에서만 diff 조회 후 대표 커밋·근거를 LLM이 정리.
  - 입력 없음: 점수 공식 대신, 생존 커밋의 메시지·stat을 LLM에 주고 대표 경험 후보를 직접 고르게 한다.
  - 일부만 입력: 입력한 항목은 위 "입력 있음" 경로로, 분류 안 되고 남은 생존 커밋은 "입력 없음" 경로로 보충해 두 트랙 후보를 함께 노출한다.
- 후보 선정 메커니즘은 입력 유무와 무관하게 "저렴한 메시지·stat 기반 1차 필터 → 비싼 diff 기반 2차 정밀 판단"이라는 2단계 비용 구조로 통일한다. 공식은 없어졌지만 이 구조는 유지한다.
- 다음 항목들은 지금 확정하지 않고 구현 후 실험으로 조정한다.
  - 1차 필터가 좁히는 후보 개수(추정치였던 10~20개는 근거 없는 값이라 확정 아님).
  - LLM이 "미분류"로 판단한 커밋의 처리 방식.
  - 일부 입력 시 두 트랙(라벨 매칭/자동 추천) 후보를 화면에 어떻게 합쳐 보여줄지.

## 후속 논의: PR 조회 순서 변경

파이프라인을 다이어그램으로 시각화한 뒤, "대표 커밋을 이미 LLM 최종 판단으로 정한 다음에 PR을 조회해 관련 커밋을 붙이는" 기존 순서에 대해 재검토했다.

### 검토한 대안

- **PR 조회 자체를 없애고 LLM이 관련 커밋을 추론하게 하는 안**: 기각. 시간 근접성+파일 겹침으로 관련 커밋을 추론하는 방식은 이미 raw/2026-08-19-연속작업지표-판별기준-session-log.md에서 체인 구조 문제로 폐기했다. LLM에게 같은 추론을 맡겨도 입력 데이터(메시지·시간)가 부실하면 똑같이 불안정하다. PR 조회는 LLM 호출이 아니라 GitHub API 호출이라 비용도 애초에 저렴해, 없애서 얻는 이득이 없고 품질만 잃는다.
- **PR 조회를 Stage 2 diff 조회와 함께 LLM 호출 이전에 미리 수행하는 안**: 채택. 기존 순서(대표 커밋 확정 → PR 조회)는 raw/2026-08-19-연속작업지표-판별기준-session-log.md에서 이미 지적된 한계, 즉 "그룹핑이 대표 커밋 선정 자체에는 영향을 주지 않는다"는 문제를 그대로 안고 있었다. PR 소속 정보를 diff와 함께 먼저 모아 LLM에 한 번에 주면, LLM이 대표 커밋을 고르는 단계에서부터 PR 맥락(같은 PR에 속한 다른 커밋)을 반영할 수 있어 이 한계가 해소된다. API 호출량은 Stage 2 대상 커밋 수만큼 그대로이고 순서만 바뀌므로 비용 증가는 없다.

### 결정 사항

- PR 조회는 대표 커밋 선정 이후의 별도 사후 단계가 아니라, Stage 2에서 diff 조회와 함께 수행하는 입력 수집 단계로 합친다.
- LLM 최종 판단 단계는 diff와 PR 소속 정보를 함께 받아, 대표 커밋 선정과 관련 커밋 근거 정리를 한 번의 판단으로 수행한다.
- 이로써 "그룹핑이 대표 커밋 선정에 영향을 주지 못한다"는 기존 한계는 해소된 것으로 본다.

## 확인 필요

- Feature 1(GitHub Repository 입력)에 "본인 기여 항목" 입력 필드를 추가해야 한다. 정확한 입력 형식(자유 텍스트/구조화 입력)은 미정.
- 기여 항목 텍스트와 실제 커밋 메시지가 의미적으로 겹치지 않는 경우(용어 차이) 대응 방식 미정.
- Feature 5(경험 선택)가 "사용자가 정의한 기여 항목" 단위 후보를 그대로 선택하는 구조로 바뀌는지 확인 필요.
- LLM 분류·판단 정확도는 실제 본인 Repository로 실행해 봐야 확인 가능하다(사용자가 출근 후 직접 테스트 예정).
