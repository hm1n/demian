# 연속 작업 지표 판별 기준 세션 로그

## 문서 목적

"Repository 데이터 조회 및 기본 분석" 기능의 확인 필요 항목 "여러 커밋에 걸친 연속 작업 지표의 계산 기준을 구현 단계에서 확정해야 합니다"와, "개발 경험 후보 생성" 기능의 확인 필요 항목 "관련 커밋을 찾는 연속 작업 지표의 구체적인 기준을 확정해야 합니다"를 함께 논의하고 결정한 내용을 보존한다. 두 항목이 가리키는 지표가 같기 때문에 하나의 논의로 다뤘다.

## 논의 내용

완전한 커밋 클러스터링은 이미 MVP 범위 밖으로 결정되어 있어, 대표 커밋에 부가 근거로 연결할 "인접한 관련 커밋"만 가볍게 판별하는 방법을 찾는 것이 목표였다.

### 검토한 신호 후보

- PR/이슈 연결: GitHub API `GET /repos/{owner}/{repo}/commits/{sha}/pulls`로 커밋이 속한 PR을 조회할 수 있다. 커밋 메시지에 이슈 번호를 적지 않아도, PR로 작업했다면 시간 간격과 무관하게 정확하게 같은 작업으로 묶을 수 있다.
- 커밋 메시지 이슈 번호 정규식 매칭: 처음에 대안으로 검토했으나, 이슈 번호를 커밋 메시지에 적지 않는 사용자에게는 전혀 작동하지 않아 폐기했다.
- 시간 근접성 + 파일 겹침(같은 작성자 + 시간 간격 임계값 이내 + 변경 파일 겹침): PR이 없는 커밋을 위한 대안으로 검토했다.

### 시간 근접성 + 파일 겹침 방식의 문제

이 방식을 "인접 커밋 순서대로 조건이 깨질 때까지 체인처럼 확장하는" 구조로 설계했는데, 다음 문제가 드러났다.

- 같은 목적의 작업이라도 일주일처럼 시간 간격이 벌어질 수 있는데, 체인 구조에서는 중간에 조건을 만족하지 않는 무관한 커밋이 하나만 껴 있어도 그 지점에서 확장이 끊겨 먼 커밋에 도달하지 못한다. 시간 임계값을 늘려도 이 구조적 문제는 해결되지 않는다.
- 체인 대신 대표 커밋 기준 앞뒤 일정 기간(예: 7일)을 구간으로 두고 그 안의 커밋을 개별적으로 검사하는 방식도 검토했으나, 이는 사실상 좁은 범위의 클러스터링을 다시 구현하는 것과 다르지 않고, 기간 값 자체도 검증되지 않은 임의의 수치를 쌓는 것이라는 지적이 있었다.

### 그룹핑의 실효성 재검토

관련 커밋 그룹핑이 실제로 결과에 얼마나 차이를 만드는지도 점검했다. "개발 경험 후보 생성" 기능은 점수 계산을 개별 커밋 단위로 먼저 수행하고, 상위 3개를 대표 커밋으로 선정한 뒤에야 관련 커밋을 연결한다. 즉 그룹핑은 어떤 커밋이 대표 커밋으로 뽑히는지에는 영향을 주지 않고, 이미 뽑힌 대표 커밋의 근거를 보강하는 역할만 한다.

기능 하나를 커밋 하나로 크게 끝낸 경우에는 애초에 연결할 인접 커밋이 없어 그룹핑이 아무 역할을 하지 못한다. 기능을 여러 커밋으로 잘게 나눠 작업한 경우에만 그룹핑이 근거의 맥락을 풍부하게 해주는 효과가 있다. 다만 이 경우에도 개별 커밋 점수가 낮아 애초에 대표 커밋으로 선정되지 못하는 문제는 그룹핑으로 해결되지 않는다는 한계가 확인됐다.

## 결정 사항 요약

- PR 단위 그룹핑은 유지한다. 대표 커밋이 속한 PR을 GitHub API로 조회해 같은 PR에 속한 다른 커밋을 관련 커밋으로 연결한다. PR 안에서는 커밋 간 시간 간격을 조건으로 두지 않는다.
- 시간 근접성과 파일 겹침을 이용한 fallback 규칙은 폐기한다. PR에 속하지 않은 커밋은 관련 커밋 그룹핑을 시도하지 않고 단일 커밋으로 그대로 분석한다.
- 커밋 메시지 이슈 번호 정규식 매칭 방식도 폐기한다.
- 그룹핑이 대표 커밋 선정 자체에는 영향을 주지 않는다는 점, 개별 커밋 점수가 낮아 대표 커밋으로 뽑히지 못하는 문제는 이 논의로 해결되지 않는다는 점을 확인했다. 이 문제는 별도 논의가 필요하다.

## 확인 필요

- 개별 커밋 점수가 낮아 대표 커밋으로 선정되지 못하는 문제, 즉 작게 쪼개서 커밋하는 습관이 점수 계산에서 불리하게 작용하는 문제를 어떻게 다룰지는 이번 논의에서 다루지 않았다.
- PR 조회 API 호출이 늘어나는 만큼 GitHub API 사용량이 실제로 어느 정도인지는 구현 후 확인이 필요하다.
