# Stage B 토큰 실측과 회당 비용 확정

## 확정

**상한을 채운 Stage B 입력은 47,861토큰이다.** 추정으로 쓰던 40,000보다 20퍼센트 많다. 출력은
891~1,400토큰으로 추정 3,000의 3분의 1 이하다. 두 값을 넣으면 Stage B 회당 비용이 0.01950달러에서
**0.01744달러**로 내려간다.

**Stage A 회당 비용은 0.00825달러에서 0.00282달러로 내려간다.** 추정이 입력 24,000토큰이었고 실측은
`hm1n/demian` 27묶음에서 5,500토큰이다. 약 3분의 1이다.

**전체 분석 한 번이 0.02182달러이므로 10달러로 458회다.** 이전 추정은 442회와 310회로 갈려 있었다.

이 측정에서 예상하지 않은 것이 하나 나왔다. **`gemini-3.1-flash-lite`는 Stage B에서 5회 모두 완전히
같은 결과를 내는데, 확정 모델 `gemini-3.5-flash-lite`는 5회에 서로 다른 후보 집합 3개를 낸다.**

## 왜 쟀는가

이슈 #70이 "Stage B 입력 토큰이 20,000인지 40,000인지 모른다"를 열어 두었고, 그 차이로 10달러 가능
횟수가 442회와 310회로 갈렸다. 이슈 #71은 "상한을 채운 Stage B 입력의 실제 토큰 수를 기록하고 회당
비용을 재계산한다"를 완료 조건으로 두었다. 둘 다 열려 있었다.

원인은 계측이 없었다는 것이다. 두 단계가 `generateObject`의 `usage`를 그대로 버렸다. Stage A는 한때
`usage.totalTokens`를 한도 회계에 썼으나 그 회계가 Groq 규약이라 걷어내면서 함께 사라졌다.

## 계측을 어디에 넣었는가

`createStageAGenerate`와 `createStageBGenerate`에 선택 인자 `onUsage`를 넣었다. 프로덕션은 넘기지
않고 측정 스크립트만 넘긴다.

**측정 스크립트가 `generateObject`를 따로 부르지 않는 것이 이 설계의 요점이다.** 호출을 한 벌 더
쓰면 상수 하나가 어긋나는 순간 재는 대상이 프로덕션이 아니게 된다. 이 프로젝트에서 이미 겪은 실패다
(Codex 리뷰 P2-3, 측정 스크립트가 묶음당 SHA 하나만 잘라 쓰던 문제).

로그에는 토큰 **개수**만 남는다. 프롬프트 본문과 응답 원문은 남기지 않는다.

## 측정 조건

`hm1n/demian`, 상세 조회 캐시로 5회 모두 같은 입력. `--skip-stage-a`로 Stage A 없이 묶음 전체를
후보로 넣었다. 그래야 patch 예산을 끝까지 채운다.

| 항목 | 값 |
| --- | --- |
| 펼친 커밋 | 30 / 상한 30 |
| PR 수 | 5 (최대 13커밋짜리 PR 포함) |
| patch 배정 | 후보 30개 전원, 굶은 후보 0 |
| patch 총량 | **정확히 60,000자** (`STAGE_B_MAX_TOTAL_PATCH_CHARS` 전량) |

**이것이 Stage B의 최악 입력이다.** patch 상한을 다 쓰고 커밋 상한도 다 썼다. 회당 비용의 상한을
재는 조건으로 맞다.

## 결과 1. Stage B 토큰과 지연

| 모델 | 입력 | 출력(중앙값) | 출력 범위 | 소요 중앙값 | 소요 최댓값 | 예산 55초 대비 |
| --- | --- | --- | --- | --- | --- | --- |
| **`gemini-3.5-flash-lite`** | **47,861** | 1,231 | 891~1,400 | 4,935ms | 5,318ms | 9.7% |
| `gemini-3.1-flash-lite` | **47,861** | 1,239 | **1,239 고정** | 4,794ms | 4,961ms | 9.0% |

입력 47,861토큰이 5회 모두, 두 모델 모두 같다. 입력은 우리가 만드는 것이라 흔들릴 자리가 없다.

`gemini-3.6-flash`(32.9초)와 `gemini-3.7-flash`(55초 초과 실패)는 다시 재지 않았다. 판정선 27.5초를
이미 넘겼고, 넘긴 후보는 원인을 확정하고 넘어간다는 제약이 있다.

## 결과 2. 확정 모델이 회차마다 다른 후보를 고른다

온도는 두 모델 모두 0이다. 그런데 결과가 갈린다.

| 모델 | 5회의 후보 집합 |
| --- | --- |
| `gemini-3.5-flash-lite` | **서로 다른 집합 3개.** {b7652e0, 4d3aa1b, 0d32908} 2회, {b7652e0, 5dfbde9, 903f0df} 2회, {b7652e0, 03b5cf2, 903f0df} 1회 |
| `gemini-3.1-flash-lite` | **5회 모두 같음.** {5d578d9, 8a6c253, 9a363f6}, 출력 토큰까지 1,239로 동일 |

`gemini-3.5-flash-lite`에서 5회 모두 살아남은 후보는 `b7652e0` 하나뿐이다. 근거 문장도 같은 후보에서
84자부터 162자까지 갈린다.

**온도 0이 결정론을 뜻하지 않는다는 것이 이 저장소에서 세 번째로 확인됐다.** 앞선 두 번은 3회
측정이어서 "3회 중 1회가 달랐다"까지였다. 5회로 늘리자 집합이 3개로 갈렸다.

이 사실이 모델 확정을 뒤집지는 않는다. `gemini-3.5-flash-lite`를 고른 근거는 인용 파일이 두세 배
많다는 것이었고(5~9개 대 2개) 그 측정은 유효하다. 다만 **맞바꾼 것이 무엇인지가 이제 분명하다.
인용 근거의 풍부함을 얻고 회차 재현성을 잃었다.** 사용자가 같은 저장소를 다시 분석하면 다른 후보가
나올 수 있다.

`gemini-3.1-flash-lite`가 결정론적인 이유는 재지 않았다. 사고 토큰 유무, 샘플링 구현, 모델 크기 어느
쪽인지 구분할 근거가 없다.

## 결과 3. Stage A 토큰

같은 계측으로 3회 쟀다. 세 회차 모두 입력 5,500, 출력 961로 같다.

| 항목 | 값 |
| --- | --- |
| 선별 입력 묶음 | 27 (제외 0) |
| 프롬프트 | 17,343바이트 |
| 입력 토큰 | **5,500** |
| 출력 토큰 | **961** |
| 바이트당 토큰 | 0.317 (3.15바이트에 1토큰) |
| 소요 | 3,094~3,252ms |

추정값 24,000/1,500은 전량 투입을 가정한 것이었고 실측의 4.4배다.

**단, 이 값은 저장소 크기에 비례한다.** 묶음 수 상한 200에서 프롬프트가 109,333바이트이므로 위
비율로 환산하면 입력 약 34,700토큰, 출력 약 7,100토큰이다. **이 두 값은 환산이고 실측이 아니다.**

## 결과 4. 회당 비용과 10달러 가능 횟수

단가는 백만 토큰당 달러다. `gemini-3.1-flash-lite` 0.25/1.50, `gemini-3.5-flash-lite` 0.30/2.50.

| 경로 | 입력 | 출력 | 회당 | 이전 값 | 근거 |
| --- | --- | --- | --- | --- | --- |
| Stage A (`demian` 27묶음) | 5,500 | 961 | **0.00282달러** | 0.00825달러 | 실측 |
| Stage A (상한 200묶음) | 34,700 | 7,100 | 0.01933달러 | — | 환산 |
| Stage B (상한 입력) | 47,861 | 1,231 | **0.01744달러** | 0.01950달러 | 실측 |
| 첫 질문 | 5,043 | 178~213 | 0.00157달러 | 0.00157달러 | 실측(2026-08-28) |

| 시나리오 | 회당 | 10달러 |
| --- | --- | --- |
| 전체 분석 (`demian` 규모) | 0.02182달러 | **458회** |
| 전체 분석 (Stage A가 상한 200묶음, 환산) | 0.03833달러 | 261회 |
| Stage B 단독 | 0.01744달러 | 573회 |

이전에 갈려 있던 442회와 310회 중 **낙관 쪽이 실제에 가까웠고, 실제는 그보다도 조금 낫다.** 입력이
추정보다 20퍼센트 많았지만 출력이 3분의 1이어서 상쇄됐고, Stage A 쪽 과대 추정이 컸다.

꼬리 질문은 이 계산에 없다. 경로가 구현되지 않았다.

## patch 총량 상한을 올릴 여지

`STAGE_B_MAX_TOTAL_PATCH_CHARS` 60,000자를 재산정할 여지가 열려 있었고(wiki 남은 조건 6번) 이제 두
축의 수치가 있다.

| 축 | 60,000자에서의 사용률 |
| --- | --- |
| 시간 예산 55초 | 9.7% |
| 모델 입력 컨텍스트 1,048,576토큰 | **4.6%** |
| 분당 입력 토큰 4,000,000 | 1.2% |

**어느 축도 벽이 아니다. 남은 제약은 비용이다.** patch를 두 배로 올리면 60,000자가 더 실린다. 이
분량이 몇 토큰인지는 재지 않았고, 바이트당 토큰 비율 3.15~4를 넣으면 15,000~19,000토큰이다. patch는
Stage A 프롬프트와 달리 코드라 이 환산의 오차가 클 수 있다. 그 범위에서 Stage B 회당이
0.0231~0.0243달러가 되고 전체 분석 10달러 가능 횟수가 458회에서 350~363회로 줄어든다.

올릴지는 근거를 더 싣는 것이 판단을 낫게 하는지에 달려 있고, 그것은 이 측정이 답하지 못한다.

## 재지 못한 것

- **저장소 하나로 쟀다.** `hm1n/demian`이다. Stage B 입력은 patch 상한이 걸려 저장소가 커도 47,861
  근처에서 멈출 것으로 보이지만 확인한 것은 아니다.
- **Stage A 상한 200묶음의 토큰은 환산이다.** 바이트당 토큰 비율이 묶음 수에 따라 일정하다는 가정이
  들어 있다.
- **`gemini-3.5-flash-lite`의 흔들림이 온도 때문인지 모른다.** 온도 기본값 1.0 비교군이 없다. 다만
  같은 온도 0에서 `gemini-3.1-flash-lite`가 결정론적이므로 온도만의 문제는 아니다.
- **꼬리 질문 비용을 계산할 수 없다.** 경로가 없다.
- **캐시 요금을 넣지 않았다.** 컨텍스트 캐싱을 쓰지 않는다.
