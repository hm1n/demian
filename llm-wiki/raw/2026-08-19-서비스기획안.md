# 서비스 기획안

## 문서 목적

이 프로젝트에서 제작하려는 서비스의 방향, 문제 정의, MVP 범위, 프론트엔드 기술 챌린지, 기술 스택, 진행 일정을 정리한 원본 기획안이다. AGENTS.md 지침과 wiki 문서의 근거 자료로 쓰인다.

## 서비스 개요

GitHub Repository의 코드와 변경 이력을 분석해 흩어져 있는 개발 경험 중 설명할 가치가 있는 것을 선별하고, 실제 코드 기반 AI 인터뷰를 통해 그 경험을 스스로 설명할 수 있도록 돕는 서비스.

### 문제 정의

개발 교육생은 프로젝트 과정에서 많은 문제를 해결하지만, 시간이 지나면 자신의 코드에서 어떤 경험이 설명할 가치가 있는지 선별하고 정리해 설명하기 어렵다.

## 핵심 가치

`Repository → 경험 선별 → 근거 확인 → AI Interview → 경험 구체화`

AI가 이력서를 대신 작성하거나 코드를 대신 설명하는 것이 아니라, 실제 Repository를 근거로 사용자가 자신의 경험을 선별하고 설명하도록 돕는다.

### 경험 선별하기

Repository의 코드, Commit 등 변경 이력을 분석해 설명할 가치가 있는 경험 후보를 제안한다. 각 경험은 AI의 주장만 보여주지 않고 관련 Commit, 파일, 코드 등의 근거를 함께 제시한다. Repository만으로 확인할 수 없는 사실은 구분한다.

예시: 관련 코드에서 Lazy Loading 적용은 확인되지만 실제 성능 개선 수치는 Repository만으로 확인할 수 없습니다.

### 인터뷰하기

발견된 경험 하나를 선택하면 해당 경험과 실제 코드를 기반으로 AI가 질문한다.

예시: `useAuth.ts`에서 인증 상태를 Context로 관리하셨는데요. 각 페이지에서 상태를 독립적으로 관리하지 않은 이유가 무엇인가요?

사용자의 답변을 바탕으로 꼬리 질문을 생성해 단순 암기가 아니라 기술 선택의 이유와 근거를 설명하도록 유도한다.

## MVP 범위

반드시 구현할 것:
- GitHub Repository 입력
- Repository 데이터 조회 및 기본 분석
- 개발 경험 후보 최대 3개 생성
- 경험 후보별 Repository 근거 표시
- 경험 선택
- 실제 코드 기반 AI 질문
- 사용자 답변
- 실시간 AI Streaming 응답
- 꼬리 질문
- Loading / Empty / Error 상태

## 프론트엔드 기술적 챌린지

### 핵심 챌린지

Vercel AI SDK 기반 실시간 AI Streaming 환경에서 Markdown과 Code Block이 포함된 긴 대화의 렌더링 성능과 스크롤 UX를 안정적으로 유지한다.

AI Interview의 메시지는 일반 채팅보다 무겁다.
- 실시간 Streaming 응답
- Markdown Parsing
- Syntax Highlighting
- Code Block
- Repository 관련 정보
- 긴 대화 누적

따라서 다음 문제를 실제로 재현하고 측정한다.

| 항목 | 확인 내용 | 검토 대상 / 예시 |
| --- | --- | --- |
| Streaming Rendering | 스트리밍 중 마지막 AI 메시지가 지속적으로 변경될 때 과거 메시지까지 불필요하게 다시 렌더링되는지 확인한다. | 컴포넌트 경계 분리, memoization, streaming state 분리 |
| Long Chat Rendering | 메시지가 계속 누적될 때 DOM 증가와 렌더링 비용을 측정한다. | Virtualization / Windowing, variable-height message 처리, viewport 밖 Code Block 렌더링 전략 |
| Code Rendering | Syntax Highlighting과 Markdown Parsing 비용을 측정한다. | Code Block Lazy Rendering, 결과 캐싱, 불필요한 re-highlight 방지 |
| Scroll UX | 스트리밍 중 자동 스크롤과 사용자의 수동 스크롤이 충돌하지 않도록 한다. | 사용자가 마지막 메시지를 보고 있으면 새 토큰에 맞춰 자동 스크롤, 사용자가 이전 대화를 읽고 있으면 강제로 아래로 이동하지 않음, 새 메시지 도착 표시 제공 가능성 검토 |

## 기술 스택

| 영역 | 기술 | 목적 |
| --- | --- | --- |
| Frontend | React + TypeScript + Vite | UI 및 컴포넌트 구현 |
| Server State | TanStack Query | Repository 분석 결과 및 API 상태 관리 |
| AI Streaming | Vercel AI SDK | `streamText`, `useChat` 기반 AI 응답 Streaming 및 채팅 상태 관리 |
| Markdown | react-markdown | AI 응답 렌더링 |
| Code Highlight | Shiki 또는 Prism | Repository 코드 표시 |
| Virtualization | TanStack Virtual | 긴 대화 렌더링 최적화 |
| Repository | GitHub API | Repository, Commit, Code 데이터 조회 |
| Performance | React Profiler / Chrome DevTools / Lighthouse | 병목 분석 및 개선 전후 검증 |
| Test | Playwright | 핵심 사용자 흐름 및 실패 상황 검증 |

## 5일 진행 계획

| Day | 목표 | 작업 내용 |
| --- | --- | --- |
| Day 1 | 문제 검증 + 기본 흐름 | 교육생 4~5명 사전 인터뷰, 인터뷰 결과로 문제 정의 및 핵심 기능 우선순위 확정, Repository 입력 및 GitHub 데이터 조회, AI SDK Repository 구조와 `useChat` 진입점 확인 |
| Day 2 | 핵심 제품 흐름 | 경험 후보 생성, 경험 선택, AI Interview Happy Path 구현, Streaming UI 구현, `useChat → Transport` 흐름 코드 리딩 |
| Day 3 | 성능 실험 | 10 / 100 / 300 message Mock Data 구성, Baseline 측정, React Profiler / Performance Panel로 병목 확인, 측정 결과에 따라 필요한 최적화만 적용, `streamText → Provider` 흐름 코드 리딩 |
| Day 4 | 안정성 및 UX | Loading / Empty / Error, Streaming 실패 및 Retry, Scroll UX, 실제 Repository 여러 건으로 검증, AI SDK에서 발견한 설계 패턴과 현재 프로젝트 구조 비교 |
| Day 5 | 재측정 및 문서화 | 동일 조건으로 성능 재측정, 개선 전후 수치 정리, E2E 검증, 설계 선택 및 Trade-off 정리, AI SDK 코드 리딩 회고 정리 |
