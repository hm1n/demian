# Repository 데이터 조회 및 기본 분석 기능 블랙리스트 판별 기준 세션 로그

## 문서 목적

"Repository 데이터 조회 및 기본 분석" 기능 정의서의 확인 필요 항목 중 "제외할 커밋을 판별하는 블랙리스트 단어와 규칙을 최종 확정해야 합니다" 항목을 논의하고 결정한 내용을 보존한다.

## 논의 내용

기존 정의서에는 병합 커밋, 오타 수정 커밋, 포맷팅이나 린트만 적용한 커밋, 의존성 버전만 올린 커밋, 문서만 수정한 커밋을 제외한다는 원칙만 있고 구체적인 판별 규칙은 없었다. 판별 방식을 두 갈래로 나눠 정리했다.

구조적으로 판별 가능한 항목은 커밋 메시지 키워드에 의존하지 않고 메타데이터나 파일 경로로 판별하는 것이 오탐이 적다고 보았다.

- 병합 커밋은 커밋의 부모(parent) 수가 2개 이상인지로 판별한다.
- 문서만 수정한 커밋은 변경 파일 전체가 `*.md`, `*.mdx`, `docs/` 경로, `README*`에 해당하는지로 판별한다.
- 의존성 버전만 올린 커밋은 변경 파일 전체가 `package.json`, `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `requirements.txt`, `poetry.lock`, `Gemfile.lock`, `go.mod`, `go.sum`, `Cargo.lock` 같은 lock 파일이나 매니페스트 파일뿐인지로 판별한다.

나머지 두 항목은 구조적 판별이 어려워 커밋 메시지 키워드로 판별하기로 했다.

- 오타 수정 커밋은 메시지에 `typo`, `오타`, `오탈자`, `misspell` 키워드가 있는지로 판별한다.
- 포맷팅이나 린트만 적용한 커밋은 메시지에 `format`, `lint`, `eslint`, `prettier`, `style`, `포맷`, `린트`, `정렬` 키워드가 있는지로 판별한다.

diff가 공백 변경뿐인지 직접 비교하는 방식도 논의했으나 구현 복잡도가 높아 1차 버전에서는 채택하지 않고, 키워드 판별만으로 우선 처리한 뒤 필요하면 나중에 보강하기로 했다.

판별 순서는 오탐 가능성이 낮은 구조적 판별을 먼저 적용하고, 그다음 키워드 판별을 적용하는 순서로 정했다. 병합 → 문서 → 의존성 → 오타 → 포맷팅 순서다.

## 결정 사항 요약

- 병합 커밋, 문서만 수정한 커밋, 의존성 버전만 올린 커밋은 커밋 메타데이터와 변경 파일 경로로 판별한다.
- 오타 수정 커밋과 포맷팅이나 린트만 적용한 커밋은 커밋 메시지 키워드로 판별한다.
- 판별 순서는 병합, 문서, 의존성, 오타, 포맷팅 순으로 적용한다.
- diff 기반 공백 변경 판별은 1차 버전에 포함하지 않는다.

## 확인 필요

- 키워드 목록은 1차 판별 기준이며 실제 커밋 데이터로 검증한 뒤 추가하거나 조정할 수 있다.

## 후속 논의: Stage 1/Stage 2 역할 재정리와 판별 방식 재검토

### 정정 사항

위 "결정 사항 요약"에서 문서/의존성 판별을 병합 판별과 같은 층위의 "구조적 판별"로 묶었는데, 이는 부정확했다. GitHub REST API 기준으로 커밋 목록 조회(Stage 1)에는 부모 커밋 수와 메시지만 포함되고 변경 파일 목록은 포함되지 않는다. 변경 파일 목록은 커밋 단건 상세 조회(Stage 2)에만 있다. 따라서 문서/의존성을 파일 경로로 판별하려면 Stage 2 호출이 이미 발생한 뒤에만 가능하며, Stage 2 호출 자체를 막는 진짜 Stage 1 필터는 병합, 오타, 포맷팅 3개뿐이었다.

### 추가 논의

의존성 변경은 새로운 기술 스택이나 라이브러리를 도입한 흔적일 수 있어 핵심 개발 경험 소재가 될 수 있다는 지적이 있었다. 파일 경로 기반으로 의존성 변경 커밋을 전부 제외하면 이런 경험을 놓칠 위험이 있다. 문서 변경도 같은 이유로 같은 수준으로 다루기로 했다.

### 최종 결정

- 문서만 수정한 커밋과 의존성 버전만 올린 커밋을 Stage 2 파일 경로로 판별하는 방식은 보류한다.
- 두 항목도 오타, 포맷팅과 동일하게 Stage 1 커밋 메시지 키워드로 판별한다.
- 문서 판별 키워드: `docs`, `documentation`, `문서`, `readme`, `README`.
- 의존성 판별 키워드: `bump`, `deps`, `dependency`, `dependencies`, `의존성`, `패키지`, `버전 업`, `upgrade`.
- Stage 2 파일 경로 기반 판별은 지금 도입하지 않는다. 실제 구현 후 토큰 비용을 측정했을 때 Stage 1 키워드 판별만으로 비용 절감이 부족하다고 확인되면 그때 도입을 검토한다.
- 이전에 논의했던 "살아남은 커밋 안에서도 lock파일·문서 파일 diff는 항상 잘라낸다"는 결정은 Stage 2 파일 정보 없이는 적용할 수 없으므로 함께 보류한다. Stage 2를 도입하는 시점에 다시 검토한다.

### 키워드 보강

문서/의존성을 Stage 1 키워드로 전환하면서 5개 카테고리 전체 키워드를 다시 정리했다. Conventional Commit 접두사와 Dependabot/Renovate 자동 커밋 패턴도 함께 포함했다.

- 오타: `typo`, `typos`, `misspell`, `misspelling`, `spelling`, `오타`, `오탈자`, `오타수정`, `맞춤법`. Conventional 접두사 `fix(typo):`.
- 포맷팅/린트: `format`, `formatting`, `lint`, `linting`, `eslint`, `prettier`, `style`, `styling`, `whitespace`, `indent`, `indentation`, `semi`, `포맷`, `포맷팅`, `린트`, `정렬`, `들여쓰기`, `공백정리`. Conventional 접두사 `style:`, `chore(lint):`, `chore(format):`.
- 문서: `docs`, `documentation`, `readme`, `changelog`, `문서`, `리드미`. Conventional 접두사 `docs:`. `comment`/`주석`은 포함하지 않는다. 코드 리팩토링과 함께 주석을 고치는 경우가 많아 오탐 위험이 크기 때문이다.
- 의존성: `bump`, `deps`, `dependency`, `dependencies`, `upgrade`, `version bump`, `의존성`, `패키지`, `버전업`, `버전 업그레이드`. Conventional 접두사 `chore(deps):`, `build(deps):`, `chore(deps-dev):`. Dependabot/Renovate가 남기는 자동 커밋 메시지 패턴 `^Bump .+ from .+ to .+`도 정규식으로 추가한다. 이 패턴은 오탐 가능성이 거의 없는 강한 신호다.

다음 단어는 의도적으로 제외했다. `update`, `정리`, `개선`, `수정`은 일반 기능 커밋 메시지에도 흔히 쓰여서 포함하면 유의미한 커밋까지 과다하게 제외될 위험이 크다.

### 확인 필요 (갱신)

- 오타, 포맷팅 키워드와 마찬가지로 문서, 의존성 키워드도 1차 기준이며 실제 커밋 데이터로 검증한 뒤 조정한다.
- Stage 2 파일 경로 기반 판별을 도입할 토큰 비용 임계치가 아직 없다.
- Stage 2 도입 전까지는 의존성/문서 성격의 커밋이 후보 점수 계산에 그대로 포함되므로, 이런 커밋이 점수에서 과대평가되지 않는지는 아직 확인하지 않았다.
