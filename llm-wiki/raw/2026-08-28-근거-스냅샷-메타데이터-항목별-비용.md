# 근거 스냅샷 메타데이터의 항목별 비용

## 문서 목적

첫 질문 실측에서 patch 몫이 168바이트로 굶는 것을 확인했다. 상한을 올리는 것과 별개로 메타데이터를
줄여야 하므로, **어느 항목이 예산을 얼마나 먹는지 실측**했다. 항목을 추측으로 고르면 효과가 없는 곳을
줄이게 된다.

## 측정 방법

계측 스크립트에 `--metadata-breakdown`을 넣었다. LLM을 호출하지 않는다. 예산이 JSON 직렬화 바이트로
걸리므로(`evidence-snapshot.ts:296`) 각 항목도 같은 방식으로 `JSON.stringify` 바이트로 쟀다. 내용은
출력하지 않고 바이트와 추정 토큰만 냈다.

## 판정 1. 파일 목록이 최대 항목이다

PR #61에서 파일 27개의 메타데이터가 4,835바이트로 **전체의 46.6%**다. 파일 하나당 179바이트다.
patch 본문 240바이트의 **20배**를 patch 없는 파일 정보에 쓴다.

한 파일의 직렬화는 이런 모양이다.

```
{"path":"...","status":"modified","additions":12,"deletions":3,"changes":15,
 "patch":null,"patchTruncated":true,"patchOmittedReason":"budget_exhausted"}
```

키 이름만 약 90바이트다. 경로가 `src/features/experience-candidates/...`처럼 길어 나머지를 채운다.

## 판정 2. 커밋마다 같은 문장을 반복한다

`커밋 verifiability`가 6커밋에 1,215바이트, 커밋당 202바이트다. `commitVerifiability(role, indexed)`가
같은 role·indexed 조합에 **같은 문장**을 낸다. 즉 6커밋 가운데 5개가 중복이다.

`커밋 pullRequests` 1,008바이트도 같다. PR #61의 커밋 6개는 **모두 같은 Pull Request 하나에 속한다.**
번호·제목·상태·base·head를 6번 반복해 싣는다.

`커밋 title`과 `커밋 message`가 369바이트로 정확히 같다. 이 저장소 커밋은 본문이 없어 `message`가
`title`과 동일하다. 즉 369바이트가 통째로 중복이다. 다른 저장소에서는 다를 수 있다.

## 판정 3. 프롬프트에 실리지 않는 항목이 예산을 먹는다

`renderInterviewEvidencePrompt`(`question-prompt.ts:117`)가 읽는 것은 `candidateSha`,
`representativeCommit`, `relatedCommits`, `evidence`, `citedFilePaths`, `unverifiableItems`,
`patchBudget.truncatedByBudget`뿐이다. 다음은 예산에 세면서 모델에게 가지 않는다.

| 항목 | 바이트 (PR #61) | 근거 |
| --- | --- | --- |
| `source` | `candidateSha·source·origin` 117의 일부 | 렌더러가 읽지 않는다 |
| `origin` | 같음 | 렌더러가 읽지 않는다 |
| `files[].changes` | 27파일 × 약 13바이트 = 약 350 | `renderFile`은 status·additions·deletions만 쓴다 |
| `patchBudget`의 수치 4개 | 107의 대부분 | `truncatedByBudget` 불리언 하나만 문장이 된다 |

## 판정 4. 렌더된 프롬프트는 JSON보다 6%만 작다

PR #61의 JSON 직렬화가 10,376바이트, 실제 프롬프트가 9,711바이트다. 키와 따옴표가 빠지는 만큼을
**반복 안내 문장이 되메운다.** `patch 본문이 근거 상한 때문에 실리지 않았습니다.`가 27번 나오며
약 48바이트 × 27 = 약 1,296바이트다. 예산 계산과 실제 크기가 크게 다르지 않으므로, 예산 항목을 줄이면
실제 프롬프트도 같이 줄어든다.

## 판정 5. 줄일 수 있는 총량이 약 2,900바이트다

PR #61 기준 추정이다.

+5,250~10,500바이트가 더해져 **약 8,300~13,600바이트**가 된다.

## 확인하지 못한 것

1. **꼬리 질문의 턴당 실제 토큰 소비를 재지 않았다.** 상한을 얼마까지 올려도 되는지의 근거다.
2. **파일 수 상한을 검토하지 않았다.** PR #61은 파일 27개다. 파일을 줄이는 것이 항목을 줄이는 것보다
   효과가 클 수 있으나 어느 파일을 버릴지 판단 기준이 없다.
3. **`message` 생략의 일반성.** 이 저장소는 커밋 본문이 없다. 본문이 있는 저장소에서는 절감이 없다.
4. **줄인 뒤 질문 품질이 실제로 오르는지 재지 않았다.** 반영 후 같은 여섯 경로를 다시 재야 한다.

# 추가 확인 (같은 날, 간소화 계획 수립 중)

## 판정 6. JSON 직렬화가 프롬프트의 상한이 아니다

`question-prompt.ts:110`이 "이 함수의 결과는 키와 따옴표가 빠져 그보다 작으므로 상한을 다시 넘기지
않습니다"라고 적어 두었다. **실측이 이를 반증한다.**

| PR | JSON 직렬화 | 실제 프롬프트 | 차이 |
| --- | --- | --- | --- |
| #61 (patch 240바이트) | 10,376 | 9,711 | 프롬프트가 665 작다 |
| #51 (patch 4,872바이트) | 10,436 | **10,632** | **프롬프트가 196 크다** |

patch가 클 때 뒤집힌다. 렌더러가 붙이는 것이 키·따옴표보다 크기 때문이다. 커밋마다 확인 수준 문장,
`변경 파일 N개:`, 파일마다 ```` ```diff ```` 울타리와 절단 안내가 붙는다. 즉 **근거 입력 상한 3,500토큰은
지금 보증되지 않는다.** 최적화가 아니라 계약 문제다.

## 판정 7. `source`와 `origin`은 제거 대상이 아니다

앞 절에서 "프롬프트에 실리지 않으므로 없어도 된다"고 분류했으나 **틀렸다.**
`isExperienceEvidenceSnapshot`(`question-request.ts:115`)이 둘을 검증한다.

```ts
if (value.source !== "contribution_match" && value.source !== "automatic_recommendation") return false;
if (value.origin !== "repository") return false;
```

이 route는 스냅샷을 다시 조립하지 않고 그대로 프롬프트에 싣는다. 두 필드는 그 전에 값의 출처 축을
확인하는 가드다. 합쳐 약 80바이트를 아끼려고 가드를 없앨 이유가 없다. **유지한다.**

`files[].changes`(약 350바이트)와 `patchBudget`의 수치 4개도 마찬가지로 제거하지 않는다. 아래 조치 1을
하면 예산에서 자동으로 빠지므로, 와이어 계약과 검증기와 테스트를 건드릴 필요가 없다.

# 간소화 계획

## 조치 1. 예산을 렌더된 프롬프트로 잰다 (가장 먼저)

`buildExperienceEvidenceSnapshot`은 지금 patch 없는 스냅샷을 **JSON으로 직렬화해** 메타데이터 크기를
잰다(`evidence-snapshot.ts:312`). 이것을 **렌더된 프롬프트 문자열로** 재도록 바꾼다. 이미 있는
"patch 없이 먼저 조립해 재는" 방식은 그대로 쓴다.

- 얻는 것: JSON에만 있는 것이 전부 예산에서 빠진다. 키 이름, 따옴표, `changes`, `patchBudget` 수치,
  `source`, `origin`이다. PR #61 기준 약 665바이트다.
- 함께 닫히는 것: 판정 6의 계약 위반이다. 재는 대상과 실제 입력이 같아진다.
- 배선 문제: `evidence-snapshot.ts`가 `question-prompt.ts`를 부르면 의존이 역류한다. 지금
  `question-prompt.ts`가 `experience-candidates`를 import한다. **렌더 함수를 인자로 주입한다.**
  기본값을 두면 호출부는 그대로다.
- 건드리지 않는 것: 와이어 계약, `question-request.ts` 검증기, 스냅샷 타입이다.

## 조치 2. 렌더러의 중복 네 곳을 없앤다

조치 1을 한 뒤에는 렌더 절감이 곧 patch 몫이 된다.

| 대상 | 지금 | 바꿀 형태 | PR #61 절감 |
| --- | --- | --- | --- |
| 커밋 확인 수준 문장 | 커밋마다 202바이트 문장. `commitVerifiability`가 세 상수 중 하나를 낸다 | 문서 앞에 세 문장을 **범례로 한 번** 두고, 커밋에는 `[대표 커밋]`·`[관련 커밋 · AI가 고른 값]` 라벨만 | 약 1,000 |
| Pull Request 정보 | 커밋 6개가 같은 PR 하나에 속하는데 6번 반복 | 같은 PR을 **한 번만** 적고 커밋에는 번호만 | 약 840 |
| 커밋 `message` | `title`과 같은 문자열을 다시 싣는다 | `message === title`이면 생략 | 369 |
| patch 부재 안내 | `patch 본문이 근거 상한 때문에 실리지 않았습니다.`가 파일마다. 27번 | 파일 목록 뒤에 **한 번** 묶어 적는다 | 약 1,200 |

**절단과 부재의 구분을 잃지 않는다.** 묶어 적을 때도 `budget_exhausted`와 `not_provided`를 나눈다.
둘을 하나로 뭉갠 것이 이슈 #46 재검증 P2였다.

## 조치 3. 상한을 1.5~2배로 올린다

`EVIDENCE_SNAPSHOT_MAX_INPUT_TOKENS` 3,500을 **5,250~7,000**으로 올린다. 이 값의 근거는 Groq 무료
등급 분당 8,000토큰이었고(`evidence-snapshot.ts:20`) Gemini 유료로 옮기면 그 제약이 사라진다.
`EVIDENCE_SNAPSHOT_BYTES_PER_TOKEN` 3은 **그대로 둔다.** 실측 3.39~3.67보다 보수적인 값이고, 상한을
올리는 것과 추정을 느슨하게 하는 것을 같은 변경에 섞지 않는다.

## 조치 4 (보류). 파일 수에 상한을 건다

커밋 수가 같은 PR #61(파일 27개)과 #48(파일 18개)의 metadataTokens가 3,444와 2,922로 522 갈렸다.
**파일 수가 항목 종류보다 영향이 크다.** 다만 어느 파일을 버릴지 정하는 기준이 없다.
`citedFilePaths`에 있는 경로를 앞에 두고 변경량 순으로 자르는 방법이 후보이나, 이는 Stage B의 선택을
그대로 신뢰하는 것이므로 조치 1~3의 효과를 먼저 재고 판단한다.

## 반영 후 검증할 것

1. 같은 여섯 경로(Gemini 3종·DeepInfra 2종·Groq 1종)를 PR #61과 #51로 다시 잰다. 비교 기준은
   **patch 몫, 첫 청크 지연, 코드 식별자를 짚은 질문인지**다.
2. **렌더된 프롬프트가 상한을 넘지 않는지 회귀 테스트로 고정한다.** 판정 6이 재발하지 않게 한다.
3. 절단과 부재를 묶어 적은 뒤에도 구분이 남는지 테스트한다.
4. PR #56·#67·#57이 `evidence_input_too_large`를 벗어나는지 확인한다. 조치 1+2+3이면 벗어날 것으로
   보이나 재지 않았다.
