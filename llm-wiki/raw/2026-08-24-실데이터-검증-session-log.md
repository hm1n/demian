# 실데이터 검증 session log

이슈 #19 작업 기록입니다. 확정값과 측정 수치는 `wiki/2026-08-24-실데이터-검증-배치-상한-확정.md`에
있고, 이 문서는 측정 중 관찰한 이상 징후와 후속 과제를 남깁니다.

## 측정 전에 깨져 있던 것

측정을 시작하자마자 Stage A가 404로 실패했습니다. 계약 문서가 "`llama-3.3-70b-versatile` 모델과
`GROQ_API_KEY` 환경 변수 조합은 실데이터 검증 전에 확정해야 합니다"로 남겨둔 항목이 실제로 깨져
있었던 것입니다. Groq 모델 목록을 조회하니 이 ID가 없었습니다.

여기서 얻은 교훈은 **고정 모델 ID는 재현성을 주지만 유효성을 주지 않는다**는 점입니다. 이동하는
별칭을 피한 결정 자체는 유지할 만하지만, 고정한 ID가 여전히 서빙되는지 확인하는 절차가 없으면
조용히 깨진 상태로 남습니다. 모델 ID를 바꿀 때 모델 목록 조회로 존재를 확인하는 것을 습관으로
삼아야 합니다.

## 실제 병목은 예상과 달랐다

계약 문서의 "확인 필요"는 요청 본문 4.5MB와 60초 시한을 걱정했습니다. 둘 다 병목이 아니었습니다.

- Stage A 입력 63커밋은 46.0KB로 4.5MB의 1.00%였습니다.
- Stage A 성공 호출은 3.1~11.1초로 55초 예산의 20% 이하였습니다.

실제 병목은 **LLM provider의 분당 토큰 한도**였습니다. Groq 무료 등급 8,000 TPM에서 입력 25커밋이
8,995 토큰으로 거부됐습니다. 우리가 통제하는 상수(본문 크기, 시한)를 검증하려다 우리가 통제하지
않는 외부 한도가 먼저 걸리는 것을 발견한 셈입니다.

추측성 최적화를 하지 않는다는 작업 원칙이 여기서 값을 했습니다. 60초 예산을 미리 최적화했다면
엉뚱한 곳을 고쳤을 것입니다.

## Vercel Hobby 상한이 60초가 아니었다

공식 문서 두 곳 모두 Hobby를 기본 300초·최대 300초로 표기합니다. 코드 전체가 60초를 전제로
설계돼 있었지만 그것은 플랫폼 제약이 아니었습니다.

값을 올리지 않고 **의도적 UX 제약으로 재해석해 문서에 명시**하는 쪽을 택했습니다. 측정된 실제
소요가 60초 안에 충분히 들어오고, 후보 생성을 수 분간 기다리는 흐름은 받아들이기 어렵기 때문입니다.
플랫폼 상한을 근거로 적은 주석과 문서를 전부 정정했습니다.

여기서 얻은 교훈은 **플랫폼 상한을 근거로 상수를 정할 때 확인일과 출처를 함께 남겨야 한다**는
점입니다. 상한은 바뀌고, 근거가 없으면 나중에 그 값이 제약인지 선택인지 구분할 수 없습니다.

## LLM 계약이 입력 크기에 비례해 깨진다

Stage A의 "입력 SHA를 정확히 한 번씩 반환" 계약은 입력 8·12개에서는 지켜졌지만 18개에서는
9/18, 4/18만 응답했습니다. 같은 조건에서 `openai/gpt-oss-20b`는 8개 입력에도 1/8만 응답했습니다.

이 계약은 출력 크기를 입력 크기에 선형으로 묶습니다. 후보만 반환하는 것이 아니라 미분류까지 전부
반환해야 하므로, 입력이 커질수록 모델이 끝까지 열거하지 못할 확률이 올라갑니다. 계약을 유지하려면
입력을 작게 유지해야 하고, 입력을 크게 하려면 계약을 바꿔야 합니다. 둘 중 하나를 골라야 합니다.

실패 모드도 나빴습니다. 모델이 절반만 응답하면 `schema_validation`으로 전체 거부되므로 사용자는
"스키마가 안 맞는다"는 안내만 받습니다. 실제 원인인 "입력이 너무 많다"는 드러나지 않습니다.

## 같은 입력에 다른 답이 나온다

같은 8커밋 입력에 대해 후보 수가 5개와 8개로 갈렸고, 같은 커밋 `6776c8e`이 실행에 따라
`automatic_recommendation`과 `contribution_match`로 분류됐습니다. 고정 모델 ID로 재현성을
확보했다고 생각했지만 모델 자체가 비결정적입니다.

`source`의 권위를 서버(Stage A)에 두기로 한 기존 결정이 이 불안정성 위에 서 있다는 점을 기록해
둡니다. Stage A가 흔들리면 Stage B가 교정할 기준값도 흔들립니다.

## diff 예산이 후보 절반을 굶긴다

가장 뚜렷한 결함입니다. `buildStageBPayload`가 커밋 순서대로 60,000자를 소비하므로 후보 20개
중 앞쪽 9개가 예산을 다 쓰고 뒤쪽 11개는 patch를 한 글자도 받지 못합니다.

```
순서별 배정 문자: 0:3618 1:2281 2:836 3:16936 4:8722 5:4895 6:2112 7:8000 8:12600
                 9:0 10:0 11:0 12:0 13:0 14:0 15:0 16:0 17:0 18:0 19:0
```

인덱스 3이 혼자 16,936자를, 8이 12,600자를 가져갑니다. 큰 커밋 몇 개가 예산을 독식하는 구조입니다.

프롬프트는 "실제 diff와 PR 소속만 근거로" 고르라고 지시합니다. 후보 절반 이상에 diff가 없는데도
그 지시를 주면, 모델은 diff가 있는 앞쪽에서 고를 수밖에 없습니다. 선정이 입력 순서에 편향됩니다.

`patchTruncated` 표시로 "전체를 본 것으로 단정하지 말라"고 안내하는 기존 설계는 절단된 파일에는
동작하지만, **patch가 아예 없는 파일에는 절단 표시조차 붙지 않습니다.** 모델은 그 후보에 diff가
원래 없는 것인지 예산 때문에 빠진 것인지 구분할 수 없습니다.

상한값을 바꾸는 것으로는 해결되지 않아서 이 이슈에서 고치지 않고 후속 과제로 분리했습니다.
배분 방식 변경은 출력 계약과 기존 테스트에 영향이 있습니다.

## 잘 동작한 것

Stage B의 PR 소속 계약은 완벽했습니다. 성공한 실행의 최종 후보 3개에 딸린 관련 커밋 6개가 모두
대표 커밋과 같은 PR이었습니다. "관련 커밋은 같은 PR에 속한 입력 SHA만" 제약을 서버가 검증하고
모델도 지켰습니다. 근거를 Repository 사실로 직접 검증하는 설계가 값을 한 지점입니다.

블랙리스트 필터도 잘 동작했습니다. `demian` 116커밋 중 53개(46%)를 걸러 상세 조회 대상을 63개로
줄였습니다. 다만 `Algorithm`에서는 435개 중 0개를 걸렀습니다. 저장소 성격에 따라 필터가 전혀
동작하지 않을 수 있다는 뜻이고, 그 경우 상세 조회가 순차로 약 6분이 걸립니다.

## 부수 관측

**`/rate_limit` 엔드포인트는 캐시된 값을 준다.** 응답 헤더가 `x-ratelimit-remaining: 4762`를
가리키는 시점에 `/rate_limit`은 4996을 반환했습니다. 처음에는 측정 코드 버그로 의심했지만
엔드포인트 쪽이었습니다. 소비량 판단은 각 응답의 `x-ratelimit-used` 헤더로만 해야 합니다.
rate limit 처리 코드가 이 엔드포인트를 신뢰하지 않는지 확인이 필요합니다.

**Groq는 토큰 한도 초과를 413으로 반환한다.** 429가 아니라 413 `rate_limit_exceeded`입니다.
두 단계의 `mapLlmError`에 413이 없어 한도 초과가 일반 실패(`llm_failure`, 502)로 분류되고
있었습니다. AGENTS.md의 "처리하지 않은 상태 코드가 있으면 지적한다" 규칙에 해당하는 누락이라
이 이슈에서 함께 고치고 회귀 테스트를 추가했습니다.

**재시도가 예산을 먹는다.** Stage B 모델의 일시적 과부하 실패에서 AI SDK 기본 재시도 3회가
20~46초를 소비했습니다. 55초 예산의 절반 이상입니다. `STAGE_B_TOTAL_BUDGET_MS`를 줄일 수 없는
실질적인 이유가 여기 있고, 동시에 재시도 정책을 우리가 정해야 할 이유도 됩니다.

**3000 파일 커밋 하나가 요청 11회를 쓴다.** `changedFiles`가 3000에서 포화하는 커밋은 상세 조회
페이지네이션에 10페이지가 필요합니다. `commitDetails: 20` 배치가 전부 그런 커밋이면 요청 220회와
약 166초가 되어 어떤 예산에도 들어가지 않습니다. 측정 대상 저장소에는 없었지만 상한 없는 구조라는
점은 기록해 둡니다.

## 후속 과제

- Stage A 입력 커밋 수 상한과 청크 분할, 분할 결과의 병합·재판단 정책. 현실적인 저장소에서 Stage A가
  완주하려면 필요합니다.
- Stage A 입력 초과 실패를 `schema_validation`이 아니라 원인이 드러나는 오류로 구분.
- Stage B patch 예산의 후보별 배분 방식. patch가 생략된 파일에도 그 사실을 모델에 알리는 표시 포함.
- Stage B 모델 과부하 실패에 대한 재시도 정책. SDK 기본값을 그대로 쓰면 예산을 통제할 수 없습니다.
- 상세 조회 병렬화. 병렬도 4에서 4배, 8에서 6.8배 빨라지고 secondary rate limit도 관측되지
  않았지만, 부분 실패 처리와 진행률 계약과 함께 설계해야 합니다.
- Stage A 분류의 실행 간 불안정성과 느슨한 기여 항목 매칭 개선.
- 한 커밋이 여러 PR에 속하는 경우와 `changedFiles`가 3000에 닿는 커밋의 파이프라인 통과 검증.
  측정 대상 저장소에 사례가 없었습니다.

## 측정 스크립트 사용법

```
GITHUB_TOKEN=$(gh auth token) npx tsx --env-file=.env scripts/measure-pipeline.ts <owner> <repo> <phase>
```

phase는 `commits`, `details`, `parallel`, `commit`, `stage-a`, `stage-b`입니다. 주요 옵션은
`--limit=N`(입력 커밋 수), `--cache=<경로>`(상세 조회 결과 재사용), `--model=`·`--stage-b-model=`
(모델 비교), `--concurrency=1,2,4`(병렬도), `--skip-stage-a`(Stage B만 측정), `--sha=`(단일 커밋)입니다.

`--cache`는 LLM 단계를 반복 측정할 때 상세 조회를 다시 하지 않게 합니다. 저장소 밖 임시 경로를
지정해야 합니다. 반복 측정이 GitHub rate limit을 불필요하게 소진하는 것을 막습니다.
