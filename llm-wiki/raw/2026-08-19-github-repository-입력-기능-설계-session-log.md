# GitHub Repository 입력 기능 설계 세션 로그

## 문서 목적

output/2026-08-19-서비스기획-확정-v1.md에서 확정한 MVP 핵심 기능 중 "GitHub Repository 입력"을 노션 기능 설계 문서로 옮기기 전, 세부 설계를 세션에서 먼저 논의하고 결정한 내용을 보존한다.

## 논의 내용

### 입력 방식

URL 붙여넣기 방식과 GitHub OAuth 로그인 후 repo 목록에서 선택하는 방식을 비교했다. URL 붙여넣기가 구현은 단순하지만, OAuth 로그인 방식을 채택했다. Private repo 지원을 함께 결정했기 때문에 어차피 OAuth 흐름이 필요하고, 목록에서 선택하는 UX가 더 낫다는 판단이다.

### 인증 범위

Public repo만 지원하는 안과 Private repo까지 지원하는 안을 비교했다. Private repo까지 지원하는 것으로 결정했다. OAuth 토큰이 필요하고 인증 흐름 전체를 구현해야 하지만, 실제 개발 경험은 private repo에 있는 경우가 많다는 점을 고려했다.

### 토큰 저장 방식

세션에만 유지하는 안과 서버에 저장해 재방문 시에도 유지하는 안을 비교했다. 서버 저장으로 결정했다. 매번 재로그인하는 부담을 없애기 위함이다. 서버 측 저장소와 암호화 처리가 필요하다.

### 커밋 조회 범위

처음에는 API 호출량과 분석 시간을 고려해 최근 N개 커밋(50/100/200)으로 제한하는 안을 제시했다. 사용자가 커밋이 600개 넘는 저장소를 갖고 있어, 분석에 시간이 걸리더라도 전체를 분석하는 것이 낫지 않겠냐는 문제 제기를 했다.

이에 따라 2단계 조회 구조로 재설계했다.

1단계는 전체 커밋 목록(제목, 작성자, 날짜)을 가벼운 API로 페이지네이션해 전부 가져온다. 600개 기준 요청 6~7회 수준이라 비용이 낮다. 커밋 메시지 키워드(refactor, migrate, replace, introduce 등)로 "기술적 의사결정 흔적"을 1차 필터링한다.

2단계는 1차 필터링을 통과한 후보 커밋만 diff/stats 같은 무거운 데이터를 상세 조회한다. 전체 커밋이 아니라 후보군만 무거운 호출이 발생하므로 API 호출량과 시간이 통제된다.

결과적으로 커밋 개수를 임의로 잘라내지 않고 전체 커밋을 스캔 대상에 포함시키면서, 비용이 큰 조회는 후보에게만 적용하는 방식으로 결정했다. Loading 상태는 "1단계 스캔 중 → 2단계 후보 분석 중" 2단계 진행률로 표시하는 것으로 방향을 잡았다.

### 조회 데이터 범위

경험 후보 선별 기준(output/2026-08-19-서비스기획-확정-v1.md의 코드 변경 규모/복잡도, 기술적 의사결정 흔적)을 계산하려면 커밋과 diff가 필요하다. 추가로 파일 트리와 언어 통계까지 조회 범위에 포함하기로 결정했다.

## 결정 사항 요약

- 입력 방식: GitHub OAuth 로그인 후 repo 목록에서 선택
- 인증 범위: Private repo 포함
- 토큰 저장: 서버 저장, 재방문 시 재사용
- 커밋 조회: 2단계 구조 (1단계 전체 커밋 메타데이터 스캔 → 2단계 후보만 diff/stats 상세 조회), 커밋 개수 상한 없음
- 조회 데이터: 커밋, diff, 파일 트리, 언어 통계

## 확인 필요

- 1단계 필터링에 쓸 커밋 메시지 키워드 목록 확정
- 2단계 후보로 넘어가는 기준(필터 통과 개수 상한 등)
- 서버 측 OAuth 토큰 암호화/저장소 방식 (구현 단계에서 결정)
