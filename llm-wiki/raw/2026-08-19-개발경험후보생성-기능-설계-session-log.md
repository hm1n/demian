# 개발 경험 후보 생성 기능 설계 세션 로그

## 문서 목적

"개발 경험 후보 생성" 기능을 설계하면서 논의한 내용과, 그 과정에서 드러난 "Repository 데이터 조회 및 기본 분석" 기능의 1단계 필터링 문제를 재논의해 결정한 내용을 보존한다.

## 논의 내용

### 경험 후보의 단위

지금까지는 "후보 커밋" 단위로 설계해왔는데, 실제 설명할 가치가 있는 개발 경험은 커밋 하나가 아니라 여러 커밋에 걸친 작업인 경우가 많다는 문제 제기가 있었다. 완전한 커밋 클러스터링, 단일 커밋만 쓰는 방식, 대표 커밋에 관련 커밋을 부가 근거로 붙이는 방식을 비교했다.

완전한 클러스터링은 실제 개발 경험과 가장 가깝지만 클러스터링 로직과 오분류 위험, 근거 표시 UI 복잡도가 크게 늘어나 MVP 범위를 넘어선다고 판단했다. 단일 커밋만 쓰면 구현은 단순하지만 근거가 빈약해질 위험이 있다.

절충안으로 대표 커밋과 관련 커밋을 부가 근거로 함께 보여주는 방식을 채택했다. 점수가 가장 높은 커밋을 대표 커밋으로 삼고, "여러 커밋에 걸친 연속 작업 여부" 지표로 걸린 인접 커밋들을 부가 근거로 같이 제시한다. 클러스터링 로직 없이도 맥락을 보강할 수 있다.

### 점수 계산 방식

코드 변경 규모/복잡도와 기술적 의사결정 흔적, 두 기준을 태그로만 분류하는 안과 가중합으로 점수화하는 안을 비교했다. 가중합 점수화로 결정했다. 두 지표를 각각 점수화해 합산하고, 합산 점수로 순위를 매겨 상위 3개를 자동으로 선정한다. 구체적인 정규화 방식과 가중치 값은 구현 단계에서 정한다.

### 후보가 3개보다 적을 때

기준을 완화해서라도 3개를 채우는 것으로 결정했다.

### 1단계 필터링 방식 재검토

`raw/2026-08-19-repository-데이터조회-기능-경계-session-log.md`에서 남겨둔 "1단계 필터 키워드 목록"을 정하려다, 리팩토링이나 마이그레이션 같은 키워드만 찾는 화이트리스트 방식 자체가 문제라는 지적이 나왔다. 기능 구현이나 버그 수정, 인프라 설정도 충분히 설명할 가치가 있는 경험일 수 있는데, 의사결정 흔적 키워드만 찾으면 이런 커밋들이 2단계 조회 대상에서 원천적으로 빠지게 된다.

이에 따라 화이트리스트 방식을 블랙리스트 방식으로 전환하기로 결정했다. "이 커밋을 찾아라"가 아니라 "이 커밋은 설명 가치가 낮으니 제외하라"는 방식이다. merge 커밋, 오타 수정, 포맷팅이나 린트, 의존성 버전만 올린 커밋, 문서만 수정한 커밋 정도만 제외하고 나머지는 모두 2단계 상세 조회 대상에 포함한다.

블랙리스트 초안은 다음과 같다.

- merge, typo, format, lint, style only, dependency bump, docs only
- 오타, 포맷팅, 의존성 업데이트, 문서 수정

이 결정에 따라 이전 세션 로그에서 논의했던 "기술적 의사결정 흔적을 나타내는 키워드로 후보를 찾는" 1단계 필터링 방식은 폐기한다. `llm-wiki/output/2026-08-19-서비스기획-확정-v1.md`에서 정한 두 가지 선별 기준(코드 변경 규모/복잡도, 기술적 의사결정 흔적)은 그대로 유지하되, 이 기준을 적용하는 시점을 1단계 필터링이 아니라 2단계 조회 이후 점수 계산 단계로 옮긴다.

커버리지가 넓어지면서 2단계 조회 대상이 늘어나 API 호출량이 커질 수 있지만, 실측 없이 미리 좁히지 않는다는 CLAUDE.md 작업 원칙에 따라 커버리지를 우선하고, 실제 성능을 측정한 뒤 필요하면 그때 좁히기로 했다.

## 결정 사항 요약

- 경험 후보는 대표 커밋과 부가 근거로 첨부하는 관련 커밋으로 구성한다. 완전한 클러스터링은 하지 않는다.
- 점수는 코드 변경 규모/복잡도 점수와 기술적 의사결정 흔적 점수를 가중합해 계산하고, 합산 점수로 순위를 매겨 상위 3개를 뽑는다. 구체적인 정규화와 가중치는 구현 단계에서 정한다.
- 후보가 3개보다 적으면 기준을 완화해서라도 3개를 채운다.
- "Repository 데이터 조회 및 기본 분석"의 1단계 필터링을 화이트리스트에서 블랙리스트 방식으로 바꾼다. merge, 오타, 포맷팅, 의존성 버전, 문서 수정만 제외하고 나머지는 모두 2단계로 넘긴다.
- 코드 변경 규모/복잡도와 기술적 의사결정 흔적 판단은 1단계가 아니라 2단계 조회 이후 점수 계산 단계에서 한다.

## 확인 필요

- 점수 정규화 방식과 가중치 값
- 대표 커밋 동점 처리 기준
- 후보가 3개보다 적어 기준을 완화할 때 구체적인 완화 순서
- 블랙리스트 단어 목록의 최종 확정 및 추가 검토
