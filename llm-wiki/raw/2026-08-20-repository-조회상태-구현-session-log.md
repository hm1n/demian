# Repository 조회 및 분석 상태 처리 구현

## 범위

- GitHub Issue #5의 Tasks, Constraints, Definition of Done을 기준으로 구현했습니다.
- 기존 `fetchAllCommits`, `filterCommitsForDetail`, `fetchRepositoryContributionData`, `buildCandidateData`를 화면 상태 오케스트레이션으로 연결했습니다.
- 조회 파이프라인의 규칙, 블랙리스트 판별 기준, 후보 데이터 산출 계약은 변경하지 않았습니다.
- 점수 계산, 순위 결정, 최종 후보 선별, 파일 트리 대체 분석은 추가하지 않았습니다.

## 구현 결정

- Empty 안내는 실제 조회 결과가 확인된 뒤에만 표시했습니다. 선택 시점에는 커밋 상태를 알 수 없기 때문입니다.
- 전체 커밋 0개와 필터 통과 커밋 0개를 서로 다른 상태와 문구로 분리했습니다.
- 필터 통과 커밋이 하나 이상이면 개수가 적더라도 정상 분석을 계속합니다. 별도 최소 개수 기준은 두지 않았습니다.
- 모든 오류 재시도는 전체 재시도로 통일했습니다. 현재 라이브러리에는 부분 재개를 안전하게 고정할 커서나 결과 병합 계약이 없습니다.
- 인증 취소 시 토큰을 지우고 입력으로 돌아갑니다. 새 토큰을 제출하면 전체 조회를 처음부터 다시 실행합니다.
- 부분 실패는 완료 개수와 전체 대상 개수를 가능한 범위에서 표시합니다. 중첩된 `cause`를 따라 원래 `rate_limit`, `auth_revoked`, `network`, `server_error` 분류도 안내에 반영합니다.

## 오류 원인 보존

- 전체 커밋 페이지네이션이 일부 성공한 뒤 네트워크, HTTP 오류, 409 상태 변경, JSON 파싱 실패로 중단되면 `partial_failure`의 `cause`에 원래 오류를 보존하도록 보강했습니다.
- 403 호출 한도가 일부 페이지 수집 뒤 발생하는 회귀 테스트를 추가했습니다.
- 이 변경은 PR #10 리뷰 후속 문서가 이슈 #5로 넘긴 원인 분류 표시 문제만 해결합니다. 422 오류 구분과 다른 backlog 항목은 가져오지 않았습니다.

## 화면과 테스트

- 1단계 전체 커밋 조회, 2단계 상세 데이터 조회, 3단계 파생 지표 계산을 별도 Loading 문구로 표시했습니다.
- 2단계 커밋 상세 조회에는 완료 개수와 전체 개수를 표시했습니다.
- 두 Empty 상태, 다섯 오류 범주, 부분 실패 원인, 전체 재시도, 인증 재진행 동작을 테스트했습니다.
- 접근성 알림을 위해 Loading에는 `status`, 오류에는 `alert` 역할을 사용했습니다.

- `npm run lint` 결과는 최종 검증 후 PR에 기록합니다.
- `npm run typecheck` 결과는 최종 검증 후 PR에 기록합니다.
- `npm run build` 결과는 최종 검증 후 PR에 기록합니다.
