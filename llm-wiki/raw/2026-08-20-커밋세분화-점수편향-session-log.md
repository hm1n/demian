# 커밋 세분화에 따른 점수 편향 문제 세션 로그

## 문서 목적

연속 작업 지표 논의(raw/2026-08-19-연속작업지표-판별기준-session-log.md) 중 발견된 문제, 즉 "개별 커밋 점수제라 여러 커밋으로 잘게 나눠 작업한 의미 있는 기능이 대표 커밋으로 못 뽑힐 위험"을 어떻게 다룰지 논의하고 결정한 내용을 보존한다.

## 논의 내용

이 문제를 제기했을 때, 실제로 문제가 되는지에 대한 반론이 있었다. 하나의 Repository 안에서는 그 사용자의 커밋 습관이 대체로 일관되기 때문에, 대표 커밋 선정은 같은 Repository 안에서의 상대 비교이므로 비교 기준(granularity) 자체가 사실상 고정된 채로 순위를 매기는 것과 같다는 논리다. PR 단위로 꼼꼼하게 작업하는 사람은 Repository 전체가 그 스타일이고, 커밋을 잘게 계속 올리는 사람도 Repository 전체가 그 스타일이라서, 점수 차이 자체는 여전히 유의미하다는 것이다.

이 논리에 남는 잔여 위험도 짚었다. 한 사람의 Repository 안에서도 기능마다 커밋 습관이 다를 수 있다. 어떤 기능은 꼼꼼하게 쪼개서 커밋하고 어떤 기능은 한 번에 몰아서 커밋할 수 있어서, 같은 Repository 안에서도 세분화된 작업이 상대적으로 저평가될 가능성은 남아 있다.

다만 이 잔여 위험이 실제로 얼마나 흔한 패턴인지 검증된 데이터가 없다. 데이터 없이 대응 로직을 만드는 것은 추측성 최적화이며, 이는 작업 원칙(실제 성능 측정 근거 없이 최적화를 먼저 적용하지 않음)과 어긋난다.

## 결정 사항 요약

- 이 문제에 대해 별도의 조치나 로직을 지금 추가하지 않는다.
- 알려진 한계로만 기록하고, 실제 구현 후 실제 Repository 데이터로 확인한다.
- 세분화된 의미 있는 기능이 저평가되는 현상이 실제로 관찰되면 그때 재검토한다.

## 확인 필요

- 실제 구현 후 검증할 방법을 아직 정하지 않았다. 본인 Repository나 확보한 다른 Repository로 대표 커밋 선정 결과를 살펴보고 판단할 것으로 예상한다.
