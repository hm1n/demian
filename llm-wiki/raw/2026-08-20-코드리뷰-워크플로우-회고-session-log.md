# 코드 리뷰 워크플로우 회고 세션 로그

## 문서 목적

GitHub Issue #1 구현 PR(#6)에서 `@codex review`를 6라운드 가까이 반복해 리뷰 코멘트가 24개까지 쌓인 경위를 기록하고, 남은 Issue #2부터 #5에 적용할 코드 리뷰 워크플로우 원칙을 보존한다. 리뷰에서 지적된 GitHub API 관련 사실은 Issue #2와 #3에서도 같은 API를 다루므로 함께 남긴다.

## 배경

Notion 기능 정의서 `Repository 데이터 조회 및 분석`을 GitHub Issue 5건으로 분리했고, 각 Issue를 PR 1개로 대응한다. 브랜치는 `feature-#N/repo-data-fetch`, 이슈와 PR 제목은 `[feature/repo-data-fetch] <제목>` 규칙을 쓴다. Issue 본문과 PR 본문 초안은 codex CLI가 파일로만 작성하고, 실제 `gh issue create`와 `gh pr create` 실행 및 리뷰 코멘트 답글은 Claude가 담당하는 역할 분리를 유지한다.

Issue #1은 기본 브랜치 전체 커밋 조회이며 PR #6으로 머지했다. 구현 파일은 `src/lib/github/types.ts`, `errors.ts`, `commits.ts`와 `commits.test.ts`이고, 이 작업에서 vitest를 처음 도입했다.

## 리뷰에서 실제로 잡힌 문제

리뷰 코멘트는 노이즈가 아니라 전부 실제 버그였다. 라운드별로 확인된 내용은 다음과 같다.

- GitHub 커밋 목록 API는 빈 저장소에서 `200 []`이 아니라 `409 Git Repository is empty`를 반환한다.
- 403 응답의 rate limit 판별을 primary(`x-ratelimit-remaining: 0`)만 보고 처리해서, secondary rate limit과 429를 놓쳤다. 이 경우 정상 사용자가 인증 취소로 잘못 분류될 위험이 있었다.
- 페이지네이션에 브랜치 이름(`sha=main`)을 그대로 쓰면 조회 도중 들어온 새 커밋 때문에 페이지 경계에서 커밋이 중복되거나 누락될 수 있다. 브랜치 head를 커밋 SHA로 한 번 고정한 뒤 페이지네이션해야 한다.
- SHA 고정 조회가 커밋 목록 조회보다 먼저 실행되는데, 커밋이 0개인 신규 저장소는 브랜치 ref 자체가 없어 이 단계에서 404가 먼저 발생한다. 그 결과 앞 라운드에서 추가한 409 방어 코드가 도달 불가능한 코드가 됐다.
- 빈 저장소 판별에 저장소 `size` 필드를 썼는데, 이 값은 KB 단위 저장 용량이라 커밋 수를 보장하지 않는다. 재조회한 기본 브랜치명이 그대로인지로 판별하는 방식으로 교체했다. 이름이 같으면 실제로 빈 저장소이고, 다르면 새 이름으로 한 번 재시도한다.
- `response.json()` 호출이 여러 곳에서 try/catch 밖에 있어서, 파싱이 실패하면 타입 없는 에러가 그대로 새어 나가거나 이미 수집한 커밋을 버리는 문제가 있었다. 모든 호출을 감싸고 중복되던 패턴은 `parseJson` 헬퍼 하나로 통합했다.

## 문제 패턴 분석

각 라운드에서 지적된 줄만 좁게 고쳤고, 그 수정이 바로 옆에 새로운 엣지 케이스를 만들어 다음 라운드에서 다시 잡히는 흐름이 반복됐다. 세 번째 항목과 네 번째 항목이 전형적인 예다. 페이지네이션 안정성을 위해 SHA 고정을 넣자마자 호출 순서 문제가 새로 생겼고, 그 결과 이전 라운드의 수정이 무효가 됐다.

즉 문제의 원인은 리뷰가 과하게 돌았다는 사실 자체가 아니라, 수정 범위를 지적된 줄로 한정해서 같은 데이터 흐름 안의 인접한 결함을 매번 놓친 데 있다.

## 결정 사항 요약

- push할 때마다 `@codex review`를 트리거하지 않는다. 한 Issue에 해당하는 구현을 모두 끝내고 로컬에서 테스트와 typecheck와 lint 통과를 확인한 뒤 한 번에 리뷰를 건다.
- 리뷰 지적을 수정할 때 지적된 줄만 고치지 않는다. 해당 함수와 그 데이터 흐름 전체를 다시 훑고 고친다. 이것이 반복 라운드를 줄이는 실제 수단이며, 라운드 수를 줄이는 것 자체보다 우선한다.
- 리뷰 라운드를 없애지는 않는다. 수정을 반영한 뒤 최소 한 번은 재검증 라운드를 거친다. 수정이 새 문제를 만들지 않았는지 확인할 방법이 그것뿐이다. 위 원칙을 지키면 보통 1~2라운드에서 수렴할 것으로 본다.
- 커밋은 논리 단위로 분리하고, 리뷰 스레드에는 답글을 남긴 뒤 `resolveReviewThread` GraphQL mutation으로 resolve까지 처리하는 흐름을 유지한다.

## 재사용 가능한 GitHub API 지식

- 빈 저장소는 커밋 목록 API에서 409를 반환하고, 브랜치 조회 API(`/branches/{branch}`)에서는 ref가 없으므로 404를 반환한다.
- 저장소 `size` 필드는 KB 단위 저장 용량이고 커밋 수와 무관하므로 빈 저장소 판별 기준으로 쓸 수 없다.
- rate limit은 세 가지를 구분해야 한다. 429는 primary이고, `403`에 `x-ratelimit-remaining: 0`이 붙으면 primary이며, `403`에 `Retry-After` 헤더가 있거나 본문 메시지에 `secondary rate limit` 또는 `abuse detection`이 있으면 secondary이다.
- 모든 `response.json()` 호출은 파싱 실패를 전제로 try/catch로 감싸고 타입이 있는 에러로 변환한다.

## 수동 검증 스크립트

`scripts/manual-test-commits.ts`를 만들어 두었고 git에는 커밋하지 않았다. 실행 방법은 다음과 같다.

```bash
GITHUB_TOKEN=$(gh auth token) npx tsx scripts/manual-test-commits.ts <owner> <repo>
```

실제 GitHub API를 호출해 `fetchAllCommits` 결과 전체를 출력한다. Issue #2와 #3 구현에서도 이 스크립트로 실제 데이터를 확인하면서 진행한다.
