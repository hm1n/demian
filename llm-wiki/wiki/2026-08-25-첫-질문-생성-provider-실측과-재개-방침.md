## 문서 목적

근거 스냅샷 하나로 첫 질문을 생성해 SSE로 흘려보내는 경로를 확정합니다. 이슈 #63이 남긴 결정
항목은 네 가지입니다. Provider와 모델, 프롬프트 문구, 전송 중 단절 시의 재개 방침, 생성 실패
재시도 방침입니다. 함께 근거 입력 상한과 바이트-토큰 환산식을 실제 요청 토큰으로 교정합니다.

프로젝트 원칙에 따라 추측으로 고르지 않았습니다. 같은 근거 스냅샷을 Groq와 Gemini에 넣고 질문
품질, 첫 청크 지연, 총 지연, 입출력 토큰을 재고 그 결과가 가리키는 것만 구현했습니다.

## 측정 방법

측정 스크립트는 `src/features/interview/measurement/question-generation.measure.mts` 하나입니다.

```
GITHUB_TOKEN=$(gh auth token) npx tsx --env-file=<.env 경로> \
  src/features/interview/measurement/question-generation.measure.mts --pr=56 --pr=61 --max-commits=4
```

근거는 합성이 아니라 실제 GitHub 응답입니다. `hm1n/demian`의 Pull Request 커밋을 상세 조회하고
`buildExperienceEvidenceSnapshot`으로 스냅샷을 조립합니다. 커밋 제목·메시지·PR·변경 파일 목록은
patch가 벗겨진 값에서 오고 patch 본문은 diff에서 오는 실제 출처 분기를 그대로 재현합니다. Stage
A·B가 만드는 값 가운데 스크립트가 대신 채우는 것은 LLM 해석 문장과 인용 파일 경로 두 개이고, 둘
다 확인 수준이 `AI가 고른 값`으로 실려 프롬프트에서 차지하는 자리는 실제와 같습니다.

프롬프트와 스트림 소비는 운영 코드를 그대로 씁니다. `buildInterviewQuestionPrompt`와
`startInterviewQuestionStream`을 호출하고, 스크립트가 따로 만드는 것은 provider 선택과 메타데이터
수집뿐입니다. 프롬프트를 손으로 다시 접으면 재는 대상과 배포되는 대상이 갈립니다. Stage A에서
라우트가 프롬프트를 손으로 다시 계산해 기여 항목을 빠뜨린 결함이 실제로 있었습니다.

측정에 쓴 근거 스냅샷은 두 개입니다. 둘 다 커밋 4개이고 크기는 비슷하지만 patch 몫이 다릅니다.

| 스냅샷 | 직렬화 | 추정 토큰 | metadataTokens | patch 바이트 |
| --- | --- | --- | --- | --- |
| PR #56 (근거 스냅샷 계약) | 10,411 | 3,471 | 3,291 | 608 / 627 |
| PR #61 (질문 스트리밍 표시) | 10,417 | 3,473 | 2,312 | 3,548 / 3,564 |

PR #56은 커밋 메시지가 길어 나머지 근거가 상한의 94%를 먹고 patch에 608바이트만 남았습니다. 이
차이가 뒤의 품질 비교에서 그대로 드러납니다.

## 무료 등급 한도는 헤더로 확인했습니다

문서가 아니라 응답으로 확인했습니다.

### Groq는 분당 토큰과 별개로 일일 토큰 한도가 있습니다

`openai/gpt-oss-120b` 호출이 429로 거절되면서 본문에 다음이 왔습니다.

```
Rate limit reached for model `openai/gpt-oss-120b` in organization `...`
service tier `on_demand` on tokens per day (TPD): Limit 200000, Used 199104, Requested 2704.
```

- **한도는 모델별입니다.** 메시지가 `for model openai/gpt-oss-120b`로 모델을 지목합니다. Stage A가
  같은 `openai/gpt-oss-120b`를 쓰므로 질문 생성이 같은 모델을 쓰면 일일 200,000토큰을 함께
  나눠 씁니다. 측정 시점에 Stage A 실측이 그 한도를 이미 199,104까지 썼습니다.
- **TPD 초과는 429입니다.** 413 `rate_limit_exceeded`가 아닙니다. TPM 초과가 413으로 오는 것과
  다릅니다. 두 경로 모두 `llm_rate_limit`으로 분류되므로 기존 분류는 그대로 맞습니다.
- **`x-ratelimit-*` 헤더는 TPD를 알려주지 않습니다.** TPD가 소진된 429 응답의 헤더가
  `x-ratelimit-limit-tokens: 8000`, `x-ratelimit-remaining-tokens: 8000`,
  `x-ratelimit-reset-tokens: 1ms`였습니다. 분당 창은 비어 있는데 일일 창이 막힌 상태입니다.
  Stage A가 잔여 토큰 헤더로 대기 시간을 정하는 방식은 TPD 소진을 감지하지 못합니다. 그때 쓸 값은
  `retry-after`이고 이 응답에는 `859`(초)가 있었습니다.
- 같은 응답에 `x-should-retry: false`가 붙어 있었는데도 AI SDK는 재시도 기본값(2회) 만큼 세 번
  호출해 6.5초를 버렸습니다. 재시도를 1회로 낮춘 뒤 같은 상황이 2.4~2.5초에 끝났습니다.
- **일일 창은 24시간 롤링이고 다시 차는 데 오래 걸립니다.** 같은 날 40분 뒤에 다시 재보니 사용량이
  199,104에서 198,452로 652토큰만 돌아와, 그날은 `openai/gpt-oss-120b`를 한 번도 호출하지
  못했습니다. 한 기능이 한도를 소진하면 같은 모델을 쓰는 다른 기능은 그날 하루를 쓸 수 없습니다.

성공한 호출의 헤더로 분당 창도 확인했습니다. `openai/gpt-oss-20b` 한 번 호출 뒤
`x-ratelimit-remaining-tokens`가 8,000에서 5,056으로 줄고 `x-ratelimit-reset-tokens`가 22.08초였습니다.
두 번째 호출 뒤에는 953까지 내려갔습니다. 한 호출이 분당 창의 약 36%를 씁니다.

### Gemini는 모델에 따라 응답조차 하지 않았습니다

Gemini 무료 등급의 하루 요청 20건이 프로젝트 전체 공유라는 것은 이미 기록돼 있습니다
(`wiki/2026-08-24-실데이터-검증-배치-상한-확정.md`). 이번 측정에서 그보다 앞서는 문제를 봤습니다.

- `models` 목록 조회는 200으로 즉시 응답합니다. API 키는 유효합니다.
- **Stage B가 쓰는 `gemini-3.7-flash`가 `generateContent`에 25초 안에 응답하지 않았습니다.**
  `gemini-3.5-flash`도 같았습니다. 두 번 반복해서 같았습니다. 오류도 아니고 응답도 아닌 무응답
  이므로 우리 쪽 시한으로만 끊을 수 있습니다.
- `gemini-3.6-flash`는 2.9초, `gemini-3.1-flash-lite`는 0.76초에 응답했습니다.
- `gemini-2.5-flash`는 404이고 본문이 "no longer available to new users"입니다.

그래서 Gemini 비교 대상은 응답하는 `gemini-3.6-flash`로 잡았습니다.

### Groq 서빙 모델을 전수 검토했습니다 (PR #67 리뷰)

1차 결정은 `gpt-oss-20b`, `gpt-oss-120b`, Gemini 셋만 비교했습니다. 일일 토큰 한도가 모델별이므로
Groq의 다른 모델은 같은 할당량 분리를 얻으면서 다른 품질을 낼 수 있다는 지적을 받아, 추측하지 않고
Groq `/models`(2026-08-25) 응답으로 서빙 목록을 확인한 뒤 조건에 맞는 후보를 실제로 쟀습니다.

| 모델 | 판정 | 근거 |
| --- | --- | --- |
| `openai/gpt-oss-20b` | 채택 | 첫 청크 1.5~2.5초. 만들어낸 사실이 있습니다. |
| `openai/gpt-oss-120b` | 쓰지 않음 | Stage A가 쓰는 모델이라 일일 한도를 공유합니다. |
| `qwen/qwen3.6-27b` | 쓸 수 없음 | 추론 모델이고 사고 과정을 본문에 그대로 흘립니다. 아래를 보세요. |
| `groq/compound`, `groq/compound-mini` | 쓸 수 없음 | 내부적으로 `openai/gpt-oss-120b`를 호출합니다. 아래를 보세요. |
| `openai/gpt-oss-safeguard-20b` | 대상 아님 | 안전 분류 모델이고 자유 텍스트 생성용이 아닙니다. |
| `allam-2-7b` | 대상 아님 | 컨텍스트가 4,096으로 이 프롬프트(약 2,900토큰)와 응답을 함께 담지 못합니다. |
| `whisper-large-v3`, `whisper-large-v3-turbo`, `canopylabs/orpheus-*`, `meta-llama/llama-prompt-guard-2-*` | 대상 아님 | 음성과 분류 모델입니다. |

**`qwen/qwen3.6-27b`는 사고 과정이 질문 자리에 나옵니다.** 기본 설정에서 출력 6,804자 가운데 대부분이
영어 `<think>` 블록이었고 우리 시스템 프롬프트를 영어로 되풀이한 내용이 그대로 들어 있었습니다. 출력
토큰이 정확히 2,048에서 멈춰 완성된 질문이 나오지 않았습니다. Groq의 `reasoningFormat: "hidden"`으로
사고 과정을 숨기면 남는 본문이 **0자**입니다. 두 스냅샷 모두 그랬고 출력 토큰은 다시 2,048이었습니다.
사고에 출력 예산을 다 쓰고 질문을 시작하지 못하는 것입니다. 이 경로가 `generation_empty`로 분류되는
것을 실제로 확인했으므로, 그 분류가 운영에서 도달 가능하다는 근거도 함께 얻었습니다.

**`groq/compound-mini`는 내부적으로 `openai/gpt-oss-120b`를 호출합니다.** 호출이 실패하면서 돌아온
본문이 그 모델을 지목했습니다.

```
Rate limit reached for model `openai/gpt-oss-120b` ... on tokens per day (TPD):
Limit 200000, Used 199746, Requested 6023.
```

고르려던 기준인 "Stage A와 일일 한도를 나누지 않는다"를 정면으로 어깁니다. 요청 토큰도 우리 프롬프트의
약 2,900이 아니라 6,023이었습니다. compound 계열이 자체 지시를 덧붙이기 때문입니다. 내장 도구로 저장소
밖 정보를 끌어올 수 있다는 원래의 우려는 확인할 필요조차 없어졌습니다. 덧붙여 이 실패는 provider가
HTTP 상태가 아니라 `type: "compound"` 본문으로 알려 와 `llm_rate_limit`이 아니라 `llm_failure`로
분류됐습니다. 채택하지 않는 모델이므로 이번 범위에서 매핑을 늘리지 않았습니다.

**결론은 후보가 없다는 것입니다.** Stage A와 일일 한도를 나누지 않으면서 이 프롬프트로 질문을 만들어
내는 Groq 모델은 `openai/gpt-oss-20b`뿐입니다. 만들어내는 사실 문제는 모델 교체로 해소되지 않으므로
`확인 필요`에 남깁니다.

### 지연

Groq가 첫 청크까지 1.5~2.5초, Gemini가 8.1~9.5초입니다. 4~5배 차이입니다. 청크 수도 다릅니다.
Groq는 한 질문을 130~225개로 잘라 보내고 Gemini는 11개로 보냅니다. 화면에 글자가 흐르는 것처럼
보이는 것은 Groq 쪽이고, Gemini는 문장 단위로 뭉쳐서 옵니다.

`wiki/2026-08-25-스트리밍-렌더링-측정과-전송-계약.md`의 렌더링 결정이 청크가 잦은 쪽을 전제로
만들어졌습니다. 프레임 단위로 모아 반영하는 결정은 청크 200개짜리 스트림에서 값을 합니다.

### 품질

품질은 수치가 아니라 응답 원문으로 봤습니다. 기준은 `AGENTS.md`의 인터뷰 설계 원칙입니다. 실제
코드나 커밋을 근거로 삼는지, 근거에 없는 것을 사실처럼 전제하지 않는지, 암기나 일반론으로 답할 수
있는 질문이 아닌지입니다.

**`openai/gpt-oss-20b`는 근거에 없는 사실을 만들었습니다.** 두 변형 모두 그랬습니다.

- PR #56 split: "UTF-16 코드 단위로 patch를 자르도록 변경한 배경"을 물었습니다. 실제 변경은 그
  반대입니다. UTF-16 코드 단위로 자르던 것을 **코드 포인트 경계**로 고쳤습니다. 같은 응답이
  `patchTruncated`가 참이면서 patch가 없는 조합을 "이슈 #46에 따라 일반 미포함으로 표시한 구현
  의도"로 물었는데, 그 커밋은 그 오표시를 **고친** 커밋입니다.
- PR #56 merged: 근거에 없는 상수 이름 `EVIDENCE_SNAPSHOT_MAX_TOTAL_PAT`를 만들어 물었습니다.
  잘린 patch 본문의 조각을 상수 이름으로 읽은 것으로 보입니다. 같은 문장에서 "UTF-16 코드 포인트
  경계"라는 그 자체로 모순인 표현을 썼습니다.
- PR #61 split·merged: 근거에 없는 대안 목록(`react-test-renderer`, `puppeteer`,
  `highlight.js`, `marked`, `react-window`)을 만들어 "검토했으나 제외한 결정 배경"을 물었습니다.
  검토한 적이 있다는 전제가 Repository 근거에 없습니다.

**`gemini-3.6-flash`는 만들어낸 사실이 없었습니다.** 두 스냅샷 모두 실제 SHA와 실제 변경을
인용했고, 대안을 전제하지 않고 "검토했던 다른 대안"을 열린 형태로 물었습니다. PR #56에서는 patch가
608바이트뿐인 근거로도 두 커밋의 관계(문자 수 상한에서 추정 토큰 상한으로의 정정)를 정확히 짚었습니다.

**질문 개수 규칙은 어느 쪽도 엄격히 지키지 않았습니다.** 프롬프트는 "정확히 1개"를 요구합니다.
`gpt-oss-20b`는 별개의 질문 두세 개를 나열했습니다. `gemini-3.6-flash`는 질문 하나에 "함께 다뤄
주세요" 목록을 붙였고 이는 프롬프트가 허용한 형태입니다.

### 프롬프트 변형

Stage A는 같은 지시를 한 문단에 두느냐 갈라 두느냐만 바꿔 전수 응답률이 0/3에서 3/4로 바뀐 적이
있습니다. 그래서 이번에도 변형을 두고 함께 쟀습니다.

`openai/gpt-oss-20b`에서 두 변형의 차이는 Stage A만큼 크지 않았습니다. 지연과 토큰은 사실상
같습니다. 지시 준수는 갈라 둔 쪽이 조금 나았습니다. 한 문단 변형은 PR #56에서 별개 질문 세 개를
냈고 갈라 둔 변형은 두 개였습니다. 만들어낸 사실은 두 변형 모두 있었습니다.

표본이 스냅샷 2개 × 변형 2개뿐이라 이 차이를 근거로 문구를 확정할 수는 없습니다. 확정 근거는
"갈라 둔 쪽이 더 나빴다는 관측이 없고, Stage A 실측이 같은 방향을 가리킨다"입니다.

## 확정 사항

### 1. Provider는 Groq, 모델은 `openai/gpt-oss-20b`입니다 — **폐기 (2026-09-02)**

**이 확정은 폐기됐습니다.** 첫 질문 경로는 Google `gemini-3.1-flash-lite`입니다. 아래 원래 서술을
남겨 두고, 무엇이 무효인지를 먼저 적습니다.

**무효 1. "Gemini 무료 등급의 하루 20요청을 Stage B가 이미 씁니다"는 쿼터 오독입니다.**
`wiki/2026-08-24-실데이터-검증-배치-상한-확정.md:164`에 쿼터 이름이
`GenerateRequestsPerDayPerProjectPerModel-FreeTier`로 적혀 있었습니다. 프로젝트당 **그리고 모델당**
20요청입니다. Stage B와 다른 Gemini 모델을 쓰면 그때도 할당량이 겹치지 않았습니다. 유료 전환과
무관하게 처음부터 틀린 근거였고, 이 오독이 "하루에 모델 하나만 측정한다"는 규칙까지 만들었습니다.

**무효 2. "Gemini는 모델에 따라 응답조차 하지 않았습니다"로 제공자 전체를 배제한 것이
과잉일반화입니다.** 25초 무응답은 `gemini-3.7-flash` 하나의 관측이었습니다. 2026-08-26 서빙 목록
확인에서 텍스트 생성 가능 모델이 12개였고, `gemini-3.1-flash-lite`는 같은 측정에서 0.76초에
응답했습니다. 모델 하나의 실패로 제공자를 닫았습니다.

**무효 3. Groq 안에서 `openai/gpt-oss-20b`를 고른 근거도 사라졌습니다.** 그 근거는 Stage A가
`openai/gpt-oss-120b`의 일일 토큰 200,000을 쓴다는 것이었는데, Stage A가 Groq를 떠나면서 나눠 쓸
한도 자체가 없어졌습니다.

**남겨 둔 문제가 실제로 터졌습니다.** 아래 서술이 "`openai/gpt-oss-20b`가 만들어내는 사실은 남는
문제"라고 적어 두었고, 그 P1이 PR #67에서 PR #65로 이관돼 열린 채 머지됐습니다. 모델을 바꾼 것이
그 문제의 해소 경로였습니다. 새 모델은 두 스냅샷 모두에서 근거 밖 사실을 만들지 않았습니다.

이하는 폐기 전 원래 서술입니다.

품질만 보면 `gemini-3.6-flash`가 낫습니다. 그런데도 Groq를 고른 이유는 두 가지입니다.

- **Gemini 무료 등급의 하루 20요청을 Stage B가 이미 씁니다.** 인터뷰 시작은 사용자 행동마다 1건
  이므로 같은 할당량을 쓰면 후보 생성이 먼저 막힙니다. 후보 생성이 막히면 인터뷰를 시작할 경험
  자체가 없습니다. 순서상 뒤 단계가 앞 단계의 할당량을 먹어서는 안 됩니다.
- **Gemini는 이번 측정에서 모델에 따라 응답조차 하지 않았습니다.** Stage B가 지정한
  `gemini-3.7-flash`가 25초 무응답이었습니다. 첫 청크를 기다려야 응답을 시작하는 이 route의 구조
  에서 무응답은 곧 시한 초과입니다.

Groq 안에서 `openai/gpt-oss-20b`를 고른 이유는 **일일 토큰 한도가 모델별이기 때문**입니다. Stage
A가 `openai/gpt-oss-120b`의 200,000토큰을 씁니다. 질문 생성이 같은 모델을 쓰면 인터뷰 한 번이
후보 생성 한도를 갉아먹고, 측정 시점처럼 Stage A가 한도를 다 쓴 날에는 인터뷰를 시작할 수 없습니다.
모델을 갈라 두면 두 기능이 각자의 200,000토큰을 씁니다. 이 문제는 추정이 아니라 이번 측정에서 실제로
겪은 일입니다. Stage A 측정이 남긴 소진 때문에 질문 생성용 `openai/gpt-oss-120b` 호출을 하루 동안
한 번도 성공시키지 못했습니다.

`openai/gpt-oss-20b`가 만들어내는 사실은 남는 문제입니다. 이 문제를 프롬프트로 줄이는 것과 모델을
바꾸는 것은 다음 이슈에서 다뤄야 합니다. 이번 범위에서 근거로 삼은 것은 "만들어낸 사실이 있어도
근거에 표시된 확인 수준을 넘어서지는 않았다"가 아니라 "품질이 더 좋은 대안이 할당량 때문에 쓸 수
없다"입니다. 아래 `확인 필요`에 남겼습니다.

### 2. 프롬프트는 규칙을 문단으로 갈라 둡니다

`question-prompt.ts`의 `split` 변형입니다. 가장 중요한 규칙(질문 1개)을 첫 문단에 단독으로 둡니다.
`merged` 변형은 지우지 않고 남겨 두어 다음 측정이 같은 비교를 다시 할 수 있게 합니다.

근거 직렬화는 JSON이 아니라 사람이 읽는 텍스트입니다. 같은 내용이라도 키와 따옴표 때문에 요청이
커지고, 확인 수준이 값 옆의 필드로 붙어 있으면 모델이 `unverifiable`을 사실과 나란한 또 하나의
데이터로 읽습니다. 확인 수준을 문장으로 풀어 항목마다 붙였습니다.

### 3. 전송 중 단절 시 이어받지 않습니다

**실제 생성 스트림은 재개하지 않습니다.** 근거는 세 가지입니다.

- 서버가 이미 보낸 청크를 보관하지 않으므로 `seq N`부터 이어 보낼 수 없습니다.
- 클라이언트가 끊긴 뒤에도 서버가 생성을 계속하는 동작은 저장 계층과 사용자 식별자에 동시에
  의존해 범위 밖입니다(`wiki/2026-08-24-경험선택-세션저장-후속-backlog.md`).
- 생성은 비결정적입니다. 처음부터 다시 만들면 같은 질문이 아니라 다른 질문이 나옵니다. 이미
  표시된 앞부분에 그 결과를 붙이면 한 메시지 안에서 서로 다른 질문이 이어집니다.

그래서 세 곳을 함께 맞췄습니다.

- 수신부는 `resumeMode: "restart"`에서 `Last-Event-ID`를 보내지 않고, 전송이 끊겨도 자동으로
  재연결하지 않습니다. 사용자에게 결정을 넘깁니다.
- 사용자가 다시 시도하면 이미 표시된 내용을 지우고 처음부터 다시 생성합니다. 지우지 않으면 위의
  "서로 다른 질문이 이어지는" 상태가 됩니다.
- route는 `POST`에 `Last-Event-ID`가 오면 422로 거절합니다. 조용히 무시하면 클라이언트가 이어받
  았다고 믿고 앞부분에 새 생성 결과를 덧붙입니다. 거절은 그 오해를 즉시 드러냅니다.

**테스트용 스트림의 재개 동작은 그대로 둡니다.** `test-stream.ts`는 내용이 결정적이라 `seq`만으로
이어붙일 수 있고, 전송 계약 회귀 테스트와 하위 이슈 B의 화면 개발이 그 경로를 씁니다. 재개 가능
여부를 스트림마다 갈라야 해서 수신부에 `resumeMode`를 두었습니다.

### 4. 생성 실패 재시도는 기다려서 풀리는 것과 갈라 다룹니다

`errors.ts`의 `clearsOnRetry`가 분류마다 어느 쪽인지 한 곳에서 정합니다. `Record`로 두어 분류가
추가될 때 빠뜨리면 컴파일이 실패합니다.

| 갈래 | 분류 | 사용자에게 |
| --- | --- | --- |
| 기다리면 풀립니다 | `llm_rate_limit`, `llm_timeout`, `llm_network`, `llm_failure`, `stream_connect_failed`, `stream_interrupted`, `generation_empty`, 모델 출력 실패(`schema_validation` 등) | 잠시 뒤에 다시 시도해 달라고 안내합니다. |
| 같은 근거로는 풀리지 않습니다 | `llm_auth`, `llm_configuration`, `llm_request`, `invalid_request`, `invalid_json`, `body_too_large`, `unauthorized`, `server_error` | 다시 시도해도 같은 결과라고 알립니다. |

#### 재시도 안내는 재개 가능 여부로 한 번 더 갈립니다 (PR #67 리뷰)

처음 안은 생성 실패 안내에 "이미 받은 내용은 그대로 두었습니다. 잠시 뒤에 다시 시도해 주세요"를
붙였습니다. 실제 생성 경로에서 그 문구가 거짓입니다. 그 경로는 이어받을 수 없어서 다시 시도가 표시된
내용을 지우고 처음부터 새로 만듭니다. 스트림 중간에 `llm_rate_limit` `error` 이벤트가 오면 사용자는
"그대로 두었다"를 읽고 버튼을 누르고, 그 순간 읽던 질문이 사라집니다. `stream_interrupted`의 비재개
문구는 이미 "지금까지 받은 내용은 사라집니다"로 정확했고 생성 오류 쪽만 빠져 있었습니다.

그래서 안내를 원인과 재시도 두 조각으로 갈랐습니다. 원인은 분류가 정하고, 재시도 문구는
`clearsOnRetry`와 재개 가능 여부가 함께 정합니다.

| 조건 | 재시도 문구 |
| --- | --- |
| 같은 근거로 풀리지 않음 | 다시 시도해도 같은 결과가 나옵니다. |
| 풀릴 수 있고 이어받을 수 있음 | 이미 받은 내용은 그대로 두었습니다. 잠시 뒤에 다시 시도해 주세요. |
| 풀릴 수 있고 이어받을 수 없음 | 잠시 뒤에 다시 시도해 주세요. 다시 시도하면 같은 근거로 질문을 처음부터 새로 만들고, 지금까지 받은 내용은 사라집니다. |

`generation_empty`는 이 표를 쓰지 않습니다. 청크가 0개라 사라질 내용이 없고, 재시도 문구를 붙이면
잃을 내용이 있다고 오해하게 만듭니다.

#### 서버 설정 실패를 아는 분류로 등록했습니다 (PR #67 리뷰)

route가 세션 처리 실패에 `server_error` 500을 돌려주는데 그 값이 수신부의 아는 분류 목록에 없었습니다.
수신부가 전송 실패로 떨어뜨려 서버 설정 문제에 "네트워크 상태를 확인해 주세요"를 보여 줍니다.

이 분기는 도달 불가가 아닙니다. 쿠키가 없으면 `auth_revoked`이지만, 쿠키가 있는데
`GITHUB_SESSION_ENCRYPTION_KEY`가 없거나 32바이트가 아니면 `decryptGitHubToken`이 `encryptionKey`의
`server_error`를 그대로 올립니다. 두 경우 사용자가 할 수 있는 일이 다르므로 분기를 지우지 않고
`server_error`를 아는 분류에 등록했습니다. `stage-a` route가 쓰는 값과 같습니다.

자동 재시도는 두 층에 둡니다.

- provider 호출은 AI SDK 재시도를 **1회**로 낮췄습니다. 기본값 2(총 3회)에서 내렸습니다. 실측에서
  일일 토큰 한도 초과가 세 번 모두 같은 429로 끝나 6.5초를 버렸고, 응답에 `x-should-retry: false`가
  있었는데도 SDK가 재시도했습니다. 한도 초과는 기다려야 풀리므로 그 시간은 첫 청크 시한만
  갉아먹습니다. 0으로 두지 않는 이유는 일시적인 5xx는 한 번 더 보내면 풀리기 때문입니다. 낮춘 뒤
  같은 한도 초과가 6.5초가 아니라 2.4~2.5초에 끝나는 것을 확인했습니다.
- 전송 계층은 실제 생성 경로에서 자동 재연결을 하지 않습니다. 3번 항목과 같은 이유입니다.

첫 청크 전과 후를 갈라 전달합니다. 첫 청크를 받은 뒤에야 응답을 시작하므로, 그 전의 실패는 HTTP
상태와 JSON 본문으로 분류를 실어 보낼 수 있습니다. 그 뒤의 실패는 이미 보낸 내용이 있으므로 스트림
안의 `error` 이벤트로 보냅니다. 수신부가 비2xx 본문의 `error.kind`를 읽어 안내를 가르는 설계가 이
순서에 의존합니다.

### 5. 청크 없이 `done`으로 끝난 스트림은 Error입니다

`wiki/2026-08-25-스트리밍-후속-backlog.md` 1번 항목이 남긴 미결을 닫습니다. 새 분류
`generation_empty`를 만들었습니다. 전송 문제가 아니므로 `stream_connect_failed`도
`stream_interrupted`도 쓰지 않습니다. 둘의 안내는 각각 "연결하지 못했다"와 "받는 도중 끊겼다"인데
이 경우는 연결도 되고 끊기지도 않았습니다. provider 호출도 실패하지 않았으므로 `llm_*` 어느 값도
맞지 않습니다.

두 곳에서 막습니다.

- **서버**: 첫 조각을 얻지 못하면 응답을 시작하지 않고 502 `generation_empty`를 보냅니다.
- **수신부**: `done`이 왔는데 받은 청크가 0개면 완료로 두지 않고 `generation_empty`로 올립니다.
  실제 생성 경로는 서버가 먼저 막지만, 이 경로가 도달 불가능한 방어 코드는 아닙니다.
  `test-stream.ts`에 `empty` 시나리오를 넣어 회귀 테스트가 실제로 이 경로를 지나갑니다.

어떤 조건에서 provider가 내용 없이 스트림을 끝내는지는 이번 측정에서 재현하지 못했습니다. 성공한
호출 6건 모두 내용이 있었습니다. 그래서 안내 문구는 사유를 단정하지 않고 "질문 내용이 한 조각도
오지 않았습니다"로 두었습니다.

## 오류 분류가 실제로 도달하는지 확인했습니다

`--check-errors`로 일부러 실패를 만들어 분류를 봤습니다. 방어 코드가 도달 가능한지 확인하라는
`AGENTS.md` 규칙에 따른 것입니다.

| 만든 실패 | 관측한 상태 | 분류 |
| --- | --- | --- |
| 잘못된 API 키 | 401 | `llm_auth` |
| 없는 모델 | 404 | `llm_configuration` |
| 첫 청크 시한 초과 | - | `llm_timeout` |
| 청크 없이 끝난 생성 | - | `generation_empty` |
| 일일 토큰 한도 초과 | 429 | `llm_rate_limit` |

### `textStream`은 provider 실패를 던지지 않습니다

이 확인이 실제 결함을 잡았습니다. 처음 구현은 `streamText`의 `textStream`을 소비했습니다.
**잘못된 키 401과 없는 모델 404를 넣었더니 둘 다 예외 없이 청크 0개로 정상 종료해
`generation_empty`로 분류됐습니다.** 인증 실패에 "질문을 만들지 못했습니다. 다시 시도해 주세요"가
나가면 사용자는 풀리지 않는 재시도만 반복합니다.

`fullStream`의 `error` 부분을 던지도록 고쳤습니다(`toThrowingTextStream`). 같은 함수가 `abort`
부분도 중단 예외로 옮깁니다. 더해서 스트림이 끝났을 때 중단 여부를 먼저 확인합니다. 시한 초과로
끊긴 스트림이 provider에 따라 정상 종료로 보일 수 있고, 그대로 두면 시간 초과가 다시
`generation_empty`로 뭉개집니다.

### 처리되지 않은 거절로 프로세스가 죽습니다

`streamText`는 실패하면 `textStream` 외에 `usage`, `response`, `text`도 함께 거절합니다. 우리가
스트림만 읽으면 나머지는 아무도 받지 않는 거절이 되고 Node가 프로세스를 끝냅니다. 측정에서 Groq
일일 토큰 한도 초과가 실제로 이 경로를 밟아 스크립트가 죽었습니다. `toThrowingTextStream`이 세
프로미스의 거절을 소비합니다. 서버에서 이 일이 나면 route 하나가 아니라 프로세스가 죽습니다.

## 근거 입력 상한과 환산식 교정

`wiki/2026-08-24-선택경험-근거-인계-계약.md`가 `확인 필요`로 남긴 항목입니다. 상한 3,500토큰과
3바이트당 1토큰 추정이 실측이 아니라 바이트 기반 추정이었습니다.

실제 요청 토큰으로 재보면 이렇습니다.

| 모델 | 프롬프트 바이트 | 입력 토큰 | 바이트/토큰 |
| --- | --- | --- | --- |
| `openai/gpt-oss-20b` | 10,797 | 2,943 | 3.669 |
| `openai/gpt-oss-20b` | 10,485 | 2,882 | 3.638 |
| `openai/gpt-oss-20b` | 10,758 | 2,935 | 3.665 |
| `openai/gpt-oss-20b` | 10,446 | 2,874 | 3.635 |
| `gemini-3.6-flash` | 10,797 | 2,943 | 3.669 |
| `gemini-3.6-flash` | 10,485 | 3,049 | 3.439 |

**`EVIDENCE_SNAPSHOT_BYTES_PER_TOKEN = 3`을 그대로 둡니다.** 실측 3.44~3.67은 이 값보다 큽니다.
바이트를 3으로 나누면 실제보다 많은 토큰을 세므로 상한을 넘지 않는 쪽으로 틀립니다. 실측값으로
올리면 추정이 정확해지는 대신 안전 여유가 사라집니다. 그리고 3.44~3.67은 한국어 커밋 메시지와
ASCII diff가 섞인 프롬프트의 값입니다. 한국어만으로 이뤄진 근거는 문자 하나가 3바이트이고 토큰도
문자당 1개에 가까워 3에 붙습니다. 3은 그 최악의 경우를 담는 값이므로 유지가 맞습니다. 이번 측정은
값을 바꾸는 근거가 아니라 값이 보수적임을 확인하는 근거입니다.

**`EVIDENCE_SNAPSHOT_MAX_INPUT_TOKENS = 3,500`도 그대로 둡니다.** 상한을 꽉 채운 스냅샷의 실제 입력
토큰이 2,874~3,049이고, 출력 토큰이 939~1,678이었습니다. 최악 조합은 2,943 + 1,678 = 4,621이고
Groq 분당 토큰 한도 8,000의 58%입니다. 꼬리 질문이 같은 근거를 매 턴 다시 싣기 때문에 남은 42%가
다음 턴의 몫입니다. 상한을 올리면 그 몫이 사라집니다. 추정이 실제보다 약 18% 크므로 상한을 올릴
여지는 있지만, 그 여지를 쓸지는 꼬리 질문의 실제 소비를 잰 뒤에 판단해야 합니다.

대신 실측으로 드러난 것은 다른 문제입니다. **커밋 수가 늘면 patch가 사실상 사라집니다.** PR #56은
커밋 4개에서 나머지 근거가 상한의 94%를 먹어 patch 몫이 627바이트(실제 608바이트)였고, 같은 PR을
커밋 6개로 늘리면 168바이트(실제 144바이트)까지 내려갔습니다. patch가 없으면 "실제 코드 기반 질문"이
커밋 메시지 기반 질문이 됩니다.
`wiki/2026-08-24-선택경험-근거-인계-계약.md`가 `확인 필요`로 남긴 "관련 커밋 수 상한"이 이 문제
입니다. 상한을 토큰이 아니라 커밋 수로 걸어야 하는지는 이 이슈의 범위 밖이라 아래에 남겼습니다.

## 기능 정의서에 반영해야 하는 것

노션 기능 정의서를 이 작업에서 고치지 않았습니다. 고쳐야 하는 곳은 두 군데입니다.

- **`실시간 AI Streaming 응답`의 Empty 절.** 현재 "이 기능은 화면에 표시할 응답이 생성되는
  경우에만 동작하므로 별도의 빈 상태는 없습니다"로 명시 결정돼 있습니다. 여기에 "내용 없이 끝난
  스트림은 Empty가 아니라 Error로 다룬다"를 더해야 합니다. 코드는 그렇게 동작하므로 갱신하지
  않으면 정의서와 코드가 어긋납니다.
- **`실시간 AI Streaming 응답`의 재연결 서술.** 전송 중 단절 시 이어받는다는 서술이 있으면 실제
  생성 경로에는 맞지 않습니다. "테스트용 스트림은 이어받고 실제 생성 스트림은 처음부터 다시
  만든다"로 갈라 적어야 합니다.
- **`실제 코드 기반 AI 질문 생성`의 `확인 필요`.** Provider와 모델(Groq `openai/gpt-oss-20b`),
  프롬프트 문구 확정, 재개 방침, 재시도 방침을 이 문서로 채울 수 있습니다.

## 하지 않은 것

- 인터뷰 화면 본체와 근거 패널을 만들지 않았습니다. 하위 이슈 B의 범위입니다.
- 사용자 답변을 반영한 꼬리 질문을 만들지 않았습니다.
- 대화 세션을 저장하지 않았습니다. 저장 계층과 사용자 식별자가 없습니다.
- `test-stream.ts`를 지우지 않았습니다. `empty` 시나리오를 더했습니다.
- provider 오류 매핑을 `stage-a.ts`·`stage-b.ts`와 합치지 않았습니다. 두 파일은 이 이슈의 파일
  경계 밖입니다. `src/features/interview/llm-error.ts`가 같은 매핑의 세 번째 사본입니다. 인터뷰
  기능 안에서는 이 파일 하나만 쓰므로 꼬리 질문이 사본을 더 늘리지는 않습니다.
- 실제 브라우저에서 화면과 함께 확인하지 않았습니다. 화면이 하위 이슈 B의 범위이고, 이번 검증은
  route 응답과 수신부 단위 테스트까지입니다.
