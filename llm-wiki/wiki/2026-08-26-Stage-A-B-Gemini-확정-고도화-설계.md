# Stage A·B 모델을 Gemini로 확정하고 고도화하는 설계

확인 날짜는 2026-08-26입니다. 이 문서는 프로덕션 판단 경로의 제공자를 Gemini 유료 등급으로 옮기고, 그 위에서 판단 품질을 올리는 순서를 정합니다. 로컬 Ollama 전환은 시연용 우회이며 이 문서의 대상이 아닙니다. 근거는 `wiki/2026-08-25-로컬-LLM-제공자-전환.md`에 있습니다.

## 1. 결론 요약

확정한 것입니다.

- Stage A와 Stage B 모두 제공자를 Google Gemini 하나로 모읍니다. Stage A의 Groq 경로는 폐기합니다.
- 유료 등급으로 전환합니다. 예산 상한은 10달러이며, 실지출 추정은 5일 기준 5달러 안팎입니다.
- 두 단계가 같은 제공자를 쓰므로 `llm-provider.ts`의 프로덕션 분기가 하나로 줄어듭니다.

확정하지 않은 것입니다.

- 모델 ID를 `gemini-3.7-flash`로 둘지입니다. 관측한 지연의 원인이 갈리지 않았습니다. 3절에 근거와 판정 규칙을 적었습니다.
- 판단 품질 고도화 4건을 어디까지 이번에 반영할지입니다. 6절에 내용을, 10절에 이슈 경계를 적었습니다.

이 문서는 설계 전체를 담고 이슈는 그보다 작게 자릅니다. 한 이슈로 묶는 범위와 후속 이슈로 미루는 범위는 10절에 적었습니다.

## 2. 왜 제공자를 옮기는가

2026-08-25 실측입니다. 근거 위치는 이슈 #66 본문과 `wiki/2026-08-25-로컬-LLM-제공자-전환.md`입니다.

- Stage A는 Groq 무료 등급의 분당 토큰 한도 8,000에 걸립니다. 정상 호출 하나가 약 7,100 토큰이라 복구 호출 한 번이 곧바로 한도를 넘겨 `llm_rate_limit` 503으로 실행이 끝났습니다.
- Groq Developer tier 업그레이드가 `Developer tier upgrades are temporarily unavailable due to high demand`로 막혀 있어 유료 전환으로 한도를 늘릴 수 없습니다.
- Stage B는 Gemini 무료 등급의 모델당 하루 20요청에 걸립니다. 반복 측정 자체가 불가능했습니다.

Groq에 남을 이유가 없어졌고, Stage B가 이미 Gemini이므로 제공자를 하나로 모으면 오류 계약과 한도 처리를 한 곳에서 관리할 수 있습니다.

유료 전환의 근거가 한도만은 아닙니다. Google은 무료 등급 요청의 입력과 출력을 모델 개선에 쓸 수 있다고 안내하고, 유료 등급에는 그 조항을 적용하지 않는 것으로 알려져 있습니다. 이 서비스는 사용자의 저장소 코드와 diff를 그대로 프롬프트에 담고 대상 사용자는 부트캠프 교육생입니다. 남의 코드를 무료 등급으로 보내는 것은 비용 문제가 아니라 취급 문제이므로, 비용 근거가 없더라도 유료 전환을 해야 합니다.

`확인 필요`입니다. 두 등급의 데이터 사용 조항 원문과 적용 범위를 확인하지 못했습니다. 확인 결과는 `raw/`에 원문 인용과 확인 날짜를 남깁니다.

이 결론은 3절 측정 계획에 제약을 겁니다. 결제 전 측정은 본인 저장소인 `demian`으로만 하고, 교육생 저장소는 유료 전환 뒤에만 입력으로 씁니다.

## 3. 모델 후보와 지연 문제

`gemini-3.7-flash`의 지연은 한도 문제가 아니라 응답 지연으로 관측됐습니다. 같은 키로 `"say hi"` 한 줄을 직접 호출한 소요입니다.

| 모델 | 상태 | 소요 |
| --- | --- | --- |
| `gemini-3.7-flash` | 200 | 16.0초 / 56.8초 / 119.2초 |
| `gemini-3.5-flash-lite` | 200 | 1.0초 |
| `gemini-3.1-flash-lite` | 200 | 0.9초 |

`thinkingConfig.thinkingBudget: 0`을 줘도 56.8초였고 응답에 `thoughtSignature`가 붙어 있었으므로 사고 예산이 원인이 아닙니다. 출력 2토큰에 이 정도가 걸리므로 `STAGE_B_TOTAL_BUDGET_MS` 55초 안에 실제 페이로드가 끝날 수 없습니다.

원인 가설이 셋입니다. 앞의 두 개만 두고 판정 규칙을 세우면 잘못된 결정을 내립니다.

1. 무료 등급 요청에 대한 제공자 측 처리 지연입니다.
2. 사고 과정을 포함한 모델 자체의 응답 특성입니다.
3. 모델별 처리 우선순위 차이입니다.

같은 표가 3번을 가장 강하게 지지합니다. `gemini-3.5-flash-lite`와 `gemini-3.1-flash-lite`는 같은 키, 같은 무료 등급에서 1초 안에 응답했습니다. 무료 등급 자체가 원인이라면 Lite 계열도 같이 느려야 하는데 100배 이상 빠릅니다. 즉 지연의 주된 원인은 등급이 아니라 모델입니다.

이 판단이 실행 순서를 바꿉니다. 결제는 지연 판정의 선행 조건이 아닙니다. Lite 계열로 운영 입력 지연을 먼저 재면 결제 없이도 후보를 좁힐 수 있습니다. 결제 전 측정은 2절 데이터 조항 때문에 본인 저장소인 `demian`으로만 합니다.

측정 기준입니다. `"say hi"` 한 줄이 아니라 운영 입력으로 재야 합니다. Stage A는 묶음 11개 프롬프트, Stage B는 커밋 30개와 patch 예산을 채운 입력을 씁니다. 각 5회를 재고 중앙값과 최댓값을 함께 남깁니다. 판정선은 두 단계 모두 최댓값이 예산 55초의 절반인 27.5초 안입니다. 절반을 기준으로 두는 이유는 라우트가 상세 조회와 판단을 같은 예산 안에서 처리하기 때문입니다.

무료 등급은 모델당 하루 20요청이므로 한 모델을 하루에 5회씩 재면 두 단계를 합쳐 10회입니다. 하루에 모델 하나를 재고 다음 날 다음 모델을 잽니다.

판정 규칙입니다.

- 무료 등급에서 Lite 계열이 27.5초 안이면 Lite를 유력 후보로 둡니다. 결제 뒤 `gemini-3.7-flash`를 같은 방식으로 재서 27.5초 안이면 `gemini-3.7-flash`로 확정하고, 넘으면 Lite로 확정합니다.
- 결제 뒤에도 `gemini-3.7-flash`가 27.5초를 넘으면 원인을 무료 등급이 아니라 모델 특성으로 확정하고 재측정을 반복하지 않습니다. 같은 측정을 다시 도는 것이 가장 흔한 시간 낭비입니다.
- Stage A와 Stage B에 서로 다른 모델을 써도 됩니다. 두 단계는 모델 ID 주입 지점이 이미 분리되어 있습니다. Stage B가 diff를 읽는 쪽이라 지연에 더 민감하므로, 한쪽만 내려야 한다면 Stage B를 먼저 Lite로 내립니다.
- 두 단계 모두 넘으면 예산 상수 재산정을 별도 이슈로 분리합니다. 이 문서에서는 상수를 바꾸지 않습니다.

Lite로 내리는 결정에는 품질 확인이 따라붙습니다. Lite 계열이 Stage A의 전수 응답 계약과 Stage B의 출력 계약을 지키는지 같은 입력 5회로 확인해야 합니다. 지연만 보고 모델을 내리면 로컬 모델에서 겪은 계약 위반을 프로덕션에서 다시 만납니다.

`확인 필요`입니다. `gemini-3.5-flash-lite`와 `gemini-3.1-flash-lite`의 단가와 구조화 출력 지원 범위를 확인하지 못했습니다. 5절 비용 산정은 `gemini-3.7-flash` 단가로만 계산한 값입니다.

## 4. 비용 산정

출처가 둘입니다. 하나는 2026-08-26 사용자 제공 산정이고, 다른 하나는 그 값을 이 문서에서 다시 계산한 결과입니다. 단가 가정은 100만 토큰당 입력 0.50달러, 출력 3.00달러입니다.

| 호출 | 입력 토큰 | 출력 토큰 | 사용자 제공 | 재계산 |
| --- | --- | --- | --- | --- |
| Stage A | 약 7,100 | 약 1,000 | 0.006달러 | 0.00655달러 |
| Stage B | 약 20,000 | 약 2,000 | 0.016달러 | 0.016달러 |
| 분석 1회 | | | 0.022달러 | 0.0226달러 |

10달러로 가능한 횟수입니다.

| 작업 | 사용자 제공 | 재계산 |
| --- | --- | --- |
| 전체 분석 | 약 450회 | 약 442회 |
| Stage A만 | 약 1,700회 | 약 1,527회 |
| Stage B만 | 약 620회 | 약 625회 |

Stage A 단독 횟수는 1,527회로 확정합니다. 사용자 제공값 1,700회는 출력 토큰을 낮게 잡은 값이며 제공자가 근거가 약하다고 알려 왔습니다. 회당 0.00655달러가 위 표의 토큰 수와 단가에서 그대로 나오는 값이므로 이쪽을 씁니다. 이 항목은 확인 필요에서 내렸습니다.

어느 값을 쓰든 결론은 같습니다. 10달러는 이 프로젝트에 충분합니다.

Stage B 입력 20,000 토큰은 `STAGE_B_MAX_TOTAL_PATCH_CHARS` 60,000자를 절반으로 환산한 값입니다. 코드 주석의 바이트당 0.676 토큰 비율을 그대로 쓰면 약 40,000 토큰이고, 그 경우 Stage B 회당 비용은 0.026달러로 올라 전체 분석 가능 횟수가 약 310회로 줄어듭니다. 2026-08-25 로컬 측정에서 커밋 30개·patch 60,000자 입력의 직렬화 크기가 145KB였으므로 상한을 채운 입력은 실제로 40,000 토큰에 가깝습니다. 절반 가정은 낙관적입니다.

`확인 필요`입니다. 실제 토큰 사용량을 재야 이 구간이 닫힙니다. 7절에 계측 항목을 적었습니다.

비용을 늘리는 요인 둘을 감안합니다.

- 스키마 검증 실패는 모델이 응답을 생성한 뒤 걸러지므로 토큰을 그대로 씁니다. 전수 응답 계약을 4회 중 3회 지킨다면 33퍼센트를 더 잡습니다.
- 인터뷰 스트리밍은 분석과 별도입니다. 턴마다 코드 컨텍스트를 재전송하므로 8턴 세션 하나가 캐싱 없이 약 0.15달러이고, 세션 30회는 약 4.5달러입니다. 이 값은 사용자 제공 추정이며 측정된 값이 아닙니다.

## 5. 코드 변경 면

제공자만 바꾸면 끝나지 않습니다. 지금 코드에는 Groq 전제가 네 곳에 박혀 있고, 제공자를 하나로 모으면서 같이 정리할 자리가 두 곳 더 있습니다.

### 5-1. 제공자와 모델 상수

`llm-provider.ts`의 `createStageAModel` 프로덕션 분기를 `createGroq()`에서 `createGoogle()`로 바꿉니다. `stage-a.ts`의 `STAGE_A_MODEL` 상수를 Gemini 모델 ID로 교체하고, 이슈 #19 실측 근거를 적은 주석을 새 근거로 갱신합니다. 로컬 분기는 그대로 둡니다. 로컬은 OpenAI 호환 경로를 계속 씁니다.

### 5-2. 한도 메타데이터 계약

`stage-a.ts`는 응답 헤더의 `x-ratelimit-remaining-tokens`와 `x-ratelimit-reset-tokens`를 읽어 `__rateLimit`을 만듭니다. 이 헤더는 Groq 규약입니다. Gemini가 같은 헤더를 주지 않으면 `__rateLimit`이 항상 null이 되고, 청크가 둘 이상일 때 첫 청크가 정상 완주하면 `candidate-client.ts`가 `LLM 토큰 한도 메타데이터가 없습니다`로 Stage A 전체를 실패시킵니다. 로컬 전환에서 이미 같은 문제를 만나 서버에서 메타데이터를 합성해 막았습니다.

점수 선별 뒤에는 보통 청크가 하나이므로 평소에는 드러나지 않습니다. 드러나는 순간이 큰 저장소이므로 방치하면 안 됩니다.

자체 회계로 옮기기로 확정합니다. 청크 간 대기 판단을 헤더에서 떼어내고 `generateObject`가 돌려주는 `usage`로 소비를 세며, 한도 초과는 사후에 상태 코드로만 처리합니다.

헤더 파싱 규칙만 교체하는 방식을 택하지 않는 이유입니다. 이 문제는 제공자를 바꿀 때마다 되돌아옵니다. Groq 규약으로 짠 코드가 로컬 OpenAI 호환 경로에서 깨져 서버에서 메타데이터를 합성해 막았고, 이제 Gemini에서 같은 자리를 또 고치고 있습니다. `usage`는 AI SDK가 제공자와 무관하게 채워 주는 값이므로 여기로 옮기면 이 자리가 더 이상 제공자에 묶이지 않습니다. Gemini에 대응 헤더가 있더라도 자체 회계로 갑니다.

자체 회계의 한계를 함께 적어 둡니다. 자체 회계는 이 프로세스가 쓴 토큰만 압니다. 같은 키를 쓰는 다른 실행이 한도를 먹고 있으면 알 수 없습니다. 그래서 선제 대기는 근사치로만 쓰고, 실제 한도 초과는 429 응답을 받은 뒤 재시도로 처리하는 경로가 반드시 함께 있어야 합니다.

헤더 덤프는 그래도 한 번 합니다. 확인용이며 그 결과로 설계를 바꾸지는 않습니다.

### 5-3. 오류 분류

`errors.ts`의 두 판별 함수는 Groq 본문 문자열에 묶여 있습니다. `isRateLimitResponseBody`는 `rate_limit_exceeded`를, `isModelOutputFailureResponseBody`는 `json_validate_failed`를 찾습니다. Gemini는 한도 초과를 429와 `RESOURCE_EXHAUSTED`로, 과부하를 503과 `UNAVAILABLE`로 돌려주는 것으로 알려져 있습니다. 두 함수의 판별 문자열과 `mapLlmError`의 413 분기를 함께 재검토해야 합니다.

413 분기는 특히 Groq 전용입니다. Groq가 분당 토큰 초과를 429가 아니라 413으로 돌려주기 때문에 만든 갈래이므로, Gemini로 옮기면 이 분기는 요청 과대만 남습니다. 분기를 지우기 전에 Gemini가 큰 입력에 어떤 상태 코드를 주는지 확인합니다.

`확인 필요`입니다. Gemini 오류 본문의 실제 문자열을 관측하지 못했습니다. 추측으로 판별 문자열을 넣지 않고, 실제 응답을 한 번 받아 본문을 근거로 확정합니다.

### 5-4. Stage A 입력 상한의 근거 소멸

`STAGE_A_CHUNK_MAX_BYTES` 10,500과 `STAGE_A_CHUNK_MAX_REQUEST_BYTES` 20,000은 모델 컨텍스트가 아니라 Groq 무료 등급의 분당 토큰 한도 8,000에서 역산한 값입니다. 근거는 `wiki/2026-08-25-Stage-A-청크-폐기와-점수-선별-전환.md`에 있습니다. 제공자를 옮기면 이 근거가 사라집니다.

여기서 고도화 여지가 생깁니다. 상한을 올리면 점수 선별에서 잘려 나가던 묶음이 판단 대상으로 들어옵니다. 2026-08-25 측정에서 `demian`은 21묶음 중 15개, `andbread`는 66묶음 중 10개만 한 청크로 나갔습니다. `andbread`에서 56묶음이 판단조차 되지 않았다는 뜻입니다.

다만 상한을 올리면 회당 비용이 그대로 올라갑니다. 입력이 두 배면 Stage A 회당 0.00655달러가 약 0.010달러가 됩니다. 상한 재산정은 지연 측정과 비용 측정이 끝난 뒤에 별도 항목으로 다룹니다. 이 문서에서는 상한을 바꾸지 않습니다.

### 5-5. 프롬프트 캐싱 배치

제공자를 하나로 모으는 실익 중 하나가 캐싱입니다. `@ai-sdk/google`은 제공자 옵션으로 `cachedContent`를 받고 사용량에 `cachedContentTokenCount`를 돌려줍니다. 근거는 `node_modules/@ai-sdk/google/dist/index.d.ts`의 두 필드입니다. 명시적 캐시를 붙일 자리가 SDK 수준에서 이미 열려 있습니다.

캐시는 접두사가 같아야 맞습니다. 그래서 구간마다 실익이 다릅니다.

- 인터뷰 스트리밍이 가장 큽니다. 8턴 세션이 같은 코드 컨텍스트를 매 턴 재전송하므로 캐시 대상이 회차마다 그대로입니다. 4절의 세션당 0.15달러 추정이 이 구간에서 나옵니다.
- Stage A와 Stage B는 실익이 작습니다. 두 단계의 프롬프트 본문은 저장소마다 다르고 같은 저장소를 다시 분석할 때만 겹칩니다. 안정적인 접두사는 시스템 프롬프트뿐이고 그 길이는 수백에서 1,000 토큰 수준입니다.

그래도 배치는 지금 잡습니다. 캐시가 접두사 일치를 요구하므로 안정적인 것을 앞에, 저장소마다 달라지는 것을 뒤에 두는 순서는 제공자 교체와 같은 시점에 정하는 것이 싸게 끝납니다. 순서만 먼저 맞춰 두고 캐시 핸들 연결은 인터뷰 배선과 함께 합니다.

`확인 필요`입니다. Gemini 명시적 캐시의 최소 토큰 요건과 최소 보관 기간, 그리고 캐시 저장 자체에 붙는 비용을 확인하지 못했습니다. 시스템 프롬프트만으로 최소 요건을 채우지 못하면 Stage A와 Stage B의 캐싱은 실익이 없다고 결론 내고 인터뷰 구간에만 씁니다.

### 5-6. `mapLlmError` 중복

`mapLlmError`가 `stage-a.ts`와 `stage-b.ts`에 거의 같은 형태로 두 벌 있습니다. 다른 부분은 오류 메시지의 단계 이름뿐입니다. 지금은 한쪽만 고치면 두 단계의 오류 분류가 어긋납니다. 5-3절에서 판별 문자열과 상태 코드 분기를 어차피 손대야 하므로, 그 작업을 두 곳에 두 번 하지 않도록 함수를 `errors.ts`로 올려 단계 이름만 인자로 받게 합니다.

이 항목은 동작 변경이 아니라 중복 제거입니다. 기존 테스트가 두 단계의 오류 분류를 이미 검증하고 있으므로 통합 후 그 테스트가 그대로 통과하는지로 확인합니다.

## 6. 판단 품질 고도화 4건

앞의 두 항목은 로컬 전환 과정에서 드러난 프로덕션 프롬프트의 계약 누락입니다. 지금까지는 프로덕션 모델이 우연히 덮어 주고 있었습니다. 세 번째는 프롬프트가 아니라 그 앞단의 선별 점수이고, 네 번째는 판단 단위가 성립하지 않는 저장소를 다루는 방식입니다.

우선순위는 6-3, 6-1, 6-2, 6-4 순서입니다. 6-3이 먼저인 이유는 순수 함수 수정이라 LLM 호출 없이 검증되고 효과가 Stage A 입력 자체에 걸리기 때문입니다.

### 6-1. Stage B 출력 계약이 프롬프트에 없습니다

`validateExperienceCandidateOutput`은 후보가 3개 미만이면 `insufficientCandidatesReason`을 요구하고 3개면 null을 요구합니다. Stage B 시스템 프롬프트는 이 규칙을 말하지 않습니다. `gemini-3.7-flash`는 스키마만 보고 지켰지만 `qwen2.5:7b`와 `llama3.1:8b`는 모두 어겼습니다.

반영을 제안합니다. 검증기가 강제하는 규칙을 프롬프트가 말하지 않는 것은 계약 누락입니다. 반영하면 모델을 바꿀 때마다 같은 실패를 다시 만나지 않습니다.

검증 방법입니다. 반영 전후로 같은 입력 5회씩 돌려 최종 후보 수와 부족 사유 채움 여부를 비교합니다. 반영 후에 후보 수 분포가 달라지면 되돌리고 그 사실을 기록합니다.

### 6-2. Stage A 판단 대상 범위가 프롬프트에 없습니다

묶음 요약의 커밋 제목에는 `Merge pull request #35` 같은 문구가 섞여 있습니다. `qwen2.5:7b`는 그 번호들을 판단 대상으로 끌어와 입력 11묶음에 46개 판정을 돌려주고 `unknown_sha`로 끝났습니다. 화면 경로에서 4회 연속 같은 방식으로 실패했습니다. 프로덕션 모델에서는 관측되지 않았습니다.

반영을 제안합니다. 판단 대상이 각 묶음 첫 줄의 `PR#번호`뿐이라는 사실은 프롬프트가 말해야 하는 범위 정보입니다.

이슈 #66은 Stage A 프롬프트 변경을 non-goal로 두었으므로, 이 항목은 이 문서의 후속 작업이며 별도 승인이 필요합니다.

검증 방법입니다. 반영 전후로 같은 입력 5회씩 돌려 전수 응답 계약 충족률과 후보 상한 준수율을 비교합니다.

### 6-3. 선별 점수가 규모에 편중돼 있습니다

`scoreWorkUnit`은 신호 아홉 개의 발화 수를 그대로 더합니다. 가중치가 없습니다. 그런데 실측에서 발화율이 높은 신호는 `many_commits`, `long_span`, `many_files` 세 개이고 전부 규모 지표입니다. `revert_or_hotfix`는 `demian`과 `andbread` 모두 0퍼센트, `infrastructure_added`는 3퍼센트 이하였습니다. 근거는 `work-unit-score.ts`의 선언부 주석이고, 그 주석은 이 점수가 대체로 규모 점수라고 이미 적고 있습니다.

여기서 모순이 생깁니다. 선별은 규모로 상위 묶음을 올려 보내고, Stage A 시스템 프롬프트는 "규모가 크다는 이유만으로 고르지 말고 설명할 거리가 있는 묶음을 고르세요"라고 지시합니다. 모델이 지시를 지키면 지킬수록 올라온 입력과 어긋납니다.

제안하는 변경입니다. 신호를 성격 축과 규모 축으로 나눕니다. 성격 축은 `revert_or_hotfix`, `infrastructure_added`, `dependency_added`, `file_rewritten_repeatedly`, `large_refactor`, `performance_or_refactor_prefix`입니다. 규모 축은 `many_commits`, `long_span`, `many_files`입니다. 정렬은 성격 축 발화 수를 먼저 보고 같을 때만 규모 축으로 끊습니다. 점수 하나로 합치지 않습니다. 합치면 다시 규모가 이깁니다.

이 항목을 셋 중 먼저 하는 이유입니다. `scoreWorkUnit`은 순수 함수이고 `work-unit-score.test.ts`가 붙어 있습니다. LLM 호출 없이 검증되므로 비용이 0이고, 실패해도 되돌리기 쉽습니다. 반대로 효과는 Stage A 입력 자체를 바꾸는 것이라 프롬프트 문구보다 큽니다.

검증 방법입니다. `demian`과 `andbread` 캐시 상세로 정렬 결과를 비교해, 새 정렬에서 올라오는 묶음과 밀려나는 묶음의 목록을 남깁니다. 성격 신호가 하나도 발화하지 않는 저장소에서는 정렬이 지금과 같아야 하며, 그 경우가 회귀 테스트 대상입니다.

`확인 필요`입니다. 성격 축이 비어 있는 저장소에서 규모 축만으로 정렬하면 지금과 동일한데, 그때 선별 품질이 나아지지 않는다는 점은 이 변경의 한계로 남습니다.

### 6-4. PR 커버리지가 낮은 저장소

`work-unit.ts`는 Pull Request에 속하지 않은 커밋을 `no_pull_request`로 제외합니다. `demian`은 83커밋 중 81개, `andbread`는 319커밋 중 319개가 Pull Request에 묶여 있어 제외 비중이 작다고 판단했습니다. 근거는 `wiki/2026-08-24-경험-판단단위-PR-묶음-전환-검토.md`입니다.

이 판단의 표본이 편향돼 있습니다. 두 저장소 모두 Pull Request 기반으로 작업한 저장소입니다. 대상 사용자는 부트캠프 교육생이고 `main`에 직접 푸시하는 저장소가 흔합니다. 그런 저장소를 넣으면 전 커밋이 제외되어 후보가 0개가 됩니다.

지금 화면이 아무 말도 하지 않는 것은 아닙니다. `WORK_UNIT_EXCLUSION_COPY`가 제외 사유를 문장으로 갖고 있고, 후보 0개 화면(`no_stage_a_candidates`, `no_final_candidates`)이 제외 정보를 `StageAExclusions`로 함께 그립니다. 즉 조용한 실패는 아닙니다. 사용자가 보는 것은 "다른 Repository를 선택해 주세요"이고, 그 이유가 Pull Request 부재라는 사실도 함께 보입니다.

그래서 필요한 것은 오류 처리가 아니라 사전 안내입니다. 저장소를 입력한 직후 커밋 목록 단계에서 Pull Request 커버리지를 계산해, 일정 비율 아래면 분석 시작 전에 알립니다. 이때 분석을 막지는 않습니다. 커버리지가 낮아도 일부 묶음으로 진행할 수 있는 저장소가 있습니다.

파일 겹침으로 묶는 폴백은 다시 꺼내지 않습니다. `andbread` 319커밋 중 282커밋이 한 묶음으로 뭉쳐 판단 단위가 무의미해졌고 그 근거로 이미 폐기했습니다.

`확인 필요`입니다. 교육생 저장소의 실제 Pull Request 커버리지 분포를 모릅니다. 사전 인터뷰에서 저장소 URL을 받아 커버리지만 계산해 보면 이 항목의 심각도가 바로 드러납니다. 커버리지가 낮은 저장소가 다수면 안내로 끝낼 문제가 아니라 판단 단위 자체를 다시 봐야 합니다.

## 7. 비용 통제와 계측

### 7-1. 실제 토큰 사용량 계측

`generateObject`는 `usage`를 돌려줍니다. Stage A는 이미 `usage.totalTokens`를 한도 회계에 쓰고 있고 Stage B는 버립니다. 두 단계 모두 입력과 출력 토큰을 서버 로그에 남깁니다. 4절의 20,000 대 40,000 구간은 이 값이 쌓이면 닫힙니다.

로그에는 토큰 수와 소요 시간만 남기고 프롬프트 본문과 응답 원문은 남기지 않습니다. 저장소 코드가 그대로 로그에 흘러 들어가는 것을 막습니다.

### 7-2. 같은 저장소 반복 분석 차단

비용을 결정하는 것은 호출 수가 아니라 같은 저장소를 반복 분석하는 것입니다. 프롬프트 한 줄을 고칠 때마다 저장소 전체가 다시 돌면 Stage A와 Stage B가 통째로 재실행됩니다.

`scripts/measure-pipeline.ts`에 이미 상세 조회 캐시(`--cache`)와 `--skip-stage-a`가 있습니다. `--skip-stage-a`는 캐시 상세에서 후보를 만들어 Stage B만 돌립니다. 여기에 Stage A 결과 자체를 파일로 저장하고 재사용하는 옵션을 더합니다. 그러면 Stage B 프롬프트를 고치는 동안 Stage A 호출이 0이 됩니다.

Stage A만 반복할 때는 Stage B를 부르지 않는 `stage-a` 단계를 그대로 씁니다. 이 단계는 이미 Stage B를 호출하지 않습니다.

### 7-3. 지출 상한

부족해질 시나리오는 무한 루프나 재시도 폭주로 호출이 몰리는 경우 하나입니다. Google Cloud 콘솔에서 예산 상한과 알림을 걸어 둡니다.

코드 쪽 상한도 이미 있습니다. Stage A 라우트의 `selectWithRecovery`는 복구 시도를 2회로 제한합니다. 한 요청이 최대 3회 호출하므로 회당 비용 상한은 Stage A 0.02달러 수준입니다. 이 상한을 늘리는 변경은 비용 근거와 함께 기록합니다.

## 8. 실행 순서

결제 전에 할 수 있는 것을 먼저 합니다.

1. 선별 점수의 축 분리(6-3)를 넣습니다. LLM 호출이 없고 기존 테스트로 검증됩니다.
2. 무료 등급에서 Lite 계열의 운영 입력 지연을 잽니다. 입력은 본인 저장소 `demian`만 씁니다. 모델당 하루 20요청이므로 하루에 모델 하나입니다.
3. 토큰 사용량 로깅을 넣습니다. 이후 모든 호출이 실제 입력·출력 토큰을 남기므로 4절의 20,000 대 40,000 구간이 닫히기 시작합니다.

그다음 결제합니다.

4. 유료 등급으로 전환하고 Google Cloud에 예산 상한과 알림을 설정합니다. 데이터 사용 조항 확인 결과를 `raw/`에 남깁니다.
5. `gemini-3.7-flash`의 운영 입력 지연을 같은 방식으로 재고 3절 판정 규칙으로 모델을 확정합니다. 판정선을 넘으면 재측정을 반복하지 않고 Lite로 확정합니다.
6. 같은 측정에서 응답 헤더를 덤프합니다. 확인용이며 5-2절 결론은 자체 회계로 고정입니다.
7. 큰 입력과 한도 초과를 일부러 만들어 오류 본문을 관측하고, 5-3절의 판별 문자열과 상태 코드 분기를 확정합니다.
8. `mapLlmError`를 `errors.ts`로 통합하고(5-6), 제공자와 모델 상수를 교체하고(5-1), 한도 회계를 `usage` 기반으로 옮깁니다(5-2). 세 변경이 같은 파일들을 건드리므로 한 묶음으로 처리합니다. `llm-provider.ts`의 회귀 테스트가 프로덕션 기본 동작을 지키는지 함께 갱신합니다.
9. 프롬프트 계약 2건(6-1, 6-2)을 각각 반영 전후 5회씩 비교해 판단합니다. Stage A 항목은 이슈 #66 non-goal이므로 별도 승인 후에 진행합니다.

이후는 후속 이슈로 넘깁니다.

10. PR 커버리지 사전 안내(6-4), 캐시 핸들 연결(5-5), `STAGE_A_CHUNK_MAX_BYTES` 재산정(5-4)입니다. 앞의 두 개는 화면과 인터뷰 배선에 걸리고, 마지막 하나는 비용 측정 결과가 필요합니다.

각 단계는 앞 단계의 측정 없이 진행하지 않습니다. 추측으로 상수와 판별 문자열을 바꾸면 지금 Groq 전제와 같은 종류의 부채가 다시 쌓입니다.

## 9. 확인 필요 목록

- `gemini-3.7-flash`의 유료 등급 지연입니다. 원인 가설 셋 중 모델별 차이가 가장 유력하지만 측정으로 갈리지 않았습니다.
- `gemini-3.5-flash-lite`와 `gemini-3.1-flash-lite`의 단가, 구조화 출력 지원 범위, 그리고 두 단계의 출력 계약 준수율입니다.
- Gemini 오류 응답의 상태 코드와 본문 문자열입니다.
- Stage B 상한을 채운 입력의 실제 토큰 수입니다. 20,000과 40,000 중 어느 쪽에 가까운지에 따라 가능 횟수가 442회와 310회로 갈립니다.
- Gemini 명시적 캐시의 최소 토큰 요건, 최소 보관 기간, 저장 비용입니다. 시스템 프롬프트만으로 요건을 못 채우면 Stage A·B 캐싱은 실익이 없습니다.
- 무료 등급과 유료 등급의 데이터 사용 조항 원문과 적용 범위입니다.
- 교육생 저장소의 Pull Request 커버리지 분포입니다. 낮은 저장소가 다수면 6-4는 안내가 아니라 판단 단위 재검토가 됩니다.
- 성격 축 신호가 전혀 발화하지 않는 저장소에서 6-3이 선별 품질을 바꾸지 못하는 한계입니다.

닫은 항목입니다. Stage A 단독 가능 횟수는 1,527회로 확정했고(4절), 한도 메타데이터 처리는 자체 회계로 확정했습니다(5-2절).
