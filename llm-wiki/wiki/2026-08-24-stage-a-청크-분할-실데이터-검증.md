# Stage A 청크 분할 실데이터 검증

이슈 #44의 `andbread/Andbread_Frontend` 실데이터 검증 기록입니다. GitHub 상세 319건은 저장소 밖 임시 캐시에 저장하고 반복 실행에서 재사용했습니다. 토큰·키·모델 응답 원문은 기록하지 않았습니다.

## 입력과 선행 실패

- 작성자 커밋 431개, 블랙리스트 통과 319개, 제외 112개였습니다.
- 상세 조회 캐시 생성은 병렬도 8로 수행했습니다. 이후 실행은 GitHub 상세 요청 0회였습니다.
- 무분할 319개 입력은 49,957토큰 요청으로 Groq 8,000 TPM의 약 6.2배여서 413 `rate_limit_exceeded`가 발생했습니다.
- 12개 청크는 17회까지 성공한 뒤 18번째에서 전수 SHA 응답 계약 위반으로 중단됐습니다. 성공 호출 사용 토큰은 2,524~5,144였습니다.
- 실패한 18번째 청크는 커밋 12개, 경량 입력 4,693바이트(단순 4문자/토큰 추정 1,174), 파일 26개, 최장 메시지 41자였습니다. 크기나 파일 수가 특별히 크지 않아 모델의 확률적 SHA 누락으로 봅니다. 실패 응답은 전체 계약 검증에서 거부되어 실제 사용 토큰과 반환 SHA 수는 수집하지 못했습니다.

## 확정 정책

- 최대 8커밋, 6,000바이트, 32파일의 세 경계를 동시에 적용합니다.
- 누락 SHA만 최대 두 번 재호출하고, 여전히 실패하면 판단 실패 수와 사유를 사용자에게 표시합니다.
- 후보가 20개를 넘으면 청크별 절반 이하만 남기는 재판단을 최대 6라운드 수행합니다.
- TPM 대기는 응답 헤더의 잔여 토큰과 reset 시간으로만 결정합니다. 8개 청크 실측의 사용 토큰 변동을 흡수하도록 6,000토큰을 다음 호출 reserve로 두고 reset 경계에 1초를 보정합니다.

## 319개 완주 결과

완주하지 못했습니다. Groq 무료 등급의 일일 토큰 한도(TPD 200,000)가 소진됐고, 리드의 측정 중단 지시에 따라 재시도하지 않았습니다. TPD 회복 뒤 같은 상세 캐시로 재측정해야 합니다.

확인된 범위는 실행별로 구분합니다.

- 첫 8개 청크 실행은 36개 청크, 288커밋까지 전수 SHA 계약을 지켰습니다. 청크 사용 토큰은 867~3,745, LLM 응답 소요는 1.7~3.6초였습니다. 37번째 호출은 TPD가 아니라 당시 4,000토큰 고정 reserve가 부족해 TPM 413으로 중단됐고, 이 관찰로 reserve를 6,000으로 고쳤습니다.
- 별도 8개 프로브는 7/8만 반환해 누락 복구 필요성을 확인했습니다. 이 프로브는 복구 도입 전 직접 호출이라 복구 성공률 측정에는 포함하지 않습니다.
- 최종 정책 실행은 입력 경계 때문에 8·5·6·8커밋인 4개 청크, 총 27커밋을 완료했고 292커밋이 남았습니다. 후보 수는 0·0·6·8, 사용 토큰은 2,279·2,454·2,946·2,467, provider 호출 자체는 합계 약 38.6초였습니다. 완료된 네 청크에서는 누락과 복구 호출이 0회였습니다.
- 최종 실행은 시작 전부터 TPD가 거의 소진돼 있었습니다. 완료된 네 호출 앞의 provider 안내 대기는 212.5초·974.2초·864.4초·813.0초로 합계 약 47분 44초였습니다. 다섯 번째 대기 안내 713.7초 도중 측정이 종료됐습니다.
- 319개 전체의 최종 후보 수, 전체 누락·중복, 복구 발동 횟수와 성공률, 재판단 라운드, 최종 품질, Stage B 품질은 확인하지 못했습니다. 319개 전체에 대해 413·429가 없었다고 주장할 수도 없습니다.

부분 실행만으로 확인된 것은 동적 청크 경계가 실제 데이터에서 8개보다 작은 5·6개 청크를 만들고, 완료 청크의 사용 토큰이 8,000 TPM 안에 들어오며, TPD 소진은 TPM reset 대기와 별개의 한도라는 점입니다. 사용자 흐름은 TPD 오류를 체크포인트와 함께 명시적으로 반환하므로 완료 청크를 다시 판단하지 않고 재개할 수 있습니다.
