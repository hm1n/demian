# Repository 확인 가능·불가 구분 계약

## 문서 목적

이슈 #47의 완료 조건에 따라 확인 가능·확인 불가 항목 목록을 문서로 확정합니다. 이슈 #32와 #47이 이미 결정한 규칙을 그대로 옮기고, 실제 구현 위치와 화면 표시 방식을 함께 기록합니다.

## 판별 단위와 축 구분

판별 단위는 문장 조각이 아니라 화면 항목입니다. 출처(`origin`) 축과 검증 여부(`VerifiabilityStatus`) 축은 서로 다른 축이며 하나로 합치지 않습니다. `origin`은 근거가 어디서 왔는지만 나타내고, `VerifiabilityStatus`는 그 값을 Repository로 확인할 수 있는지만 나타냅니다.

## 확인 가능 항목

- 커밋 SHA, 제목, 메시지 원문
- 파일 경로, 상태, 추가·삭제 줄 수, 변경 수
- patch 본문
- PR 번호, 제목, 상태, 브랜치
- 관련 커밋이 대표 커밋과 같은 PR에 속한다는 관계

모두 GitHub 응답 값이거나 서버의 `assertCandidateEvidence`가 검증을 통과한 관계입니다. 목록과 상세 화면 모두 이 항목들을 표시하는 자리에 `확인 가능` 안내를 함께 둡니다.

### AI 선택과 확인 가능의 경계 (PR #52 재검증 P2로 확정)

`relatedShas`와 `citedFilePaths`는 어떤 SHA·경로를 후보로 넣을지 LLM이 고른 값입니다. `assertCandidateEvidence`는 다음 두 가지만 증명합니다.

- 관련 SHA가 대표 커밋과 같은 PR에 속한다는 사실
- 인용 경로가 후보 커밋(대표 커밋과 관련 커밋)의 실제 변경 파일 목록 안에 있다는 사실

**그 항목이 실제로 근거로서 관련이 있다는 판단은 증명하지 않습니다.** 대표 커밋이 건드린 파일 중 근거와 무관한 파일도 `citedFilePaths`에 들어오면 검증을 통과합니다. 그래서 화면에 다음 구분을 둡니다.

- `인용 파일 N개`, `관련 커밋 N개`처럼 **개수 자체**는 `AI 선택` 태그로 표시합니다. `확인 가능`으로 표시하지 않습니다.
- 상세 화면의 관련 커밋 목록에는 "대표 커밋과 같은 PR에 속한다는 관계까지만 확인되고, 근거로서 관련 있다는 판단은 확인 불가"라는 안내를 함께 둡니다.
- PR 번호·제목·상태·브랜치처럼 LLM의 선택 없이 GitHub 응답 그대로인 값에만 `확인 가능`을 씁니다.

이 구분이 흐려지면 이 이슈가 없애려던 바로 그 오표시(LLM이 고른 것을 Repository 사실처럼 제시)가 다른 자리에서 재발합니다.

## 확인 불가 항목

- 성능 개선 폭
- 사용자 영향
- 다른 대안과의 비교
- 협업·논의 배경
- 커밋 메시지에 적힌 수치·비교·의도가 실제로 그러했는지
- LLM이 작성한 `evidence` 문장 전체

커밋 메시지에 적힌 수치나 비교, 의도는 "메시지에 그렇게 적혀 있다"는 사실까지만 확인 가능하고 주장의 참·거짓은 확인 불가입니다. `evidence` 문장은 Repository 값이 아니라 해석이므로 문장 전체를 확인 불가로 분류합니다.

## 구현 위치

`src/features/experience-candidates/evidence-verifiability.ts`에 판별 규칙을 상수로 고정했습니다.

- `VERIFIABILITY_LABEL`: `Record<VerifiabilityStatus, string>` 형태의 라벨 맵입니다. `EVIDENCE_ORIGIN_LABEL`과 같은 방식을 따릅니다.
- `EVIDENCE_VERIFIABILITY_NOTICE`: `evidence` 문장 옆에 표시하는 확인 불가 안내 문구입니다. 목록과 상세 화면이 같은 문구를 공유합니다.
- `REPOSITORY_VERIFIED_NOTICE`: 상세 화면에서 변경 파일·코드 변경 내역·PR 정보가 확인 가능임을, 관련 커밋은 PR 소속 관계까지만 확인됨을 알리는 문구입니다.
- `REPOSITORY_UNVERIFIABLE_ITEMS`: 확인 불가 고정 목록입니다. 상세 화면에 항상 렌더링합니다.
- `AI_SELECTION_LABEL`: `relatedShas`·`citedFilePaths`가 LLM 선택값임을 표시하는 짧은 태그입니다. 목록 화면의 인용 파일·관련 커밋 개수 앞에 둡니다.
- `RELATED_COMMITS_VERIFICATION_NOTICE`: 상세 화면의 관련 커밋 목록에 두는 안내입니다. PR 소속 관계까지만 확인되고 관련성 판단은 확인 불가임을 설명합니다.

`VerifiabilityStatus` 타입은 `src/features/experience-candidates/types.ts`에 `EvidenceOrigin`과 나란히 추가했습니다.

## 하지 않은 것

- 판별용 LLM 호출을 추가하지 않았습니다. Gemini 무료 등급 모델별 하루 20요청과 Stage B 라우트 예산 55초 안에서 후보 생성 자체의 쿼터를 지키기 위함입니다.
- 문장에서 수치를 찾는 정규식 휴리스틱을 채택하지 않았습니다. "메시지에 30% 개선이라고 적혀 있다"와 "실제로 30% 개선되었다"를 구분할 수 없어 오탐이 원칙을 훼손하기 때문입니다.
- Stage B 출력 계약을 확장하지 않았습니다. 모델에게 항목별 검증 여부를 표기하게 하는 것은 검증할 수 없는 판단을 하나 더 모델에 맡기는 것이고, 실측에서 모델이 기존 계약조차 항상 지키지 않았기 때문입니다.

## 후속 backlog와의 관계

`wiki/2026-08-24-경험후보목록-후속-backlog.md`의 4번 항목인 후보 카드 접근성 이름 문제를 이 PR에서 함께 처리했습니다. 이 이슈가 카드에 `확인 가능` 태그를 추가로 붙이면서 접근성 이름이 더 길어지는 상황이었습니다.

1차 시도는 카드 버튼에 `aria-label`로 제목과 출처만 담는 것이었으나, PR #52 Codex 1차 리뷰 P1에서 이 방식이 배지·근거 문장·확인 가능·불가 안내·지표를 스크린리더 사용자에게서 완전히 숨긴다는 지적을 받았습니다. 이 이슈의 목적이 그 구분을 노출하는 것이므로 merge blocker로 처리했고, `aria-describedby`로 전체 내용을 접근성 설명으로 계속 노출하도록 고쳤습니다. 처리 경위는 backlog 문서에 새 줄로 추가했습니다.

## 확인 필요

- 목록 화면의 `확인 가능` 태그는 인용 파일·관련 커밋·PR 정보 지표 묶음 앞에 하나만 둡니다. 항목 하나하나에 개별 태그를 붙이는 대신 묶음 단위로 표시했으며, 이 표시 단위가 사용자 인터뷰에서 충분한지는 확인되지 않았습니다.
