# 코드 리뷰 전략

## 문서 목적

PR #6에서 `@codex review`가 6라운드 가까이 반복되고 리뷰 코멘트가 24개까지 쌓인 경험을 근거로, Issue #2부터 #5까지 적용할 코드 리뷰 전략을 정리한다. 경위와 지적 내용 원문은 raw/2026-08-20-코드리뷰-워크플로우-회고-session-log.md에 있다.

## 진단

PR #6에서 나온 지적 6건 중 세 건(커밋 목록 API의 409, 브랜치 ref 부재로 인한 404, 저장소 `size` 필드 오용)은 모두 "빈 저장소"라는 하나의 근본 원인이 다른 지점에서 드러난 것이다. 라운드가 반복된 원인은 리뷰 도구의 성능이 아니라, 매 라운드에서 그 근본 원인의 한 단면만 수정했다는 데 있다.

따라서 전략의 목표는 리뷰 라운드 수를 줄이는 것이 아니라, 한 라운드가 처리하는 수정 범위를 근본 원인 단위로 넓히는 것이다.

## 머지 판단 기준

리뷰의 목적은 잠재적 문제를 모두 제거하는 것이 아니라 현재 PR을 안전하게 머지할 수 있는지 판단하는 것이다. 이 기준은 2026-08-20에 프로젝트 owner가 제시했고 원문은 raw/2026-08-20-AI-코드리뷰-운영원칙.md에 있다.

### severity 구분

| 등급 | 취급 | 해당하는 문제 |
| --- | --- | --- |
| P0 / P1 | 현재 PR의 merge blocker다. 즉시 수정하고 재검증한다. | 기능 오동작, 데이터 손실이나 누락, 보안과 권한 문제, 핵심 요구사항 위반, 기존 기능의 regression, 예외 처리 때문에 사용자에게 잘못된 결과가 전달되는 문제 |
| P2 / P3 | merge blocker가 아니다. 후속 Issue나 backlog로 분리한다. | robustness 개선, 발생 가능성이 매우 낮은 edge case, 극단적인 race condition, 구조 개선, 코드 스타일 차이, PR 범위 밖의 리팩터링 |

P2와 P3에는 예외가 두 가지 있다. 현재 PR의 Acceptance Criteria를 직접 위반하는 경우와 수정 비용이 매우 작은 경우에는 같은 PR에서 함께 반영한다.

### 종료 기준

리뷰어가 더 이상 지적하지 않을 때까지 반복하지 않는다. 다음 네 조건을 만족하면 머지한다.

- Acceptance Criteria를 모두 만족한다.
- P0과 P1 문제가 해결되었다.
- 테스트와 lint와 typecheck가 통과한다.
- 남아 있는 P2와 P3 문제가 후속 작업으로 분리되었다.

## 4단계 흐름

### 0단계. 로컬 셀프 리뷰

PR을 올리기 전에 로컬에서 diff 리뷰를 한 번 돌린다. 왕복 비용이 없으므로 가장 싼 라운드다. PR #6의 실패 유형을 체크리스트로 고정해서 사용한다.

- 호출하는 API마다 상태 코드 표를 만든다. 200, 404, 409, 403, 429, 422 각각에 대해 코드가 무엇을 하는지 적는다.
- 모든 `response.json()` 호출이 try/catch 안에 있는지 확인한다.
- 페이지네이션 커서가 이동할 수 있는 ref(브랜치명)가 아니라 고정 값(커밋 SHA)인지 확인한다.
- 호출 순서를 확인한다. 앞 단계가 먼저 던지는 에러 때문에 뒤 단계의 방어 코드가 도달 불가능해지지 않는지 본다.
- 판별 기준이 대리 지표가 아니라 직접 지표인지 확인한다. 저장소 `size`로 커밋 유무를 판단한 것이 대리 지표의 예다.

### 1단계. 리뷰 1회 트리거

한 Issue에 해당하는 구현을 모두 끝내고 로컬 테스트와 typecheck와 lint 통과를 확인한 뒤에만 `@codex review`를 건다. push할 때마다 트리거하지 않는다.

### 2단계. 수정

지적 코멘트를 줄 단위로 처리하지 않는다. 다음 순서를 따른다.

1. 코멘트를 전부 수집한 뒤 근본 원인별로 묶는다. "빈 저장소", "rate limit 분류", "JSON 파싱"처럼 묶는다.
2. 묶음 하나마다 해당 함수와 그 데이터 흐름 전체를 다시 읽는다. 지적되지 않은 같은 성격의 결함까지 함께 찾는다.
3. 묶음 하나를 커밋 하나로 만든다.
4. 지적 한 건마다 회귀 테스트를 하나 추가한다. PR #6의 지적 6건에 각각 테스트가 있었다면, 페이지네이션 SHA 고정을 넣은 시점에 호출 순서 문제가 즉시 실패로 드러났을 것이다.
5. 리뷰 스레드 답글에는 어떤 줄을 고쳤는지가 아니라 어떤 묶음을 어떻게 다시 설계했는지를 적고 `resolveReviewThread` GraphQL mutation으로 resolve한다.

### 3단계. 재검증 리뷰 1회

수정이 새로운 문제를 만들지 않았는지 확인할 수단은 재검증 라운드뿐이므로 생략하지 않는다. 다만 재검증의 목적은 앞 라운드의 P0과 P1이 실제로 해결되었는지 확인하는 것으로 한정한다. 흐름은 1차 리뷰, P0과 P1 수정, 재리뷰, 머지 순서다.

재검증에서 새로 나온 지적은 severity로 갈라서 처리한다. P0이나 P1이면 2단계를 한 번 더 돌린다. P2나 P3면 별도 Issue나 backlog로 옮기고 이번 PR은 머지한다. 새 P2와 P3 때문에 라운드를 반복하지 않는다.

새 지적이 직전 수정 때문에 생긴 것인지 원래 있던 것인지는 구분해서 기록한다. 직전 수정이 만든 P0이나 P1이 계속 나오면 2단계의 묶음 범위가 여전히 좁다는 신호로 본다.

이 절은 "새 지적이 나오면 2단계를 반복한다"는 초기 서술을 severity 기준으로 갱신한 것이다. 초기 서술은 non-blocking 지적까지 라운드를 늘리는 방향이었고, 머지 판단 기준 절과 충돌하므로 이 서술을 따른다.

## 부가 장치

### AGENTS.md의 Code Review Rules 절

Codex 코드 리뷰는 저장소의 `AGENTS.md` 파일을 읽고 그 안의 `## Code Review Rules` 절을 리뷰 규칙으로 적용한다. 따라서 0단계 체크리스트를 사람만 보는 문서가 아니라 `AGENTS.md`에 규칙으로 적어 두면 bot의 리뷰 기준에도 반영된다. 규칙은 루트에 저장소 전체 규칙을 두고, 특정 디렉터리에만 해당하는 규칙은 그 디렉터리의 `AGENTS.md`에 둔다. 하위 디렉터리 파일이 나중에 이어붙기 때문에 상위 규칙을 덮어쓴다.

### PR 본문의 Edge Cases 절

`.github/pull_request_template.md`에 이미 `Edge Cases`와 `Review Points` 절이 있다. 이 칸을 서술형 문장 대신 API 상태 코드 표로 채운다. 표로 적으면 비어 있는 칸이 바로 드러나므로 사람 리뷰어가 줄 단위가 아니라 표 단위로 검증할 수 있다.

다만 Codex 공식 문서에는 PR 제목이나 본문을 리뷰 컨텍스트로 읽는지가 명시돼 있지 않다. 이 장치의 bot 대상 효과는 `확인 필요` 상태다. 사람 리뷰어와 이후 작업자에게는 효과가 있으므로 유지한다.

### 실데이터 선행 검증

`scripts/manual-test-commits.ts`로 실제 저장소를 리뷰 이전에 돌려본다. 빈 저장소를 포함해서 확인한다. Codex 리뷰는 샌드박스에서 테스트나 명령을 실행한다는 근거가 없고 코드 변경 자체를 분석하므로, 실행으로만 드러나는 문제는 bot이 아니라 이 스크립트가 먼저 알려준다.

### 수렴 지표 기록

Issue #2 PR부터 라운드 수와 지적 건수를 `log.md`에 남긴다. 두 라운드 안에 수렴하지 않으면 전략 자체를 재검토한다.

## 적용 사례: Issue #3

Issue #3 구현에 이 전략을 적용한 결과다. 경위는 raw/2026-08-20-repository-기여항목상세조회-구현-session-log.md에 있다.

1차 리뷰에서 지적 13건이 나왔다. 이 중 P0과 P1로 분류한 것은 네 건이다. 작업 브랜치가 이슈 #2 결과물이 없는 `main` 기준이어서 `develop`에 머지하면 타입이 깨지는 문제, 부분 실패가 원인 오류 종류를 덮어써서 재시도 안내가 불가능한 문제, 커밋이 없는 저장소의 파일 트리 404를 "Repository를 찾을 수 없음"으로 잘못 안내하는 문제, 이슈와 무관한 파일 변경이 PR에 섞인 문제다. 앞의 세 건은 Acceptance Criteria나 사용자에게 전달되는 결과에 직접 영향을 주고, 마지막 한 건은 수정 비용이 한 줄이다.

나머지 아홉 건은 P2와 P3다. 이번에는 수정 비용이 모두 작아서 같은 라운드에 함께 반영했다. 브랜치 기준 문제는 리뷰어가 `origin/develop` 위로 rebase하고 필수 필드 픽스처를 보정해 먼저 해소했고, 나머지는 구현 담당 agent에게 항목별 지시로 한 번에 넘겼다.

재검증 라운드에서 새로 나온 지적은 네 건이고 전부 P2와 P3다. 빈 저장소 판별에 404만 보고 409를 보지 않는 점, `partialCommits`에 상세 타입이 담긴다는 주석 부재, PR endpoint URL 검증 누락, 세션 로그의 설명 누락이다. 종료 기준에 따라 이 네 건은 후속 작업으로 분리하고 라운드를 더 늘리지 않았다.

라운드는 2회로 수렴했고 최종 상태에서 테스트 117건과 lint와 typecheck가 통과했다. PR #6의 6라운드와 비교하면 근본 원인 단위 묶음과 severity 기준 종료가 함께 작동한 결과로 본다. 다만 사례가 한 건이므로 수렴 원인의 비중은 `확인 필요` 상태다.

## Codex 리뷰 bot에 대해 확인한 사실

확인 날짜는 2026-08-20이다.

- Codex 코드 리뷰는 PR diff와 저장소의 `AGENTS.md` 규칙을 컨텍스트로 사용한다.
- `AGENTS.md`는 루트부터 아래로 내려가며 탐색해 이어붙이고, 하위 파일이 상위 지침을 덮어쓴다.
- GitHub에서는 P0과 P1 등급 문제만 코멘트로 남긴다. 등급이 낮은 문제는 bot이 보고하지 않으므로 0단계 로컬 리뷰가 그 부분을 담당해야 한다.
- 리뷰 규칙은 테스트나 branch protection을 대체하지 않는다는 점이 공식 문서에 명시돼 있다.

출처는 https://learn.chatgpt.com/docs/third-party/github 와 https://developers.openai.com/codex/guides/agents-md 이다.

## 확인 필요

- Codex 리뷰가 PR 본문을 컨텍스트로 읽는지 확인하지 못했다. Issue #2 PR에서 본문 표에만 적힌 엣지 케이스를 bot이 언급하는지 관찰해서 판단한다.
- `AGENTS.md`에 `## Code Review Rules` 절을 아직 추가하지 않았다. 0단계 체크리스트 중 어디까지를 규칙으로 옮길지 결정해야 한다.
- 새 전략을 적용했을 때 라운드 수가 실제로 1~2회로 줄어드는지 검증되지 않았다. Issue #3에서 2회로 수렴한 사례가 한 건 있으나, 근본 원인 단위 묶음과 severity 기준 종료 중 무엇이 얼마나 기여했는지는 구분하지 못했다.
- P0부터 P3까지의 등급을 판정하는 주체와 기준이 문서로 고정되지 않았다. Codex bot은 자체 기준으로 P0과 P1만 코멘트하므로, 로컬 리뷰에서 사람이나 리뷰 agent가 매기는 등급과 어긋날 수 있다.
- 후속 작업으로 분리한 P2와 P3를 어디에 적을지 정하지 않았다. GitHub Issue와 backlog 중 어느 쪽을 기본으로 쓸지 결정해야 한다.
