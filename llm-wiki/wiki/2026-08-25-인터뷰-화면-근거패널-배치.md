# 인터뷰 화면 근거 패널의 배치와 patch 표시 분량

## 문서 목적

이슈 #64가 `확인 필요`로 남긴 두 가지를 결정으로 확정합니다. 근거 패널을 질문 옆에 둘지 아래에 둘지, 그리고 patch를 화면에 어느 분량까지 보여 줄지입니다. 구현은 `src/features/interview/interview-screen.tsx`, `interview-evidence-panel.tsx`, `interview-request.ts`에 있습니다.

이 문서는 표시 방식을 새로 정하지 않습니다. Markdown과 Code Block 렌더링, 프레임 단위 반영, 자동 스크롤, 낭독 대상은 이슈 #60이 실측으로 확정했고(`wiki/2026-08-25-스트리밍-렌더링-측정과-전송-계약.md`) 이 화면은 그 결정을 그대로 씁니다.

## 결정 1. 근거 패널을 질문 아래에 한 열로 둡니다

질문 영역과 근거 패널을 두 열로 나누지 않고 한 열로 세로 배치합니다. 좁은 화면과 넓은 화면이 같은 배치를 씁니다.

근거는 세 가지입니다.

첫째, 이 화면의 목적은 첫 질문을 읽는 것입니다. 근거 패널은 기본으로 접혀 있으므로 아래에 두어도 질문을 읽는 데 방해가 되지 않습니다. 반대로 옆에 두면 접혀 있는 동안에도 질문 폭을 상시 줄입니다. 이슈 #64가 "근거를 기본으로 펼쳐 두는 안"을 채택하지 않은 것과 같은 이유입니다.

둘째, 질문 로그와 근거 패널의 스크롤 축이 다릅니다. `InterviewStreamView`의 로그는 `max-height: 60vh` 안에서 자기 스크롤을 가지고 자동 스크롤·수동 스크롤 충돌 처리를 그 안에서 합니다. 근거 패널은 patch를 펼치면 높이가 늘어나 페이지 스크롤을 씁니다. 두 열로 두면 사용자가 patch를 읽으려고 페이지를 내리는 동안 질문 로그가 화면 위로 빠지고, 그 안에서는 자동 스크롤이 계속 돕니다. 어느 쪽도 온전히 보이지 않습니다.

셋째, 2열을 도입할 실측 근거가 없습니다. 이슈 #60의 렌더링 측정은 질문이 화면 폭을 다 쓰는 조건에서 했습니다. 좁은 폭에서의 재파싱·리플로우 비용은 측정하지 않았습니다. AGENTS.md의 "추측성 최적화를 먼저 적용하지 않는다"를 배치 결정에도 같게 적용해, 측정하지 않은 레이아웃을 먼저 넣지 않습니다.

이슈 #64 Approach는 근거 패널을 "나란히" 둔다고 적었습니다. 같은 이슈가 이 배치를 `확인 필요`로 남겼으므로 스케치가 아니라 위 근거를 따랐습니다.

**확인 필요**: 넓은 화면에서 질문과 근거를 함께 보고 싶다는 요구가 사용자 인터뷰에서 나오는지 확인하지 않았습니다. 나오면 DOM 순서를 그대로 두고 `@media (min-width: 1024px)`에서 2열로 바꾸는 것이 가능한 구조입니다.

## 결정 2. 화면에서 patch를 추가로 자르지 않습니다

파일마다 접어 두고, 펼치면 스냅샷에 실린 patch 본문을 한 글자도 자르지 않고 그대로 보여 줍니다. 대신 본문 영역의 높이를 `max-height: 320px`로 제한해 안에서 스크롤하게 합니다.

이슈 #64는 "스냅샷의 patch는 입력 상한까지 실려 있어 그대로 펼치면 매우 길 수 있습니다"를 우려로 적었습니다. 실제 상한을 계산해 보면 그렇지 않습니다.

- `EVIDENCE_SNAPSHOT_MAX_INPUT_TOKENS`는 3,500이고 `EVIDENCE_SNAPSHOT_BYTES_PER_TOKEN`은 3입니다.
- patch에 배정되는 몫 `maxPatchBytes`는 전체 상한에서 메타데이터 몫을 뺀 값이므로 항상 `3,500 × 3 = 10,500`바이트보다 작습니다.
- 이 몫은 파일 하나가 아니라 대표 커밋과 관련 커밋의 **모든 파일이 나눠 쓰는 총량**입니다.

즉 한 스냅샷의 patch를 전부 펼쳐도 10KB 남짓입니다. 이슈 #60이 측정한 스트리밍 메시지 재파싱 비용은 4,919자에서 2.94밀리초였고, patch는 Markdown 파싱 대상이 아니라 `<pre><code>`에 그대로 들어가는 텍스트입니다. 게다가 파일별로 접혀 있어 한 번에 펼쳐지는 것은 사용자가 연 파일뿐입니다.

화면에서 자르지 않기로 한 더 중요한 이유는 절단 알림의 뜻입니다. 지금 사용자에게 알려야 하는 절단이 두 가지입니다. Stage B가 이미 자르거나 뺀 것(`patchTruncated`, `patchOmittedReason`)과 스냅샷 상한이 자른 것(`patchBudget.truncatedByBudget`)입니다. 화면이 여기에 표시 분량 절단을 더하면 사용자가 보는 "…" 이 세 가지 가운데 무엇인지 구분할 수 없습니다. 근거가 온전한지 판단하는 것이 이 화면의 목적인데 그 판단 근거를 화면이 흐리게 됩니다.

## 절단 알림은 두 경로를 각각 표시합니다

임시 화면 `ExperienceInterviewEntry`는 두 경로를 `if`/`else if`로 보아 상한 절단이 있으면 상위 단계 절단을 알리지 않았습니다. 새 화면은 두 조건을 독립적으로 보고 해당하는 안내를 각각 표시합니다. 원인이 다르고 사용자가 할 수 있는 판단도 다릅니다. 상한 절단은 우리 입력 예산이 만든 것이고, 상위 단계 절단은 Stage B 단계에서 이미 사라진 diff입니다.

## 확인 수준 표시 경계

`evidence-verifiability.ts`의 라벨과 안내 문구를 그대로 씁니다. 새 문구를 만들지 않았습니다.

- 대표 커밋의 변경 파일 개수에만 `확인 가능`을 붙입니다.
- 관련 커밋 개수와 인용 파일 개수는 **개수 자체를** `AI 선택`으로 표시합니다. PR #57 1차 리뷰 P2가 정한 경계입니다.
- 커밋 하나하나의 확인 수준은 스냅샷이 실어 온 `verifiability`를 그대로 씁니다. 화면이 다시 판단하지 않습니다. `status`가 `verified`여도 `aiSelected`가 참이면 `확인 가능` 태그를 씌우지 않습니다. 관련 커밋이 이 경우입니다.
- 확인 불가 고정 목록은 스냅샷의 `unverifiableItems`를 그대로 렌더링합니다.

patch 본문이 없는 이유는 `budget_exhausted`와 `not_provided`를 다른 문구로 갈랐습니다. 앞은 우리가 상한 때문에 뺀 것이고 뒤는 GitHub가 준 적이 없는 것이어서 사용자가 할 판단이 다릅니다.

## 접근성

낭독 대상을 늘리지 않았습니다. 화면 전체에 `aria-live`를 두지 않습니다. 안쪽 질문 텍스트가 프레임마다 자라나므로 조상에 live region이 하나라도 켜져 있으면 스크린리더가 자라나는 질문 전체를 반복해 읽습니다. PR #61 리뷰가 정정한 결정이고, 회귀를 막는 테스트를 `interview-screen.test.tsx`에 두었습니다. 질문 자리에서 조상 사슬을 따라 올라가며 켜진 `aria-live`가 없음을 확인합니다.

임시 화면은 자기 `<section>`에 `aria-live="polite"`를 두고 있었습니다. 그 화면에는 자라나는 텍스트가 없어 문제가 되지 않았지만 같은 구조에 질문을 넣으면 바로 이 결함이 됩니다. 대체하면서 걷어냈습니다.

근거를 펼치는 요약(`<summary>`)에는 `aria-describedby`로 `REPOSITORY_VERIFIED_NOTICE`와 `EVIDENCE_VERIFIABILITY_NOTICE`를 연결했습니다. `aria-label`로 이름만 바꾸면 안내가 스크린리더에서 사라집니다. 이슈 #47 PR #52 1차 리뷰의 P1이 그 실수였습니다.

## Loading, Empty, Error

세 상태를 새로 만들지 않았습니다. 같은 상태를 두 곳에서 그리면 어긋납니다.

- **Loading**은 `InterviewStreamView`의 "질문을 준비하고 있습니다"가 담당합니다. 첫 내용이 도착하기 전 `connecting`·`idle` 상태에서 표시됩니다.
- **Empty**는 없습니다. 최종 후보 0개는 앞 단계 Empty가 처리하므로 이 화면에 도달하지 않습니다. 청크 없이 `done`으로 끝난 스트림의 화면 상태는 `wiki/2026-08-25-스트리밍-후속-backlog.md`의 범위입니다.
- **Error**는 `InterviewStreamView`의 오류별 안내와 다시 시도 버튼이 담당합니다. 스냅샷을 만들지 못하는 오류는 확정 단계에서 이미 갈라져 이 화면에 오지 않습니다.

## 요청 본문 배선 (PR #65 리뷰 P1로 고침)

요청 계약은 이슈 #63과 착수 전에 고정했습니다.

```
POST /api/interview/stream
Content-Type: application/json
{ snapshot: ExperienceEvidenceSnapshot }
```

화면은 `InterviewStreamView`에 `snapshot`을 넘기는 것으로 이 계약을 만족시킵니다. 본문 직렬화, `POST` 전환, 재개 방침은 `useInterviewStream`이 담당합니다.

```tsx
<InterviewStreamView snapshot={snapshot} fetchImpl={fetchImpl} />
```

**처음에는 이렇게 하지 않았습니다.** 그 시점의 `useInterviewStream`에는 본문을 받는 통로가 없었고 두 파일이 이슈 #63의 소유라, 본문을 만들어 `fetchImpl`로 붙이는 `interview-request.ts`를 따로 두고 `INTERVIEW_STREAM_ROUTE_ACCEPTS_SNAPSHOT`을 `false`로 둔 채 PR을 올렸습니다. route가 아직 `GET`만 내보내서 `POST`를 보내면 405가 나고, 405 본문에는 아는 오류 분류가 없어 화면에 "연결을 시작하지 못했습니다"만 남기 때문이었습니다.

### 그 결정이 만든 결함

플래그가 꺼진 동안 화면은 `GET /api/interview/stream`을 부르고, 그 route는 `test-stream.ts`의 고정 `TEST_MESSAGE`를 돌려줍니다. 그 텍스트는 자리표시자가 아니라 demian 내부 `selectStageACandidates`의 청크 경계를 묻는 완성된 한국어 면접 질문입니다.

결과가 이렇습니다. 사용자가 자기 저장소 경험을 확정하면 우리 코드에 대한 질문을 받고, 화면은 그 아래 "이 질문의 근거"로 사용자의 스냅샷을 붙여 보여 줍니다. 질문이 그 커밋에서 생성된 것처럼 보이고, 어떤 저장소를 골라도 같은 질문이 나옵니다. `AGENTS.md`가 못박은 "AI는 항상 실제 Repository의 커밋과 파일을 근거로 제시한다"에 정면으로 걸립니다.

PR #65 1차 리뷰에서 사람 리뷰와 Codex가 같은 지점을 독립적으로 P1으로 잡았습니다. Codex는 자리표시자를 유지하거나 개발 전용 경로 뒤로 감추는 안을 제시했으나 채택하지 않았습니다. 이슈 #63이 실제 경로를 이미 만들었으므로 감출 이유가 없습니다.

배운 것은 배선 상태를 적는 방식입니다. PR 본문에 "스냅샷 전송이 꺼져 있다"까지만 적고 **그 결과 사용자가 무엇을 보는지**를 적지 않았습니다. 앞은 구현 상태이고 뒤가 리뷰가 판단해야 하는 사실입니다. 그 누락이 이 PR을 머지 가능한 것처럼 보이게 했습니다.

### 고친 내용

PR #67이 develop에 머지되어 `useInterviewStream`이 `snapshot` 옵션을 받게 된 뒤 rebase하고 배선했습니다. `interview-request.ts`와 그 테스트는 삭제했습니다. 같은 일을 하는 코드가 두 벌 남으면 다음 작업자가 어느 쪽이 진짜 배선인지 알 수 없습니다.

`streamUrl` prop도 없앴습니다. `?scenario=`는 `GET` 경로의 테스트 스트림에만 뜻이 있는데 화면은 이제 항상 `snapshot`을 넘겨 `POST`로 갑니다. 시나리오 주소를 받는 prop을 남겨 두면 실제로는 동작하지 않는 통로가 됩니다. 시나리오별 화면 검증은 `fetchImpl`로 응답 본문만 갈아 끼워서 합니다. `snapshot`과 무관하게 동작합니다.

### 회귀 테스트

`interview-screen.test.tsx`에 두 개를 두었습니다. 첫째, 확정 후 나가는 요청이 `/api/interview/stream`으로 가는 `POST`이고 본문이 `{ snapshot }`과 같은지 봅니다. 둘째, 경험이 다르면 본문의 `candidateSha`가 달라지는지 봅니다. 배선이 끊겨 `GET`으로 돌아가면 두 테스트가 모두 깨집니다.

"서로 다른 스냅샷에 같은 질문이 나오지 않는다"를 직접 검증하지 않은 이유는 질문 텍스트가 모델 출력이라 결정적이지 않기 때문입니다. 화면이 통제하는 것은 요청까지이므로 요청을 고정합니다.

### 재개 방침은 화면이 정하지 않습니다

`snapshot`을 넘기면 그 스트림이 `resumeMode: "restart"`가 됩니다. 전송 중 단절에서 자동 재연결을 하지 않고, `다시 시도`가 이미 표시된 메시지를 지우며, `stream_interrupted` 안내가 비재개 문구로 갈립니다. 스냅샷 유무가 이 모드를 결정하고 화면은 따로 지정하지 않습니다. 근거는 이슈 #63의 `wiki/2026-08-25-첫-질문-생성-provider-실측과-재개-방침.md`에 있습니다.

## 머지 조건

이 PR은 배선을 고쳐도 바로 머지하지 않습니다. **인터뷰 화면을 사용자 경로에 올리는 PR이 이 PR입니다.** PR #67만 머지된 상태에서는 화면이 여전히 `ExperienceInterviewEntry`라 질문 생성 경로가 사용자에게 노출되지 않습니다.

그래서 PR #67에서 열린 채 머지된 P1(확정한 모델 `openai/gpt-oss-20b`가 근거에 없는 사실을 만드는 문제)의 차단 자격이 이 PR로 이관되어 있습니다. 이관이 성립하려면 이 PR이 provider 전환 완료 전에 머지되지 않아야 합니다. 근거는 `wiki/2026-08-20-코드리뷰-전략.md`에 있습니다.


## 삭제한 것
