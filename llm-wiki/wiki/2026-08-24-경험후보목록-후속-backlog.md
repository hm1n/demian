이슈 #45 PR #48의 종료 기준을 충족하기 위해 merge blocker가 아닌 리뷰 항목을 분리합니다. 2026-08-20 코드 리뷰 전략에 따라 P2와 P3는 새 GitHub Issue를 만들지 않고 이 문서에서 추적합니다.

## 미뤄 둔 항목

### 1. 기존 성공 화면 CSS 제거

`src/features/repository-analysis/repository-analysis.module.css`의 `.candidateList` 관련 규칙 5개와 `.metric`, `.summary`는 `SuccessState` 제거 이후 사용되지 않습니다. 새 `experience-candidate-list.module.css`가 같은 역할의 이름을 다시 정의하므로 구 정의를 제거하면 죽은 코드와 중복을 함께 해소할 수 있습니다.

발견 주체는 오케스트레이터 로컬 리뷰이며, 근거 위치는 두 CSS 모듈과 `src/features/repository-analysis/repository-analysis-view.tsx`의 성공 상태 호출부입니다.

### 2. `.eyebrow` 특이도 정리

`src/features/experience-candidates/experience-candidate-list.module.css`의 `.eyebrow`는 `.state p`보다 특이도가 낮아 `color`와 `font-size`에 `!important`를 사용합니다. 같은 파일의 `.state .evidenceNotice`처럼 `.state .eyebrow`로 범위를 좁히면 불필요한 우선순위 강제를 제거할 수 있습니다.

발견 주체는 오케스트레이터 로컬 리뷰이며, 근거 위치는 새 CSS 모듈의 `.state p`, `.eyebrow`, `.state .evidenceNotice`입니다.

### 3. 후보 0개 불변식 명시

최종 후보 0개는 `src/features/repository-analysis/repository-analysis.ts`의 `no_final_candidates` Empty가 처리하므로 `ExperienceCandidateList`에 도달하지 않습니다. 그러나 컴포넌트를 후보 0개로 직접 호출하면 "경험 후보 0개를 선정했습니다"를 표시할 수 있어, 이슈 #45 Definition of Done의 후보 0개 렌더링 항목은 성공 화면에서 실제 검증할 수 없었습니다.

상태 머신 불변식을 코드로 고정할지 이슈 문구에서 Empty 경로로 명확히 할지 결정이 필요합니다. 발견 주체는 오케스트레이터 로컬 리뷰이며, 근거 위치는 `repository-analysis.ts`의 최종 후보 분기와 `experience-candidate-list.tsx`입니다.

### 4. 후보 카드와 상태 영역의 접근성 이름

후보 카드 전체가 하나의 버튼이어서 제목, 배지, 근거 문장, 안내와 지표가 접근성 이름으로 이어 붙습니다. `aria-label`로 제목과 출처만 제공하는 방안을 검토해야 합니다. 목록과 상세를 감싼 `aria-live="polite"`가 전환 때 전체 내용을 다시 낭독하는 문제도 같은 흐름에서 확인해야 합니다.

발견 주체는 오케스트레이터 로컬 리뷰이며, 근거 위치는 `src/features/experience-candidates/experience-candidate-list.tsx`의 카드 버튼과 두 상태 `<section>`입니다.

**2026-08-24 이슈 #47에서 처리했습니다.** 이슈 #47이 카드에 `확인 가능` 태그를 추가로 붙이면서 이 문제를 악화시켰습니다. 카드 버튼에 `aria-label={\`${indexedTitle} · ${EVIDENCE_ORIGIN_LABEL[origin]}\`}`을 지정해 접근성 이름을 제목과 출처로 고정했습니다. 근거 문장, 안내, 지표는 시각적으로는 그대로 노출하되 접근성 이름에서는 제외됩니다. `aria-live="polite"`가 전환마다 전체 내용을 다시 낭독하는 문제는 이번에 다루지 않았습니다.

**2026-08-24 PR #52 Codex 1차 리뷰 P1로 위 수정을 정정했습니다.** `aria-label`만 지정하면 버튼 자손이 접근성 트리에서 flatten되어 배지, 근거 문장, 확인 가능·불가 안내, 지표가 스크린리더 사용자에게 전혀 전달되지 않는 문제가 있었습니다. 이 이슈의 목적 자체가 그 구분을 노출하는 것이므로 이는 merge blocker P1로 처리했습니다. 배지·근거 문장·안내·지표를 `display: contents`인 래퍼 span으로 묶고 `id`를 부여한 뒤 버튼에 `aria-describedby`로 연결해, 짧은 접근성 이름은 유지하면서 전체 내용을 접근성 설명(accessible description)으로 계속 노출하도록 고쳤습니다.

### 5. 커밋 색인 실패의 시각적 구분

색인 실패 제목은 `커밋 색인 실패 · SHA7` 문구로만 정상 제목과 구분됩니다. 색상이나 배지 같은 시각적 신호를 추가할지 검토해야 합니다.

발견 주체는 오케스트레이터 로컬 리뷰이며, 근거 위치는 `experience-candidate-list.tsx`의 `indexedTitle`과 `.title` 렌더링입니다.

### 6. `llm-wiki/log.md` 정렬 규칙

`llm-wiki/log.md` 위쪽은 최신순이지만 이번 변경 전부터 일부 2026-08-24 행이 표 아래쪽에 덧붙어 있어 순서가 일관되지 않습니다. 기존 행 이동은 판단과 처리 흔적을 지우지 않는다는 `llm-wiki/AGENTS.md` 규칙과 충돌할 수 있으므로, 먼저 새 행의 삽입 위치와 기존 행 정리 방식을 문서로 정해야 합니다.

발견 주체는 오케스트레이터 로컬 리뷰이며, 근거 위치는 `llm-wiki/log.md`와 `llm-wiki/AGENTS.md`의 로그 작성 절입니다.

### 8. 커밋 색인 실패 상태의 확인 가능 태그 오표시

목록 카드 metrics에서 `확인 가능` 태그는 PR 정보 자리 앞에 옵니다. 이 자리에 오는 값은 세 갈래입니다. `PR #n`, `PR 정보 없음`, `커밋 색인 실패`입니다. 앞의 둘은 Repository 응답 값(PR 존재 여부)이라 `확인 가능` 태그가 맞지만, `커밋 색인 실패`는 Repository 사실이 아니라 커밋 조회 자체가 실패한 우리 쪽 상태입니다. 이 경우 화면이 `확인 가능 · 커밋 색인 실패`로 읽혀, 이슈 #47이 막으려던 것과 같은 계열의 오표시가 남습니다.

## 리뷰 수렴 기록

`@codex review`는 3회 트리거되어 전략의 1차 리뷰와 재검증 1회를 초과했습니다. 봇 지적은 1차 P1 1건, 2차 P1 1건, 3차 P2 1건으로 총 3건이었고, 오케스트레이터 로컬 리뷰는 8건 중 2건을 같은 PR에서 수정하고 6건을 이 문서로 분리했습니다.

2차 감사 로그 누락은 merge blocker인 P1이므로 수정이 전략에 맞았습니다. 3차 P2는 원래 backlog 분리 대상이었으나 이미 수정과 검증이 끝난 뒤였고, 롤백하면 라운드가 한 번 더 늘어나므로 되돌리지 않았습니다. 라운드 초과 원인은 push마다 리뷰를 트리거하면서 재검증 1회와 P2 이하 분리 규칙을 확인하지 않은 운영에 있습니다.
