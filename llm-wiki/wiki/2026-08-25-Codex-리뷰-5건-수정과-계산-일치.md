## 2. 판단 단위 전환이 마지막 단계에서 깨져 있었다

이번 작업의 핵심은 경험 판단 단위를 커밋에서 Pull Request 묶음으로 바꾼 것입니다. 그런데
Stage B가 그 전제를 지키지 않았습니다.

중복 방지가 SHA 수준에만 있었습니다. `schema.ts`가 "경험 후보의 대표 커밋 SHA는 서로 달라야
합니다"를 강제하지만 Pull Request 수준 방지는 코드 어디에도 없었습니다. `expandCandidatesToCommits`
가 커밋 21개짜리 묶음을 서로 독립인 항목 21개처럼 펼쳐 보내므로 최종 후보 3개가 실제로는 경험
1개일 수 있었습니다.

기존 테스트가 이 결함을 정상으로 단정하고 있었습니다. "후보 3개 계약" 테스트의 픽스처가 세 번째
커밋을 `{ ...commits[1], sha: "c" }`로 만들어 두 번째 커밋의 Pull Request 번호를 그대로 물려받고
있었습니다. 같은 PR의 커밋 둘이 최종 후보 세 자리 중 둘을 차지하는 상황을 통과로 못박아 둔
셈입니다.

## 3. 502로 거부하지 않은 이유

처음에는 계약 위반으로 거부하는 방안을 검토했습니다. 기각했습니다.

Stage B에는 복구 경로가 없습니다. Stage A의 `selectWithRecovery` 같은 것이 없어서 502가 나면
화면은 오류 상태와 재시도 버튼뿐이고 조회를 처음부터 다시 합니다.

기존 502 세 종류가 무엇을 잡는지 보면 경계가 분명합니다. `unknown_sha`는 없는 SHA를 만들어낸
것, `unrelated_sha`는 관계없는 커밋을 같은 PR이라 주장한 것, `unknown_file_path`는 없는 파일을
인용한 것입니다. 전부 Repository에 대해 거짓을 주장한 조작이고, 근거 무결성이 깨졌으므로 전체를
버리는 것이 맞습니다.

같은 PR 중복은 조작이 아닙니다. 입력으로 준 커밋 중 둘을 고른 것이고 둘 다 실제 커밋이고 diff도
실제입니다. 게다가 그때까지 프롬프트가 "다른 PR에서 골라라"라고 말한 적이 없었습니다. 규칙을
알려주지 않고 위반으로 처벌하면서 멀쩡한 후보 3개를 버리고 사용자에게 오류를 띄우는 셈입니다.

그래서 세 겹으로 갔습니다. 입력을 Pull Request 단위 묶음으로 구성해 모델이 "이건 한 경험"으로
읽게 하고, 프롬프트에 규칙을 명시하고, 그래도 어기면 묶음당 첫 후보만 남기고 정리합니다.

정리에는 함정이 있었습니다. `schema.ts`가 후보 3개 미만이면 부족 사유를 요구하고 3개이면 사유가
null이어야 한다는 불변식을 강제합니다. 정리로 3개가 2개가 되면 이 불변식이 깨지고,
`repository-analysis.ts`가 사유에 non-null 단정을 쓰고 있어 조용히 깨지면 뒤에서 터집니다.
정리로 개수가 줄면 사유를 직접 채웁니다.

## 4. 후보 0개일 때가 제외 사유를 가장 알아야 할 순간이다

선별 정보를 성공 상태에만 실어 보내고 있었습니다. 후보가 0개로 끝나는 두 갈래는 제외 건수와
사유를 그대로 버렸습니다.

`andbread`는 66묶음 중 10개만 판단 대상이 됩니다. 그 10개가 모두 탈락하면 사용자는 "후보가
없습니다"만 보고 56묶음이 있었다는 것도 모릅니다. 어떤 커밋도 사용자 모르게 배제하지 않는다는
원칙이 정면으로 깨지는 지점입니다.

선택 필드로 둔 이유가 있습니다. Stage A 전에 나는 빈 상태 세 종류에는 선별 정보가 아예 존재하지
않습니다. 필수로 만들면 그 세 갈래가 거짓 값을 채워야 합니다.

## 5. 크기를 재는 곳이 둘로 갈려 있었다

라우트가 프롬프트 상한을 검사할 때 요약만 재고 기여 항목을 빠뜨렸습니다. 모델에 실제로 실리는
프롬프트에는 기여 항목이 붙습니다. 기여 항목은 사용자 입력이고 길이 상한이 없습니다.

원인은 라우트가 프롬프트 문자열을 손으로 다시 계산하는 구조였습니다. 만드는 곳과 재는 곳이
갈리면 다시 어긋납니다. `renderStageAPrompt`를 순수 함수로 뽑아 실제 호출과 라우트가 같은 함수를
쓰게 했습니다. 두 경로가 같은 문자열을 만드는지 검증하는 테스트를 넣었습니다. 구조화 출력 호출을
부분 모킹해 실제로 보내는 프롬프트 인자를 가로채 비교합니다.

시스템 프롬프트는 예산에 넣지 않았습니다. `STAGE_A_CHUNK_MAX_BYTES`는 프롬프트 5,842바이트가 총
3,949토큰이었던 실측에서 바이트당 0.676토큰으로 역산한 값인데, 그 총 토큰은 시스템 프롬프트가
이미 실린 호출의 usage입니다. 상한이 시스템 프롬프트의 토큰 기여를 이미 반영하고 있어 글자 수를
또 더하면 이중 반영입니다.

라우트를 고치자 클라이언트 청크 분할기와 어긋났습니다. 분할기는 여전히 요약만 재고 있었습니다.
양쪽이 다른 것을 재니 클라이언트가 통과할 수 없는 청크를 만들어 보냅니다.

라우트를 고치기 전에는 같은 입력이 422 대신 분당 토큰 한도 초과로 413을 받았습니다. Codex가

## 7. 대가는 판단받는 묶음 수다

기여 항목이 길수록 판단받는 묶음이 줄어듭니다. `demian` 기준 없으면 16개, 200자면 10개,
2,000자면 6개입니다. 대략 600바이트당 묶음 하나입니다.

청크를 더 나누는 방법도 됩니다. 택하지 않았습니다. 분당 토큰 한도 8,000은 청크를 나눠도 합계에
걸립니다. 200자에서 청크 두 개면 약 9,700토큰으로 한도를 넘어 대기가 걸립니다. 이날 `gpt-oss-120b`
대기가 794초에서 1,398초까지 늘어난 것을 관측한 뒤라 대기는 받아들일 수 없는 비용입니다.

빠진 묶음은 경계 점수가 올라간 형태로 화면에 나옵니다. 다만 사유가 `below_score_threshold`로
표시되어 사용자에게는 "점수가 낮아서"로 읽힙니다. 실제 원인은 기여 항목이 예산을 먹은 것입니다.
컷 자체는 점수순이고 기여 항목이 경계 위치만 바꾸므로 사유 분류는 그대로 두었습니다.

기여 항목 자체에 바이트 상한을 두는 방안은 실측 근거가 없어 보류했습니다. 이제 근거가 생겼으므로
별건으로 판단할 사안입니다.

## 8. 측정 도구가 상한에 닿지도 않았다

`stage-b` 단계가 프로덕션과 다른 것을 재고 있었습니다. 프로덕션은 후보 묶음을 대표 커밋 여럿으로
펼쳐 넣는데 스크립트는 묶음당 SHA 하나를 그대로 상한까지 자르고 있었습니다.

| 저장소 | 수정 전 커밋 수 | 수정 후 | 커밋 2개 이상 PR | 최대 |
| --- | --- | --- | --- | --- |
| demian | 16 | 30 | 16개 중 12개 | 3커밋 |
| andbread | 10 | 30 | 10개 중 10개 | 4커밋 |

상한 30을 검증하는 측정이 상한에 닿지도 않았습니다. 상세 재조회 시간과 patch 몫을 운영 입력이
아닌 것에서 재고 있었습니다.

같은 Pull Request에서 커밋 여러 개가 실제로 펼쳐졌는지 세어 로그에 남기게 했습니다. 하나도
없으면 커밋 단위 입력과 구별되지 않아 운영 경로를 검증하지 못하므로 경고를 찍습니다.

## 9. 평범한 Error가 재시도 루프를 만든다

P2-2 수정에서 예산을 혼자 넘는 묶음을 만나면 실패시키기로 했는데, 처음 구현이 평범한 `Error`를
던졌습니다.

`repository-analysis.ts`의 `samePayloadAlwaysFails`가 `CandidateRequestError`만 봅니다. 평범한
`Error`는 재시도 지점을 남기므로, 같은 입력으로 반드시 같은 실패를 반복하는 버튼을 사용자에게
줍니다. `invalid_request`와 재시도 불가로 바꿨습니다.

도달 불가능하다고 판단한 단정이 실제로는 도달 가능했다는 점도 함께 확인했습니다. 선별이 요약만
재고 기여 항목을 안 쟀기 때문에 기여 항목이 예산을 먹는 경로로 닿습니다.

## 10. 병렬 작업에서 배운 것

네 갈래를 파일 배타로 나눠 하위 에이전트에 동시에 맡겼습니다. 편집 파일 목록이 겹치지 않게
분해하고, git 명령을 금지해 인덱스 충돌을 막고, 각자 자기 테스트만 돌리게 해 남의 미완성 코드로
인한 오탐을 막았습니다.

분해에 빈틈이 있었습니다. `stage-b/route.ts`가 `buildStageBPayload`의 반환을 참조하는데 어느
갈래에도 속하지 않았습니다. 페이로드 모양을 바꾼 갈래에게 "자기 파일 밖 타입 오류는 무시하라"고
지시했으므로 그대로 두면 라우트가 조용히 깨진 채 완료 보고가 옵니다. 호출부 전수 조사로 잡았습니다.

교훈은 분해할 때 편집 파일만 나누면 부족하고 **바뀌는 export의 호출부까지 세어 주인을 정해야
한다**는 것입니다.

## 확인 필요

- 프로덕션 모델 `gpt-oss-120b`로는 여전히 한 번도 돌리지 못했습니다. 이번 수정 전체가 20b
  실호출과 캐시 기반 계산으로만 검증됐습니다.
- 같은 Pull Request 중복 정리는 실호출에서 발생을 관측한 적이 없습니다. 프롬프트 규칙 추가만으로
  충분한지, 정리가 실제로 발동하는지 미확인입니다.
- 기여 항목이 길 때 판단 묶음이 줄어드는 것이 선별 품질에 미치는 영향을 재지 않았습니다. 600바이트
  당 묶음 하나라는 비율만 확인했습니다.
- 기여 항목 전용 바이트 상한을 둘지 결정하지 않았습니다.
- P2-2는 현재 두 저장소로 재현되지 않습니다. 최대 묶음이 `demian` 876바이트, `andbread`
  1,402바이트로 상한 10,500 대비 여유가 7.5배입니다.
- 빈 상태의 제외 표시를 실제 브라우저에서 확인하지 않았습니다. 테스트로만 덮었습니다.
