# Stage B diff·PR 판단 계약

## 입출력

- 입력은 `owner`, `repo`, Stage A의 `candidates`이며 클라이언트는 patch를 보내지 않는다.
- 서버가 후보 SHA를 순차 조회하고 diff, PR 소속, Stage A source와 기여 항목을 Gemini에 한 번 전달한다.
- 출력은 최대 3개 후보와 부족 사유, 최종 후보 및 관련 커밋의 제한된 diff다. `diffs[].files[]`는
  절단 또는 생략된 patch에 `patchTruncated: true`를 포함한다.
- 입력 `candidates[].sha`는 40자 소문자 hex 커밋 SHA만 허용하고 브랜치명·태그 같은 이동 가능한 ref는
  422로 거부한다. 이동 가능한 ref로 페이지네이션을 돌면 파일 목록이 중복·누락될 수 있고 응답의 SHA
  자리에 ref가 새어 나가기 때문이다.
- 모델은 `gemini-3.7-flash`, SDK 기본 환경 변수 `GOOGLE_GENERATIVE_AI_API_KEY`를 사용한다.
- 이동하는 `gemini-flash-latest` 별칭 대신 고정 ID를 사용해 같은 입력의 재현성과 프로젝트의 고정 ref 규칙을 지킨다.

## 상한: 이슈 #19 실측으로 확정

측정 근거는 `wiki/2026-08-24-실데이터-검증-배치-상한-확정.md`에 있다.

- 후보 20개, 파일 patch 4,000자, 전체 patch 60,000자, 라우트 전체 예산 `STAGE_B_TOTAL_BUDGET_MS`
  55초는 실측으로 확정해 유지한다.
- 최소 LLM 잔여 예산 `STAGE_B_MIN_LLM_BUDGET_MS`는 10초에서 **20초로 올렸다.** 성공한 LLM 호출이
  최대 19.9초 걸렸으므로 잔여 10초로 호출을 시작하면 완주하지 못할 가능성이 높다.
- 파일 patch 4,000자는 실측 파일 279개 중 40개(14%)만 절단한다. 파일별 patch는 중앙 1,257자,
  p90 5,235자, 최대 44,013자였다.
- 파일 patch는 절단 사실을 모델에 표시하고, 전체 예산 이후 patch는 생략하되 SHA와 stat은 유지한다.
- 모델 `gemini-3.7-flash`는 유효함을 확인했다. `gemini-2.5-flash`는 신규 사용자에게 404이고
  `gemini-3.5-flash`는 55초 예산을 다 쓰고 시한 초과했다.

## patch 예산 배분: 후보별 균등 배분

- 후보별 몫은 `STAGE_B_MAX_TOTAL_PATCH_CHARS`를 후보 수로 나눈 내림값이다. 후보 20개면 각 3,000자다.
- 파일별 `STAGE_B_MAX_PATCH_CHARS` 상한은 후보의 몫 안에서 적용한다. 몫이 파일 상한보다 작으면
  몫이 실질 상한이 된다.
- 몫을 다 쓰지 않은 후보의 잔액은 뒤 후보로 이월한다. 이월은 앞에서 뒤로만 흐르므로 어떤 후보도
  자기 몫보다 적게 받지 않는다. 뒤에서 앞으로의 재분배는 두 번 순회가 필요한데 얻는 이득이 작아
  채택하지 않았다.
- 예산 때문에 patch가 빠진 파일도 `patchTruncated: true`를 받는다. 모델이 그 후보의 diff를 전부
  본 것으로 오해하지 않게 하려는 것이다.

## 상세 화면 표시 계약

- 대표 커밋의 변경 파일 목록은 patch를 제거한 `includedCommits[sha].files` 전체를 기준으로 표시하고,
  코드 변경 본문만 `diffs`의 같은 SHA와 파일 경로에서 결합합니다.
- patch 본문은 unified patch 텍스트의 줄 접두어를 유지한 채 파일별 `details` 영역에 표시합니다.
  syntax highlighting과 가상 스크롤은 성능 측정 근거가 생기기 전에는 도입하지 않습니다.
- 전체 파일 목록에 있지만 patch가 없는 파일은 `diff 미포함`으로 표시합니다. `patchTruncated: true`인
  파일은 `diff 절단`으로 표시하고, 대표 커밋이나 관련 커밋에 절단 파일이 하나라도 있으면 후보 단위
  안내도 함께 표시합니다.
- 대표 커밋에 표시할 patch가 하나도 없어도 변경 파일 목록, 관련 커밋과 PR 정보는 유지합니다.
- 관련 커밋은 화면 뷰 모델의 `normalizedRelatedShas`를 상한 없이 표시하며 화면에서 관계를 다시
  추론하거나 원시 배열의 중복과 대표 SHA 자기 참조를 되살리지 않습니다.

### 왜 바꿨나 (이슈 #19 실측)

- 이전 구현은 커밋 순서대로 예산을 소비했다. 후보 20개를 넣으면 앞쪽 9개가 60,000자를 다 쓰고
  **나머지 11개(55%)는 patch를 한 글자도 받지 못했다.**
- 더 나쁜 것은 그 상태에서 모델이 **patch를 못 받은 후보를 실제로 최종 선정했다는 점이다**
  (payload 인덱스 3·9·17 중 9번과 17번). "실제 diff와 PR 소속만 근거로" 고르라고 지시하면서
  근거를 주지 않으면, 모델은 지시를 지키지 않고 답을 만든다. 근거 부재는 입력 단계에서 막아야 한다.
- 균등 배분 후에는 후보 20개 전원이 patch를 받고 총량은 여전히 정확히 60,000자를 쓴다.

## 라우트 시간 예산

- 55초 예산은 LLM 단계만이 아니라 GitHub 조회와 LLM 판단을 합친 라우트 전체 기준이다.
- 조회 루프는 반복 사이에 잔여 시간을 확인하고 10초 미만이면 LLM을 호출하지 않고 종료한다.
- 예산 확인은 조회 반복 앞과 루프 종료 후 양쪽에서 하며, 잔여가 최소 LLM 예산 미만이면 LLM을 호출하지 않는다.
- 예산 소진은 `llm_timeout` 504로 반환한다. 이슈 #18에서 확정: 클라이언트는 이 kind를 Stage A의
  LLM 시간 초과와 구분해 라우트 전체 예산 초과로 안내한다. 오류 kind는 추가하지 않고 요청 단계로
  구분한다. 근거는 `raw/2026-08-24-후보생성-상태연결-session-log.md`에 있다.
- 조회 요청 하나가 오래 걸리면 끝날 때까지 예산을 넘길 수 있다. 필요해지면 조회 계층에
  `AbortSignal`을 배선한다.
- 최소 LLM 잔여 예산은 이슈 #19 실측으로 20초로 확정했다.
- Vercel Hobby의 실제 실행 상한은 60초가 아니라 300초다(이슈 #19에서 공식 문서로 확인, 2026-08-24).
  `maxDuration = 60`과 55초 예산은 플랫폼 제약이 아니라 대기 시간을 제한하려는 우리 쪽 UX 결정이다.
- 55초 예산은 줄일 수 없다. 모델의 일시적 과부하 실패 시 AI SDK 기본 재시도 3회가 20~46초를
  소비하기 때문이다.

## source 값의 권위

- `source`는 LLM 판단이 아니라 Stage A가 SHA별로 확정한 값이다. 출력 스키마가 필수로 요구해
  모델도 쓰지만 권위는 서버에 있으며, 불일치하면 거부하지 않고 Stage A 값으로 덮어쓴다.
- 서버가 정답을 확정적으로 아는 필드는 교정하고, 환각 SHA처럼 모델 의도를 알 수 없는 필드는
  전체 거부한다. 이 구분을 이후 검증 실패 등급의 일반 기준으로 삼는다.
- `evidence`, `citedFilePaths`, PR 관계는 계속 실제 Repository 근거와 대조하므로 source 교정이
  근거 안전성을 낮추지 않는다.
- source 불일치는 모델이 입력을 잘못 읽었다는 신호일 수 있다. 그러나 다른 필드는 Repository
  사실로 직접 검증하며, 최대 55초 호출 뒤 재시도해도 같은 오류가 반복될 수 있어 전체 거부는
  채택하지 않았다. 이 신호가 필요해지면 거부가 아니라 로깅으로 다룬다.

## 결정과 한계

- 출력 계약은 `relatedShas`와 `citedFilePaths`의 중복을 막지 않으며, 대표 SHA가 자신의
  `relatedShas`에 포함돼도 같은 PR 소속 검사를 통과한다. 중복은 서버가 정답을 확정적으로 아는
  교정 가능한 값이고, 응답 전체를 거부해 Gemini 무료 등급의 모델별 하루 20요청 한도를 소모하지
  않도록 소비자인 화면 뷰 모델에서 원본 순서를 유지해 정규화한다. 원본 후보 응답은 감사 목적으로
  보존한다.
- 대표 선정과 관련 근거 정리는 한 요청으로 처리한다. 요청 분할과 서버 내부 후보 축소 재시도는 하지 않는다.
- 실행 시한 초과는 `llm_timeout` 504로 종료한다. 사용자 재시도는 이슈 #18에서 연결됐다. Stage B
  오류는 Stage A 결과를 재사용해 Stage B부터 재시도하며, 서버 측·클라이언트 측 후보 축소 재시도는
  채택하지 않았다.
- `fileTree`는 조회하지 않고 인용 경로를 입력 diff 경로로 제한한다. 전체 트리 근거가 필요해지면 이슈 #32에서 확장한다.
- 관련 커밋은 Stage A가 만든 입력 SHA 집합 안에서 같은 PR에 속한 커밋만 허용한다.
- Loading·Empty·Error 상태 연결은 이슈 #18에서 해소됐다. Repository 분석 상태 머신이 5·6단계에서
  `/api/candidates/stage-b`를 호출한다.
- 관련 커밋의 PR 소속 계약은 이슈 #19 실측에서 **완벽히 지켜졌다.** 성공한 실행의 최종 후보 3개에
  딸린 관련 커밋 6개가 모두 대표 커밋과 같은 PR이었다. 이 계약은 신뢰할 수 있다.
- 개수 초과 422는 정상 흐름에서 **도달 불가다.** Stage A가 후보를 `INITIAL_STAGE_A_CANDIDATE_LIMIT`
  이하로 자체 강제하고 이 라우트가 `STAGE_B_MAX_CANDIDATES` 초과를 막는데 두 값이 같기 때문이다.
  이 422는 형식 위반 방어용으로만 의미가 있다. 두 상수는 함께 바꿔야 이 성질이 유지된다.

## 확인 필요

- `relatedShas`와 `citedFilePaths` 중복 및 대표 SHA 자기 참조를 서버 응답 단계에서 정규화해 모든
  소비자에게 같은 값을 제공할지는 후속 결정이 필요하다.
- **이슈 #44에서 한다.** 균등 배분과 Stage A 입력 청크 분할을 반영한 뒤 선정 품질을 설정된 모델
  `gemini-3.7-flash`로 재측정해야 한다. 기록된 품질 관측은 균등 배분 이전 측정이고, 균등 배분 후
  실행은 일일 무료 한도가 소진돼 `gemini-3.6-flash`로만 확인했다.
- 낮은 성공률(후보 8개 기준 14회 호출 중 성공 3회)의 원인은 **모델의 일시적 과부하가 아니라 무료
  등급 일일 쿼터 소진**이었다. `gemini-3.7-flash`의
  `GenerateRequestsPerDayPerProjectPerModel-FreeTier` quotaValue는 20, 즉 하루 20요청이다. provider가
  준 "high demand" 메시지를 원인으로 읽은 초기 해석은 정정했다. 근거는 측정 위키에 있다.
- 따라서 필요한 것은 과부하 재시도 정책이 아니라 한도 인식이다. 하루 20요청 한도에서는 재시도가
  쿼터만 더 태운다. SDK 기본 재시도가 예산의 절반 이상을 소비할 수 있다는 사실 자체는 그대로다.
- 후보가 3개인데 부족 사유를 함께 반환해 `schema_validation`으로 거부된 실행이 있었다. 모델이 이
  계약을 항상 지키지는 않는다.
- Gemini 무료 등급의 일일 한도는 모델별로 따로 걸린다. `gemini-3.7-flash`가 막힌 뒤에도
  `gemini-3.6-flash`·`gemini-3.5-flash`·`gemini-3.5-flash-lite`는 각자 여유가 남아 동작했다. 다만
  모델을 바꿔 측정을 이어가면 실행 간 비교가 모델 간 비교로 바뀐다.
