# 스트리밍 렌더링 비용 측정과 전송 계약

## 문서 목적

기능 정의서 `실시간 AI Streaming 응답`이 `확인 필요`로 남긴 네 항목을 실제 측정값과 함께 확정합니다. 네 항목은 리렌더링 범위 최소화 방식, 메시지 누적에 따른 DOM 증가 관리 방식, Syntax Highlighting과 Markdown Parsing 비용 관리 방식, 스트리밍 연결이 끊긴 뒤 재연결하는 방식입니다. 앞의 세 항목은 측정으로 확정했고 마지막 항목은 설계 결정으로 확정했습니다.

프로젝트 원칙에 따라 추측으로 최적화를 먼저 넣지 않았습니다. 측정을 먼저 하고 그 결과가 가리키는 것만 구현했습니다.

## 측정 방법

측정 스크립트는 `src/features/interview/measurement/streaming-render-cost.measure.mts` 하나입니다. `node <파일>`로 그대로 다시 실행할 수 있습니다.

1부는 Node에서 CPU 비용을 측정합니다. Markdown 파싱, React 렌더 트리 생성, Syntax Highlighting은 모두 DOM이 필요 없는 순수 JS 작업이므로 Node에서 잰 값이 브라우저에서도 그대로 의미를 가집니다. 2부는 Playwright가 띄운 실제 Chromium에서 layout 비용을 측정합니다. Node에서 잴 수 없는 항목, 즉 DOM이 쌓였을 때의 append 비용과 스크롤 비용이 대상입니다.

측정 대상 메시지는 스크립트 안에서 만드는 합성 코퍼스입니다. 실제 질문 생성 경로가 아직 없어서 실제 응답을 쓸 수 없습니다. 한 메시지는 제목, 산문 문단 두 개, 목록, TypeScript Code Block 한 개로 이루어지고 길이는 733자입니다. 난수를 쓰지 않으므로 같은 입력이 모든 비교 대상에 똑같이 들어갑니다.

측정값은 warmup 5회 뒤 21회 표본의 중앙값입니다. Chromium의 `performance.now()`는 0.1밀리초 단위로 잘려 나오므로 20회를 한 묶음으로 재고 나누어 분해능을 확보했습니다.

측정 환경은 Node v24.18.0, Windows 11, react-markdown 10.1.0, shiki 4.4.3, Playwright 1.62.1의 headless Chromium입니다. 절대값은 기기에 따라 달라지므로 아래 결정은 모두 같은 실행 안에서의 상대 비교를 근거로 삼았습니다.

## 측정 결과

### 리렌더 범위

이미 쌓인 메시지 20개가 있는 상태에서 청크 하나가 도착할 때의 비용입니다.

| 방식 | 청크 1개당 | 청크 31개 누적 |
| --- | --- | --- |
| 대화 전체를 다시 렌더 | 6.75 ms | 209 ms |
| 스트리밍 중인 마지막 메시지만 렌더 | 0.13 ms | 4 ms |

차이는 51.7배입니다. 대화 전체를 다시 렌더하는 비용은 누적 메시지 수에 비례해서 커집니다. 메시지 80개 기준으로 한 번 전체를 다시 렌더하면 32.62밀리초가 들고, 이는 60fps 한 프레임인 16.7밀리초의 두 배입니다.

### 스트리밍 메시지 길이에 따른 재파싱 비용

마지막 메시지만 다시 렌더하더라도 그 메시지가 길어지면 청크당 비용이 함께 커집니다.

| 스트리밍 메시지 길이 | 청크 1개당 재파싱 |
| --- | --- |
| 733자 (Code Block 1개) | 0.53 ms |
| 1,331자 (Code Block 2개) | 0.63 ms |
| 2,527자 (Code Block 4개) | 0.85 ms |
| 4,919자 (Code Block 8개) | 2.94 ms |

길이에 거의 비례합니다. SSE 청크는 한 프레임 안에 여러 개가 도착할 수 있으므로 도착할 때마다 렌더하면 같은 프레임 안에서 같은 파싱을 여러 번 하게 됩니다.

### Syntax Highlighting

| 항목 | 비용 |
| --- | --- |
| `createHighlighter` (테마 1개, 언어 1개) | 53.67 ms (최초 1회) |
| `codeToHtml` 1회 (13줄 TypeScript) | 1.09 ms |
| 미완성 코드에 청크마다 highlight (18청크) | 11.08 ms |

같은 Code Block 하나를 스트리밍 도중 청크마다 highlight하면 완료 후 한 번만 하는 것보다 10.2배가 듭니다. `createHighlighter`는 최초 1회에만 드는 비용이지만 50밀리초대여서 첫 화면을 막지 않도록 다뤄야 합니다.

### 실제 Chromium DOM 비용

메시지 하나는 Markdown만으로 12개 노드, Code Block을 shiki로 highlight하면 71개 노드가 더해져 실질 82개 노드입니다.

| 메시지 | DOM 노드 | 메시지 1개 append | 스트리밍 청크 1개 | 하단 자동 스크롤 |
| --- | --- | --- | --- | --- |
| 1 | 82 | 0.30 ms | 0.030 ms | 0.000 ms |
| 5 | 410 | 0.28 ms | 0.030 ms | 0.000 ms |
| 10 | 820 | 0.43 ms | 0.070 ms | 0.000 ms |
| 20 | 1,640 | 0.25 ms | 0.035 ms | 0.000 ms |
| 40 | 3,280 | 0.57 ms | 0.070 ms | 0.005 ms |
| 80 | 6,560 | 0.52 ms | 0.105 ms | 0.000 ms |
| 160 | 13,120 | 0.50 ms | 0.090 ms | 0.000 ms |

DOM 노드가 82개에서 13,120개로 160배 늘어나는 동안 append 비용은 0.30밀리초에서 0.50밀리초로만 늘었습니다. 스트리밍 청크 하나가 유발하는 layout은 0.1밀리초 아래이고 하단으로의 자동 스크롤은 측정 한계 아래입니다.

즉 이 화면의 병목은 누적된 DOM이 아니라 JavaScript 쪽의 Markdown 재파싱입니다.

## 확정한 최적화 결정

### 1. 리렌더 범위는 스트리밍 중인 메시지로 한정합니다

완료된 메시지는 `React.memo`로 고정하고 스트리밍 중인 마지막 메시지만 갱신합니다. 근거는 51.7배 차이입니다. 완료된 메시지의 Markdown 결과는 내용이 더 이상 바뀌지 않으므로 다시 파싱할 이유가 없습니다.

### 2. 청크 반영은 애니메이션 프레임 단위로 모읍니다

도착한 청크를 버퍼에 모으고 `requestAnimationFrame`마다 한 번만 화면에 반영합니다. 근거는 재파싱 비용이 메시지 길이에 비례한다는 측정입니다. 4,919자 메시지에서 청크당 2.94밀리초이므로 한 프레임에 청크 다섯 개가 도착하면 14.7밀리초를 같은 파싱에 씁니다. 프레임당 한 번으로 모으면 그 프레임에서 한 번만 파싱합니다. 도착 순서는 버퍼에서 그대로 유지되므로 표시 순서는 달라지지 않습니다.

### 3. Syntax Highlighting은 코드 블록이 닫힌 뒤에 한 번만 합니다

스트리밍 중인 미완성 코드에는 highlight를 적용하지 않고 일반 텍스트로 보여 줍니다. 코드 펜스가 닫힌 뒤에 한 번만 highlight합니다. 근거는 10.2배 차이입니다. 미완성 코드는 문법적으로 깨져 있어서 highlight 결과 자체도 최종 결과와 다릅니다.

highlighter는 모듈 하나에 단일 인스턴스로 두고 최초 필요 시점에 만듭니다. 53.67밀리초가 최초 1회에 들기 때문에 메시지마다 만들면 안 됩니다. 테마와 언어는 실제로 쓰는 것만 등록합니다.

### 4. 가상 스크롤을 도입하지 않습니다

`@tanstack/react-virtual`이 `package.json`에 있지만 이번 범위에서 쓰지 않습니다. 근거는 Chromium 실측입니다. DOM 노드가 160배 늘어도 append와 layout 비용이 거의 늘지 않았습니다. 가상 스크롤은 스크롤 위치 복원, 높이 추정, 자동 스크롤 판정을 모두 복잡하게 만드는데 그 대가로 얻을 이득이 측정에서 확인되지 않았습니다.

재검토 기준을 함께 남깁니다. 메시지가 160개를 넘거나, 메시지 1개 append 비용이 한 프레임의 절반인 8밀리초를 넘으면 다시 측정합니다. 인터뷰 한 건의 대화는 질문과 답변을 합쳐도 수십 개 규모이므로 현재 기준으로는 도달하지 않습니다.

### 5. 낭독 대상은 메시지가 아니라 상태와 새 메시지 안내입니다 (PR #61 리뷰)

메시지가 쌓이는 자리에 `role="log"`와 `aria-live="polite"`를 함께 두었다가 `aria-live="off"`로 고쳤습니다. `role="log"`는 완성된 메시지가 하나씩 추가되는 패턴을 전제하는데, 이 화면은 메시지 하나의 텍스트가 프레임마다 자라납니다. 그 자리를 live region으로 두면 스크린리더가 커지는 질문 전체를 프레임마다 다시 읽습니다.

정작 알려야 할 두 가지가 live region이 아니었습니다. 상태 문단은 `aria-describedby`로만 연결되어 있어 `연결이 끊겨 다시 연결하고 있습니다` 같은 전이가 낭독되지 않았고, 새 메시지 도착 안내는 나타나도 알림이 없었습니다. 자동 스크롤이 멈춘 것을 볼 수 없는 사용자는 새 내용이 왔다는 사실을 알 방법이 없습니다. 둘 다 `aria-live="polite"`로 바꿨습니다.

새 메시지 안내 문단은 조건부로 만들지 않고 항상 두고 내용만 비웁니다. live region은 붙어 있는 동안의 변경만 알리므로, 내용을 담은 채 새로 나타나면 낭독하지 않는 스크린리더가 있습니다. 빈 상태에서 grid 간격이 생기지 않도록 `:empty`일 때만 절대 위치로 빼서 grid 항목에서 제외합니다.

이슈 #47 PR #52 1차 리뷰가 `aria-label`로 안내를 가린 것을 P1으로 잡은 적이 있습니다. 이번은 안내를 노출하는 방식은 지켰지만 무엇을 낭독시킬지가 반대로 가 있었습니다.

## 측정의 한계

측정 대상은 실제 AI 응답이 아니라 합성 코퍼스입니다. 실제 질문의 Code Block 길이와 언어 종류가 다르면 절대값이 달라집니다. 다만 위 결정은 모두 배수 비교에 근거하므로 절대값이 달라져도 방향은 유지됩니다.

Chromium은 headless로 실행했고 GPU 합성 경로를 쓰지 않습니다. 따라서 paint와 합성 비용은 이 측정에 포함되지 않았습니다. 측정한 것은 DOM 조작과 layout까지입니다.

`react-dom/server`의 `renderToStaticMarkup`으로 렌더 비용을 쟀습니다. 브라우저의 재조정 비용과 정확히 같지는 않지만 Markdown 파싱과 React 엘리먼트 생성이 비용의 대부분이므로 비교 목적에는 충분합니다.

## 전송과 오류 계약

### 전송 방식

기능 정의서 결정에 따라 SSE를 씁니다. `EventSource`가 아니라 `fetch`와 `ReadableStream`으로 직접 SSE를 파싱합니다. `EventSource`는 요청 헤더를 붙일 수 없고 POST를 보낼 수 없으며 재연결 시점과 횟수를 제어할 수 없습니다. 이 기능은 재연결 횟수를 제한해야 하고 뒤에 붙을 질문 생성 경로가 근거 스냅샷을 본문으로 보내야 하므로 `EventSource`로는 부족합니다.

### 이벤트 계약

| 이벤트 | data | 뜻 |
| --- | --- | --- |
| `chunk` | `{ "seq": number, "text": string }` | 도착한 응답 조각입니다. `seq`는 1부터 1씩 늘어납니다. |
| `done` | `{ "seq": number }` | 스트림이 정상적으로 끝났습니다. `seq`는 마지막 청크 번호입니다. |
| `error` | `{ "kind": string, "message": string }` | 생성 쪽에서 오류가 났습니다. `kind`는 아래 오류 분류를 따릅니다. |

각 청크는 SSE `id` 필드로 `seq`를 함께 보냅니다. 재연결할 때 클라이언트가 `Last-Event-ID` 헤더로 마지막으로 받은 `seq`를 보내면 서버가 그 다음 청크부터 이어서 보냅니다.

### 오류 분류

`src/features/experience-candidates/errors.ts`의 기존 규칙을 그대로 씁니다. 생성 쪽에서 발생한 오류는 기존 `ExperienceCandidateOutputErrorKind`를 그대로 실어 보내고 이 기능이 다시 분류하지 않습니다. 상태 코드 매핑도 `wiki/2026-08-21-stage-a-선별-계약.md`의 표를 따릅니다.

전송 계층에서만 생기는 두 가지는 기존 분류에 대응하는 값이 없어서 이 기능이 정의합니다. 하나는 응답 본문이 시작되기 전에 실패한 경우이고 다른 하나는 본문을 받는 도중 끊긴 경우입니다. 둘은 사용자에게 줄 안내가 다릅니다. 앞은 아직 받은 내용이 없고 뒤는 이미 받은 내용을 지우면 안 됩니다. 기존 `llm_*` 분류는 provider 호출에 대한 것이므로 브라우저와 서버 사이의 전송 실패에 갖다 붙이지 않았습니다.

| 상황 | kind | 화면 동작 |
| --- | --- | --- |
| 응답 시작 전 실패, 또는 분류를 읽을 수 없는 비2xx 응답 | `stream_connect_failed` | 오류 안내와 다시 시도 버튼을 보여 줍니다. |
| 본문 수신 도중 끊김 | `stream_interrupted` | 이미 받은 내용을 유지한 채 재연결을 시도하고, 실패하면 안내와 다시 시도 버튼을 보여 줍니다. |

### 스트림 시작 전 오류 본문도 분류를 그대로 옮깁니다 (PR #61 리뷰)

처음 안은 비2xx 응답을 본문을 읽지 않고 전부 `stream_connect_failed`로 뭉갰습니다. 스트림이 시작되기 전의 실패를 전송 문제로만 본 것인데 사실이 아닙니다. 질문 생성 route는 첫 토큰 전에 나는 실패를 `stage-a`·`stage-b`와 같은 방식으로 HTTP 상태와 JSON 본문에 실어 보냅니다. `llm_rate_limit` 503이 대표적입니다.

본문을 버리면 두 가지가 함께 틀어집니다. 한도 초과에 "네트워크 상태를 확인해 주세요"라는 틀린 안내가 나가고, 기다리면 풀리는 오류가 재시도 안내 없이 끝납니다. 이 route가 내는 422 `invalid_request`에서 이미 관측되던 문제입니다.

그래서 비2xx 응답의 본문에서 `error.kind`를 읽어 아는 분류이면 그대로 올립니다. 아는 분류의 목록은 `src/features/interview/errors.ts`에 `Record`로 두었습니다. 배열이 아니라 `Record`인 이유는 `ExperienceCandidateOutputErrorKind`에 값이 추가될 때 여기 빠뜨리면 컴파일이 실패하게 하기 위해서입니다. 조용히 누락되면 새 분류가 다시 전송 실패로 뭉개집니다.

route 단계의 거절 분류(`unauthorized`, `invalid_json`, `invalid_request`, `body_too_large`)는 `ExperienceCandidateOutputErrorKind`에 없으므로 `InterviewStreamRequestErrorKind`로 따로 두었습니다. 값과 상태 코드는 `stage-a` route와 같습니다.

이렇게 올린 분류는 `stream_interrupted`가 아니므로 자동 재연결 대상이 아닙니다. 서버가 한도 초과나 인증 실패를 명시한 상황에서 1초 뒤에 같은 요청을 다시 보내는 것은 의미가 없습니다. 이미 받은 내용은 그대로 두고 사용자에게 결정을 넘깁니다.

### 재연결 방식

전송 도중 끊긴 경우에만 자동으로 재연결합니다. 최대 두 번 시도하고 간격은 1초와 2초입니다. 재연결 요청에는 `Last-Event-ID` 헤더로 마지막 `seq`를 실어 보내고 서버는 그 다음 청크부터 보냅니다. 이미 화면에 있는 내용은 지우지 않습니다.

자동 재연결을 두 번으로 제한한 이유는 이 범위에 서버 지속 생성이 없기 때문입니다. 서버가 클라이언트 연결과 무관하게 생성을 이어 가고 결과를 저장하는 동작은 저장 계층과 사용자 식별자에 동시에 의존해서 `wiki/2026-08-24-경험선택-세션저장-후속-backlog.md`로 미뤄 두었습니다. 따라서 무한히 재시도해도 이어받을 상태가 서버에 남아 있다고 보장할 수 없습니다. 두 번 안에 붙지 않으면 사용자에게 결정을 넘깁니다.

시작 자체가 실패한 경우에는 자동으로 재시도하지 않습니다. 인증 실패나 잘못된 요청처럼 같은 요청을 반복해도 풀리지 않는 원인이 섞여 있기 때문입니다.

## 확인 필요

- 실제 질문 생성 경로가 붙은 뒤에 실제 응답으로 다시 측정해야 합니다. 이번 측정은 합성 코퍼스 기준입니다.
- 이 화면을 실제 질문 생성 경로에 배선하는 시점은 아직 정해지지 않았습니다. 배선 지점이 이슈 #59의 화면 작업과 같은 자리입니다.
- 서버가 재연결 요청을 이어받으려면 진행 중인 생성 상태를 들고 있어야 합니다. 이번 범위의 테스트용 스트림은 내용이 결정적이라 `seq`만으로 이어붙일 수 있지만, 실제 LLM 스트림은 그렇지 않습니다. 저장 계층이 생긴 뒤에 다시 정해야 합니다.
