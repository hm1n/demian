# Stage A 전량 투입과 점수 역할 이동 검토

2026-08-27. 근거 이슈 #69. 다른 세션에서 나온 두 제안(이 문서에서 A-1, A-2로 부릅니다)을 현행
코드와 맞춰 본 결과입니다.

`wiki/2026-08-25-Stage-A-청크-폐기와-점수-선별-전환.md`의 4절이 정한 점수 컷오프를 재검토합니다.
그 문서를 대체하지는 않습니다. 컷오프 폐기는 아직 채택 조건을 만족하지 않은 상태입니다.

## 0. 검토 대상 두 제안

A-1은 점수를 컷오프에서 정렬로 바꾸는 설계 변경입니다. 작업 묶음 전량을 한 호출에 넣되 점수
내림차순으로 배치하고, 프롬프트에서 앞쪽은 자세히 판단하고 뒤쪽은 채택 여부만 훑으라고 지시해
재현율 100퍼센트와 호출 1회를 함께 얻는다는 것입니다.

A-2는 A-1의 전제 검증입니다. 전량 판단으로 출력 토큰이 늘어 55초 시한이 출력 생성 시간에서
깨질 수 있으므로, 출력을 짧은 플래그나 코드로 압축하고 제공자별 초당 출력 토큰을 실측해 예산을
다시 잡자는 것입니다. 채택 묶음에는 최소 필드, 탈락 묶음에는 사유 코드, 판단 불가에는 SHA만
싣는 비대칭 출력을 함께 제안했습니다.

## 1. 결론

컷오프 폐기와 전량 투입은 채택합니다. 다만 이슈 #69의 제공자 전환 이후에만 실행할 수 있고,
66묶음 전수 응답 준수율 실측을 채택 조건으로 둡니다.

A-2의 비대칭 출력은 채택하지 않습니다. 현행 출력이 이미 그 제안보다 작습니다. A-1의 비대칭
지시(앞쪽 상세·뒤쪽 약식)도 채택하지 않습니다. 근거는 8절에 적습니다.

| 제안 요소 | 현행 상태 | 판단 |
| --- | --- | --- |
| 점수 내림차순 배치 | 이미 구현 | 추가 작업 없음 |
| 컷오프 제거(전량 투입) | 미구현 | 조건부 채택 |
| SHA·인덱스 최소 출력 | 이미 구현 | 추가 작업 없음 |
| 탈락 사유 코드 추가 | 미구현 | 채택하지 않음 |
| 앞쪽 상세·뒤쪽 약식 지시 | 미구현 | 채택하지 않음 |
| 출력 토큰 분리 계측 | 미구현 | 채택 |

## 2. Stage B는 원본 데이터를 다시 조회합니다

A-2가 "Stage B가 원본 묶음 데이터를 다시 조회하는 구조라면 Stage A 출력에서 근거 텍스트도 뺄 수
있다"고 적었습니다. 확인 결과 그 구조입니다.

`src/app/api/candidates/stage-b/route.ts:110`의 순회가 후보 SHA마다
`fetchCommitDetailBySha(auth, candidate.sha)`로 GitHub에서 커밋 상세를 새로 가져옵니다. Stage B의
판단 입력인 diff와 파일 목록은 Stage A 출력에서 오지 않습니다.

Stage A에서 Stage B로 넘어가는 값은 `StageACandidate` 세 필드뿐입니다(`types.ts:44`).

```
sha:              string
source:           "contribution_match" | "automatic_recommendation"
contributionItem: string | null
```

라우트의 `isCandidate`가 이 세 필드만 통과시키므로 근거 문장이 흘러갈 경로 자체가 없습니다.

세 필드 모두 실제로 쓰입니다. `sha`는 재조회 키이고, `source`와 `contributionItem`은
`buildStageBPayload`로 넘어가 기여 항목에 맞은 후보를 먼저 남기는 판단에 씁니다. 지금 지울 수
있는 필드는 없습니다.

## 3. Stage A 출력은 이미 최소 형태입니다

`stage-a.ts:133`의 구조화 출력 스키마가 요구하는 것이 전부입니다.

```
pullRequestNumber: integer
contributionItem:  string | null
recommended:       boolean
```

자유 서술 필드가 없습니다. 식별자도 40자 SHA가 아니라 Pull Request 번호이고, 응답을 받은 뒤
`shaByPullRequest`로 대표 SHA로 옮깁니다(`stage-a.ts:419`). A-2가 권한 "짧은 인덱스 번호와 SHA
교차 검증"이 이미 이 형태로 구현되어 있습니다.

A-2가 걱정한 두 가지도 이미 막혀 있습니다.

첫째, `unjudgedShas`와 `unclassifiedShas`의 구분은 출력에 실어 받는 값이 아니라 입력 집합과 응답
집합의 대조에서 유도합니다. 응답에 없는 번호는 판단 불가로, 입력에 없던 번호는 `unknown_sha`
오류로, 중복 번호는 `schema_validation`으로 처리합니다(`stage-a.ts:425`~`439`). 커버리지 검증
능력도 같은 대조에서 나옵니다.

둘째, 출력 토큰 1만 추정은 실제보다 큽니다. 현행 스키마로 66개 결정을 담은 JSON 전체가
4,560바이트입니다. 대략 1,200~1,500토큰이므로 초당 100토큰대 제공자에서도 15초 안쪽입니다.

```
{"pullRequestNumber":113,"contributionItem":null,"recommended":false}   69바이트
66개 결정 전체                                                        4,560바이트
```

그러므로 비대칭 출력은 출력을 줄이지 않고 늘립니다. 탈락 묶음에 사유 코드를 더하면 필드가 셋에서
넷이 되고, 채택 묶음에 근거 한 줄을 붙이면 Stage B가 읽지 않는 문장을 생성하는 비용이 새로
생깁니다.

## 4. 전량 판단에서 늘어나는 것은 추론 토큰입니다

A-2의 걱정 자체는 방향이 맞습니다. 이유가 다릅니다.

`gpt-oss` 계열은 추론 토큰이 출력에 실립니다. 위키 6절이 프롬프트 바이트가 거의 같은데도 총
토큰이 2,954에서 3,949까지 34퍼센트 흔들린 것을 기록했습니다. 판단 대상이 15묶음에서 66묶음으로
늘면 이 값이 늘어나는데, 출력 스키마를 줄여도 줄지 않습니다.

따라서 A-2에서 실제로 필요한 작업은 출력 압축이 아니라 계측 항목 변경입니다. `scripts/measure-pipeline.ts`는
Groq 응답 헤더의 `usedTokens` 한 값만 찍으므로 입력과 출력이 분리되지 않습니다. 제공자별 초당
출력 토큰과 추론 토큰 발생량을 재려면 입출력 분리와 첫 토큰 지연을 추가해야 합니다.

## 5. 정렬은 이미 구현되어 있습니다

`selectWorkUnitsForStageA`가 `sortByScoreDescending`으로 점수 내림차순 정렬을 먼저 하고
(`work-unit-selection.ts:92`) 그 순서대로 `selected`에 담습니다. 그 배열이 그대로 `units`가 되어
프롬프트에 실리므로 모델은 이미 점수 높은 묶음을 먼저 읽습니다.

그러므로 A-1에서 새로 하는 일은 컷오프 제거 하나입니다.

## 6. 컷의 근거가 품질이 아닙니다

컷을 정하는 것은 점수가 아니라 프롬프트 바이트 예산입니다. 점수는 예산이 떨어지는 지점을 어디로
옮길지만 정합니다. 증거는 `thresholdScore`의 정의입니다. 미리 정한 기준선이 아니라 예산에
마지막으로 들어간 묶음의 점수를 사후에 읽은 값입니다(`work-unit-selection.ts:143`).

그런데 화면 문구는 품질 판정으로 말합니다.

```
below_score_threshold: "점수가 기준에 못 미쳐 판단 대상에서 제외했습니다"
over_byte_budget:      "한 번에 보낼 수 있는 분량을 넘어 제외했습니다"
```

첫 번째 문구가 사실과 다른 이유가 둘입니다. 잘린 묶음은 프롬프트에 실리지 않았으므로 설명할
거리가 있는지 판단된 바가 없습니다. 그리고 "기준"은 저장소마다 움직입니다. 같은 2점 묶음이
`demian`에서는 1점 경계까지 내려가 통과하고 `andbread`에서는 3점 경계에서 잘립니다.

버려지는 분량도 작지 않습니다. `andbread`는 66묶음 중 10개만 판단 대상이 되어 재현율이
15퍼센트입니다. 위키 5절이 점수가 대체로 규모 점수라고 스스로 진단하고, `demian`에서는 신호 9개
중 `file_rewritten_repeatedly` 52퍼센트와 `many_commits` 43퍼센트가 점수를 지배한다고 기록했습니다.
그 배제가 옳다는 근거는 없습니다.

전량 투입 이후에는 `below_score_threshold`가 평상시 저장소에서 발생하지 않고 `over_byte_budget`만
남습니다. 남는 문구는 실제 사유와 일치합니다.

## 7. 점수는 지우지 않고 역할만 내려놓습니다

점수가 지금 세 가지 일을 합니다.

| 역할 | 위치 | 전량 투입 후 |
| --- | --- | --- |
| 프롬프트 배치 순서 | `work-unit-selection.ts:92` | 유지 |
| 판단 대상 배제 | `work-unit-selection.ts:128` | 컨텍스트 한도를 넘는 저장소에만 남음 |
| 병합 트림의 동점 처리 | 위키 7-2절, 입력 순서 = 점수 순서 | 유지 |

컷오프가 완전히 사라지는 것이 아닙니다. 컷의 위치를 올리는 변경입니다. `andbread`는 커밋 319개에
66묶음으로 전량이 약 24,000토큰이지만, 커밋 1,000개짜리 저장소는 묶음이 200개 안팎이 되어
`gpt-oss` 계열 컨텍스트 131,072토큰을 스칩니다. 그런 저장소에서는 점수가 남길 묶음을 계속
정합니다.

## 8. 비대칭 지시를 채택하지 않는 이유

위키 10절이 기록한 사고가 이 종류입니다. 시스템 프롬프트가 "각 PR 번호를 정확히 한 번
반환하세요"와 "합쳐서 최대 N개입니다"를 한 문단에 담았더니 뒤가 앞을 덮어, 6건 중 5건에서 모델이
정확히 상한 개수만 답했습니다. "뒤쪽은 채택 여부만 빠르게 훑으라"는 지시는 전수 응답 규칙과 같은
축에서 충돌합니다.

정렬 순서에 정보가 있다는 전제도 데이터와 어긋납니다. 위키 5절이 점수는 위쪽만 잘 가르고 아래쪽
순서는 쓰지 않는다고 명시했습니다. `andbread`는 66묶음 중 56개가 2점 이하에 뭉쳐 있고 `demian`은
20위와 21위가 모두 0점입니다. "뒤쪽"이라는 구간을 정렬로 정의할 수 없습니다.

무엇보다 검증할 수 없습니다. 모델이 뒤쪽을 훑었는지와 지시대로 얕게 봤는지를 출력으로 구별할
방법이 없으므로, A-2가 스스로 경계한 조용한 절단을 프롬프트로 정당화하게 됩니다.

## 9. 채택 조건: 66묶음 전수 응답 준수율

전량 투입으로 얻는 재현율은 모델이 전수 응답 계약을 지킬 때만 진짜입니다. 66개를 보내고 20개만
판단하면 46개가 `unjudgedShas`로 떨어집니다. 지금 56개가 제외로 표시되는 것과 사용자가 보는
결과가 크게 다르지 않고, 게다가 제외는 결정론적인데 판단 불가는 실행마다 다른 묶음이 빠집니다.

가진 근거는 묶음 15개에서의 값뿐입니다(위키 10절).

```
개정 후: 15개(누락0)  5개(누락10)  15개(누락0)  15개(누락0)     4회 중 3회 준수
```

66묶음은 4.4배 긴 목록입니다. 목록이 길수록 중간에 끊는 경향이 강해진다는 것은 예상일 뿐이므로,
같은 입력을 최소 3회 돌려 준수율과 판단 불가 건수를 함께 기록하고 채택을 결정합니다.

## 10. 실행 순서와 상한 재산정

이 변경은 이슈 #69의 제공자 전환 이후에만 실행할 수 있습니다. 위키 5절 실측 바이트에 관측
최대치 바이트당 0.676토큰을 적용하면 아래와 같고, Groq 무료 등급 분당 한도 8,000에서는 작은
저장소 전량조차 한도를 혼자 채웁니다.

| | 선별 후(현행) | 전량 |
| --- | --- | --- |
| demian | 15묶음 9,070B / 약 6,100토큰 | 21묶음 11,659B / 약 7,900토큰 |
| andbread | 10묶음 10,263B / 약 6,900토큰 | 66묶음 35,550B / 약 24,000토큰 |

청크를 나눠 우회할 수 없습니다. 분당 토큰 한도는 청크를 나눠도 합계에 걸립니다
(`candidate-client.ts:164`).

전환과 함께 다시 역산할 상수가 셋입니다. 모두 8,000 한도에서 나온 값입니다.

| 상수 | 현재 | 위치 |
| --- | --- | --- |
| `STAGE_A_MAX_SELECTION_BYTES` | 10,500 | `work-unit-selection.ts:22` |
| `STAGE_A_CHUNK_MAX_BYTES` | 10,500 | `stage-a.ts` |
| `STAGE_A_CHUNK_MAX_REQUEST_BYTES` | 20,000 | `stage-a.ts` |

비용은 늘어납니다. 위키가 잡은 입력 100만 토큰당 0.50달러 가정으로 Stage A 입력이 약 7,100에서
24,000토큰이 되면 회당 0.0036달러에서 0.012달러가 됩니다. 분석 1회 총 0.0226달러가 0.031달러
안팎이 되어 10달러 예산 안 분석 횟수가 442회에서 약 320회로 줄어듭니다.

순서는 이렇습니다.

1. 이슈 #69 제공자 전환
2. `scripts/measure-pipeline.ts`에 입출력 토큰 분리와 첫 토큰 지연 추가
3. `STAGE_A_MAX_SELECTION_BYTES`를 새 제공자 한도에서 역산해 상향
4. `andbread` 66묶음 전량을 같은 입력으로 3회 이상 보내 준수율과 판단 불가 건수 기록
5. 준수율이 유지되면 `below_score_threshold` 배제와 그 화면 문구 제거

준수율이 무너지면 다음 선택지는 비대칭 지시가 아니라 청크 격리입니다. 컷오프를 올리면 청크가
여러 개로 갈릴 확률이 오르므로, 한 청크의 실패가 나머지를 죽이지 않게 만드는 작업이 짝이 됩니다.

## 11. 확인 필요

66묶음 전수 응답 준수율을 재보지 않았습니다. 9절의 판단 전부가 이 값에 걸립니다.

전량 투입이 선정 품질을 올린다는 증거가 없습니다. 얻는 것은 재현율이고, 후보 상한 5는 그대로이므로
잘렸던 묶음이 실제로 후보가 되는지는 확인되지 않았습니다. 위키 5절이 남긴 사실은 선별을 통과한
PR#66이 프롬프트 개정 후 후보로 뽑혔다는 것뿐이고, 잘린 묶음에 대한 관측은 없습니다.
