# 실데이터 검증과 배치·상한 확정

이슈 #19의 측정 결과입니다. 미검증 초기 상수 8개를 실측 근거로 확정하고, 알려진 API 경계 세 항목과
LLM 후보 선정 품질을 관측했습니다.

## 측정 방법과 환경

- 측정일 2026-08-24. 측정 스크립트는 `scripts/measure-pipeline.ts`이며 `npx tsx`로 수동 실행합니다.
  파일명이 `*.test.ts`가 아니므로 vitest 기본 include 패턴에 잡히지 않고, `npx vitest list`로 수집
  대상에 없음을 확인했습니다. 테스트 스위트는 실호출을 하지 않습니다.
- 측정 대상은 `hm1n/demian`(작성자 커밋 116개)이며, 페이지네이션 비용만 `hm1n/Algorithm`(작성자 커밋
  435개)로 보조 측정했습니다. `demian`을 주 대상으로 고른 이유는 실제 PR 소속과 의미 있는 기능 커밋이
  함께 있어 선정 품질을 사람이 검증할 수 있는 유일한 후보이기 때문입니다.
- GitHub 토큰은 `GITHUB_TOKEN=$(gh auth token)` 환경 변수로만 주입하고 파일에 저장하지 않습니다.
  LLM 키는 `.env`(gitignore 대상)에서 읽습니다. 이 문서에는 수치와 요약만 남기고 응답 원문은 남기지
  않습니다.
- 반복 횟수: 커밋 목록 조회 9회, 상세 조회 배치 7회(병렬도 1·2·4·8·16 포함), Stage A 호출 9회,
  Stage B 호출 14회. GitHub core rate limit은 5000 중 약 1000을 소비했고 한도에 닿지 않았습니다.

## Vercel Hobby 실행 상한

- Hobby의 함수 실행 상한은 **기본 300초, 최대 300초**입니다. fluid compute는 신규 프로젝트에서 기본
  활성이며 이 표는 그 상태의 값입니다. 요청·응답 본문 상한은 4.5MB입니다.
- 출처와 확인일(2026-08-24):
  - <https://vercel.com/docs/functions/limitations>
  - <https://vercel.com/docs/functions/configuring-functions/duration>
- 따라서 라우트의 `maxDuration = 60`과 예산 상수 55초는 **플랫폼 상한이 아니라 우리가 스스로 건
  제약**입니다. 이 사실을 명시적으로 기록합니다. 측정된 실제 소요가 60초 안에 충분히 들어오고, 후보
  생성을 수 분간 기다리는 UX가 받아들이기 어려워 60초를 UX 상한으로 유지합니다. 300초가 필요해지는
  근거가 나오면 그때 올립니다.

## `changedFiles` 3000 상한 왜곡

- **측정 대상 저장소에서는 관측되지 않았습니다.** `demian` 63커밋의 `changedFiles`는 중앙 4, p90 8,
  최대 17이며 300이나 3000 근처에 아무것도 없습니다.
- 기전은 공개 대형 커밋으로 우리 코드 경로(`fetchCommitDetail`)를 그대로 통과시켜 확인했습니다.
  - 상세 응답의 파일 목록은 페이지당 300개이고 `rel="last"`가 10페이지이므로 하드 상한은 3000개입니다.
  - 실제로 `changedFiles`가 **정확히 3000에서 포화**했습니다. 같은 응답의 `additions`는 6,718,755로
    **포화하지 않은 실제 총량**을 유지했습니다.
- 즉 상한에 닿는 커밋은 "파일 3000개인데 추가 670만 줄"이라는 **내부적으로 모순된 신호**가 되어
  Stage A 입력으로 들어갑니다. `changedFiles`는 `files.length`에서 파생되므로 포화하지만
  `additions`/`deletions`는 GitHub의 `stats`를 그대로 쓰기 때문입니다.
- 비용도 큽니다. 이 커밋 하나가 요청 11회와 8.3초, patch 문자 5,770,352자를 소비했습니다.
- `/api/github/commit-details`는 `withoutPatch`로 patch를 벗겨 응답하므로 4.5MB 응답 상한을 넘기지는
  않습니다. 이 경로는 문제 없습니다.

## 422 응답 관측

- **정상 흐름에서는 개수 초과 422가 관측되지 않았고, 도달 불가입니다.** `selectStageACandidates`가
  후보를 `INITIAL_STAGE_A_CANDIDATE_LIMIT`(20) 이하로 자체 강제하고, `/api/candidates/stage-b`는
  `STAGE_B_MAX_CANDIDATES`(20) 초과를 422로 막습니다. 두 값이 같으므로 Stage A를 거친 입력은 개수
  때문에 422가 되지 않습니다.
- 측정에서 Stage A가 낸 후보는 최대 8개였고 422는 발생하지 않았습니다.
- 따라서 이 422는 개수 초과가 아니라 형식 위반(SHA 형식, 중복, 스키마 불일치) 방어용으로만 의미가
  있습니다. 두 상수를 각각 바꿀 때 같이 바꿔야 이 성질이 유지됩니다.

### diff 예산 배분 결함과 수정

**수정 전(선착순 배분).** `buildStageBPayload`가 커밋 순서대로 patch 예산을 소비해, 후보 20개를
넣으면 **앞쪽 9개가 60,000자를 다 쓰고 나머지 11개(55%)는 patch를 한 글자도 받지 못했습니다.**
재현 결과가 동일했습니다.

```
순서별 배정 문자: 0:3618 1:2281 2:836 3:16936 4:8722 5:4895 6:2112 7:8000 8:12600
                 9:0 10:0 11:0 12:0 13:0 14:0 15:0 16:0 17:0 18:0 19:0
```

**관측된 실제 피해는 "순서 편향"이 아니라 "근거 없는 선정"이었습니다.** 처음에는 모델이 diff가
있는 앞쪽에서만 고를 것이라고 예상했지만, 실측은 그 예상을 반박했습니다. 선착순 배분 상태의
성공한 실행이 고른 최종 후보 3개는 payload 인덱스 3·9·17이었고, **9번과 17번은 patch를 한 글자도
받지 못한 후보입니다.** 즉 모델은 앞쪽으로 쏠린 것이 아니라, "실제 diff와 PR 소속만 근거로"
고르라는 지시를 받은 상태에서 **diff가 전혀 없는 후보를 근거 없이 선정**하고 있었습니다. 예상보다
나쁜 결과이며, 상한값이 아니라 배분 방식이 원인이라는 결론은 그대로입니다.

**수정 후(균등 배분).** 총량 60,000자와 후보 20개는 유지하고 배분 방식만 바꿨습니다.

- 후보별 몫은 `60,000 / 후보 수`(내림)입니다. 후보 20개면 각 3,000자입니다.
- 파일별 4,000자 상한은 후보의 몫 안에서 적용합니다. 몫이 파일 상한보다 작으면 몫이 실질 상한입니다.
- 몫을 다 쓰지 않은 후보의 잔액은 뒤 후보로 이월합니다. 이월이 앞에서 뒤로만 흐르므로 어떤 후보도
  자기 몫보다 적게 받지 않습니다.

같은 후보 20개에 대한 실측 결과입니다.

```
순서별 배정 문자: 0:3000 1:2281 2:836 3:5883 4:3000 5:3000 6:2112 7:3888 8:3000 9:3000
                 10:3000 11:3000 12:3000 13:3000 14:3000 15:3000 16:3000 17:3000 18:3000 19:3000
```

- **후보 20개 전원이 patch를 받고 굶는 후보가 0개입니다**(수정 전 9개 수령 / 11개 굶음).

## 부수 관측

- `/rate_limit` 엔드포인트는 캐시된 값을 돌려줍니다. 응답 헤더가 `x-ratelimit-remaining: 4762`를
  가리키는 시점에 `/rate_limit`은 4996을 반환했습니다. 소비량 판단은 각 응답의 `x-ratelimit-used`
  헤더로만 해야 합니다.
- Groq는 분당 토큰 한도 초과를 429가 아니라 **413 `rate_limit_exceeded`**로 반환합니다. 두 단계의
  `mapLlmError`에 413이 없어 한도 초과가 일반 실패(`llm_failure`, 502)로 분류되고 있었습니다.
  413을 `llm_rate_limit`으로 매핑하고 회귀 테스트를 추가했습니다.
- **더 큰 문제가 그 뒤에 있었습니다. SDK가 재시도한 실패는 `RetryError`로 감싸져 오고
  `RetryError`는 `APICallError`가 아닙니다.** 따라서 `mapLlmError`의 `APICallError` 분기 전체가
  실제 provider 오류에 대해 도달하지 않고, 429·413·503이 모두 `llm_failure`로 뭉개졌습니다.
  Gemini 일일 한도 초과(429)가 `llm_failure`로 보고되는 것을 실제로 관측해 발견했습니다.
  `generateObject`는 기본으로 재시도하므로 이 경로가 오히려 일반적입니다. 즉 413 매핑만 고쳐도
  프로덕션에서는 여전히 동작하지 않았을 것입니다. `RetryError.lastError`를 벗겨 분류하도록
  고쳤고, 같은 한도 오류가 `llm_rate_limit`으로 분류되는 것을 실데이터로 재확인했습니다.

## 확인 필요

- Stage A 입력 커밋 수 상한과 청크 분할이 필요합니다. Groq 무료 등급 8,000 TPM에서 입력은 12개
  내외가 한계인데 `demian`의 상세 조회 대상은 63개입니다. 분할 결과의 병합·재판단 정책이 없으면
  현실적인 저장소에서 Stage A가 완주하지 못합니다. 후속 이슈가 필요합니다.
- Stage A의 "입력 SHA 전수 응답" 계약 자체가 입력 수에 비례해 깨집니다. 계약을 유지하려면 입력을
  작게 유지해야 하고, 입력을 크게 하려면 계약을 바꿔야 합니다.
- Stage A 분류의 실행 간 불안정성과 느슨한 기여 항목 매칭은 프롬프트나 모델 수준의 개선이 필요합니다.
- Stage B 모델의 일시적 과부하 실패에 대한 재시도 정책이 필요합니다. 현재는 SDK 기본 재시도가
  예산의 절반 이상을 소비할 수 있습니다.
- 균등 배분 후 Stage B 선정 품질을 `gemini-3.7-flash`로 다시 측정해야 합니다. 일일 무료 한도
  소진으로 `gemini-3.6-flash`로만 확인했습니다.

  입력 품질 문제입니다. 별도 이슈 후보입니다.
- 상세 조회 병렬화는 효과가 확인됐으나 부분 실패·진행률 계약과 함께 설계해야 합니다.

  실제 파이프라인 통과를 검증하지 못했습니다.
