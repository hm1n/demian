# 워크트리·에이전트 운영 절차

Orca 워크트리로 병렬 작업을 돌리면서 반복해 물린 문제와 그 대응을 남긴다. 코드가 아니라 작업
환경에 관한 것이므로 세션 로그가 아니라 여기에 둔다.

## 워크트리 생성 시 base가 낡을 수 있다

`orca worktree create --base-branch develop`은 **로컬** `develop`을 base로 쓴다. 로컬 `develop`이
`origin/develop`보다 뒤처져 있으면 낡은 커밋에서 워크트리가 만들어진다.

Wave 2에서 실제로 발생했다. 로컬 `develop`이 Wave 1 머지 2건을 반영하지 않은 상태였고, 새
워크트리가 그 커밋에서 시작됐다.

- 워크트리를 만들기 전에 로컬 `develop`을 `git merge --ff-only origin/develop`으로 맞춘다.
- 이미 만들었다면 워크트리에서 `git reset --hard origin/develop`으로 옮긴다.
- 워크트리 생성 직후 `git log --oneline -1`로 base를 **직접 확인한다.** 지정한 브랜치 이름만 보고
  최신이라고 가정하지 않는다.

## 브랜치를 fast-forward해도 node_modules는 따라오지 않는다

`git merge --ff-only`는 `package.json`을 갱신하지만 `node_modules`는 손대지 않는다. 새 의존성이
추가된 커밋을 당겨오면 설치가 빠진 상태가 된다.

Wave 2 머지 후 검증에서 실제로 발생했다. `@testing-library/jest-dom`, `@testing-library/react`,
`jsdom`이 빠진 상태여서 테스트가 306개가 아니라 280개로 나오고 `toHaveValue` 타입 오류가 났다.
**코드 결함으로 오진할 수 있는 형태였다.**

- 브랜치를 크게 옮긴 뒤 검증할 때는 `npm ci`를 먼저 실행한다. `npm install`이 아니라 `npm ci`를
  쓴다. lockfile을 수정하지 않기 때문이다.
- 테스트 개수가 예상과 다르면 코드를 의심하기 전에 설치 상태를 확인한다.

## 워크트리 브랜치 이름은 생성 후 확인한다

`orca worktree create`에 `--branch` 플래그가 없다. 브랜치 이름은 `--name`에서 파생되며 한글과
공백이 그대로 들어갈 수 있다. Wave 2에서 `hm1n/17-Stage-B-최종-판단`이 만들어졌다.

- 생성 직후 `git branch -m <원하는 이름>`으로 바꾼다. PR을 만들기 전에 한다.

## 오케스트레이션 브랜치를 이관 수단으로 쓰지 않는다

워크트리를 만들 때 생기는 오케스트레이션용 브랜치는 origin에 푸시되지 않을 수 있고, 작업이
진행되는 동안 `develop`보다 크게 뒤처진다. Wave 2 종료 시점에 `hm1n/feature`는 origin에 없고
`develop`보다 57커밋 뒤처져 있었다.

- 세션 간·기기 간에 남겨야 하는 내용은 **`develop`에서 딴 브랜치에 커밋해 PR로 올린다.**
- 대화 내용, 스크래치패드 브리프, Orca 워크트리 코멘트는 기기를 옮기면 사라진다. git에 푸시된
  것만 남는다.

## 에이전트를 도중에 바꿀 수 있다

작업을 이어받게 하려고 새 워크트리를 만들 필요가 없다. 같은 워크트리에 다른 에이전트 터미널을
띄운다.

```
orca terminal create --worktree issue:<번호> --command "claude" --title "<제목>"
```

`orca worktree create`가 아니라 `orca terminal create`를 쓴다. 브랜치, 커밋 이력,
`node_modules`가 그대로 유지되고 기존 터미널도 남는다. Wave 2에서 Codex 토큰이 부족해져
Claude Code로 전환할 때 이 방법을 썼다.

- 에이전트를 바꾸면 **프로젝트 스킬 컨텍스트가 초기화된다.** 새 에이전트는 `AGENTS.md`와
  `.agents/skills/`를 처음 읽는다. 지시 브리프에 필수 문서 목록을 명시해 넘긴다.

## 병렬 작업의 파일 경계를 미리 나눈다

Wave 0에서 3개 PR이 같은 파일을 수정해 머지 후 테스트가 깨졌다
(`2026-08-21-wave-0-머지-후-테스트-실패.md`). 이후 웨이브에서는 브리프에 담당별 소유 디렉터리를
명시하고 있다.

- `llm-wiki/log.md`처럼 모든 작업이 건드리는 공용 파일은 **파일 맨 끝에 자기 행 1줄만** 추가하게
  한다. 충돌은 오케스트레이터가 해결한다.
- 같은 문서를 갱신하는 후속 작업은 새 행을 추가하지 않고 **기존 행을 수정한다.**
