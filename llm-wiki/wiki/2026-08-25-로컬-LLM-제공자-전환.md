# 로컬 LLM 제공자 전환 (이슈 #66)

확인 날짜는 2026-08-25입니다. 측정 환경은 RTX 4070 Laptop, VRAM 8,188MiB, Ollama 0.32.15입니다.

## 1. 배경

2026-08-26 발표 시연에 파이프라인 1회 완주가 필요한데 두 단계 모두 외부 제공자 한도에 막혔습니다. Stage A는 Groq 무료 등급의 분당 토큰 한도 8,000에 정상 호출 하나가 약 7,100 토큰을 써서 복구 호출이 곧바로 한도를 넘겼습니다. Stage B는 `gemini-3.7-flash`가 두 토큰 출력에 16.0초에서 119.2초를 써서 예산 55초 안에 끝나지 않았습니다. 근거는 이슈 #66 본문에 있습니다.

판단 품질과 프로덕션 제공자는 바꾸지 않습니다. 로컬 실행 결과는 계약 준수율이나 후보 품질의 근거로 쓰지 않습니다. 프로덕션 판단 품질의 근거는 이슈 #19 실측뿐입니다.

## 2. 전환 방식

제공자 결정을 `src/features/experience-candidates/llm-provider.ts` 한 곳으로 모았습니다. `createGroq()`가 `baseURL`과 `apiKey`를 받으므로 Ollama의 OpenAI 호환 엔드포인트를 가리키면 새 의존성 없이 전환됩니다. `package.json`에 추가한 패키지가 없습니다.

Gemini API는 OpenAI 호환이 아니므로 로컬에서는 Stage B도 Groq 제공자를 통해 같은 OpenAI 호환 경로를 탑니다.

환경변수는 다음과 같습니다. `LLM_BASE_URL`이 비어 있으면 프로덕션 경로(Stage A는 Groq `openai/gpt-oss-120b`, Stage B는 Google `gemini-3.7-flash`)가 그대로 동작합니다.

| 환경변수 | 뜻 | 시연에서 쓴 값 |
| --- | --- | --- |
| `LLM_BASE_URL` | 로컬 전환의 유일한 스위치입니다 | `http://localhost:11434/v1` |
| `LLM_API_KEY` | Ollama는 검사하지 않지만 SDK가 요구합니다. 비우면 자리값을 채웁니다 | `ollama` |
| `STAGE_A_MODEL` | 로컬 전환일 때만 적용합니다 | `qwen2.5:7b` |
| `STAGE_B_MODEL` | 로컬 전환일 때만 적용합니다 | `qwen2.5:7b` |
| `LLM_TIMEOUT_MS` | 로컬 전환일 때만 프로덕션 시한을 대신합니다 | `300000` |
| `LLM_TEMPERATURE` | 로컬 전환일 때만 샘플링 온도를 지정합니다. 미설정이면 제공자 기본값입니다 | `0` |
| `NEXT_PUBLIC_LLM_STAGE_B_MAX_INPUT_COMMITS` | Stage B 입력 커밋 수를 줄입니다. 프로덕션 상수보다 크게는 못 만듭니다 | `4` |
| `NEXT_PUBLIC_LLM_STAGE_B_MAX_TOTAL_PATCH_CHARS` | Stage B patch 총량을 줄입니다. 프로덕션 상수보다 크게는 못 만듭니다 | `12000` |

모델 환경변수는 `LLM_BASE_URL`이 설정된 경우에만 적용합니다. 모델만 바꾸는 경로를 열어 두면 프로덕션 실행이 로컬 사정에 끌려갑니다. `LLM_BASE_URL`을 설정하고 모델 환경변수를 빠뜨리면 `llm_configuration` 오류로 먼저 끊습니다. 프로덕션 모델 ID를 로컬 엔드포인트로 보내면 404가 되고, 그 404는 원인이 환경변수 누락이라는 사실을 감춥니다.

입력 축소값에 `NEXT_PUBLIC_` 접두사를 쓴 이유는 입력 커밋 수 상한을 `candidate-client.ts`가 브라우저에서 적용하기 때문입니다. 서버 전용 환경변수로는 읽을 수 없습니다.

## 3. Ollama 서버 설정이 실효 컨텍스트를 결정합니다

OpenAI 호환 경로에서는 요청마다 `num_ctx`를 넘길 수 없으므로 서버 설정이 필요합니다. 여기서 실효 컨텍스트는 `OLLAMA_CONTEXT_LENGTH`가 아니라 `OLLAMA_CONTEXT_LENGTH / OLLAMA_NUM_PARALLEL`입니다.

측정한 사실입니다. `num_ctx` 16,384를 준 모델에 41,411자(약 18,000토큰) 프롬프트를 보내면 `prompt_tokens`가 8,194로 돌아왔습니다. 오류도 경고도 없습니다. 병렬 슬롯 기본값 2가 컨텍스트를 반으로 갈랐기 때문입니다. `OLLAMA_NUM_PARALLEL=1`과 `OLLAMA_CONTEXT_LENGTH=16384`를 서버에 주고 다시 보내면 같은 프롬프트가 12,329토큰짜리 요청에서 온전히 처리됩니다.

프롬프트가 조용히 잘리면 그 뒤에 나오는 실패가 원인을 가립니다. Stage B에서 실제로 `unknown_file_path`가 났습니다. 모델은 보지 못한 파일을 인용한 것이 아니라, 잘려서 보지 못한 입력을 추측으로 메운 것입니다.

VRAM 8,188MiB에서 `qwen2.5:7b`의 GPU 전량 적재 한계는 컨텍스트 16,384입니다.

| 컨텍스트 | `ollama ps` 크기 | 배치 |
| --- | --- | --- |
| 4,096 | 4.7GB | 100% GPU |
| 16,384 | 5.5GB | 100% GPU |
| 32,768 | 6.8GB | 8%/92% CPU/GPU |

환경변수는 Ollama 서버 프로세스가 시작할 때 읽습니다. `setx`로 저장한 뒤에도 이미 떠 있는 서버에는 적용되지 않으므로 Ollama를 다시 띄워야 합니다. 실행이 느릴 때는 품질 문제로 의심하기 전에 `ollama ps`의 `PROCESSOR` 열을 먼저 봅니다.

## 4. 구조화 출력은 Ollama에서 동작합니다

`@ai-sdk/groq`는 `response_format: json_schema`로 스키마를 동봉해 보냅니다. Ollama의 OpenAI 호환 계층이 이를 받아 스키마에 맞는 객체를 돌려줬습니다. Stage A 스키마로 직접 호출해 확인했고, Stage A 실행에서도 `generateObject`가 정상 동작했습니다. 프롬프트로만 JSON을 요구하는 별도 경로는 필요하지 않았습니다.

## 5. Stage A 실측

`demian` 저장소, 작성자 커밋 213건 중 블랙리스트 통과 118건, 점수 선별 뒤 입력 묶음 11개 기준입니다.

| 실행 | 결과 | 소요 | 전수 응답 계약 |
| --- | --- | --- | --- |
| 1회 | 성공, 후보 5/5 | 23.2초 | 11/11 충족 |
| 2회 | 후보 상한 초과로 `schema_validation` | 13.9초 | 11/11 충족 |
| 3회 | 성공, 후보 5/5 | 13.7초 | 11/11 충족 |

예산 55초 안입니다. 2회는 모델이 상한 5개를 넘겨 골랐습니다. 라우트의 `selectWithRecovery`가 이 경우를 최대 2회 재시도하므로 화면 경로에서는 복구 대상입니다. 측정 스크립트는 라우트를 거치지 않아 그대로 끝났습니다.

## 6. Stage B는 프로덕션 입력을 로컬 컨텍스트에 담을 수 없습니다

프로덕션 입력(커밋 30개, patch 총 60,000자)은 직렬화 145KB입니다. 캐시 상세로 조합한 크기는 다음과 같습니다.

| 커밋 수 | patch 예산 | 직렬화 크기 |
| --- | --- | --- |
| 30 | 60,000 | 144,959B |
| 30 | 20,000 | 94,936B |
| 30 | 0 | 70,155B |
| 12 | 20,000 | 59,231B (18,136토큰) |
| 8 | 12,000 | 39,900B (12,329토큰) |

커밋 30개는 patch를 한 글자도 싣지 않아도 70KB입니다. 컨텍스트 16,384에는 들어가지 않습니다. 그래서 로컬에서는 입력 커밋 수와 patch 총량을 함께 줄여야 합니다. 두 값 모두 프로덕션 상수보다 크게는 만들 수 없게 막았습니다. 프로덕션 예산은 이슈 #19 실측(상세 조회 커밋당 868밀리초, 파일별 patch 중앙 1,257자)에 묶여 있습니다.

커밋 8개·patch 12,000자와 커밋 4개·patch 12,000자를 각각 돌린 결과입니다.

| 입력 | 결과 | 소요 |
| --- | --- | --- |
| 커밋 8개 | `schema_validation` (부족 사유 누락) | 54.2초 |
| 커밋 8개 | `schema_validation` (부족 사유 누락) | 60.4초 |
| 커밋 8개 | `unrelated_sha` | 47.7초 |
| 커밋 8개 | `unknown_file_path` | 27.4초 |
| 커밋 8개 | `unknown_file_path` | 25.5초 |
| 커밋 4개 | 성공, 최종 후보 3개 | 31.8초 |
| 커밋 4개 | 성공, 최종 후보 3개 | 30.7초 |
| 커밋 4개 (Stage A 연결) | 성공, 최종 후보 3개 | 30.2초 |

커밋 4개에서는 후보마다 patch 3,000자가 실렸습니다. 커밋 8개에서 반복된 `unknown_file_path`는 인용 검증이 후보 단위라는 점과 맞물립니다. 허용 경로는 그 후보의 대표 커밋과 관련 커밋의 파일뿐이므로, 입력에 다른 후보의 파일이 많을수록 작은 모델이 경계를 넘습니다.

## 7. Stage B 시스템 프롬프트에 없는 출력 계약이 있습니다

`validateExperienceCandidateOutput`은 후보가 3개 미만이면 `insufficientCandidatesReason`을 요구하고 3개면 null을 요구합니다. 프로덕션 시스템 프롬프트는 이 규칙을 말하지 않습니다. `gemini-3.7-flash`는 스키마만 보고 지켰지만 `qwen2.5:7b`와 `llama3.1:8b`는 모두 어겼습니다.

프로덕션 프롬프트를 바꾸지 않기로 하고, 로컬 제공자일 때만 붙는 안내 문구를 `stage-b.ts`에 두었습니다. 문구는 부족 사유 규칙과 함께 SHA·파일 경로를 입력에서 그대로 복사하라는 지시를 담습니다. 이 문구를 붙인 뒤 부족 사유 위반은 사라졌습니다.

`확인 필요`입니다. 이 규칙을 프로덕션 프롬프트에도 넣을지는 결정하지 않았습니다. 넣으면 프로덕션과 로컬의 프롬프트가 다시 같아지지만 Gemini 출력에 미치는 영향을 측정해야 합니다.

## 7-1. Stage A는 커밋 제목의 PR 번호를 판단 대상으로 오인합니다

묶음 요약의 커밋 제목에는 `Merge pull request #35` 같은 문구가 섞여 있습니다. `qwen2.5:7b`는 그 번호들을 입력으로 끌어와 입력 11묶음에 대해 46개 판정을 돌려주고 `unknown_sha`로 끝났습니다. 화면 경로에서 재시도 버튼까지 눌러 4회 연속 같은 방식으로 실패했습니다. 실패마다 다른 PR 번호 묶음이 나왔습니다(#0, #53, #89, #35 이하 12개, #44 이하 4개).

같은 입력에서 측정 스크립트로 돌린 초기 3회는 전수 응답 계약을 지켰으므로, 이 혼동은 확률적으로 나타납니다. 프로덕션 모델 `openai/gpt-oss-120b`에서는 관측되지 않았습니다.

해소한 조합은 두 가지를 함께 적용한 것입니다.

1. 로컬 전용 프롬프트 문구로 판단 대상을 각 묶음 첫 줄의 `PR#번호`로 못박고, 커밋 제목 안의 다른 번호는 대상이 아니라고 명시했습니다.
2. `LLM_TEMPERATURE=0`을 줬습니다.

같은 입력으로 3회씩 비교한 결과입니다.

| 조건 | Stage A 결과 |
| --- | --- |
| 안내 없음, 온도 0 | 3회 모두 실패. 매번 동일하게 46개 판정 |
| 안내 있음, 제공자 기본 샘플링 | 1회 성공, 1회 후보 상한 초과, 1회 입력 밖 PR 번호 |
| 안내 있음, 온도 0 | 3회 모두 성공. 11/11 계약 충족, 12.7~13.7초 |

온도만 0으로 낮추면 잘못된 응답이 고정되므로 프롬프트 안내가 먼저입니다. 두 값 모두 로컬 전환일 때만 적용되고 프로덕션 프롬프트와 샘플링은 그대로입니다.

## 8. 모델 선택

`llama3.1:8b`는 컨텍스트 16,384에서 7.3GB를 써서 13%가 CPU로 넘어갔고, Stage B 한 번이 242.7초였으며 부족 사유 규칙도 같이 어겼습니다. 시연 모델은 `qwen2.5:7b`입니다.

## 9. 한도 메타데이터

Ollama는 `x-ratelimit-remaining-tokens`를 보내지 않습니다. 그대로 두면 `__rateLimit`이 null이 되고, 청크가 둘 이상일 때 첫 청크가 정상 완주하면 `candidate-client.ts`가 이 응답을 저하가 아니라 형식 오류로 보고 `LLM 토큰 한도 메타데이터가 없습니다`로 Stage A 전체를 실패시킵니다. 클라이언트는 서버 환경변수를 읽을 수 없으므로 서버의 `stage-a.ts` 로컬 분기에서 메타데이터를 합성합니다. 프로덕션 경로의 null은 라우트 `degrade`의 표식이므로 그대로 둡니다.

## 9-1. 시연 경로 UI 완주

`.env.local`에 위 값을 넣고 `npm run dev`로 띄운 뒤 Playwright로 화면을 조작해 저장소 입력부터 인터뷰 대상 확정까지 한 번에 완주했습니다. 저장소 분석과 상세 조회를 포함해 총 145.0초였고, Stage A와 Stage B가 각각 200으로 응답했습니다. 확정 화면에는 대표 커밋 변경 파일 8개, 관련 커밋 0개, 인용 파일 4개와 함께 앞 단계 patch 절단 알림이 표시됐습니다.

리허설 중에 소스를 고치면 Fast Refresh 전체 리로드가 일어나 화면 상태가 초기화됩니다. 측정 중에는 편집하지 않습니다.

## 10. 재현 절차

1. `OLLAMA_CONTEXT_LENGTH=16384`과 `OLLAMA_NUM_PARALLEL=1`을 설정하고 Ollama를 다시 띄웁니다.
2. `ollama pull qwen2.5:7b`로 모델을 준비하고, 호출 뒤 `ollama ps`에서 `100% GPU`와 `CONTEXT 16384`를 확인합니다.
3. `.env.local`에 2절 표의 환경변수를 넣습니다. `LLM_TEMPERATURE=0`을 빠뜨리면 Stage A가 확률적으로 입력 밖 PR 번호를 답합니다. 이 파일은 `.gitignore`의 `.env*`에 걸려 커밋되지 않습니다.
4. `npm run dev`로 띄우고 저장소 분석부터 인터뷰 대상 확정까지 진행합니다.
5. 단계별 수치만 보려면 `GITHUB_TOKEN=$(gh auth token) npx tsx --env-file=.env.local scripts/measure-pipeline.ts hm1n demian stage-b`를 씁니다. 로컬 전환에서는 환경변수가 모델을 결정하므로 `--model` 플래그는 무시됩니다.
