# Stage A 메시지·stat 선별 계약

## 결정

Stage A는 커밋 SHA와 메시지, 전체 stat, 파일별 경로와 상태 및 stat으로 구성한 경량 커밋과 줄 단위 `contributionItems`를 입력받습니다. 요청 파일에 `patch`가 있으면 크기 상한이 아니라 입력 계약 위반 422로 거부합니다. LLM에도 같은 경량 정보만 전달하며 PR 정보, 작성자와 날짜는 전달하지 않습니다.

LLM은 각 SHA에 `contributionItem`과 `recommended`를 반환합니다. `contributionItem`이 입력 목록의 원문과 정확히 일치하면 `contribution_match` 후보가 됩니다. 기여 항목이 있어도 나머지 커밋 중 설명할 가치가 있으면 `recommended`를 참으로 반환하며, 서버는 라벨이 `null`, `미분류`, 입력 목록에 없는 값 중 무엇이든 `automatic_recommendation` 후보로 정규화합니다. `recommended`가 거짓인 SHA만 미분류로 남습니다.

`미분류`는 LLM 응답의 예약 라벨입니다. 사용자가 같은 문자열을 기여 항목으로 입력해도 `contribution_match`로 해석하지 않습니다.

Stage A 응답은 `candidates`와 `unclassifiedShas`로 구성합니다. 후보는 SHA, 기존 `ExperienceCandidateSource`, 일치한 기여 항목 또는 `null`만 포함합니다. Stage B의 근거, 인용 파일 경로, 관련 SHA, 최대 3개 제한은 포함하지 않습니다.

## 청크 분할과 병합 계약

클라이언트는 커밋을 최대 8개, Stage A 경량 JSON 6,000바이트, 파일 32개 이하인 청크로 나눕니다. 세 조건 중 하나라도 다음 커밋에서 넘으면 그 직전에서 경계를 닫습니다. 12개 청크는 실데이터 18번째 호출에서 SHA 전수 응답 계약이 깨졌고, 실패 청크 자체는 4,693바이트·파일 26개·최장 메시지 41자로 과대하지 않아 확률적 누락으로 판단했습니다. 따라서 개수 축소만 믿지 않고 누락 SHA만 최대 두 번 다시 판단합니다. 그래도 판단하지 못한 SHA 수와 사유는 오류 화면에 표시합니다.

청크 결과는 입력 SHA 기준으로 합치며, 완료한 청크의 후보·미분류·처리 SHA를 재시도 지점에 보존합니다. 실패 뒤 재개할 때 처리 SHA는 다시 보내지 않습니다. 후보가 20개를 넘으면 후보 청크마다 절반 이하만 남기도록 모델에 재판단을 요청합니다. 각 라운드는 후보 수를 반드시 줄이고 최대 6라운드에서 종료합니다. 상한 안에 수렴하지 못하면 순서 절단하지 않고 남은 후보 수와 실패 사유를 표시합니다.

각 응답은 Groq의 `x-ratelimit-remaining-tokens`와 `x-ratelimit-reset-tokens`, 실제 사용 토큰 수를 안전한 수치 메타데이터로 반환합니다. 다음 요청 전에 잔여 토큰이 실측 reserve 6,000보다 적으면 reset 시간과 1초의 경계 보정만큼 기다립니다. 고정 간격이나 경과 시간으로 진행 상태를 만들지 않습니다. 화면에는 실제 처리 수/전체 수/남은 수와 TPM 초기화 대기 여부를 표시합니다.

## 검증과 오류 계약

입력에 없는 SHA가 하나라도 있거나 입력 SHA가 하나라도 누락되면 전체 LLM 결과를 거부합니다. 누락을 미분류로 간주하면 모델의 명시적 판단과 불완전한 응답을 구분할 수 없기 때문입니다. 따라서 `unclassifiedShas`에는 LLM이 반환했고 `recommended`를 거짓으로 명시한 SHA만 포함됩니다. 구조 위반과 중복 SHA도 전체 결과를 거부합니다. 요청 본문은 4.5MB를 넘으면 LLM 호출 전에 거부합니다. GitHub 세션 쿠키는 LLM 비용 노출을 막기 위한 호출 권한 경계로만 사용합니다.

| 상황 | 오류 kind | HTTP status |
| --- | --- | --- |
| 세션 없음 또는 무효 | `unauthorized` | 401 |
| JSON 파싱 실패 | `invalid_json` | 400 |
| 요청 본문 4.5MB 초과 | `body_too_large` | 413 |
| 요청 계약 위반 | `invalid_request` | 422 |
| 구조화 응답 위반 | `schema_validation` | 502 |
| 입력에 없는 SHA | `unknown_sha` | 502 |
| LLM 네트워크 실패 | `llm_network` | 502 |
| LLM 인증 실패 | `llm_auth` | 502 |
| LLM 호출 한도: Groq 429, 또는 본문에 `rate_limit_exceeded`가 있는 413 | `llm_rate_limit` | 503 |
| LLM 타임아웃 | `llm_timeout` | 504 |
| LLM API 키 누락 또는 Groq 404 모델 없음 | `llm_configuration` | 500 |
| Groq 400·409·422 요청 또는 상태 거부, 그리고 한도 본문이 아닌 413(요청·컨텍스트 과대) | `llm_request` | 502 |
| 그 밖의 Groq HTTP 실패 | `llm_failure` | 502 |

`llm_network`는 provider 응답을 받기 전의 전송 실패에만 사용합니다. Groq가 HTTP status를 반환한 경우에는 status에 따라 인증, 호출 한도, 타임아웃, 설정, 요청, 일반 실패로 분류합니다.

413은 status만으로 갈리지 않습니다. Groq는 분당 토큰 한도 초과를 429가 아니라 413 `rate_limit_exceeded`로 반환하지만, 요청·컨텍스트가 모델 한도보다 큰 경우도 413입니다. 앞은 기다리면 풀리고 뒤는 같은 페이로드로는 풀리지 않으므로 사용자에게 줄 안내가 갈립니다. 따라서 413은 응답 본문으로 판별하며, 한도 본문일 때만 `llm_rate_limit`(503)이고 나머지는 `llm_request`(502)입니다. 본문이 없으면 한도로 단정하지 않고 `llm_request`로 둡니다. 판별은 `errors.ts`의 `isRateLimitResponseBody`가 담당하고 Stage B도 같은 규칙을 씁니다.

이 분류는 provider 오류가 `RetryError`로 감싸여 도달하는 경우에도 적용됩니다. AI SDK는 재시도한 실패를 `RetryError`로 감싸고 `RetryError`는 `APICallError`가 아니므로, `lastError`를 벗긴 뒤 분류합니다. `generateObject`가 기본으로 재시도하기 때문에 이 경로가 예외가 아니라 일반입니다.

## 경계

화면의 Loading, Empty, Error 상태 연결은 이슈 #18의 책임입니다. Stage B의 diff 조회와 최종 후보 세 개 선정은 이슈 #17의 책임입니다. 후보 상한 20개는 이슈 #19의 실측으로 확정됐습니다. 후보 수는 병목이 아니며 실제 병목은 입력 커밋 수입니다. 상한을 넘긴 응답은 순서대로 절단하지 않고 전체 거부합니다. Stage A 응답 순서는 후보 순위가 아니므로 절단하면 근거 없이 후보를 잃기 때문입니다.

프로덕션 호출자 부재 한계는 이슈 #18에서 해소됐습니다. Repository 분석 상태 머신이 4단계에서 `/api/candidates/stage-a`를 호출합니다. 엔드포인트는 공개적으로 도달할 수 있으므로 GitHub에서 검증한 PAT 세션을 계속 요구합니다. 상태 매핑 결정은 `raw/2026-08-24-후보생성-상태연결-session-log.md`에 있습니다.

Groq 호출은 route의 60초 실행 제한보다 먼저 오류 계약을 반환하도록 55초에 중단합니다. 이슈 #19의 실측으로 55초를 확정했습니다. 성공한 호출은 3.1~11.1초, 계약 위반으로 끝난 호출도 29.0초였습니다.

Vercel Hobby의 실제 실행 상한은 60초가 아니라 **300초**입니다(이슈 #19에서 공식 문서로 확인, 2026-08-24). 따라서 `maxDuration = 60`과 55초 시한은 플랫폼 제약이 아니라 후보 생성 대기 시간을 제한하려는 우리 쪽 UX 결정입니다.

## 이슈 #19 실측으로 해소된 항목

측정 근거는 `wiki/2026-08-24-실데이터-검증-배치-상한-확정.md`에 있습니다.

- 모델은 `openai/gpt-oss-120b`로 확정했습니다. 기존 `llama-3.3-70b-versatile`은 Groq 모델 목록에서 사라져 404를 반환했습니다. 환경 변수는 SDK 기본값인 `GROQ_API_KEY`가 맞습니다.
- 후보 상한 20개는 60초 안에서 안정적입니다. 후보 수 자체가 시간을 늘리지 않습니다.
- 요청이 4.5MB에 가까워지는 상황은 오지 않습니다. 입력 63커밋이 46.0KB로 상한의 1.00%였습니다. 커밋 수 상한은 본문 크기 때문에 필요한 것이 아닙니다.
- Vercel Hobby의 실제 실행 상한은 300초로 확인했고, 55초 시한은 응답 여유가 충분합니다.

## 확인 필요

- **"입력 SHA를 정확히 한 번씩" 계약이 입력 수에 비례해 깨집니다.** 입력 8·12개에서는 지켰지만 18개에서는 9/18, 4/18만 응답했습니다. 계약을 유지하려면 입력을 작게 유지해야 하고, 입력을 크게 하려면 계약을 바꿔야 합니다.
- 기여 항목 의미 매칭 품질은 **느슨한 것으로 관측됐습니다.** "GitHub API 오류 처리와 부분 실패 복구 구현"에 UI 상태 연결 커밋과 클라이언트 요청 계층 커밋을 매칭했습니다. 설명 가치가 낮은 `+2/-2` 커밋과 줄 길이 정리 리팩터도 추천했습니다. 프롬프트나 모델 수준의 개선이 필요합니다.
- 같은 입력에 대한 분류가 실행마다 달라집니다. 같은 커밋이 실행에 따라 `contribution_match`와 `automatic_recommendation`으로 갈렸습니다.
