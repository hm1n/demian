# Repository 데이터 조회 후속 backlog

## 문서 목적

Issue #3 PR(#8) 리뷰에서 non-blocking으로 판정해 이번 PR에 반영하지 않은 항목을 모아 둔다. 판정 기준은 wiki/2026-08-20-코드리뷰-전략.md의 머지 판단 기준 절이다. 별도 GitHub Issue를 만들지 않고 이 문서를 기록 위치로 쓴다.

각 항목은 무엇을 미뤘는지, 왜 미뤘는지, 어떤 신호가 관측되면 다시 꺼내는지를 함께 적는다.

## 이번 PR에서 반영한 항목

비교 기준으로 남긴다. Codex 리뷰가 P2로 올린 세 건 중 다음 한 건은 수정 비용이 매우 작고 사용자에게 잘못된 안내가 전달되는 문제여서 같은 PR에서 처리했다.

- 파일 트리 조회의 409 응답을 빈 저장소로 처리한다. 이전에는 409가 `classifyErrorResponse`를 거쳐 `server_error`로 분류돼, 커밋이 없는 저장소에 서버 문제라는 틀린 안내가 나갔다.
- 함께 트리 404와 409를 빈 저장소로 보는 조건을 "상세 조회 대상 커밋이 없을 때"로 좁혔다. 커밋을 이미 수집했다면 그 저장소는 빈 저장소일 수 없으므로 실패로 던진다.

## 미뤄 둔 항목

### 1. 트리 404 이후 저장소 상태 재확인

언어 통계 조회와 파일 트리 조회 사이에 저장소가 삭제되거나 이전되면, 그때의 404를 빈 저장소로 오인할 수 있다는 지적이다. 근거는 PR #8의 리뷰 스레드다.

미뤄 둔 이유는 두 가지다. 첫째, 두 요청 사이의 짧은 구간에서만 성립하는 극단적인 레이스다. 둘째, 재확인을 넣으면 Repository 단위 API 호출이 다시 늘어나는데, 이번 단계에서 호출량을 줄인 방향과 반대다. 위의 "커밋이 없을 때만 빈 저장소로 본다" 조건으로 오인 범위가 이미 크게 좁아진 상태다.

실제로 빈 트리로 잘못 보고된 사례가 관측되면 `commits.ts`의 `resolveBranchHeadSha`가 쓰는 재확인 방식을 같은 형태로 가져온다.

### 2. 422 응답을 서버 오류와 구분

커밋 상세와 PR 조회에서 422가 오면 지금은 `server_error`로 분류돼 재시도 가능한 장애처럼 안내된다는 지적이다. 근거는 PR #8의 리뷰 스레드다.

미뤄 둔 이유는 `classifyErrorResponse`가 Issue #1과 #2 구현이 함께 쓰는 공용 분류라는 점이다. 새 오류 종류를 추가하면 이번 PR 범위를 넘는 변경이 되고, 그 종류를 소비하는 화면도 아직 없다. 422가 실제 호출에서 관측된 근거도 없어 `확인 필요` 상태다.

실데이터 검증에서 422가 관측되면 오류 종류를 추가한다. 그때 안내 문구까지 함께 정한다.

### 3. `changedFiles`와 `stats` 불일치

`changedFiles`는 응답의 `files` 배열 길이로 계산한다. GitHub이 파일 목록을 생략하거나 상한(3000개)에서 잘라내면 `additions`는 남아 있는데 `changedFiles`만 줄어든다.

미뤄 둔 이유는 이 규모의 커밋이 실제 대상 저장소에 있는지 확인되지 않았다는 점이다. 실데이터에서 파일 3000개를 넘는 커밋이 나오면 잘림 여부를 함께 전달하는 필드를 추가한다.

### 4. 수집 결과 크기 상한

커밋마다 파일별 `patch`를 그대로 보관한다. 필터 통과 커밋이 많은 저장소에서는 메모리와 이후 LLM 토큰 비용이 함께 커진다. Issue #3이 상한 도입을 실측 이후로 미뤄 둔 항목이라 이번에도 넣지 않았다.

실제 저장소에서 응답 크기와 소요 시간을 측정한 뒤 상한이나 요약 방식을 정한다.

### 5. 상세 조회 병렬화

커밋당 상세 1회와 PR 1회를 순차로 호출한다. 커밋이 많으면 대기 시간이 선형으로 늘어난다. 이 역시 Issue #3이 실측 이후로 미뤄 둔 항목이다.

측정 결과가 나오면 동시 요청 수와 rate limit 여유를 함께 보고 결정한다.

### 6. 작은 기록 항목

- `partialCommits`에는 부분 실패 시 `CommitDetail` 값이 담기지만 필드 타입은 `CommitSummary[]`다. 호출자가 좁혀 쓸 수 있다는 주석이 없다.
- 테스트가 커밋 상세와 언어 통계와 파일 트리 요청 URL은 검증하지만 PR 조회 요청 URL은 검증하지 않는다.
- 구현 세션 로그에 부분 실패의 원인 오류 종류를 `cause`로 보존한다는 설명이 없다.

### 7. Issue #5 상태 화면 후속 항목

- 3단계 파생 지표 계산은 `buildCandidateData`의 동기 객체 조립이며 실제 계산은 없다. 현재는 `setTimeout(0)`으로 상태를 그릴 기회만 만든다.
- 커밋 목록 응답 JSON 파싱 실패는 `network`로 분류되어 사용자에게 네트워크 연결 확인 안내가 표시된다.
- 테스트를 위해 `AnalysisDependencies`에 `yieldToBrowser`를 주입하고 프로덕션 DOM에 `data-error-kind`를 남겼다.
