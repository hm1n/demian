# 경험 판단 단위를 커밋에서 PR 묶음으로 전환하는 검토

확인 날짜: 2026-08-24
대상 이슈: [#49 Stage A 입력 범위 축소](https://github.com/hm1n/demian/issues/49)
관련 이슈: [#12 경험 후보 생성](https://github.com/hm1n/demian/issues/12), [#44 Stage A 입력 청크 분할과 병합 판단](https://github.com/hm1n/demian/issues/44), [#19 실데이터 검증과 배치·상한 확정](https://github.com/hm1n/demian/issues/19)
선행 문서: `wiki/2026-08-24-stage-a-청크-분할-실데이터-검증.md`, `wiki/2026-08-24-실데이터-검증-배치-상한-확정.md`, `wiki/2026-08-21-stage-a-선별-계약.md`

## 1. 결론

이슈 #49는 입력 범위 축소를 해결책으로 전제했습니다. 실측 결과 범위를 줄이지 않고도 목표를 달성할 수 있음을 확인했습니다. 판단 단위를 개별 커밋에서 PR 묶음으로 바꾸면 Stage A 입력이 81퍼센트 줄고 재판단 라운드가 구조적으로 사라집니다. 추가 GitHub API 호출은 발생하지 않습니다.

이슈 #49 착수 전 논의를 정리한 핸드오프 문서는 세 가지 개선안을 A, B, C 순서로 제시했습니다. 실측 결과 이 우선순위는 뒤집어야 합니다. C안에 해당하는 묶음 전처리가 핵심이고, B안에 해당하는 페이로드 축소는 별도로 진행할 필요가 없습니다.

## 2. 확인한 사실

### 2-1. PR 소속 정보는 Stage A 이전에 이미 조회되어 있습니다

`src/lib/github/contributions.ts`의 `fetchCommitDetail`이 커밋마다 `fetchAllPullRequests`를 호출합니다. `fetchCommitDetailBySha`도 같습니다. 반환 타입 `CommitDetail`은 `pullRequests` 필드를 가지고 있으며 상세 조회 캐시 파일에도 이 필드가 저장되어 있습니다.

따라서 PR 단위로 묶는 작업은 추가 API 호출을 발생시키지 않습니다. 핸드오프 문서는 C안을 이슈 #44에서 확정한 청크 분할 정책을 변경하는 작업으로 분류해 후순위로 두었으나, 실제로는 이미 비용을 지불한 데이터를 사용하지 않고 있던 상태였습니다.

Stage B는 이 데이터를 이미 사용합니다. `src/features/experience-candidates/stage-b.ts`의 `buildStageBPayload`가 후보마다 `pullRequests`를 페이로드에 담습니다.

### 2-2. PR에 묶이지 않은 커밋은 드뭅니다

| 저장소 | 커밋 | PR 묶음 | PR 없는 커밋 | 판단 단위 |
| --- | --- | --- | --- | --- |
| `hm1n/demian` | 83 | 19 | 2 | 21 |
| `andbread/Andbread_Frontend` | 319 | 66 | 0 | 66 |

두 저장소 모두 블랙리스트를 통과한 커밋 기준입니다. PR당 커밋 수는 `demian`이 평균 4.3개, `andbread`가 평균 4.8개입니다. 최대 묶음은 각각 9개와 21개입니다.

## 3. 실측

### 3-1. 측정 조건

`src/features/experience-candidates/candidate-client.ts`의 `splitCommits`와 `toStageARequest`를 그대로 복제한 스크립트로 측정했습니다. `demian` 앞 40개 커밋을 넣었을 때 청크가 7개로 나뉘어 실제 실행 결과와 일치했으므로 복제가 정확하다고 판단했습니다.

토큰 환산은 같은 40개 커밋 실행에서 Groq가 보고한 17,992 토큰을 기준으로 보정했습니다. 보정값은 2.10 바이트당 1 토큰입니다. 이 값은 출력 토큰을 포함하므로 입력만 놓고 보면 실제 바이트당 토큰 수는 이보다 큽니다. 표의 토큰 수치는 이 보정에 따른 추정이고, 바이트 수치는 실측입니다.

### 3-2. 입력량 감소

| 저장소 | 방식 | 판단 단위 | 페이로드 | 추정 토큰 | 감소율 |
| --- | --- | --- | --- | --- | --- |
| `demian` | 현재 | 83 | 73,034 바이트 | 34,778 | - |
| `demian` | PR 묶음 | 21 | 12,474 바이트 | 5,940 | 83퍼센트 |
| `andbread` | 현재 | 319 | 188,334 바이트 | 89,683 | - |
| `andbread` | PR 묶음 | 66 | 36,292 바이트 | 17,282 | 81퍼센트 |

페이로드는 청크마다 재전송되는 시스템 프롬프트를 포함한 값입니다. PR 묶음 방식의 커밋 환산 비용은 `andbread` 기준 커밋당 54 토큰입니다. 핸드오프 문서 B안이 목표로 제시한 커밋당 80에서 100 토큰보다 낮습니다. B안은 정보를 버려서 절감하는 방식이었으나 PR 묶음은 중복 경로와 중복 통계를 제거해 절감하므로 정보 손실이 더 적습니다.

Groq 무료 등급의 일일 한도 200,000 토큰을 기준으로 `andbread` 완주 횟수는 하루 1.5회에서 11.6회로 늘어납니다. 현재 수치는 재판단 라운드를 제외한 값이므로 실제 개선폭은 이보다 큽니다.

### 3-3. 재판단 라운드 제거

청크마다 상위 2개만 반환하도록 쿼터를 고정했을 때의 계산입니다.

| 저장소 | 방식 | 청크 | 쿼터 합 | 재판단 발생 |
| --- | --- | --- | --- | --- |
| `demian` | 현재 | 11 | 22 | 발생 |
| `demian` | PR 묶음 | 3 | 6 | 없음 |
| `andbread` | 현재 | 40 | 80 | 발생 |
| `andbread` | PR 묶음 | 7 | 14 | 없음 |

핸드오프 문서 A안에 해당하는 청크 쿼터만 적용하면 `andbread`에서 쿼터 합이 80이 되어 상한 20을 여전히 넘습니다. A안 단독으로는 재판단 라운드가 사라지지 않습니다. PR 묶음과 함께 적용해야 사라집니다.

현재 코드는 `stage-a.ts`의 시스템 프롬프트에서 `payload.candidateLimit ?? INITIAL_STAGE_A_CANDIDATE_LIMIT`을 청크마다 전송합니다. 청크가 14개면 실효 상한이 280개가 됩니다. 재판단 라운드는 이 구조가 만들어낸 문제입니다.

### 3-4. PR 묶음이 판단 품질을 높이는 이유

`andbread`의 최대 묶음을 압축 표현으로 확인했습니다. 다음은 실제 측정 결과에서 발췌한 요약입니다.

- PR#113 `PWA + Supabase 알림 기능 구현`은 커밋 18개, 기간 69일, 파일 56개입니다. 요약에는 iOS PWA 환경 대응, `next-pwa` 의존성 제거와 커스텀 서비스워커 작성, Supabase edge function 기반 알림 구현이 함께 나타납니다.
- PR#66 `vercel 배포 오류 수정`은 커밋 18개, 기간 1일, 파일 28개입니다. 커밋 18개 중 8개가 파일명 대소문자 변경입니다.

두 묶음 모두 인터뷰에서 설명할 가치가 있는 경험입니다. 그런데 같은 내용을 개별 커밋으로 보면 `chore: console.log 제거`, `chore: supabase.ts 업데이트`, `fix: 타입 오류 수정`, `Rename Modal.tsx to Modal.tsx`처럼 개별로는 잡무로 보이는 커밋이 대부분입니다. 이런 커밋은 블랙리스트 대상이거나 점수가 낮습니다.

Stage A가 선별하지 못하는 원인을 여기서 다시 해석할 수 있습니다. 핸드오프 문서 3-1은 원인을 비교 기준 없는 절대 판단 요구로 보았습니다. 이 해석은 일부만 맞습니다. 비교 기준을 제공해도 개별 잡무 커밋은 여전히 잡무입니다. 경험이 커밋 단위에 존재하지 않기 때문에 커밋 단위로는 선별할 수 없습니다.

### 3-5. 휴리스틱 점수 발화율

핸드오프 문서 5-1이 제시한 신호를 PR 묶음 단위로 적용했습니다.

| 신호 | `demian` 21단위 | `andbread` 66단위 |
| --- | --- | --- |
| 의존성 추가 | 14퍼센트 | 6퍼센트 |
| 인프라·배포 파일 신규 생성 | 0퍼센트 | 3퍼센트 |
| 같은 파일 3회 이상 재작성 | 43퍼센트 | 5퍼센트 |
| revert 또는 hotfix 연쇄 | 0퍼센트 | 0퍼센트 |
| 대형 리팩토링 | 0퍼센트 | 12퍼센트 |
| perf 또는 refactor 프리픽스 | 14퍼센트 | 11퍼센트 |
| 커밋 5개 이상 | 43퍼센트 | 35퍼센트 |
| 기간 3일 이상 | 0퍼센트 | 15퍼센트 |
| 파일 10개 이상 | 29퍼센트 | 44퍼센트 |

점수 상위 묶음은 실제로 설명 가치가 높은 작업과 일치했습니다. `andbread` 상위는 PR#113이 7점, PR#148이 6점, PR#128과 PR#123이 4점, PR#58이 4점, PR#66이 3점입니다. 신호가 하나도 없는 묶음은 `andbread`에서 25개이며 여기에 속한 커밋은 44개입니다. 묶음당 평균 1.8개 커밋이므로 0점 구간에는 소형 작업만 들어갑니다.

다만 신호의 성격을 정확히 기록해 둡니다. revert 또는 hotfix 연쇄는 두 저장소 모두 0퍼센트이고 인프라·배포 파일 신규 생성은 3퍼센트 이하입니다. 이 두 신호는 사실상 작동하지 않습니다. 발화율이 높은 커밋 5개 이상, 파일 10개 이상, 기간 3일 이상은 모두 규모 지표입니다. 따라서 이 점수는 대체로 규모 점수입니다. PR 묶음에서 규모와 설명 가치의 상관이 높으므로 사용에는 문제가 없으나, 일곱 가지 경험 유형을 탐지한다고 설명하면 과장입니다.

## 4. PR에 묶이지 않은 커밋의 처리

### 4-1. 결정

PR에 묶이지 않은 커밋은 경험 후보 대상에서 제외합니다. 폴백 묶음 규칙은 도입하지 않습니다.

근거는 2-2의 실측입니다. `andbread`는 319개 커밋 전부가 PR에 묶여 있고 `demian`은 83개 중 2개만 묶이지 않았습니다. 제외되는 비중이 작습니다. 또한 4-2에서 확인했듯 폴백 규칙의 정확도가 충분하지 않아 도입 비용에 비해 얻는 것이 적습니다.

제외는 조용히 이루어져서는 안 됩니다. 제외한 커밋 수와 사유를 사용자에게 표시하고 사용자가 확장해 확인할 수 있는 경로를 제공해야 합니다. 이 요건은 이슈 #49의 조용한 배제 금지 원칙을 따릅니다.

### 4-2. 폴백 규칙 측정 기록

결정에 따라 사용하지 않지만, 나중에 PR을 쓰지 않는 저장소를 다시 검토할 때 필요하므로 측정값을 남깁니다. 정답은 PR 소속이고 순도는 커밋 가중 순도입니다. 각 묶음에서 최다 정답 라벨이 차지하는 커밋 수를 전체 커밋 수로 나눈 값입니다.

`andbread` 319개 커밋, 정답 66묶음 기준입니다.

| 규칙 | 묶음 | 순도 | 최대 묶음 |
| --- | --- | --- | --- |
| 정확 경로 겹침 | 31 | 16퍼센트 | 282 |
| 정확 경로 겹침에 묶음 최대 8커밋 제한 | 95 | 51퍼센트 | 8 |
| 정확 경로 겹침이며 72시간 이내 | 143 | 69퍼센트 | 37 |
| 디렉터리 겹침 | 7 | 9퍼센트 | 311 |
| 디렉터리 겹침이며 24시간 이내 | 130 | 77퍼센트 | 29 |

경로 겹침만 사용하면 전이 관계 때문에 연쇄 병합이 일어납니다. 커밋 A와 B가 파일을 공유하고 B와 C가 다른 파일을 공유하면 A와 C가 무관한데도 한 묶음이 됩니다. 그 결과 319개 중 282개가 하나의 묶음이 되었습니다. 연쇄를 끊는 요소는 시간 제한입니다. 디렉터리 겹침 단독은 9퍼센트로 가장 나쁩니다. 공통 상위 디렉터리가 전체를 흡수합니다.

가장 나은 규칙은 디렉터리 겹침이며 24시간 이내로 77퍼센트입니다. 묶음이 130개로 정답 66개의 두 배이므로 과분할 상태입니다. 이 용도에서는 과분할이 과병합보다 안전합니다. 과분할된 묶음도 일관된 작업 단위이지만, 과병합된 묶음은 서로 무관한 작업이 섞여 판단이 불가능합니다.

### 4-3. 이전 측정값 정정

같은 날 세션 중간에 정확 경로 겹침의 순도를 75퍼센트로 보고한 기록이 있습니다. 그 측정은 전이 폐쇄를 적용하지 않은 묶기였습니다. 전이 폐쇄를 적용해 다시 측정한 값은 위 표와 같이 `andbread`에서 16퍼센트, `demian`에서 14퍼센트입니다. 4-2의 값이 정확한 값입니다.

## 6. 함께 수정해야 하는 지점

### 6-1. Stage B는 커밋 키 기반입니다

`stage-b.ts`의 `buildStageBPayload`는 `candidateBySha`로 후보를 조회하며 커밋 하나당 페이로드 항목 하나를 만듭니다. patch 예산 `STAGE_B_MAX_TOTAL_PATCH_CHARS`를 커밋 수로 나누어 배분합니다.

Stage A가 PR 묶음을 넘기면 묶음 하나가 커밋 여러 개로 펼쳐집니다. 묶음 8개에 평균 4.8개 커밋이면 38개 커밋이 되고 커밋당 patch 예산이 1,578자로 줄어듭니다. 현재 실측된 후보당 3,750자보다 크게 낮습니다.

대응 방안으로 묶음당 대표 커밋을 `changes` 기준 상위 3개로 제한하는 방법을 제안합니다. 묶음 8개면 24개 커밋이 되어 커밋당 2,500자를 확보합니다. 이 값은 실측 수준과 비슷합니다.
