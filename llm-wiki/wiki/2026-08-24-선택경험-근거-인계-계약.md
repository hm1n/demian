# 선택 경험 근거 인계 계약

## 문서 목적

이슈 #54가 확정한 근거 스냅샷 계약을 기록합니다. 사용자가 고른 경험 하나의 Repository 근거를 `실제 코드 기반 AI 질문 생성`과 `실시간 AI Streaming 응답`이 그대로 소비할 수 있는 형태로 고정합니다. 구현은 `src/features/experience-candidates/evidence-snapshot.ts`와 `types.ts`에 있습니다.

## 왜 계약이 필요한가

근거는 출처가 두 곳으로 갈립니다. 커밋 제목, 메시지, PR 정보, 변경 파일 목록은 `data.includedCommits`에서 오고 patch가 제거된 상태입니다. `/api/github/commit-details`가 `withoutPatch`로 벗기기 때문입니다. patch 본문은 `candidates.diffs`에만 있습니다. 소비자가 이 분기를 매번 다시 조립하면 출처가 섞입니다.

확인 가능과 확인 불가 구분도 문제입니다. 이슈 #47이 만든 구분은 `evidence-verifiability.ts`의 화면 문구 상수로만 존재합니다. 인계 payload에 실리지 않으면 확인 불가 항목이 사실처럼 다뤄집니다. 이는 `AGENTS.md`의 "Repository만으로 확인할 수 없는 사실은 명확히 구분해서 보여줘야 한다" 원칙 위반입니다.

근거 입력 크기 상한도 없었습니다. 상한을 소비자마다 정하면 같은 413이 질문 생성과 꼬리 질문 두 곳에서 재발합니다.

## 스냅샷 구조

`ExperienceEvidenceSnapshot`은 다음을 담습니다.

- `candidateSha`, `source`, `origin`
- `evidence`: LLM이 작성한 해석 문장과 그 확인 수준
- `representativeCommit`: 대표 커밋 하나
- `relatedCommits`: 관련 커밋 목록
- `citedFilePaths`: LLM이 고른 인용 경로와 그 확인 수준
- `unverifiableItems`: `REPOSITORY_UNVERIFIABLE_ITEMS`를 그대로 실은 확인 불가 고정 목록
- `patchBudget`: 총 상한, 실제 사용 문자 수, 상한 때문에 자른 사실

커밋 하나는 `sha`, `role`, `indexed`, `title`, `message`, `pullRequests`, `files`, `verifiability`를 가집니다. `role`은 대표와 관련을 구분하고, `indexed`는 커밋 색인 조회 성공 여부입니다.

파일 하나는 `path`, `status`, `additions`, `deletions`, `changes`, `patch`, `patchTruncated`, `patchOmittedReason`을 가집니다.

## 확인 수준을 payload 필드로 싣는 방식

`EvidenceVerifiability`는 `status`, `aiSelected`, `detail` 세 필드입니다. `status`는 기존 `VerifiabilityStatus`를 그대로 씁니다. `aiSelected`를 따로 둔 이유는 `VerifiabilityStatus`가 두 값뿐이어서 "관계는 확인되지만 관련성 판단은 확인 불가"인 항목을 한 값으로 표현할 수 없기 때문입니다. `detail`은 무엇까지 확인되는지 소비자가 그대로 인용할 수 있는 한 문장입니다.

항목별 값은 다음과 같습니다.

| 항목 | status | aiSelected | 근거 |
| --- | --- | --- | --- |
| `evidence` 문장 | `unverifiable` | true | Repository 값이 아니라 AI의 해석입니다. |
| 대표 커밋 | `verified` | false | SHA, 제목, 메시지, 변경 파일, patch, PR 정보는 GitHub 응답 값입니다. |
| 관련 커밋 | `verified` | true | 대표 커밋과 같은 PR에 속한다는 관계까지만 확인됩니다. |
| `citedFilePaths` | `verified` | true | 후보 커밋의 실제 변경 파일 목록에 있는 경로임까지만 확인됩니다. |
| 색인 실패 커밋 | `unverifiable` | 관련 커밋이면 true | 조회 실패 상태이므로 Repository 사실이 아닙니다. |

확인 가능으로 표시하는 범위는 서버 `assertCandidateEvidence`가 실제로 증명한 것까지입니다. 증명 범위는 세 가지입니다. SHA가 입력 집합에 속한다는 사실, 관련 커밋이 대표 커밋과 같은 PR에 속한다는 사실, 인용 경로가 입력 diff 경로에 존재한다는 사실입니다. 근거로서 관련이 있다는 판단은 증명하지 않습니다.

색인 실패 커밋을 `unverifiable`로 둔 것은 `wiki/2026-08-24-경험후보목록-후속-backlog.md` 8번과 같은 성격의 오표시를 새로 만들지 않기 위한 것입니다. 8번 자체는 목록 화면 문제이고 이번 범위에서 고치지 않았습니다.

## patch 예산

총 상한은 `EVIDENCE_SNAPSHOT_MAX_TOTAL_PATCH_CHARS = 12,000`자입니다.

근거는 Groq 무료 등급의 분당 토큰 한도 8,000입니다. 초과를 429가 아니라 413 `rate_limit_exceeded`로 반환합니다. 꼬리 질문이 같은 근거를 매 턴 다시 싣기 때문에 한 번의 요청이 한도를 다 쓰면 다음 턴이 곧바로 막힙니다. 그래서 patch에 3,000토큰만 배정하고, 레포가 이미 쓰는 4문자당 1토큰 추정으로 12,000자를 상한으로 두었습니다. 남는 한도는 커밋 메타데이터와 시스템 프롬프트, 응답 토큰이 씁니다.

배분은 커밋 간 균등 배분입니다. 커밋별 몫은 총 상한을 커밋 수로 나눈 내림값이고, 몫을 다 쓰지 않은 커밋의 잔액은 뒤 커밋으로 이월합니다. 이월은 앞에서 뒤로만 흐르므로 어떤 커밋도 자기 몫보다 적게 받지 않습니다. 선착순 배분을 쓰지 않은 이유는 뒤 항목이 patch를 한 글자도 받지 못하는 결함이 Stage B에서 이미 관측되었기 때문입니다.

## 절단과 미포함 판정

절단을 부재보다 먼저 판정합니다. Stage B에서 예산이 소진되면 `patchTruncated: true`이면서 `patch`가 없는 조합이 실제로 나오고, 이 조합을 일반 미포함으로 표시한 것이 이슈 #46의 재검증 P2였습니다.

`patchOmittedReason`은 본문이 없는 이유를 두 값으로 구분합니다.

- `budget_exhausted`: Stage B 예산 또는 이 스냅샷의 총 상한 때문에 본문이 빠졌습니다.
- `not_provided`: GitHub이 애초에 patch를 주지 않았습니다. 바이너리 파일이 대표적입니다.

`patchTruncated`는 Stage B 절단과 이 스냅샷의 상한 절단을 모두 포함합니다. 의미는 "원본보다 짧다"입니다.

## 실패 처리

`buildExperienceEvidenceSnapshot`은 `EvidenceSnapshotResult`를 돌려줍니다. 실패 사유는 두 가지입니다.

- `representative_commit_not_indexed`: 대표 커밋을 커밋 색인에서 찾지 못했습니다. 제목, 메시지, PR, 변경 파일이 모두 없어 인터뷰할 근거가 없습니다.
- `no_repository_evidence`: 대표 커밋에 변경 파일이 없습니다.

이슈 #55의 Approach는 Error 대상으로 "대표 커밋 색인 실패와 근거 상한 초과"를 들었습니다. 이 가운데 상한 초과는 실패로 올리지 않았습니다. 균등 배분이 상한을 넘는 입력을 자르고 `patchBudget.truncatedByBudget`으로 사실을 알리므로, 상한 초과는 정상 상태이고 스냅샷을 만들지 못하는 경우가 아닙니다. 대신 소비자가 절단을 무시하지 않도록 파일별 절단 표시와 예산 요약을 함께 싣습니다.

## 하지 않은 것

- LLM을 호출하지 않았습니다. 프롬프트도 작성하지 않았습니다. 질문 생성 이슈가 이 스냅샷을 입력으로 받습니다.
- API 라우트를 추가하지 않았습니다. 서버에 저장하지 않았습니다.
- `assertCandidateEvidence`를 다시 실행하지 않았습니다. Stage B 라우트가 이미 검증한 결과를 소비합니다.
- 커밋 안에서 파일 단위 균등 배분을 하지 않았습니다. 파일마다 몫을 쪼개면 모든 파일이 쓸모없이 짧은 조각만 받습니다. 파일 단위는 Stage B와 같은 선착순이고 소진은 그 커밋의 몫 안에서만 일어납니다.

## 확인 필요

- 총 상한 12,000자는 문자 수 추정입니다. 실제 토큰 수를 재서 확정하는 것은 질문 생성 이슈에서 합니다.
- 한 커밋에 큰 파일이 앞쪽에 있으면 그 커밋 안의 뒤쪽 파일이 patch를 받지 못합니다. Stage B와 같은 한계이고, 파일 단위 상한을 둘지는 실제 질문 생성 결과를 보고 판단해야 합니다.
- 관련 커밋 수가 많으면 커밋별 몫이 작아져 patch가 사실상 통계만 남습니다. 관련 커밋 수 상한을 둘지는 확정하지 않았습니다.
