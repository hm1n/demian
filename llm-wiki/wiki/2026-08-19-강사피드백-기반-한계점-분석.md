# 강사 피드백 기반 기능 설계 한계점 분석

## 문서 목적

강사 인터뷰 결과를 현재 확정된 기능 설계와 대조해, 예상되는 문제와 한계점을 항목별로 정리한다. 각 항목은 강사 발언의 근거 위치와 관련 설계 결정의 근거 위치를 함께 표시한다.

## 1. 의도 없이 위임한 사용자에게는 핵심 가치가 성립하지 않을 위험

강사는 "내가 알고 프롬프트를 치면 설명할 수 있는데, 내가 모르고 해줘! 하고 지시하면 결국 모르는 게 되어 버린다"고 지적했다. 프롬프트에 의도를 담아 지시한 사용자에게는 도움이 되지만, 그냥 위임만 한 사용자에게는 의미가 없다는 평가다(`raw/2026-08-19-강사인터뷰-피드백.md` 1번).

현재 설계는 이 구분을 두지 않는다. "실제 코드 기반 AI 질문"과 "꼬리 질문" 기능 모두, 경험을 선택하면 대표 커밋과 관련 커밋을 근거로 질문을 만들고 사용자가 답변한다는 흐름만 정의했다(`raw/2026-08-19-코드기반ai질문-기능-설계-session-log.md`, `raw/2026-08-19-꼬리질문-기능-설계-session-log.md`). 사용자가 애초에 그 코드를 만들 때 의도를 가지고 있었는지 아닌지를 구분하거나, 의도가 없는 사용자에게 다른 방식으로 접근하는 로직은 설계에 없다.

서비스의 핵심 가치인 "Repository 근거로 질문하면 사용자가 스스로 설명하게 된다"는 전제가, 실제로는 "사용자가 그 결정을 내릴 때 이미 의도를 가지고 있었는가"라는 선행 조건에 의존한다는 점이 이번 인터뷰에서 드러났다. 이 전제가 검증되지 않은 상태로 MVP 범위가 확정되어 있다.

## 2. 수치화·정량화를 끌어내는 장치가 질문 설계에 없음

강사는 "정리를 못 하는 사람은 수치화를 잘 못 한다. 내가 뭘 얼마나 개선했는지를 잘 뽑아내지 못해서 그런 부분에서 피드백을 많이 준다"고 말했다(`raw/2026-08-19-강사인터뷰-피드백.md` 2번). 즉 강사가 실제로 개입하는 지점은 학생이 수치화를 못 할 때 그 부분을 캐물어 뽑아내는 것이다.

현재 설계에서 수치·정량 정보를 다루는 곳은 "경험 후보별 Repository 근거 표시"의 확인 불가 판단 규칙뿐이다. 이 규칙은 "성능 개선 폭, 사용자 영향처럼 구체적인 수치가 코드나 커밋에 없으면 확인 불가로 표시한다"는 내용으로(`raw/2026-08-19-경험후보근거표시-기능-설계-session-log.md`), 사실을 구분해 보여주는 데서 끝난다. "코드 기반 AI 질문"과 "꼬리 질문" 설계에는 수치화를 캐묻는 질문 전략이 명시되어 있지 않다.

강사가 지적한 피드백 방식, 즉 수치가 없을 때 그것을 끌어내려고 캐묻는 개입이 지금 설계에는 빠져 있다. 확인 불가 표시는 사실 구분 UI이지 학습 개입이 아니다.

## 3. 최소 숙련도 이하 사용자에 대한 처리 방침이 없음

강사는 AI가 계속 질문해 스스로 설명하게 만드는 방식에 대해 "적정 수준이면 도움이 되겠지만 개발을 아예 접해보지 않은 사람, 바이브 코딩을 아예 접해보지 않은 사람들에게는 크게 도움이 되지 않을 것 같다"고 평가했다(`raw/2026-08-19-강사인터뷰-피드백.md` 3-1번).

MVP 범위와 기능 설계 전체에 사용자 숙련도를 파악하거나 질문 난이도를 조정하는 절차가 없다. 대상 사용자층을 어느 수준부터로 정의할지도 확정된 문서가 없다. 최소 숙련도 미달 사용자에게는 효과가 없다는 근거가 나왔는데, 이를 걸러내거나 온보딩 단계에서 기대치를 조정하는 장치가 설계에 없다.

## 4. 선별 기준 두 가지의 실효성이 외부 검증을 받지 못함

강사에게 "Git 기록에서 변경 규모나 구현 복잡도, 기술적 의사결정 흔적을 보고 경험을 추천하는 기준이 적절한가"를 물었으나 답변을 받지 못했다(`raw/2026-08-19-강사인터뷰-피드백.md` 5번, 답변 없음). 추가 기준을 물었을 때는 "추가하면 당연히 좋을 것 같은데 구현 복잡도가 올라갈 것 같다"는 반응만 받았다(5-1번).

`llm-wiki/output/2026-08-19-서비스기획-확정-v1.md`에서 확정하고 `raw/2026-08-19-개발경험후보생성-기능-설계-session-log.md`에서 가중합 점수화까지 구체화한 두 기준, 코드 변경 규모·복잡도와 기술적 의사결정 흔적이 실제로 "설명할 가치가 있는 경험"을 잘 짚어내는지에 대해 교육 현장의 명시적 확인을 받지 못했다는 뜻이다. 이 기능 설계에는 이미 "점수 정규화 방식과 가중치 값 미정"이라는 확인 필요 항목이 남아 있는데, 기준 자체의 타당성 검증도 함께 미해결 상태로 봐야 한다.

## 5. 커밋 전량 조회와 대화 전체 이력 반영 결정에 따른 비용 문제가 현장에서도 지적됨

강사는 "커밋이 많아져서 커밋을 다 가져오는 게 비용이 커질 수 있다. 프롬프트 날릴 때의 토큰이 많이 들 거다"라고 지적하며, 커밋 이력을 간략하게 만들어 넘기는 방식을 제안했다(`raw/2026-08-19-강사인터뷰-피드백.md` 6번).

이 지적은 이미 설계 단계에서 인지하고 있던 위험과 맞닿아 있다. `raw/2026-08-19-개발경험후보생성-기능-설계-session-log.md`는 1단계 필터링을 화이트리스트에서 블랙리스트로 바꾸면서 "2단계 조회 대상이 늘어나 API 호출량이 커질 수 있지만, 실측 없이 미리 좁히지 않는다는 작업 원칙에 따라 커버리지를 우선하고 실제 성능을 측정한 뒤 필요하면 그때 좁히기로 했다"고 명시했다. `raw/2026-08-19-꼬리질문-기능-설계-session-log.md`도 "대화 전체 이력과 원래 근거 커밋을 모두 반영하며, 인터뷰 특성상 대화 턴 수가 많지 않아 지금 시점에 비용을 이유로 이력을 줄일 필요는 없다"고 결정했다.

두 결정 모두 "지금은 비용을 이유로 범위를 좁히지 않는다"는 판단인데, 실측 시점이나 비용이 일정 수준을 넘었을 때 좁히는 트리거 조건은 문서에 없다. 부트캠프 교육 기간이 3~4개월이라는 강사 발언(`raw/2026-08-19-강사인터뷰-피드백.md` 2번)을 고려하면 대상 Repository의 커밋 수가 적지 않을 수 있어, 이 비용 문제가 이론적 위험이 아니라 실제로 발생할 가능성이 있다는 현장 확인으로 봐야 한다. 강사가 제안한 커밋 이력 요약 압축 같은 대안은 현재 설계에서 검토되지 않았다.

## 6. 검증된 부분

- 꼬리 질문으로 기술 선택 이유를 캐묻는 방식은 "실제 면접 질문들이 보통 기술의 결정 이유를 물어보기 때문에 도움이 될 것 같다"는 긍정 평가를 받았다(`raw/2026-08-19-강사인터뷰-피드백.md` 4번). `raw/2026-08-19-꼬리질문-기능-설계-session-log.md`의 설계 방향과 부합한다.
- "기술 선택 이유를 자기 언어로 바꿀 수 있게 하는 것"이 교육적으로 가치 있다는 평가를 받았다(6번 기타 피드백). 다만 이 평가는 사용자가 이미 어떤 형태로든 의사결정을 내렸다는 전제 위에 있으므로, 1번 항목의 위험과 함께 읽어야 한다.

## 범위 밖 아이디어 (참고용, 이번 분석에서 채택하지 않음)

강사는 "코드 리뷰 결과를 기반으로 면접 때 이런 걸 준비해보라고 제안해주는" 기능을 좋은 방향으로 언급했다(`raw/2026-08-19-강사인터뷰-피드백.md` 1번). 이는 MVP 확정 범위 밖의 새 기능이므로, CLAUDE.md의 "MVP 범위를 벗어나는 기능은 먼저 논의 없이 추가하지 않는다"는 원칙에 따라 이번 분석에서는 문제점으로 다루지 않고 이후 논의 후보로만 기록한다.

## 확인 필요

- 의도 없이 위임한 사용자를 어떻게 식별하거나 안내할지
- 수치화를 캐묻는 질문 전략을 코드 기반 AI 질문·꼬리 질문 설계에 추가할지
- 서비스가 전제하는 최소 사용자 숙련도를 어떻게 정의하고, 미달 사용자를 어떻게 처리할지
- 선별 기준 두 가지의 실효성을 실제 사용자 테스트로 어떻게 검증할지
- 커밋 조회량과 대화 이력 반영에 대한 비용 실측 계획과, 비용이 일정 수준을 넘었을 때 적용할 압축·요약 방안
